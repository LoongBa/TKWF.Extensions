## 一、背景与问题

### 1.1 频控接线纵向割裂（AC-02 P0）

`LoginProtectionOptions`（`AuthCenterOptions.cs` L31-64）声明四组 IP 维度额度：`SmsHourlyLimitPerIp=20`（L43）、`PasswordPerHourPerIp=20`（L59）、`OAuthPerMinutePerIp=10`（L49）、`TicketRedeemPerMinutePerIp=10`（L63）。实际接线：

| 维度 | 声明 | 实际消费 |
|---|---|---|
| 密码 identifier | 5 次/10min（`pwd:login:{identifier}`） | ✅ `PasswordLoginService.cs` L80（IRateLimitCheck 点检查） |
| 找回 identifier/uid | `pwd:reset:{identifier}`/`pwd:reset-email:{uid}` 系列 | ✅ `PasswordResetService.cs` L70/L102-104 |
| 外部门票 IP | `ext:ticket:{ip}` | ✅ `ExternalTicketLoginService.cs` L69-74（唯一 IP 点检查） |
| **密码 IP** | `PasswordPerHourPerIp=20` | ⚠️ 仅 `AuthLoginAttemptService` 60min 滑窗 COUNT（L78-84）——**审计从域**（后置计数，非前置阻断） |
| **短信 IP** | `SmsHourlyLimitPerIp=20` | ❌ **零消费**（全仓唯一命中 = Options 声明自身）——契约死键 |
| 联邦 IP | `OAuthPerMinutePerIp=10` | ⚠️ COUNT 滑窗（L67-70），且联邦入口经 Federation 连接层（域外） |
| 短信 phone | 60s/小时/天 | ✅ `SmsVerificationService` L71-77（发送面） |

**后果**：攻击者轮换 identifier（密码）+ 轮换手机号（短信）即可绕开 identifier 维度点检查——单 IP 分布式爆破在 Domain 层无前置阻断。README「登录保护」表行宣称"短信 60s/小时/天/IP"中 IP 项失真。

### 1.2 票据换发是冻结守卫唯一缺口（AC-04 P0）

`OAuthTicketService.ExchangeAsync`（`OAuthTicketService.cs` L102-199）全链 (a)~(i)：票据存在性 → 单次消费 → TTL → app_id → state → PKCE → 已绑定 → CAS 消费 → 签发（L170-175），**无任何冻结检查**。对照冻结守卫矩阵（V0.13.0 顶层）：

| 签发/认证路径 | 守卫位置 |
|---|---|
| Refresh 续期 | `TokenService.cs` L241（`ACCOUNT_FROZEN`） |
| 联邦登录（UId 直读 / 回读） | `FederatedLoginOrchestrator.cs` L72-73 / L126 |
| 短信认证 | `SmsAuthenticationProvider.cs` L65 |
| 密码认证 | `PasswordAuthenticationProvider.cs` L70-71 |
| UserHelper 恢复 | `AuthenticationUserHelperBase.cs` L51/L84 |
| 找回（发起+完成） | `PasswordResetService.cs` L205-209 |
| 弱身份清理判别 | `WeakIdentityCleanupService.cs` L180 |
| **票据换令牌** | **❌ 缺口** |

**后果**：冻结用户持有未过期票（TTL 5min）仍可换得全套令牌（access + refresh 30d）——与 login 路径不一致，违反冻结核心语义「拦截新签发」。

### 1.3 Long-lived 契约零实现（AC-08）

`AuthCenterOptions.LongLivedTokenExpirationDays = 7`（`AuthCenterOptions.cs` L111-112）——**全仓库唯一命中，零消费**。README「二、令牌契约」宣称"生命周期：Access 2h / **Long-lived 7d（壳端低敏）** / Refresh 30d"。`TokenService.IssueTokenAsync`（`TokenService.cs` L86-133）签发 exp 恒 = `AccessTokenExpirationMinutes`（L91），`TokenIssueRequest`（`ITokenService.cs` L18-23）无长时表态。**契约承诺与实现背离**——壳端/低敏场景（README 声称的消费面）实际只能拿 2h access，无兑现路径。

### 1.4 ResetAsync 绕过 TokenVersion 失效链路（AC-14）

`IAuthFactorService.ResetAsync`（`AuthFactorService.cs` L158-172）：查因素 → 直改 `SecretHash`/`MustChange`/`SecretUpdatedAt`（L164-168）→ 写 Reset 事件（L170）——**无 `IncrementTokenVersionAsync`**。对比 `UnbindAsync`（L116-125）显式含 ⑤ TokenVersion++（L125，同 UoW）。`IAuthAccountService.WritePasswordAsync`（`IAuthAccountService.cs` L113-150）在 L139 委托 `Factors.ResetAsync` 后**自补** L148 `IncrementTokenVersionAsync`（+L141-147 历史追加）——因此**内链完整，外链裸奔**：消费方直接调 `IAuthFactorService.ResetAsync`（管理侧重置密码因素等）绕过 TokenVersion++ 且不入 PasswordHistory。**后果**：重置后旧 refresh token（最长 30d）仍可续期换新对——与 SetPasswordAsync/UnbindAsync 语义不一致。

### 1.5 票据换发 authType 恒 sms（AC-10）

`OAuthTicketService.ExchangeAsync` L168-169 注释自证："此处认证方式取默认登录方式 **sms**，认证强度取手机号级"——L170-175 `IssueTokenAsync(new TokenIssueRequest(entity.UserId, AuthTypes.Sms, (int)AuthLevel.Phone))` **硬编码** `AuthTypes.Sms` + `AuthLevel.Phone`。签发时（`IssueAsync` L55-98）无任何认证方式信息落票（`OAuthTicketEntity` 表列见 `README §五`——Ticket/AppId/RedirectUri/State/CodeVerifierHash/UserId/ExpiresAt/IsConsumed 等，无 AuthType）。**后果**：口令兑换（redeem）/扫码验证/联邦 holders 等经票据换发路径所得 token 与 refresh 行（`TokenService.cs` L124 `AuthType` 落 `TKWF_AuthRefreshToken.AuthType`）audit 归因恒 sms——审计失真（登录历史/异常检测按 authType 聚合时全部误归短信）。

## 四、目标模型与决策（五条逐条闭环）

### 4.1 AC-02（P0）：登录门面 IP 维度频控接线

**现状**：见 §1.1。`IRateLimitCheck` 点检查（v4.10.67 原语 + Initializer fallback `MemoryRateLimitCheck`——`AuthCenterExtensionInitializer.cs` L94-97 fail-closed「始终在」）已就位但只覆盖 identifier/uid 维度；IP 维度唯一先例 = `ExternalTicketLoginService.cs` L67-74（`IHttpContextAccessor.RemoteIpAddress` + `unknown` 兜底 + `TicketRedeemPerMinutePerIp` 额度 + 429 `TICKET_RATE_LIMITED`）。

**选项**：
- **A（选定）**：登录门面补 IP 维度 `IRateLimitCheck` 点检查——`PasswordLoginService.LoginAsync` 增 `login-ip:{ip}` key；`SmsLoginService.LoginAsync` 与发送面 `SmsVerificationService` 统一查 **`sms-ip:{ip}` 单一 IP 桶**（额度 `SmsHourlyLimitPerIp`，默认 20/h，契约激活）。**评审 P1-1 key 统一理由**（防「换号不换 IP」刷验证码 + 刷登录双口）：登录与发送共用同一桶，攻击者在任一端口（发码/登录）的消费都从同一 20/h 配额扣除——"发送打满则登录额度耗尽（反之亦然）"，单向打通即双向封口；(原稿 `sms-login-ip`/`sms-send-ip` 两 key 实为不同桶、与"共用同一 IP 桶"表述自相矛盾，测试用例 3 依赖共享桶将失效——本选型统一为单桶修正)。
- B：仅强化 `AuthLoginAttemptService` COUNT（IP 已入审计从域）——**否决**：审计表是后置计数，防不了窗口内并发爆破；且 `SmsHourlyLimitPerIp` 仍死键。C：把 IP 塞进既有 identifier key——**否决**：key 语义污染（identifier 归一化 vs IP 原始串），额度混算。
- **选定 A**。理由：与 V0.10.0 先例同构（同设施、同失败语义）、激活死键完成契约兑现、点检查为前置阻断（fail-closed）。

**实施细节**：
1. `PasswordLoginService.cs`：ctor 增 `IHttpContextAccessor?`（第 6 参，末尾可空——测试宿主零破坏）；L80 前增 IP 点检查 `_rateLimit.TryAcquire($"login-ip:{ipKey}", protection.PasswordPerHourPerIp, TimeSpan.FromHours(1), out _)` 失败抛 `RateLimitedException(0, ...) { ErrorCode = "PASSWORD_RATE_LIMITED" }`（429 语义复用）；`ipKey` 取 `RemoteIpAddress?.ToString()`，空白 → `"unknown"`（对齐先例）。
2. `SmsLoginService.cs`：ctor 增 `IHttpContextAccessor?` + `IRateLimitCheck`（末尾可空参数——Existing 构造点适配）；`LoginAsync` 认证前查 **`sms-ip:{ip}`**（额度 `SmsHourlyLimitPerIp`，1h 窗——登录 + 发送共用单桶）失败 `SMS_RATE_LIMITED`；同时校验手机号 identifier 面已有（`SmsVerificationService` 校验频控）不重复。
3. `SmsVerificationService.cs`：**ctor 增 `IRateLimitCheck?` + `IHttpContextAccessor?`（末尾可空参数——Existing 构造点适配，对齐 SmsLoginService 同款，评审 P1-5①）**；`SendCodeAsync` 内（L71-77 既有 phone 三键之后）增 **`sms-ip:{ip}`** 点检查（额度 `SmsHourlyLimitPerIp`，1h 窗，同桶）——发送 + 登录共用同一 IP 桶（防"换号不换 IP"刷验证码 + 刷登录双口，任一端口消费同一配额）。
4. `AuthCenterExtensionInitializer.cs`：`AddConstructibleService` 注册无需变（ctor 参数由守卫工厂经 ActivatorUtilities 解析——`IHttpContextAccessor`/`IRateLimitCheck` 均已在容器：前者框架注册、后者 L97 fallback）；无新 Options 键（复用既有 `PasswordPerHourPerIp`/`SmsHourlyLimitPerIp`）。
5. 失败码：`PASSWORD_RATE_LIMITED`（复用）+ 新 `SMS_RATE_LIMITED`（登录面 429；发送面沿用既有发送频控码）。文档同步（§七）。

**兼容性**：纯增量——既有调用方（门面签名不变——ctor 参数在守卫工厂内解析，消费方 `User.Use<门面>()` 形态零改动）；默认值不变；IP 键在单机/未配 ForwardedHeaders 时退化为代理单桶（fail-closed 非静默放行——使用指南 P2-4 反代段落已含此告诫，同步扩到登录路径）。

### 4.2 AC-04（P0）：票据换发冻结守卫

**现状**：见 §1.2。全体签发路径（登录 Provider 层/联邦编排/Refresh/UserHelper/找回/弱身份清理）均经 `IFreezeStateProvider.IsFrozenAsync(uid)`（帧内快照 + 写路径失效）拦 `ACCOUNT_FROZEN`；`OAuthTicketService.ExchangeAsync` 是唯一裸路径。

**选项**：
- **A（选定）**：`ExchangeAsync` 在 (g) 绑定校验后、(h) CAS 消费前插入冻结检查——`User.Use<IFreezeStateProvider>()` 懒加载（DI004），`IsFrozenAsync(entity.UserId)` true → `DomainException("ACCOUNT_FROZEN") { ErrorCode = "ACCOUNT_FROZEN" }`（B3b 类型化语义：400 + errorCode）。
- B：放在 (h) 消费后（签发前）检查——**否决**：冻结时不消耗票（票 TTL 5min，解冻后仍可用），先消费后检查浪费票据并迫使重新授权。
- C：`TokenService.IssueTokenAsync` 统一加冻结守卫——**否决**：TokenService 是底层签发原语，联邦建号直读路径等前置已守卫，在签发原语再拦会构成"双守卫 + 竞态窗口"（守卫成本翻倍且语义重叠）；冻结判定保留在各编排路径单点（现状即如此）。
- **选定 A**。对齐 `FederatedLoginOrchestrator` L126 同构插入点（回读守卫 → 签发）。

**实施细节**：
1. `OAuthTicketService.cs`：增 `IFreezeStateProvider? _freezeState;` + `FreezeState => _freezeState ??= User.Use<IFreezeStateProvider>();`（镜像 TokenService L54-55 形态）+ `IAuthAccountQueryService? _accountQuery;` + `AccountQuery => _accountQuery ??= User.Use<IAuthAccountQueryService>();`（只读面——`GetByUIdAsync` 返回完整 `AuthAccountEntity`，评审 P1-2；Refresh L240 同款判定来源）。
2. `ExchangeAsync` 在 L159（(g) TICKET_NOT_BOUND 检查）之后、L161（(h) MarkConsumedAsync）之前插入**双守卫**（对齐 `TokenService.RefreshTokenAsync` L240-241 语义——禁用双检 + 冻结拦截）：
   `var acct = await AccountQuery.GetByUIdAsync(entity.UserId, ct);`
   `if (acct is null || !acct.IsEnabled) throw new DomainException("ACCOUNT_DISABLED") { ErrorCode = "ACCOUNT_DISABLED" };`
   `if (await FreezeState.IsFrozenAsync(entity.UserId, ct: ct)) throw new DomainException("ACCOUNT_FROZEN") { ErrorCode = "ACCOUNT_FROZEN" };`
   ——账号禁用用显式 `ACCOUNT_DISABLED`（Refresh L240 以 `ACCOUNT_NOT_FOUND` 承载同语义：禁用账号不得换发新令牌）；冻结 → `ACCOUNT_FROZEN` 400（评审 P1-2 对齐语义：ExchangeAsync 只补 IsFrozen 不补 IsEnabled = 与 Refresh 双检不完整对齐）。
3. 文档语义（README/指南票据段）：票据换取 = 认证完成路径，禁用/冻结中用户不得换发——`ACCOUNT_DISABLED`/`ACCOUNT_FROZEN` 400。

**兼容性**：行为变更（禁用/冻结用户换发从 200 → 400 `ACCOUNT_DISABLED`/`ACCOUNT_FROZEN`）为**安全修复**（评审 P0，预期行为）；非禁用/非冻结路径零变化；`BindTicketAsync`（已认证补绑，不签发）保持不检查——绑定无令牌发放，账号状态语义不适用。

### 4.3 AC-08：Long-lived 契约实现（选型：实现而非移除）

**现状**：`LongLivedTokenExpirationDays`（`AuthCenterOptions.cs` L111-112）全仓零消费；README「生命周期：Access 2h / Long-lived 7d（壳端低敏）/ Refresh 30d」承诺与实现背离。

**选项**：
- **A（选定）**：**实现契约**——`TokenIssueRequest` 末位增 `bool IsLongLived = false`（默认参零破坏）；`IssueTokenAsync` 在 `IsLongLived` 时 exp = `AccessTokenExpirationDays` 语义的长时表态：access exp = `LongLivedTokenExpirationDays`（天）+ refresh 生命周期不变（Refresh 仍是收权点，长时态不延长 refresh）；`authType` 旁写长时标记 claim（如 `long_lived: true`——契约化，验签可读）。
- B：移除契约（删 Options 键 + README 声明）——**否决**：README 生命周期契约是既有公开承诺（壳端/低敏场景真实存在，V0.8.0 起文档声明）；删除 = 回退承诺且无消费方替代路径。C：仅文档移除"Long-lived"字样保留键——**否决**（契约半死，同 AC-02 死键问题）。
- **选定 A**。理由：契约兑现成本低（签发面单点 + 默认参零破坏）；长时态语义边界明确（壳端会话延长，Refresh 收权不变——安全模型不扩面）。

**实施细节**：
1. `ITokenService.cs`：`TokenIssueRequest` 末位增 `bool IsLongLived = false`（record 位置参数——既有调用方零改动）。
2. `TokenService.cs` `IssueTokenAsync`（L91 改）：
   `var exp = request.IsLongLived ? now.AddDays(_options.Value.LongLivedTokenExpirationDays) : now.AddMinutes(_options.Value.AccessTokenExpirationMinutes);`
   payload 增 `["long_lived"] = request.IsLongLived`（仅 true 写键或恒写布尔——选定恒写，验签侧统一读）；`ExpiresIn` 返回秒（L132）同步用长时态值。
3. `ValidateTokenAsync`：回读 `long_lived` claim（可选——不做强制语义，仅载荷可观测）；`VerifyResponse` 不新增面（本期只签发面）。
4. Refresh 生命周期不变（`RefreshTokenExpirationDays` L127）——长时态是 access 级延长，refresh 仍 30d rotation（收权点语义保持）。
5. 消费入口：壳端/低敏消费方（如 desktop shell 会话）经 `TokenService.IssueTokenAsync(new TokenIssueRequest(uid, authType, authLevel, IsLongLived: true))` 显式请求；既有端点（登录/刷新）不传 = 默认 2h 零变化。**无新端点、无新 Web 开关**（领域决策 = `TKWF:AuthCenter:LongLivedTokenExpirationDays`，配置分层合规）。
6. **黑名单 TTL 适配（评审 P1-3——撤销语义与签发语义对齐）**：`RevokeTokenAsync`（`TokenService.cs` L270-291）L286 `ExpiresAt = now.AddMinutes(AccessTokenExpirationMinutes)` 恒 2h——7d 长时态 token 撤销后黑名单行 2h 即过期；注释（L278"该 token 自然过期时间"）与实现不符（当前 `GetByJtiAsync` 不过滤 `ExpiresAt` 故观测不到，但语义脆弱——既有规划「黑名单过期清理任务」接入后即暴露）。**修订**：`RevokeTokenAsync` 末位增可选参 `DateTime? tokenExpiresAt = null`——调用方持验签结果时传 token 的 `exp`（logout 链路 `ambient` 已带，L321 透传）→ `ExpiresAt = tokenExpiresAt`；缺省（纯 jti 撤销、无载荷）按签发语义保守回退 `LongLivedTokenExpirationDays`（覆盖任何签发形态——黑名单行 jti 唯一只增，多留不早删无副作用）。黑名单行生命周期覆盖 token 全生命。

**兼容性**：零破坏（默认参）；新 claim 为附加信息（旧 token 无该键——验签侧做缺失容错）；长时态有效期仍受 Refresh rotation/TokenVersion/黑名单全局机制约束。

### 4.4 AC-14：ResetAsync 补 TokenVersion 失效链路

**兼容性**：行为变更 = 修复（重置后旧 refresh 失效——与 SetPasswordAsync 语义对齐，评审本体）；UoW 引入在测试宿主退化路径已覆盖（`ITransactionManager` 未注册 → 不硬失败，L119-120 同款）；消费方零签名变化。

## 九、风险与回滚

| 风险 | 等级 | 缓解 |
|---|---|---|
| AC-02 IP 频控误伤（多用户共享 NAT/出口 IP 触发 429） | 中 | 额度默认 20/h 沿用既有声明（不新增收紧）；`unknown` 桶 fail-closed 不空放；文档指引反代 ForwardedHeaders 保真实 IP；误伤可加白/调额（领域配置单点） |
| AC-08 长时态安全性（7d access 泄露窗口扩大） | 中 | 刷新收权点不变（30d rotation + TokenVersion + 黑名单）；长时态仅壳端/低敏调用方显式请求（默认端点零变化）；如需差异化撤销另立 ADR（登记不包含项 2） |
| AC-14 双递增回归（内链 WritePasswordAsync 曾外层 ++） | 高（易漏） | 实施细节明确收敛点（L148 删除 + Bind 分支保留一次）；测试 `WritePassword_ResetPath_SingleBump` 锁精确一次 |
| AC-10 存量票回退语义 | 低 | `?? AuthTypes.Sms` 回退与现状逐 bit 一致；`Exchange_LegacyTicket_FallbackSms` 用例锁定 |
| AC-04 冻结判定插入点（消费前）竞态 | 低 | 检查→消费窗口内冻结属「政策时点」语义（与 login 路径同构——认证成功后冻结生效以签发为准）；不引入分布式锁 |
| 生成物漂移（AC-10 实体变更） | 中 | 重生成纪律：`run-xcodegen.ps1 -Ext AuthCenter` + `.g.cs` 提交 + 健康自检清单 1/3/4 项 |
| **回滚** | — | 全部改动为增/改路径（无破坏性签名删除——除 L148 收敛点）；回滚 = revert 提交 + 重建；已签发的长时态 token 靠黑名单逐 jti 撤销（回滚窗口） |
