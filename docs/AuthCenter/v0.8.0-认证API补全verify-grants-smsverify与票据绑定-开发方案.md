## 一、背景与目标

### 问题

EduPlatform 转告（2026-10-06 · 已裁定归属扩展组，"通用认证能力归扩展、消费方零手写"）提出三类缺口，经本仓库核对**全部属实**：

| # | 缺口 | 转告陈述 | 代码实证 | 结论 |
|---|------|---------|---------|------|
| 1 | `/verify` 缺失 | 令牌验签 + 授权快照（introspection），应用已持令牌后的日常调用 | `AuthCenterWebExtension.ConfigureEndpoints`（L73-90）仅 6 端点，无 `/verify` | ✅ 属实 |
| 2 | `/grants` 缺失 | 应用授权状态查询（§5.2a，按 `app_id` 返回授权范围/有效期） | 同上，无 `/grants` | ✅ 属实 |
| 3 | `/sms/verify` 缺失 | 验证码**独立校验**（绑定场景复用；现仅 `login/sms` 合一） | `ISmsVerificationService.VerifyCodeAsync`（单次消费语义）已存在但**无独立端点** | ✅ 属实（能力在，端点缺） |
| 4 | **B5 票据绑定缺口** | `IssueAsync` 无 UserId 绑定入口 + `ExchangeAsync` L143 强制 `TICKET_NOT_BOUND`——两端点自相矛盾，第三方票据回调无法实现 | `OAuthTicketIssueRequest`（IOAuthTicketService.cs L14-19）无 `UserId` 字段；`IssueAsync`（L76-86）`entity.UserId` 恒 null；`ExchangeAsync`（L143-146）`UserId is null → TICKET_NOT_BOUND`；测试 L46/66/81/104/120 手动赋值 `entity!.UserId` 才过 | ✅ **真实契约缺口** |
| 5 | `SmsScenes.Bind`（转告 §三.2 担心缺绑定场景） | "若缺绑定场景请一并补枚举" | `SmsScenes.Bind` **已存在**（ISmsVerificationService.cs L33-34），`/sms/send-code` 白名单已含 Bind（WebExtension L98） | ✅ **无需补枚举**（转告偏差：已天然满足） |

### 目标

1. **内建 3 端点**（`AuthCenterWebExtension.ConfigureEndpoints` 扩编，minimal API + Options 开关，对齐 V0.6.0 6 端点模式）：
   - `GET {prefix}/verify`——验签 + 授权快照（已认证 Bearer，复用中间件验签产物，零二次验签）
   - `GET {prefix}/grants?app_id`——应用授权状态查询（已认证 Bearer，**新数据底座 `AuthGrantEntity`**——OAuth2 grants 语义前瞻）
   - `POST {prefix}/sms/verify`——验证码独立校验（匿名游客帧，复用 `ISmsVerificationService.VerifyCodeAsync` 单次消费）
2. **填补 B5 票据绑定缺口**：`OAuthTicketIssueRequest` 增 `UserId` + 新增 `BindTicketAsync(ticket)`（**已认证帧**，userId 取自身份帧而非请求体——Oracle P0-1 修订）——签发即绑 + 登录后补绑双路径，`ExchangeAsync` 校验语义不变。
3. **配置分层合规**：3 端点开关进 `AuthCenterEndpointOptions`（`TKWF:AuthCenter:Web`，纯暴露面）；领域能力不动。
4. **测试全绿 + 文档同步**（README/使用指南/一览表）。

## 五、技术方案

### 5.1 `/verify` 端点（T4——验签 + 授权快照，零二次验签）

**端点为已认证端点**（不 `.AllowAnonymous()`——Bearer 必需，与 `/logout` 同构）：

```
GET {prefix}/verify        → 200 VerifyResponse（已认证 Bearer 持令牌应用的 introspection 日常调用）
```

**设计决策（偏离转告的 grants? 可选项，Oracle 已审）**：

1. **复用中间件验签产物，不二次调 `ITokenVerifier`**——`JwtAuthenticationMiddleware` 验签成功已把 `TokenValidationResult` 写入 `ctx.Items["AuthCenter.TokenValidationResult"]`（V0.6.0 T4 行为），`/verify` handler 直接读取映射——**零重复验签**（与 logout 取 jti 同构）；`VerifyMode.RemoteIntrospection` 装配层替换 `ITokenVerifier` 时**中间件已跟随**（验签走远程 introspection），`/verify` 快照天然一致。
2. **判别器 = `Items["AuthCenter.TokenValidationResult"]`**（权威验签标记），非 `Items["DomainUser"]`——`UseWebSession` 装配下匿名游客也是 `DomainUser<TUserInfo>`（`IsAuthenticated=false`），只查 DomainUser 无法区分；`TokenValidationResult` 仅成功验签后写入（中间件 L105），缺即未认证。
3. **返回固定验签快照，不含动态 `grants?` 聚合**——授权状态是 **app 维度**（需 `app_id` 参数），`/verify` 无该参数；保持单一职责（`/verify` = 身份快照，`/grants` = 授权快照），消费方组合调用。转告的 `grants?` 为可选项，本方案以 `/grants` 独立端点承载。
4. **无效 Bearer → 401（非 RFC 7662 `200{active:false}`）——Oracle P1-4 明示**：`RejectInvalidToken=true` → 中间件 401 短路；`=false` → 透传匿名，handler 读不到 `Items[TokenValidationResult]` → 401（显式拒绝，不静默）。**README/指南显式标注**："`/verify` 为**已认证内省**（authenticated introspection），无效令牌返回 401 而非 RFC 7662 `200{active:false}`；如需 RFC 7662 fanout 模式另行提案"。

**VerifyResponse DTO**（Web 层语义——TokenValidationResult 字段映射）：

```csharp
public sealed record VerifyResponse(
    bool Valid,                       // 恒 true（到达即已验签）
    string UserId,
    string AuthType,
    int AuthLevel,
    bool TeacherVerified,
    long Exp,                          // ExpiresAtUtc → unix 秒
    string Jti);
```

**handler 逻辑**：`ctx.Items["AuthCenter.TokenValidationResult"]` 取 `TokenValidationResult`（**唯一判别器**）→ 缺失 → 401 → 映射 `VerifyResponse`。

### 5.2 `/grants` 端点 + `AuthGrantEntity` 数据底座（T1/T2/T4）

**背景（评估识别的关键缺口）**：转告要求 `/grants` 返回"应用授权状态（授权范围/有效期）"，但扩展**当前无授权记录数据源**（OAuthTicket 为 TTL 5min 一次性票据；PlatformAccountMap 为跨系统映射，均无 scope/valid_until 语义）。EduPlatform 独立立项方案 §7.1 定义 `GrantRecord`（应用授权 scope/valid_until/source）为**认证中心实例数据**——即数据底座应落扩展侧。**最优+前瞻**：新增 `AuthGrantEntity`（对齐 OAuth2 authorization grant 语义，为 B-口令兑换产品线预留写入点）。

**实体设计**（SG1 声明式，`[DomainGenerateCode]` partial；Oracle P0-2/P1-3/P2-1/P2-4 修订内嵌）：

```
AuthGrantEntity
├── Id            (long, IsIdentity 主键)
├── UserId        (string 50——平台内部 id，JWT sub 同源)
├── AppId         (string 100——授权应用）
├── Scopes        (string 500——逗号分隔授权范围；v0.8.0 login 源空串；
│                    ⚠️ P2-1 已知局限：按单 scope 查询需 LIKE 无法走索引——
│                    未来 scope 维度查询变热时 normalizate 为 AuthGrantScopeEntity(GrantId, Scope)，本迭代不过度设计）
├── ValidUntil    (DateTime?——**应用授权有效期**（Oracle P1-3）：
│                    null = 持续至 Status 翻转为 Revoked（对齐 OAuth2 grant persist 语义，非会话有效期；
│                    login 源默认 null；redeem 源未来按口令 valid_until 填值））
├── Source        (string 20——授权来源，**AuthGrantSources 常量类**（Oracle P2-4）：
│                    Login = "login" / Redeem = "redeem"（预留）；镜像 OAuthTicketTypes/SmsScenes 范式）
├── Status        (int——0 Active / 1 Revoked；管理吊销预留）
├── CreateTime / UpdateTime
└── **唯一索引 UX_AuthGrant_User_App_Source(UserId, AppId, Source)**（Oracle P0-2——并发 exchange 防重复 grant 行；
    写入 upsert 以此复合键冲突判定）
```

**⚠️ Oracle P1-3 语义澄清（写入 README/指南）**：`ValidUntil` = **应用授权有效期**（用户授权该 app 访问其数据的持久授权，跨会话；null = 持续至吊销），**非会话有效期**（2h access / 30d refresh 是令牌生命周期，与 grant 正交）。`/grants` 返回应用授权状态，非会话状态。

**写入点（本迭代最小——经 `IAuthGrantCommandService` 门面，Oracle P1-1）**：`OAuthTicketService.ExchangeAsync` 成功（签发 JWT 对后）→ `User.Use<IAuthGrantCommandService>().RecordLoginGrantAsync(entity.UserId, entity.AppId)` → 门面内 **upsert 幂等**（以 `UX(UserId,AppId,Source=Login)` 复合键：存在则 `EntityUpdateWhereAsync` 刷新 Active 态（UpdateTime），不存在则 `EntityCreateAsync`；DB 唯一约束兜底 TOCTOU——两个并发 insert 第二个抛唯一冲突 → catch → 重查转 update）。**效果**：第三方票据回调场景（B5 修复后）exchange 成功即落授权，`/grants` 可查。`Source="redeem"` 写入由 B-口令兑换产品线落地（本迭代不做）。
**事务性说明**：grant 写入失败不阻断 JWT 签发（token 独立有效；grant 仅服务 `/grants` 查询）——可接受降级，README 标注。

**门面契约**（ADR90 门面范式 + Oracle P1-1 拆分）：

```csharp
/// <summary>授权查询门面——只读。</summary>
public interface IAuthGrantQueryService : IDomainService
{
    /// <summary>查询用户对指定应用（或全部）的有效授权记录（Status=Active，按 CreateTime 倒序）。</summary>
    Task<IReadOnlyList<AuthGrantEntity>> GetGrantsAsync(string userId, string? appId = null, CancellationToken ct = default);
}

/// <summary>授权写入门面——跨聚合写归门面（OAuthTicketService 不得直触 AuthGrantEntityDataService）。</summary>
public interface IAuthGrantCommandService : IDomainService
{
    /// <summary>记录登录授权（upsert 幂等：UserId+AppId+Source=Login 唯一约束，存在刷新 Active / 不存在创建）。</summary>
    [AllowAnonymousFlag]                       // 匿名面：exchange 为匿名端点调用链内触发（门面帧内）
    Task RecordLoginGrantAsync(string userId, string appId, CancellationToken ct = default);
}
```

- 实现 `AuthGrantQueryService`/`AuthGrantCommandService`（internal sealed : DomainServiceBase）——`User.Use<AuthGrantEntityDataService>()` 懒加载委托（红线合规，零 IFreeSql/IEntityDAC）。
- 注册：Initializer `services.AddConstructibleService<IAuthGrantQueryService, AuthGrantQueryService>()` + `AddConstructibleService<IAuthGrantCommandService, AuthGrantCommandService>()` + `[DiContractIgnore]`。

**端点**（已认证 Bearer，不 AllowAnonymous）：

```
GET {prefix}/grants?app_id=xxx    → 200 GrantsResponse（Web DTO 映射）
```

handler：已认证帧 `user.Use<IAuthGrantQueryService>().GetGrantsAsync(user.UserId, appId)` → 映射 `GrantsResponse(IReadOnlyList<GrantView>)`（`GrantView(AppId, Scopes, ValidUntil, Source, Status)`——Scopes 拆为 `IReadOnlyList<string>`，拆分在 Web 层（Oracle P2-2 部分采纳：facade 保持返回 entity 与 `IAuthAccountQueryService` 一致，拆分归 `GrantView` 构造器——避免 DTO 层过度；若后续 scope 查询变热再整体 DTO 化））。`app_id` 为空 → 返回全部有效授权。

### 5.3 `/sms/verify` 端点（T4——验证码独立校验）

**匿名端点**（游客帧 + `.AllowAnonymous()`，与 `/sms/send-code` 同构）：

```
POST {prefix}/sms/verify    { phone, code, scene }     → 200 { verified: true } / 400 / 429
```

| 校验 | 行为 |
|------|------|
| 参数 | `phone`/`code` 必填；`scene` **白名单**（`SmsScenes.Login/Register/Bind/Reset`——复用 send-code 同款校验，`SmsScenes.Bind` 已存在，无需补枚举）→ 非法 `INVALID_SCENE` 400 |
| 领域校验 | `guest.Use<ISmsVerificationService>().VerifyCodeAsync(phone, code, scene)`——**内置单次消费**（成功 MarkVerified）+ 频控 5 次/小时（`SMS_VERIFY_ATTEMPT_LIMIT`） |
| 失败映射 | `AuthenticationException` → `SMS_CODE_NOT_FOUND`/`SMS_CODE_EXPIRED`/`SMS_CODE_MISMATCH` → 400；`SMS_VERIFY_ATTEMPT_LIMIT` → 429 |
| 成功 | `200 { verified: true }`（不返回令牌——独立校验非登录；绑定编排后续由消费方/未来绑定端点承接） |

> **⚠️ 范围边界（转告 §四.2 澄清 + Oracle P2-5）**：`/sms/verify` 仅完成**验证码独立校验**；校验通过后**绑定写入**（微信 openid → 手机号回填 `AuthAccount.Phone`）不在本转告范围。**使用指南显式给出绑定流程过渡示例**：消费方实现 `/bind/phone` 时调用 `ISmsVerificationService.VerifyCodeAsync` 校验 + 自行写 `AuthAccount.Phone` 回填（含账号合并防劫持双验证）；认证中心后续迭代（如 v0.9.0）可内建 `/bind/phone` 端点纳入路线图。

### 5.4 B5 票据绑定缺口（T3——转告 §三.3 方案 a，Oracle P0-1/P1-2 修订）

```csharp
// IOAuthTicketService 契约扩展
public sealed record OAuthTicketIssueRequest(
    string AppId,
    string RedirectUri,
    string? State = null,
    string? CodeVerifier = null,
    string TicketType = "login",
    string? UserId = null);            // ⭐ 新增——签发即绑定（authorize 时已知用户）

Task<string> IssueAsync(OAuthTicketIssueRequest request, CancellationToken ct = default);

/// <summary>登录后补绑——第三方回调先授权后登录绑定（authorize 签发 → 登录 → 绑定 → 换取）。
/// ⚠️ 已认证帧调用（Oracle P0-1）：userId 取 <see cref="DomainServiceBase.User"/>（当前认证用户），
/// **不接受请求体 userId 参数**——防票据泄漏后攻击者绑定任意 userId 实现账号接管。</summary>
Task BindTicketAsync(string ticket, CancellationToken ct = default);
```

**⚠️ Oracle P0-1 安全模型（已认证帧，不接收 userId 参数）**：转告 §三.3 要求"绑定**当前认证用户**"——`BindTicketAsync` **不加 `[AllowAnonymousFlag]`**（对齐 `/logout` 已认证端点语义），userId 从 `User.UserId`（已认证 `DomainUser`）取，不经请求体。**流程印证**：转告场景"authorize 签发 → **登录**绑定 → exchange 换取"——绑定发生在用户已登录后（认证帧），非匿名回调时；`IssueAsync`/`ExchangeAsync` 保持 `[AllowAnonymousFlag]`（前者签发高熵 bearer、后者 ticket+PKCE 双因子——合法匿名面）。

**实现**（OAuthTicketService）：
1. `IssueAsync`：`request.UserId` 非空 → `entity.UserId = request.UserId`（签发即绑，主路径——authorize 时用户已登录带 UId）。
2. `BindTicketAsync(ticket)`：`GetByTicketAsync` → 不存在 `TICKET_NOT_FOUND`；`IsConsumed` → `TICKET_CONSUMED`；过期 → `TICKET_EXPIRED`；**CAS 条件绑定（Oracle P1-2）**——DataService 新方法 `BindUserAsync(long id, string userId)`（FreeSql `EntityUpdateWhereAsync`：`WHERE Id = ? AND UserId IS NULL`）→ 返回 false → `TICKET_ALREADY_BOUND`（镜像 `MarkConsumedAsync` 条件 select-then-update 模式，防并发双绑竞态——先查仅用于友好错误码，最终一致性由条件更新保证）；成功 → 赋 `User.UserId`。
3. `ExchangeAsync` **不动**（保留 L143 `UserId is null → TICKET_NOT_BOUND`——绑定后才可换取的既有安全设计成立，缺口只在签发侧，现已补入口）。

**错误码**：`OAuthTicketErrorCodes` 增 `TicketAlreadyBound = "TICKET_ALREADY_BOUND"`。

**测试收敛**：`OAuthTicketServiceTests` 删 L46/66/81/104/120 手动 `entity!.UserId = "u-123"` + `UpdateAsync` 回填——改 `IssueAsync(new OAuthTicketIssueRequest(..., UserId: "u-123"))` 签发即绑；新增 `Bind_Ticket_AfterIssue_BindsAuthenticatedUser`（stub 用户 u-123）/ `Bind_NoAuthenticatedFrame_Rejected`（无帧抛守卫）/ `Bind_ConsumedOrExpiredOrAlreadyBound_Rejected` / CAS 并发双绑只 1 成 1 `TICKET_ALREADY_BOUND`。
