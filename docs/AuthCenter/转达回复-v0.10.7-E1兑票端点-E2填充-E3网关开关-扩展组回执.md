## 一、E1 🔴 `/login/ticket/redeem` —— ✅ 已交付（AuthCenter V0.14.0 功能线）

### 1.1 交付内容

新增业务兑票端点（独立门面 `IExternalTicketRedeemService`/`ExternalTicketRedeemService`，`[ApiExpose]` 生成化挂载）：

```
POST {authCenterBase}/login/ticket/redeem     body: { "ticket": "..." }
→ 200 FederatedTicketPayload 明文（11 契约键 camelCase 逐字吻合 + extensions 第 12 键随票透传）
→ 400 { error: "TICKET_INVALID" | "ACCOUNT_FROZEN" | "ACCOUNT_DISABLED" }   # ⚠️ 契约偏差见 1.2
→ 429 { error: "TICKET_RATE_LIMITED" }
→ 503 { error: "TICKET_SERVICE_NOT_CONFIGURED" }
```

**行为**（与 DMP ADR05 方案 B / 转达方案 A 逐条对应）：

| DMP 诉求 | 实现 |
|---|---|
| 验票返 payload 明文、**不建会话不发 token** | ✅ 终止于验票 + L2 检查，返回 payload；**不依赖 `IFederatedLoginOrchestrator`**（不编排不建号） |
| 无账号（新粉丝）兑票放行 → register 分流 | ✅ PlatformUid 直读 → 反查 fallback → 两路均未命中**放行**（不建号——建号归事件链预置/DMP register/登录编排） |
| 伪造票 400 / 频控 429 / 未配置 503 | ✅ 验票 null 统一 `TICKET_INVALID`（P1-3 不泄露判因）；频控独立桶；守卫失败 fail-hard 503 |
| 冻结/禁用 403 | ⚠️ **本迭代为 400 + errorCode 细分**（见 1.2 P0-1 回执确认项） |
| `/login/ticket` 既有语义不受影响 | ✅ 独立门面独立开关（`TicketRedeemEndpointEnabled` 默认 true，与 `TicketLoginEndpointEnabled` 可分别关断）；`/login/ticket` 回归零变化 |

**频控容量（P0-2 定案）**：独立桶 `ext:ticket-redeem:{ip}`（与登录桶不互挤），阈值 **`TKWF:AuthCenter:LoginProtection:TicketRedeemServicePerMinutePerIp` 默认 60/min/IP**——专为服务间调用设计（DMP 后端出口 IP 集中，配额语义「每后端实例」；10/min 的登录阈值会误伤营销图文点击洪峰）；运维可独立调优。

**反面（DMP 侧）**：`Platform:TicketRedeemEndpoint=https://wx.loongba.cn/login/ticket/redeem`（实际路由按部署前缀：`{RestBasePath}/auth/login/ticket/redeem`）；**错误处理须按 errorCode 分支（非硬校验 403 状态码）**（见 1.2）。

### 1.2 P0-1 回执确认项（3 项，请 DMP 确认）

1. **400 vs 403 状态码**：DMP ADR05 冻结契约写 `403 ACCOUNT_FROZEN|ACCOUNT_DISABLED`——框架 `WebExceptionMiddleware` 当前无「403 + 自定义 errorCode」通道（`DomainException` 系 400 / `UnauthorizedAccessException` 403 但 errorCode 恒 `FORBIDDEN` 无细分）；本端点冻结/禁用返回 **400 + errorCode 细分**（与 AuthCenter 既有联邦登录守卫 `FederatedLoginOrchestrator` 完全同语义）。**DMP 客户端按 errorCode 分支即可（400 粗分失败面 + errorCode 细分账号态）**；若 DMP 硬校验 403 状态码，需等待框架 403 通道（转达中，两选项并陈：`ForbiddenException` 新类型 / `DomainException.StatusCode` 覆写；框架落地后本端点升格 403，errorCode 不变）——请 DMP 确认当前消费方式。
2. **extensions 第 12 键**：200 响应体除 11 契约键外含第 12 键 `"extensions"`（`protocol_type`/`is_test` 元数据随票透传，Federation 契约原样）——**DMP 反序列化须容忍未知键**（默认 STJ 忽略未知键即可；严格模式需适配）。
3. **兑票峰值**：单出口 IP 兑票峰值是否 < 60/min？超出请按容量假设调优配置键（默认 60 已为登录桶 6 倍，频控语义 = 防重试风暴 + DoS 纵深，非业务限流）。

### 1.4 附带事项答复（转达 §4）

- **事项 1（AutoProvision 建号）**：兑票端点**不建号不做 AutoProvision 判断**（保持"只兑票"语义——建号归事件链预置/DMP register/登录编排；双建号竞态规避）。⚠️ 组合提示：若 DMP register 经 `IExternalIdentityProvisioningService.ProvisionAsync`/登录编排建号，仍受 `TKWF:AuthCenter:FederatedProvisioning:AutoProvision`（默认 true）门控，false → `ACCOUNT_NOT_PROVISIONED`。

## 二、E2 🟡 AES 填充 16 vs 32 字节 —— 前提是讹传，**无需修改**

**扩展组核对结论**：`WeChatEventCrypto.DecryptMsg` 使用 `Aes.Create()` + `CipherMode.CBC` + `PaddingMode.PKCS7`——**PKCS7 填充恒按 AES 算法块大小 = 16 字节**（FIPS 197 固定 128bit），与微信官方实现（WXBizMsgCrypt 各语言参考实现）完全一致。「32 字节块」是流传讹误：混淆了 **EncodingAESKey 43 字符 Base64 解码 = 32 字节密钥**（AES-256 密钥长度 ≠ 块大小）；微信官方文档明确 AES-256-CBC + PKCS7 补块（16 字节）。

**模拟器实测「改 16 字节才通」正是与官方一致的证明**——扩展侧零代码改动。

**真机偶发「收不到回复/兜底回复」请按以下方向排查**（与填充无关）：
1. 5 秒被动回复超时（微信侧超时即重试 → 重试触发幂等/门控分支 → 兜底）；
2. 事件类型门控（unsubscribe/事件类协议分支强制禁回复）；
3. 签名/EncodingAESKey 与公众号后台配置不一致（多号配置）；
4. 内置测试卡片开关误开（`EnableBuiltInTestTemplate` 生产须 false）。

**请求**：DMP 提供真机事件日志（msg_signature 验签是否通过、handler 分支、回复超时时间线）以便定位。
