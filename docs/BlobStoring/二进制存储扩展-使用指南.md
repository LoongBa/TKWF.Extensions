# 二进制存储扩展使用指南

> **扩展**: `TKWF.Ext.BlobStoring` | **版本**: V0.3.1（安全修复——路径白名单收紧 + 存量数据迁移指引，见「七、安全说明」） | **框架**: .NET 10

本指南帮助消费方快速集成二进制存储扩展，实现本地文件系统 Blob 上传/下载/删除与元数据持久化。

---

## 三、上传 / 下载 / 删除

### 3.1 上传文件

```csharp
public class FileService(IBlobStorageService blobStorage)
{
    public async Task<BlobInfo> UploadFileAsync(Stream stream, string fileName, string contentType)
    {
        // 上传成功返回元数据：Name / Path / ContentType / Size
        // Path 为相对 RootPath 的路径（Guid 子目录隔离，避免文件名冲突），可直接用于后续下载/删除
        return await blobStorage.UploadAsync(fileName, stream, contentType);
    }
}
```

例子：

```csharp
using var stream = File.OpenRead("avatar.png");
var blob = await blobStorage.UploadAsync("avatar.png", stream, "image/png");
Console.WriteLine($"Stored at: {blob.Path}, Size: {blob.Size}");
```

### 3.2 下载文件

```csharp
var stream = await blobStorage.DownloadAsync(blob.Path);
if (stream != null)
{
    // 使用完释放流
    using (stream)
    {
        await stream.CopyToAsync(outputStream);
    }
}
else
{
    // 文件不存在
}
```

> 下载返回 `FileStream`（V0.2.0 流式下载，大文件不占内存；不存在返回 `null`），调用方负责释放。

### 3.3 删除文件

```csharp
var deleted = await blobStorage.DeleteAsync(blob.Path);
// 已存在并删除 → true；不存在或失败 → false（异常静默）
```

### 3.4 存在性检查

```csharp
var exists = await blobStorage.ExistsAsync(blob.Path);
```

## 四、元数据记录

### 4.1 保存记录

`BlobRecordEntity` 与文件存储独立——上传成功后可将元数据记录到 `BlobRecord` 表：

```csharp
public class FileService(IBlobRecordStore recordStore)
{
    public async Task SaveRecordAsync(BlobRecordEntity record)
    {
        await recordStore.SaveAsync(record); // 插入（Id=0）或更新（Id>0，先删后插）
    }
}
```

### 4.2 按 ID / 名称查询

```csharp
var byId = await recordStore.GetAsync(id);
var byName = await recordStore.GetByNameAsync("avatar.png");
```

### 4.3 列表查询

```csharp
// 全部（前 20 条）
var all = await recordStore.GetListAsync();

// 按内容类型过滤 + 分页
var images = await recordStore.GetListAsync(contentType: "image/png", skip: 0, take: 50);
```

### 4.4 删除记录

```csharp
await recordStore.DeleteAsync(recordId);
```

## 五、自定义实现

### 5.1 自定义 IBlobStorageService

若需替换本地文件系统（如 Azure Blob、Amazon S3、MinIO）：

```csharp
// 消费方 ConfigureServices 中
services.AddScoped<IBlobStorageService, AzureBlobStorageService>();
```

TryAdd 语义确保消费方实现优先。`IBlobStorageService` 接口不依赖本地文件系统概念（Path 为相对逻辑路径），可平滑替换后端。

### 5.2 自定义 IBlobRecordStore

若需替换 FreeSql 存储（如 MongoDB、文件）：

```csharp
// 消费方 ConfigureServices 中
services.AddScoped<IBlobRecordStore, MongoBlobRecordStore>();
```

## 六、异常处理

扩展采用**异常静默**模式：

- 文件上传/下载/删除/存在性检查失败时记录 Warning 日志，**不抛出异常**
- 元数据记录读写失败时记录 Warning 日志，**不抛出异常**
- 业务调用不会因文件存储失败而中断

> 唯一例外：① `UploadAsync` 的 `content` 参数为 `null` 时抛出 `ArgumentNullException`（编程错误，非运行时故障）；② **路径/文件名校验失败抛 `ArgumentException`（fail-closed，见「七、安全说明」——安全缺陷不静默）**。

## 七、安全说明（V0.3.1 新增——路径安全）

> V0.3.1 对 `LocalStorageService` 的路径校验做了**安全修复**（BL-P0：rooted/UNC 路径穿越漏洞闭环）——上传文件名与读路径校验升级为**段级白名单字符集 + 规范化前缀双保险**。

### 7.1 白名单语义（允许的形态）

- 上传 `name`：**单段**文件名——段首与段尾**必须字母数字（ASCII）**，中缀仅允许 `.`/`_`/`-`。
- 读路径 `path`（Download/Delete/Exists）：同字符集的多段相对路径，段间以 `/` 分隔；整路径锚定 `^[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?(?:/[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?)*\z`。
- **规范化前缀双保险**：路径经 `Path.GetFullPath` 规范化后**必须位于 RootPath 之下**（OrdinalIgnoreCase 前缀比较 + 分隔符边界）——即使白名单未来放宽，也逃不出存储根目录。

### 7.2 拒绝形态清单（V0.3.1 起抛 `ArgumentException`，fail-closed 不静默）

| 形态 | 示例 |
|------|------|
| 绝对路径（rooted） | `/etc/passwd`、`\Windows\System32\x`、`/a/b` |
| UNC | `//server/share/x`、`\\server\share\x` |
| 盘符 / NTFS ADS | `C:\evil`、`C:evil.txt`、`good.txt::$DATA` |
| 穿越段 | `../../x`、`a/../b.txt`、`.`、`..` |
| 前导分隔符 / 空段 / 尾分隔符 | `/a/b`、`a//b`、`a/b/` |
| 尾点 / 尾空格 | `evil.txt.`、`evil ` |
| 尾随换行 | `evil.txt\n` |
| 字符集外（中文/空格/括号/`~`/控制字符等） | `你好.txt`、`my file(1).jpg`、`~1/evil.txt` |

### 7.3 fail-closed 语义

校验失败抛 `ArgumentException`（**不静默吞掉、不返回 null/false**）——非法输入直达调用方；校验在 try 块**外**，不落入异常静默 catch（与「六、异常处理」的静默语义正交）。

### 7.4 兼容性声明（行为变更，V0.3.1 起生效）

- **白名单收紧**：中文/空格/括号等文件名自 V0.3.1 起**被拒**（`ArgumentException`）——这是**有意的 fail-closed 收紧**；消费方文件名请使用 **ASCII 安全字符**（字母数字 + `.`/`_`/`-`）。
- 合法 ASCII 文件名（含大小写，如 `photo.JPG`、`my-file_v2.tar.gz`）与内部生成路径 `{guid}/{name}` **完全兼容**，零回归。

### 7.5 存量数据提示（升级前必读——行为变更）

V0.3.1 **前**经旧黑名单校验已存储的**非白名单文件名**（中文/空格/括号等），其 `StoredPath`（如 `{guid}/中文名.png`）在 V0.3.1 起的 Download/Delete/Exists 读路径**同样被白名单拦截——不可读不可删**。升级前处置：

1. **扫描** `BlobRecord` 表 `StoredPath` 命中非白名单的行——判定以与 7.1 正则**等价**为准；SQL 可先用 `LIKE '%[^A-Za-z0-9._/-]%'` 或按中文/空格/括号模式圈定候选后**人工复核**；
2. **重命名/迁移**命中行：经 `IBlobStorageService` 上传到新白名单名 → 更新 `BlobRecord.Path` → 删除旧物理文件/旧记录；
3. 或按业务评估是否接受「旧档只读归档」（改走导出通道）。

> 本扩展**不引入迁移工具**（C 档范围外）——迁移指引如上，供消费方自取；升级后**新写入自动合规**。

### 7.6 FileManagement 链路上游提示

`FileManagement` 上传安全链的 F7 黑名单**不拒**中文名/空格——V0.3.1 起**实际拒绝发生在 BlobStoring 白名单并向上传播**（`FileManager` 上传调用处无 try 包裹 → `ArgumentException` fail-fast 直达调用方）；`RenameFileAsync` 改名**不触碰 Blob 路径**，不受本收紧影响。

## 八、实体表结构

`BlobRecordEntity` 映射到 `BlobRecord` 表（SG1 自动生成建表 DTO/DataService）：

| 列名 | 类型 | 说明 |
|------|------|------|
| Id | BIGINT (PK, Identity) | 主键 |
| Name | NVARCHAR(256) | Blob 名称（业务键） |
| Path | NVARCHAR(1024) | 存储路径（相对 RootPath） |
| ContentType | NVARCHAR(128) | MIME 内容类型 |
| Size | BIGINT | 文件大小（字节） |
| Tags | NVARCHAR(MAX) | 标签（JSON 数组字符串） |
| UploaderName | NVARCHAR(128) | 上传者名称 |
| CreateTime | DATETIMEOFFSET | 创建时间 |
| UpdateTime | DATETIMEOFFSET | 更新时间 |
