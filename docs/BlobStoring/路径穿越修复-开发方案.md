## 1. 目标与背景

### 1.1 目标

**消除 `LocalStorageService` 四入口（Upload/Download/Delete/Exists）的目录穿越逃逸**，使一切用户可控路径在 `Path.Combine(RootPath, ...)` 拼接前即被结构性拒绝——**fail-closed**（校验失败抛 `ArgumentException`，延续 C2 评审语义，不静默吞掉）。修复形态：**段级白名单正则 + 规范化前缀双保险**（第 3/4 章详述），对齐 Metrics M-01 / Dashboard D-01 白名单先例。

修复验收标准（对应 B-01 整改建议）：
1. `EnsureSafeRelativePath` 拒**前导分隔符**（`/`、`\` 开头）→ rooted 绝对路径 / UNC 全灭；
2. 补 `/etc/passwd`、`\Windows\System32\x`、`//server/share/x`（UNC）等 B-01 列示形态测试用例；
3. 既有合法行为零回归：内部生成的 `{guid}/{name}` 相对路径、`photo.JPG` 等大小写文件名不受影响。

### 1.2 背景：C2 评审既有修复与 BL-P0 缺口

`LocalStorageService` 在 V0.1.1（`57e7206`）经 C2 评审修复引入 `EnsureSafeRelativePath`（L155-164）——校验为**黑名单式**：拒绝空/空白、`.`/`..` 段、`:`（盘符）。BL-P0 评审实证该修复**拦不住 rooted/UNC**：

> B-01（P0）：`EnsureSafeRelativePath` + Download/Delete/Exists——**rooted/UNC 路径穿越**：校验只拦 `.`/`..`/`:` 段，`/etc/passwd`、`\Windows\System32\x`、`//server/share/x` 均通过（segments 无非法段）；`Path.Combine(root, rooted)` 实测直接返回 rooted 路径（.NET 行为）——任意文件读/删/探测 + UNC SMB 访问。测试 InlineData 未覆盖此形态。

**根因**：黑名单永远追着攻击形态走——`Split('/', RemoveEmptyEntries)` 把前导分隔符**静默吞掉**（`/etc/passwd` → `["etc","passwd"]` 视为普通相对段），而 `Path.Combine(root, rooted)` 按 .NET 语义**第二个参数为绝对路径时直接返回它本身**（第 2 章实证），拼合结果整体逃逸 RootPath。**黑名单只能拒"已知恶意组合"，无法结构性保证"未列举形态不可达"**——这正是 B-01 判定 P0 的原因。修复方向（B-01 整改建议）：白名单字符集 + 规范化前缀校验双保险。

## 2. 漏洞面枚举

> 实证环境：.NET 10.0.10 / Windows 10.0.26300。每面给出 ① 现有校验判定 ② `Path.Combine`/`GetFullPath` 实证行为 ③ 逃逸判定。`root = ./blobs`（临时根）；`CURRENT-CHECK` = 现有 `Replace('\\','/') + Split('/', RemoveEmptyEntries)` 视角。

### A. Rooted 绝对路径（`/etc/passwd`、`\Windows\System32\x`）

| 项 | 实证 |
|---|---|
| 输入 | `/etc/passwd` / `/Windows/System32/x`（反斜杠归一后同形） |
| CURRENT-CHECK | `safe='/etc/passwd'` → `segs=[etc,passwd]`——**无非法段 → 通过** ❌ |
| `Path.Combine(root, in)` | `/etc/passwd`（**rooted=True——path2 为绝对路径时 Combine 直接返回 path2**）❌ |
| `Path.GetFullPath` | `F:\etc\passwd`（逃逸 root，指向任意盘符根） |
| 危害 | 任意文件**读**（Download）/ **删**（Delete）/ **存在性探测**（Exists）——B-01 原文实证 |

### B. UNC 路径（`//server/share/x`、`\\server\share\x`）

| 项 | 实证 |
|---|---|
| 输入 | `//server/share/x` / `\\server\share\x` |
| CURRENT-CHECK | 归一 `//server/share/x` → `segs=[server,share,x]`——**通过** ❌（`RemoveEmptyEntries` 吞掉前导双分隔符） |
| `Path.Combine(root, in)` | `\\server\share\x`（UNC，rooted=True）❌ |
| `Path.GetFullPath` | `\\server\share\x` |
| 危害 | **SMB 共享任意访问**——读/删/探测远程文件（B-01 原文） |

### C. 盘符 / 冒号（`C:\evil`、`C:evil.txt`、ADS `good.txt::$DATA`）

| 项 | 实证 |
|---|---|
| 输入 | `C:\evil`（rooted）/ `C:evil.txt`（drive-relative）/ `good.txt::$DATA`（NTFS ADS） |
| CURRENT-CHECK | 三形态 `:` 均被 `segments.Any(s => s.Contains(':'))` **拦截** ✅（L162-163） |
| `Path.Combine(root, in)` | `C:\evil`（rooted=True）/ `C:evil.txt`（drive-qualified，`GetFullPath` → `C:\evil.txt`） |
| 危害 | 现行已拦截；若 `:` 漏拦则盘符/ADS 逃逸。白名单后**结构性不可达**（`:` 不在字符集） |

### D. `..` 穿越（`../../x`、`a/../b.txt`）

| 项 | 实证 |
|---|---|
| 输入 | `../../x` / `a/../b.txt` |
| CURRENT-CHECK | 段级 `is "." or ".."` **拦截** ✅（L160） |
| `Path.Combine` + `GetFullPath` | `root\..\..\x` → `...\Local\x`（逃逸）；`root\a/../b.txt` → `root\b.txt`（段折叠留在 root 内） |
| 危害 | 现行已拦截；白名单后 `..`/`.` 首字符为 `.`——首字符要求字母数字，**结构性不可达** |

### E. 分隔符混用 / 前导分隔符 / 空段（`a\b/c`、`/a/b`、`a//b`、`a/b/`）

| 项 | 实证 |
|---|---|
| 输入 | `a\b/c.txt`（混用）/ `/a/b`（前导）/ `a//b`（空段）/ `a/b/`（尾空段） |
| CURRENT-CHECK | 混用段拆分正常；**前导分隔符被 `RemoveEmptyEntries` 吞掉** → `/a/b` segs=`[a,b]` **通过** ❌（A/B 的使能形态）；空段/尾空段吞掉后通过（无害——GetFullPath 折叠在 root 内） |
| `Path.Combine(root, '/a/b')` | `/a/b`（rooted=True）❌（= 漏洞面 A） |
| 白名单应对 | 整体正则 `^[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?(?:/[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?)*\z`——**段首与段尾必须字母数字**（中缀可含 `.`/`_`/`-`），前导分隔符结构必败；`\z` 严格字符串末尾（`evil.txt\n` 尾随换行必败） |

### F. 短文件名 / 编码 / 尾点尾空格绕过（`C:\PROGRA~1`、`~1/evil.txt`、`evil.txt.`、`evil `、`你好.txt`）

| 项 | 实证 |
|---|---|
| 输入 | `C:\PROGRA~1`（8.3 短名）/ `~1/evil.txt` / `evil.txt.`（尾点）/ `evil `（尾空格）/ `你好.txt`（Unicode） |
| CURRENT-CHECK | `:`/`..` 段外全部**通过**（无其他字符约束）；`evil.txt.` 经 `GetFullPath` → `evil.txt`（**Windows 尾点剥离**）——不逃逸但文件名混淆（读错文件）；Unicode/短名均在 root 内解析，不逃逸但不可控 |
| `Path.GetFullPath` | `C:\Program Files`（短名展开，**配合盘符逃逸放大**）；`root\evil.txt`（尾点剥离）；`root\你好.txt`（root 内） |
| 危害 | 短名/Unicode 单独不逃逸（盘符/UNC 已被 C/B 拦）；**尾点/尾空格属 Windows 归一混淆**——白名单字符集排除空格，段尾 `.` 由正则结构排除（第 4 章） |

### 漏洞面汇总

| 面 | 形态 | 现状 | 修复后 |
|----|------|:---:|:---:|
| A | `/etc/passwd`、`\Windows\...` rooted | ❌ 通过 | ✅ 拒（段首非字母数字——前导分隔符） |
| B | UNC `//server/share/x` | ❌ 通过 | ✅ 拒（前导分隔符） |
| C | 盘符/ADS 冒号 | ✅ 已拦 | ✅ 结构性不可达 |
| D | `..` 段 | ✅ 已拦 | ✅ 结构性不可达 |
| E | 前导分隔符（A/B 使能件） | ❌ 通过 | ✅ 拒（正则整体锚定） |
| F | 短名/Unicode/尾点尾空格 | ⚠️ 不逃逸但混淆 | ✅ 字符集+结构排除/显式声明 |

## 3. 选项对比与选定

### 选项 1：黑名单加固（现状打补丁）

在 `EnsureSafeRelativePath` 追加 ① 前导分隔符判断 ② `Path.GetFullPath` 前缀比较。保留 `segments.Any(...)` 黑名单骨架。

| 维度 | 评估 |
|---|---|
| 优点 | 改动最小；既有测试大部分保持 |
| 缺点 | **追着攻击形态走**——B-01 已实证黑名单漏拦（`RemoveEmptyEntries` 吞前导分隔符）；`GetFullPath` 前缀比较需处理大小写/尾分隔符/短名展开等归一差异，边界易漏；无法结构性保证"未列举形态不可达"；与 Metrics/Dashboard 先例（白名单）方向背离 |
| 结论 | **不选**——本次 FAIL 的核心教训即黑名单不完备 |

### 选项 2：白名单字符集（段级正则 + 规范化前缀校验）——**选定**

对齐 Metrics M-01 / Dashboard D-01 逐段白名单先例，结构上列示"允许的字符集"，未列举即拒绝：

```csharp
// 段级白名单（逐段概念示意——Dashboard SegmentPattern 同型；实际实现为 §4.3 整路径锚定的 SafeRelativePathPattern）：
// 段首与段尾必须字母数字（防前导分隔符/点段/尾点/斩断首尾字符列），中缀允许 . _ -（文件名点号扩展）
private static readonly Regex SegmentPattern = new(
    @"^[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?\z",
    RegexOptions.Compiled | RegexOptions.CultureInvariant);
```

安全性质：「**不可包含也无需列举**」——`/`、`\`、`:`、空格、控制字符、`~`、`$` 等等一切不在字符集内的字符**结构上不可能出现**；`.`/`..` 段、前导点、尾点由正则**锚定结构**排除（段首与段尾必须字母数字 + 中缀仅 `[._-]`）；尾随换行（`evil.txt\n`）由 `\z`（严格字符串末尾）排除。再叠加 **`Path.GetFullPath` + RootPath 前缀 OrdinalIgnoreCase 校验**（纵深防御——即使正则未来被放宽/误配，规范化后仍必须落在 RootPath 之下）。

| 维度 | 评估 |
|---|---|
| 安全强度 | 段级白名单 = 攻击面收敛到"允许的字符集"；前缀校验兜底归一差异（大小写/尾分隔符） |
| 兼容性 | `photo.JPG`（FileManagement 既有测试用例，其 F7 黑名单放行）✅；内部 `{guid}/{name}` ✅（guid 十六进制、name 常规文件名字符）；**注意**：中文/空格/括号文件名被拒（有意的 fail-closed 收紧，第 4.5 章兼容性声明） |
| 一致性 | 与 Metrics/Dashboard 同型实现，仓库内模式统一 |
| 代价 | 行为收紧（上传名校验更严）——需指南安全节声明 + 版本 note |

### 选项 3：规范化前缀校验单保险（只做 GetFullPath 前缀比较）

| 维度 | 评估 |
|---|---|
| 优点 | 代码最少 |
| 缺点 | **单保险**：`GetFullPath` 在乱码路径上抛 `ArgumentException`（"路径中具有非法字符"）行为复杂；前缀比较须处理 `\.\`/`\\?\` 设备路径前缀（实测 `Path.GetFullPath` 对 device path 如 `\\?\C:\x` **原样返回**——与 RootPath 前缀不匹配 → fail-closed **拒绝**，本面结构性封堵，并非"可绕过"；但该防护完全依赖"前缀精确匹配"这一判定本身，仍属单保险）；RootPath 为相对路径（`./blobs`）时以当前工作目录为锚，`GetFullPath` 结果随 CWD 变——单独使用误判面大 |
| 结论 | 单保险不足——**与选项 2 组合为双保险**，不单独使用 |

### 选定

> **选项 2（白名单字符集）+ 选项 3（规范化前缀校验）双保险**：段级白名单正则结构性拒绝 rooted/UNC/穿越段/盘符/控制字符，`GetFullPath`+前缀校验兜底归一逃逸——对齐 Metrics M-01 / Dashboard D-01 先例，B-01 整改建议（"EnsureSafeRelativePath 拒前导分隔符 + 补测试"）的强化实现。

### 4.2 `EnsureSafeRelativePath` 重写（核心）

```csharp
/// <summary>
/// 相对路径防穿越校验（V0.3.1 BL-P0 修复）——段级白名单字符集 + 规范化前缀双保险：
/// ① 段级正则（<see cref="SafeRelativePathPattern"/>）整体校验——拒绝根路径/UNC（前导分隔符）、
///    "."/".." 段、盘符/ADS（':'）、控制字符、空格、尾点/尾分隔符/尾随换行及一切白名单外字符；
/// ② <see cref="Path.GetFullPath"/> 规范化后必须位于 RootPath 之下（OrdinalIgnoreCase 前缀）——
///    纵深防御（正则误配/未来放宽的兜底）。
/// 校验失败抛 <see cref="ArgumentException"/>（fail-closed，延续 C2 语义）。
/// </summary>
private void EnsureSafeRelativePath(string path, string paramName)
{
    ArgumentException.ThrowIfNullOrWhiteSpace(path);

    var normalized = path.Replace('\\', '/');
    // 整路径锚定正则（拒绝空段/尾分隔符/尾随换行——RemoveEmptyEntries 在此是陷阱：前导分隔符会被静默吞掉）
    if (!SafeRelativePathPattern.IsMatch(normalized))
        throw new ArgumentException(
            "路径仅允许 段(首尾字母/数字、中缀./_-) 以 '/' 分隔（拒绝绝对路径/UNC/盘符/穿越段/尾点/尾随换行/空白及控制字符）", paramName);

    // 双保险：规范化后必须位于 RootPath 之下
    var full = Path.GetFullPath(Path.Combine(_options.Value.RootPath, normalized));
    if (!IsUnderRoot(full))
        throw new ArgumentException("路径解析后超出存储根目录", paramName);
}
```

关键点：
- **整体正则（非逐段 Split）**：`^[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?(?:/[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?)*\z`——整体锚定使**前导分隔符（`/x`、`//x`）段首非字母数字 → 必败**；**段尾必须字母数字**（尾点 `evil.txt.`、尾分隔符 `a/b/` 必败——Windows 尾点剥离混淆与空段同灭）；**`\z` 严格字符串末尾**（尾随换行 `evil.txt\n` 必败——与"空白及控制字符拒"声明自洽，评审 P0-1/P1-2 闭环）；`RemoveEmptyEntries` 吞前导分隔符的漏洞面结构性不可达（不再用 Split 判定分段）；
- **`:` 不入字符集** → 盘符/ADS 结构性不可达；
- **段首与段尾必须字母数字**（中缀可含 `.`/`_`/`-`）→ 前导点（`.`/`..`/`.name`）与**尾点**（`evil.txt.`）必败（Windows 尾点剥离混淆消除）；单字符段 `a` 经 `[A-Za-z0-9]` 直配、可选组跳过形态通过；`evil ` 空格不入字符集必败；
- **`IsUnderRoot`**：`OrdinalIgnoreCase` 前缀比较 + 边界（`full == root` 或 `full` 以 `root + 分隔符` 开头）——防 `root` 自身（如 `/data/root`）时 `root-prefix`/`root2` 前缀误判。

### 4.3 Helper（新增，类内 private static）

```csharp
private static readonly Regex SafeRelativePathPattern = new(
    @"^[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?(?:/[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?)*\z",
    RegexOptions.Compiled | RegexOptions.CultureInvariant);

private bool IsUnderRoot(string fullPath)
{
    var root = Path.GetFullPath(_options.Value.RootPath);
    var rootWithSep = root.EndsWith(Path.DirectorySeparatorChar)
        ? root : root + Path.DirectorySeparatorChar;
    return fullPath.Equals(root, StringComparison.OrdinalIgnoreCase)
        || fullPath.StartsWith(rootWithSep, StringComparison.OrdinalIgnoreCase);
}
```

> 注：`EnsureSafeRelativePath` 由 static 改为实例方法（需读 `_options.Value.RootPath`）——`EnsureSafeFileName` 调用链同步。

### 4.4 四入口接线确认（无签名变化）

| 方法 | 接线 | 校验 |
|------|------|------|
| `UploadAsync`（L29-68） | `EnsureSafeFileName(name)`（L35，try 外→fail-closed 直达调用方） | `EnsureSafeRelativePath(name)` + `Path.GetFileName(name) != name`（防伪造非单段名） |
| `DownloadAsync`（L74-97） | `EnsureSafeRelativePath(path, nameof(path))`（L78，try 外） | 双保险 |
| `DeleteAsync`（L100-121） | L103 同上 | 双保险 |
| `ExistsAsync`（L124-140） | L127 同上 | 双保险 |

> 内部生成的 `{guid}/{name}`（`UploadAsync` 产出的 `BlobInfo.Path`）——guid 段为 32 位十六进制，name 段经上传校验，**必过**白名单；`GetFullPath` 前缀校验对合法路径必过（root 内）。`BlobRecordEntity.Path`（NVARCHAR(1024)）存储语义不变。

### 4.5 兼容性声明（行为收紧，须入指南）

| 形态 | 现状（V0.3.0） | 修复后（V0.3.1） | 说明 |
|------|---------------|-----------------|------|
| `photo.png`/`photo.JPG`/`my-file(1).jpg` | ✅ | ✅（`(1)` 含括号则 ❌） | 字母数字/`. _ -`（含大小写）全兼容——FileManagement `photo.JPG` 测试用例实证不回归 |
| `{guid}/{name}` 内部路径 | ✅ | ✅ | 结构必过 |
| 中文名/Emoji/`()（）`/空格 | ✅（黑名单未禁用） | ❌ 拒（`ArgumentException`） | **有意的 fail-closed 收紧**——白名单字符集外即拒；FileManagement 链路上游 F7 同为黑名单（**不拒**中文名/空格）——**实际拒绝发生在 BlobStoring 白名单并向上传播**（`FileManager` 上传调用处无 try 包裹 → `ArgumentException` fail-fast 直达调用方；`RenameFileAsync` 改名不触碰 Blob 路径，不受本收紧影响）；如消费方确有 Unicode 需求 → 缺口记录（第 7 章），另行评估 `\p{L}\p{N}` Unicode 白名单方案 |
| `..`/rooted/UNC/盘符 | X（V0.1.1 已拦/漏拦见 §2） | ❌ 拒（结构性） | 修复目标 |
| RootPath 为相对路径（`./blobs`） | 相对 CWD 解析 | 双保险下**同样相对 CWD**（`GetFullPath` 取 CWD 锚点）——RootPath 解析语义不变 | 无回归 |

**存量数据迁移指引**（P1-1 评审闭环——读路径回归必述，选评审方案 a）：V0.3.1 前经旧黑名单校验已存储的**非白名单文件名**（中文/空格/括号等——FileManagement F7 放行、历史上传可达），其 `StoredPath = {guid}/中文名.png` 形路径在 V0.3.1 起对 Download/Delete/Exists **同样被白名单整体拦截**——存量文件**不可读不可删**。处置：

1. **行为变更显著标注**：README 版本线 + 指南「安全说明」节同步提示（§6.1/§6.2 落实）；
2. **消费方迁移指引**：升级前扫描 `BlobRecord` 表 `StoredPath` 命中非白名单的行（判定以与 `SafeRelativePathPattern` 等价的正则为准；SQL 可先用 `LIKE '%[^A-Za-z0-9._/-]%'` 或含中文/空格/括号模式圈定候选后人工复核），对命中行**重命名/迁移**——经 `IBlobStorageService` 上传到新白名单名 → 更新 `BlobRecord.Path` → 删除旧物理文件/旧记录；或按业务评估是否接受"旧档只读归档"（改走导出通道）；
3. **脚本/指引落点**：BlobStoring 侧**不引入迁移工具**（本 C 档范围外），指引落使用指南（§6.1）供消费方自取。

> 备选方案（评审 b：读路径仅保留 `IsUnderRoot` 前缀单保险、正则仅作纵深，可零破坏兼容存量）**未选**——其需在 §3 重新论证"读路径单保险 + 前缀校验"的等价安全性（§3 选项 3 的顾虑仍存在：归一差异/大小写/尾分隔符边界 + RootPath 相对 CWD），且制造"上传收紧/读路径放宽"的策略不一致面。本方案取 (a) 全路径统一收紧 + 显式迁移指引：上传/读路径同一正则、同一白名单语义，行为变更透明，代价是存量非白名单文件的迁移义务落在消费方（上列指引已给出实操路径）。
