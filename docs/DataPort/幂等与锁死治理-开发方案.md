## 一、现状与代码事实

### 1.1 状态机

`DataImportRecordEntity.Status`（`DataImportRecordEntity.cs` L46-49）四态：

```
创建（L87）→ Processing → Succeeded（BatchFailures.Count == 0，ExecuteImportAsync L138）
                       → Failed（核心导入抛异常 best-effort 落库，L150-164）
                       → PartiallySucceeded（BatchFailures.Count > 0，L138-141）
```

- 终态才写 `EndTime`（`UpdateStatusAsync`/`MarkFailedAsync`）；Processing 期间 `EndTime = null`——**超时判定锚点充足**。
- Failed 仅覆盖"核心导入异常"路径（Provider 读取/转换抛异常）；**进程崩溃/kill 时连 Failed 都不会落库**——记录直接冻结在 Processing。

### 1.2 FileHash 幂等覆盖的层（记录层 = 文件级，非记录行级）

- 幂等分支（`DataImportTaskService.cs` L60-74）：`existing.Status is "Processing" or "Succeeded"` → 返回已有批次（`ImportResult.Empty`，拒绝）；**else 分支（含 PartiallySucceeded、Failed）→ `ResetToProcessingAsync`（L71）→ `ExecuteImportAsync` 全量重跑**。
- 记录层唯一键（实体 L16-18）：`TKWFIX_Dir_Filehash`（FileHash 唯一）+ `TKWFIX_Dir_Batchno`（BatchNo 唯一）——**无行级明细表、无 FileHash+行号唯一键**。
- **R2 边界（README L13-14）**：消费方在 `OnBatchWrite` 自管业务数据持久化，DataPort 不感知业务实体——**无法也不应在消费方业务表上施加行级约束**（唯一键对消费方表无效）。
- 并发竞态兜底：`CreateAsync` 唯一冲突 → re-query by FileHash 返回已有批次（L96-107）。

### 1.3 PartiallySucceeded 失败批次信息现状（DP-04 重导的前置事实）

- 失败明细仅存在于 `result.BatchFailures`（`BatchFailure.BatchIndex` + Exception），落库时**只拼前 5 条文本进 `ErrorSummary`**（L139-141）——**失败批次索引集合未结构化持久化**，重导时无从知道"哪些批次已成功"。

### 1.4 Processing 卡死场景（DP-05）

- 无超时清理、无重置管理 API、无断点续传——全仓 `grep "Processing"` 只有状态赋值/分支判定，零恢复路径。
- 卡死后果链：进程崩溃 → 记录冻结 Processing → `ImportAsync` 幂等分支 L65 把 Processing 视为"进行中拒绝" → **同文件永远无法再导入**；消费方唯一出路 = 手动改库。
- 并发场景额外注记：另一实例恰在导入**同一文件**时（多实例部署/用户并发双击），Processing 拒绝语义是必要的"单飞"保护——超时机制必须与活跃 Processing 区分（见 §4 超时判定基于 `UpdateTime` 而非最终态），不可误清活跃任务。

### 1.5 BackgroundJobs 接线能力核对（DP-05 候选前置）

- `TKWF.Ext.BackgroundJobs` README 白纸黑字：**"扩展不内建调度器——由消费方经 BackgroundJob/Quartz/Hangfire 定时调用"**（`_Framework/BackgroundJobs/README.md` L120、L181；`IJobHistoryCleanupService.cs` L10）——该扩展只提供"持久化增强 + 清理服务门面"，**无周期任务注册 API**（Quartz 存 储封装在 BackgroundJobs.Quartz，调度器归消费方）。
- **结论**：DP-05 不能"直接向 BackgroundJobs 挂周期任务"；正确形态 = **对齐 `IJobHistoryCleanupService` 先例**——DataPort 提供超时恢复门面 + Initializer 启动扫描兜底 + 文档给消费方周期调度接线示例。

## 三、决策 DP-04：PartiallySucceeded 重导幂等语义

### 3.1 候选方案评估

| 候选 | 语义 | 优点 | 缺点 | 判定 |
|------|------|------|------|------|
| **A. 拒绝（仅 Failed 重导）** | PartiallySucceeded 与 Succeeded 同为终态，幂等分支拒绝重导；重导仅限 Failed | 改动最小（L65 分支加 `or "PartiallySucceeded"` + 文档）；彻底消除重复写入 | **牺牲部分失败重试能力**——批次级失败（如某批字段越界）修复后无法重导，只能改文件换哈希重导；能力回退不符合"消费方自管 + 批次错误可修复"的导入常态 | ✗ 能力回退 |
| **B. 追加差异（失败批次重放）** | 重导时**仅重放失败批次**（新包装适配器跳过已成功批次的 `OnBatchWrite` 回调——消费方写库不触发，已成功数据零重复写）；Failed 仍全量重导 | 保留部分失败重试能力 + 消除重复写入（批次级幂等）；FailedBatchIndexes 结构化记录亦可作可观测性数据 | 需持久化失败批次索引（新列）；重放语义边界需文档（OnValidate 对失败批次全量重跑） | ✅ **选定** |
| **C. 行级明细表（FileHash+行号唯一键）** | 新增明细行 + 消费方表数据幂等键适配 | 记录层行级幂等 | **R2 冲突**：消费方业务表归消费方，行级唯一键对消费方表无约束力；引入新表 + 消费方 OnBatchWrite 自管理 + 键对齐成本高 | ✗ 违反 R2 边界 |

### 3.2 选定：B——失败批次重放（批次级幂等，definition 模式实现）

> **评审闭环（2026-11-09，P0-1/P0-2）**：原 §3.3 的 `RetryBatchReplayAdapter<T>` 装饰器机制**弃用**——两处硬缺陷：① **不可编译/不可安全绕过**：`ImportAdapterBase<T>` 的 `OnValidate`/`OnConvert`/`SheetName` 为 protected（透传内层受限，包装器无法在派生外调用），`BuildImportDefinition` 为 internal 且无 InternalsVisibleTo（无法经实例构建调度载体）——CS1540 级别障碍 + 反射绕过不可安全；② **batchIndex 获取**：包装器需自数批次推导批次号，核心未直给。**重设计 = 转达框架组公开 `BuildImportDefinition`（P0-1 方案 A）+ 扩展统一改走 definition 模式 onBatch 回调**（核心 `IImportService.ImportAsync(filePath, ImportDefinition<T>, onBatch, ...)` 已具备该重载，onBatch 直给 `(batchIndex, ...)`——顺带解决 batchIndex 获取）；onBatch 闭包内完成"重放过滤 + 心跳 + 已尝试上限跟踪"三职责。重放集合语义补两处数据正确性（P0-2，见 §3.3 ④）。

> 一句话：**PartiallySucceeded 重导 = 仅重放"失败 ∪ 首跑未尝试"批次（跳过已成功批次回调，消费方零重复写、零数据丢失）；Failed 全量重导；Succeeded/Processing 拒绝不变。**

理由：
1. 对齐 R2 边界——幂等落在 **DataPort 可控制层（批次回调调度）**，不侵入消费方业务表；
2. 保留"部分失败可重试"能力（方案 A 的损失点）；
3. 重放判定状态（FailedBatchIndexes/MaxAttemptedBatchIndex）结构化落库，顺带修复 ErrorSummary 仅文本无可观测明细的现状；
4. 对已存在的 PartiallySucceeded 旧记录（无新列）**向后兼容**——空状态按全量重导（等效现状）。

### 3.3 实施细节（P0-1 重设计 + P0-2 语义加固）

**① 转达框架组：`BuildImportDefinition` internal → public（前置依赖，阻塞项）**

- 现状事实（反编译核证）：核心运行库 `ImportAdapterBase<T>`（`TKWF.Utility.DataPort`）——`DataSourceName`/`ColumnMapping`/`OnBatchWrite` 为 public，`SheetName`/`OnValidate`/`OnConvert` 为 **protected**，`BuildImportDefinition()`（内部方法，负责把受保护的钩子接线进 `ImportDefinition<T>`）为 **internal** 且测试程序集无 IVT——扩展无法经实例调用，也无法在派生类外安全重建消费者适配器的完整导入语义。
- **选定方案 A（推荐）**：转达框架组将 `BuildImportDefinition` 提升为 `public`（internal→public 非破坏性；先例：ADR89 条件原子原语由扩展转达框架组落地）。`ImportDefinition<T>` 为 public record（`ColumnMapping`/`SheetName`/`Validate`/`Convert` 均 public），`OnBatchWrite` 为 public virtual（扩展可直接调用）——**definition 模式 onBatch 重载核心已具备**（`IImportService.ImportAsync<T>(filePath, ImportDefinition<T>, Func<int,int,IReadOnlyList<T>,CancellationToken,Task> onBatch, ...)`，README §三.3 既有），本机制所需框架增量**仅此一处**（方法访问级别）。
- **降级预案（次选，仅应急）**：若框架组未在本迭代窗口落地——反射提取 internal 定义 + **安全降级全量重导**（P0-1 方案 B）——**披露反射脆弱性**：核心运行库内部实现（字段/签名）演进可能破坏反射提取，且绕过了编译期契约，仅作应急通道、不作为长期方案；进入该路径须在代码注释与使用指南显式标注（见 §六 风险表）。
- **决策记录（P1-5 IVT/访问）**：选定方案 A → **无反射、无新增 InternalsVisibleTo**（DataPort csproj 不加 IVT——测试经 public 门面 `IDataImportTaskService` 走生产路径，无需访问 internal）；原 `RetryBatchReplayAdapterTests` 独立测试文件取消（包装器已不存在），DP-04 测试并入 `DataImportTaskServiceTests` 生产路径断言。

**② 实体新增列 ×3（`_Framework/DataPort/DataImportRecordEntity.cs`）**

```csharp
/// <summary>失败批次索引集合（JSON 数字数组字符串，如 "[0,2]"；PartiallySucceeded 时落库，重导判定重放集合；null 表示兼容旧记录按全量重导）。</summary>
[FreeSql.DataAnnotations.Column(Position = 16, IsNullable = true)]
[MaxLength(512)]
public string? FailedBatchIndexes { get; set; }

/// <summary>首跑批次大小（重放时校验一致性，P0-2 ①——防重导传不同 BatchSize 致批次索引错位写错行）。</summary>
[FreeSql.DataAnnotations.Column(Position = 17, IsNullable = true)]
public int? BatchSize { get; set; }

/// <summary>首跑已尝试的最大批次索引（≥0；导入结束落库；重放判定"未尝试尾部"纳集，P0-2 ②——早停路径不丢数据）。</summary>
[FreeSql.DataAnnotations.Column(Position = 18, IsNullable = true)]
public int? MaxAttemptedBatchIndex { get; set; }
```

- **列数说明（评审 P0-2 ①"1 新列 → 2 新列" → 实为 3 新列，偏移理由）**：P0-2 ① 要求持久化首跑 `BatchSize`（第 2 列）；P0-2 ② 给出两选一——"记录已尝试最大批次索引"（判定法）或"StopOnBatchFailure 场景降级全量重导"。**选定判定法**（理由见 ④），而判定法本身要求**记录"已尝试最大批次索引"**（第 3 列 `MaxAttemptedBatchIndex`）——无此列则早停（StopOnBatchFailure=true / Terminate 中断）后的未尝试尾部批次无法与"已尝试失败批次"区分，重放集合漏尾部 → 永久数据丢失（正是 P0-2 要求修复的漏洞）→ 第 3 列为正确性必需。相比持久化 `StopOnBatchFailure` 布尔标志，`MaxAttemptedBatchIndex` 更通用：一条统一判据覆盖 continue/stop/Terminate 一切中断源（见 ④）。若强行压缩为 2 列 → 早停尾部丢失或需 StopOnBatchFailure 标志列（等价再 +1），故不压。
- 写入时机：`UpdateStatusAsync` 落终态时一并写入（PartiallySucceeded → FailedBatchIndexes + MaxAttemptedBatchIndex；Succeeded → 仅 MaxAttemptedBatchIndex，FailedBatchIndexes=null；Failed → 均 null）；变更后重跑 `pwsh .xCodeGen/run-xcodegen.ps1 -Ext DataPort`（生成物 `.g.cs`/DTO 入库）。

**③ DataService 扩展（`DataServices/DataImportRecordEntityDataService.cs`）**

- `UpdateStatusAsync` 增可选尾参 `string? failedBatchIndexes = null, int? maxAttemptedBatchIndex = null`（L50-65 签名尾参，非破坏）；PartiallySucceeded 时序列化 `result.BatchFailures.Select(b => b.BatchIndex)` 为 JSON 数字数组 + 传入 onBatch 闭包跟踪的 `maxAttemptedBatchIndex`（**取 `max(既有, 本次)`**——防重导早停低估首跑覆盖）。也**未新增构造器/注册改动**。
- `ResetToProcessingAsync`（L33-47）**不清空 `FailedBatchIndexes`/`BatchSize`/`MaxAttemptedBatchIndex`**（重导判定依据）；保留 StartTime（既有 CanUpdate=false 语义）。
- 新方法 `ListStaleProcessingAsync(DateTime olderThanUtc, int limit)`——`EntitySelectAsync(r => r.Status == "Processing" && r.UpdateTime < olderThanUtc, ...)` 供 DP-05 复用（§4.3 ②）。
- 新方法 ×2（**ADR89 条件原子更新**，基类内部 `InternalUpdateWhereAsync` 已有转发，见 `DataService.g.cs` L74-79）：
  - `Task<int> TouchProcessingAsync(long id, DateTime utcNow, CancellationToken ct)`——`EntityUpdateWhereAsync(r => r.Id == id && r.Status == "Processing", () => new DataImportRecordEntity { UpdateTime = utcNow }, ct)`——心跳用，仅 Processing 态更新（防覆写终态）。
  - `Task<int> MarkStaleFailedAsync(long id, DateTime staleBeforeUtc, string errorSummary, DateTime utcNow, CancellationToken ct)`——`EntityUpdateWhereAsync(r => r.Id == id && r.Status == "Processing" && r.UpdateTime < staleBeforeUtc, () => new DataImportRecordEntity { Status = "Failed", EndTime = utcNow, ErrorSummary = errorSummary, UpdateTime = utcNow }, ct)`——**CAS 恢复**（P1-1），条件更新 + 影响行数返回。

**④ 重放机制实现 = definition 模式 + onBatch 过滤闭包（替代原 `RetryBatchReplayAdapter`）**

原 §3.3 ③ 的 `RetryBatchReplayAdapter<T>` 包装适配器**取消**（P0-1：protected 钩子不可透传 + `BuildImportDefinition` internal 不可调用——CS1540 级别不可编译；包装器需自数批次获取 batchIndex）。新形态：**核心调度入口统一走 definition 重载，扩展在 onBatch 回调内完成"重放过滤 + 心跳 + 已尝试上限跟踪"三职责**——batchIndex 由核心回调直接给出（顺带解决 batchIndex 获取问题）；`ImportService` 核心零改动。

`_Framework/DataPort/DataImportTaskService.cs` 新增内部执行助手（实施按此形态，伪代码）：

```csharp
// 统一执行路径：新建 / Failed 全量 / PartiallySucceeded 重放 均经 definition 重载（心跳覆盖所有长导入）
private async Task<ImportResult> ExecuteCoreImportAsync<T>(
    string filePath, ImportAdapterBase<T> adapter,
    ReplayFilter? replayFilter,                 // null = 全量重放（新建/Failed/旧记录兼容）
    ImportBatchOptions batchOptions, long recordId, CancellationToken ct) where T : new()
{
    var definition = adapter.BuildImportDefinition();   // ① 框架公开后可用（含消费方 SheetName/OnValidate/OnConvert）
    var maxAttempted = -1;                              // 已尝试最大批次索引（onBatch 跟踪）
    var lastHeartbeat = DateTime.UtcNow;

    var result = await _importService.ImportAsync(filePath, definition,
        async (batchIndex, startRowIndex, batch, ct2) =>
        {
            if (maxAttempted < batchIndex) maxAttempted = batchIndex;

            // ⚠️ 心跳（P1-2，§4.3 ③）：距上次 touch ≥ HeartbeatIntervalMinutes → CAS 刷新 UpdateTime
            if (_options.HeartbeatIntervalMinutes > 0 &&
                (DateTime.UtcNow - lastHeartbeat).TotalMinutes >= _options.HeartbeatIntervalMinutes)
            {
                try { await DataService.TouchProcessingAsync(recordId, DateTime.UtcNow, ct2); lastHeartbeat = DateTime.UtcNow; }
                catch { /* 心跳失败不终止导入——静默/LogWarning（瞬时 DB 故障不杀合法导入） */ }
            }

            // 重放过滤（见 BuildReplayFilter）：跳过"已成功且已尝试"批次 = 消费方零写库
            if (replayFilter is not null && !replayFilter.ShouldReplay(batchIndex))
                return;

            await adapter.OnBatchWrite(batch, ct2);     // OnBatchWrite 为 public virtual——扩展可直接调用
        },
        batchOptions, ct);

    await PersistReplayStateAsync(recordId, result, maxAttempted, ct);  // FailedBatchIndexes/MaxAttemptedBatchIndex 落库
    return result;
}

// P0-2 ② 统一重放判据（判定法，选定理由如下）——一条规则覆盖 continue/stop/Terminate 一切中断源：
//   replay(batchIndex) = (batchIndex ∈ FailedBatchIndexes) || (batchIndex > MaxAttemptedBatchIndex)
//   ——continue 模式 MaxAttempted=末批 → 尾部为空集 → 精确重放失败批次（零重复写）；
//     早停 模式 MaxAttempted=中断批次 → 未尝试尾部全部纳入重放（零数据丢失），已成功前缀仍跳过（零重复写）。
internal sealed record ReplayFilter(HashSet<int>? FailedSet, int? ReplayFromBatchIndex)
{
    public static ReplayFilter Full => new(null, null);          // 全量重放（新建/Failed/旧记录/脏数据降级）
    public bool ShouldReplay(int batchIndex)
        => (FailedSet is not null && FailedSet.Contains(batchIndex))
           || (ReplayFromBatchIndex is int from && batchIndex >= from);
}

// 从既有记录构造重放过滤器：
//   FailedBatchIndexes 空/解析失败 → 全量（旧记录兼容 / T11 脏数据降级全量）
//   否则 → FailedSet = 解析集合；ReplayFromBatchIndex = MaxAttemptedBatchIndex + 1（跑批上界由运行期自然封顶）
internal static ReplayFilter BuildReplayFilter(DataImportRecordEntity existing)
{
    var failed = ParseFailedBatchIndexes(existing.FailedBatchIndexes);      // JSON 数字数组 → HashSet<int>，失败 → null
    if (failed is null) return ReplayFilter.Full;
    return new ReplayFilter(failed, existing.MaxAttemptedBatchIndex is int m && m >= 0 ? m + 1 : null);
}
```

- **语义要点**：`OnValidate`/`OnConvert` 对所有行全量执行（重导时失败批次内含坏行仍需被验证/跳过——重导后再失败批次会再次收集）；仅 `OnBatchWrite` 按判据过滤——**跳过批次 = 消费方零写库 = 已成功数据零重复**。
- `ProviderName` 仍记原始 `adapter.GetType().Name`（新建分支 L86 不动；重导分支不动该列）。
- **选定判定法（非"StopOnBatchFailure 降级全量"）的理由**：① 早停首跑时前缀批次（0..k-1）已成功——全量降级会把前缀重复写（非幂等消费方脏数据），判定法前缀仍跳过 → **零重复写**；② 尾部（k+1..N）从未尝试——判定法纳入重放 → **零数据丢失**；③ 单条统一规则无需在重放分支按模式分别编码，且天然覆盖 Terminate 等非批次失败中断源（省去 StopOnBatchFailure 布尔标志列，见 ② 列数说明）。

## 四、决策 DP-05：Processing 超时治理

### 4.1 候选方案评估

| 候选 | 机制 | 优点 | 缺点 | 判定 |
|------|------|------|------|------|
| **(a1) 启动扫描** | Initializer `InitializeAsync` 内（或宿主启动帧）调用恢复服务：重置超时 Processing → Failed | 零调度依赖、实现最小、部署重启正是卡死主场景（进程崩溃 → 下次启动即治愈）；对齐"异常静默 + 后台 fire-and-forget" | 不覆盖长驻进程运行期间卡死（需等下次重启） | ✅ 组合入选定 |
| **(a2) BackgroundJobs 周期任务** | 消费方经 BackgroundJob/Quartz 周期调用恢复门面 | 对齐 `IJobHistoryCleanupService` 先例（README L120/L181 既定接线形态）；长驻期间定时治愈 | **BackgrounJobs 无调度器**——周期触发责任在消费方调度器，DataPort 侧只能提供门面 + 文档接线示例；无法"自动挂" | ✅ 组合入选定（门面 + 文档） |
| **(b) 断点续传** | 记录游标（已导入行/批次 → 下次导入从断点续跑） | 终极能力 | **强依赖核心运行库改造**（ImportService 流式切分不支持"从第 N 批/行续"），需框架组评估；与 DP-04 重放机制部分重叠但语义不同（重放=失败重试；续传=中断恢复） | ✗ **列后续**（V0.2.0 路线图既有候选，本期不实施） |

### 4.2 选定：超时清理（(a1)+(a2) 组合）——新门面 + 心跳 + 启动扫描 + 消费方周期接线示例

> **评审闭环（2026-11-09，P1-1/P1-2）**：恢复标记改 **CAS 条件更新**（防 scan→mark 间隙覆写终态，P1-1，§4.3 ②）；原"活跃 Processing 不会被误清"表述修正——**导入中途无心跳真实存在**，超 60min 合法导入会被误清 → 方案增加**心跳设计**（§4.3 ③）；测试下标 T9-T11 入 §3.4。

> 一句话：**新建 `IStaleImportRecoveryService` 门面（CAS 重置超时 Processing → Failed + 错误记录）；导入心跳（onBatch 内周期条件 touch UpdateTime）保活跃；Initializer 启动扫描兜底；文档提供 BackgroundJobs 周期调度接线示例（对齐 JobHistoryCleanupService 先例）。断点续传列为后续。**

- **超时判定**：`Status == "Processing" && UpdateTime < now - ProcessingTimeoutMinutes`——基于 **UpdateTime**（创建时设置 L90；**导入心跳每间隔刷新 UpdateTime**，P1-2 §4.3 ③）。
- **活跃 Processing 不会被误清的表述修正（P1-2）**：**引入心跳前该表述不成立**——现状导入流程跨批无 UpdateTime 写入（"最后触碰时间"仅创建时一次），超 60min 的合法长导入会被误清。**方案增加心跳**：导入执行中周期条件 touch `UpdateTime`（WHERE Status='Processing'，CAS），心跳间隔（默认 1 分钟）<< 超时阈值（默认 60 分钟）→ 健康进行的导入 UpdateTime 恒新、恢复扫描天然跳过；**残余误清面** = 心跳间隔内的停滞/进程存活但无回调推进（GC/死锁/超长单批转换）→ 该场景本应标记超时（风险表 + Options 调大指引，§6）。**心跳为机制组成部分而非可靠性铁律**：无法接受活跃导入被误清的消费方可调大 `ProcessingTimeoutMinutes`（或置 0 禁用恢复扫描，心跳随之停用）。
- **默认值**：`ProcessingTimeoutMinutes = 60`（大于任何合理导入时长；消费方可调）+ `HeartbeatIntervalMinutes = 1`（显著小于超时阈值）。Notes：均经 DataPortOptions（`DataPortOptions.cs`，绑定 `TKWF:DataPort` 既有节，零新配置节）
