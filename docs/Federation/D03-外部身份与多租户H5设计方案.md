## 一、背景与目标

### 1.1 业务场景

用户在微信公众号（图文消息、菜单、二维码、分享）进入某商户 H5，系统需要：

1. 识别"这个人是谁"（微信 openid / 平台统一身份）；
2. 定位"进入的是哪个商户"（租户 `mid`），加载该商户数据分区（独立数据库）；
3. 判断"是否已是该商户会员"，分别引导：会员卡 / 注册会员 / 关注公众号；
4. 大部分功能免登录可看，少数功能需要身份/会员才可操作。

### 1.2 设计目标

| # | 目标 |
|---|---|
| G1 | **AB/CD 两阶段解耦**：身份采集（AB）不认识商户，业务兑付（CD）不依赖联邦/微信内部 |
| G2 | **三层身份模型**：外部身份（L1）→ 平台身份（L2）→ 商户会员（L3） |
| G3 | **档案前瞻**：外部身份档案字段全量预留，按认证等级可空、可回填 |
| G4 | **入口抽象**：图文 / 菜单 / 二维码 / 扫码 / 直接访问统一为 ticket → 业务兑付 |
| G5 | **通道分类显式化**：ChannelType × Verification → Capability 派生，杜绝"配置了但没权限" |
| G6 | **能力位分级**：L0 匿名 ~ L4 强认证，前后端共用一套能力判定 |
| G7 | **多 provider 预留**：微信 / 支付宝 / 抖音 / 小程序 / OIDC 同一编排 |
| G8 | **合规就绪**：个人信息分类、授权留痕、可删除、日志脱敏 |

### 1.3 非目标（本期不做）

- 业务领域商户侧功能细化（会员卡页、注册页、关注引导页、分级守卫的页面实现）——见 §十三 实施路线 第 2 部分；
- 跨商户会员统一权益（积分通兑、跨店储值）——仅预留 UnionID 归并能力；
- 一公众号多商户的消歧规则——仅声明业务侧自决，结构预留；
- 支付/储值/提现强认证实现——仅定义 L4 分级位。

## 二、问题拆解：两个阶段，四个动作

```
┌────────────── AB 阶段：联邦/微信侧（身份域） ──────────────┐
│  A 身份采集（联邦）     B 身份归一（AuthCenter）            │
│  外部基本身份           外部身份 → 平台身份（L1→L2）        │
│  openid/unionid/档案    首次分配 platformUid               │
│  （不认识"商户"）        档案记录在 AuthCenter 内部          │
└──────────────────────────┬────────────────────────────────┘
                    ticket（FederatedTicketPayload）
┌──────────────────────────▼────────────────────────────────┐
│  C 业务兑付（业务系统）     D 租户路由（业务系统）           │
│  凭 ticket 解读身份        解读 → 商户 mid → 数据分区       │
│  查询/免登/业务自决         会话绑定租户                     │
│  （不依赖联邦/微信内部）     （不认识微信协议）              │
└────────────────────────────────────────────────────────────┘
```

**核心不变量**：

- AB 不认识"商户"——没有租户概念，只有 `provider` / `ChannelId` / `ChannelAlias` / `openid` / `unionid` / `platformUid`；
- CD 不认识"微信"——只消费 ticket 解出的 payload，按业务自己的约定解读；
- **AB 与 CD 之间的唯一耦合点是 ticket**（及其载荷契约 `FederatedTicketPayload`）。

## 三、命名与边界定案（v0.2 确认）

| 概念 | 定案名 | 归属 | 说明 |
|---|---|---|---|
| 逻辑票据（通用） | **ticket** | 应用层通用语 | 不绑定实现，业务系统/联邦侧通用 |
| 联邦免登票据载荷 | **`FederatedTicketPayload`** | **Federation.Abstractions**（签发/兑付共享契约） | 联邦场景的 T；非联邦场景（优惠券核销码、预约码）由对应系统定义自己的载荷派生类，互不相识 |
| 密封票据中间人 | **`ISealedTicketService<T>`** | TrustCenter（实现）/ 主框架（契约） | **泛型中间人，零业务知识**：只保证"存进去什么、取出什么"；对任意 T 同样工作 |
| OAuth 授权码 | **`IAuthorizationCodeService`** | TrustCenter | 与 ticket 无关（ADR109 D4 拆分后两者独立），勿混淆 |
| 业务商户行外键 | **`ExternalChannelId` + `ExternalChannelType`** | 业务商户表 | 中性命名（不写 WeChat 前缀），多平台顺手可扩展；当前实现仅微信 |
| 通道对外别名 | **`ChannelAlias`** | WeChatOperations/通道配置 | 可变对外名（公众平台可能因重名改名）；业务绑定**不依赖它** |

**关键结论**：

1. **TrustCenter 是通用中间人**：`ISealedTicketService<T>` 对任意 T 存/取；联邦签 `FederatedTicketPayload`，券系统签自己的 Payload，各 T 由签发/兑付双方共享定义，TrustCenter 不关心业务细节。
2. **业务绑定只用不变键**：`(ExternalChannelType, ExternalChannelId)`；别名变更零影响。

## 四、通道模型（联邦/微信侧核心）

### 4.1 三级维度

```
ChannelType（通道形态，稳定，接入时定，一等字段）
  ├─ mp_subscription  订阅号
  ├─ mp_service       服务号
  ├─ mini_program     小程序
  └─ （未来）work_wechat / open_platform / alipay / douyin ...

Verification（认证状态，可变，独立维度，不合并进 ChannelType）
  ├─ none        未认证
  ├─ verified    已认证
  └─ （未来）enterprise_verified 企业认证等

Capability（能力面，派生，不手工配置）
  网页授权 / userinfo / 静默授权 / 模板消息 / 支付 ...
  ← 由 (ChannelType, Verification) 推导并缓存
```

**设计规则**：

1. **`ChannelType` 与 `Verification` 不合并**：`(订阅号, 已认证)` 与 `(服务号, 已认证)` 能力不同；`(服务号, 未认证)` 存在且受限——合成枚举会引出大量非法组合。
2. **Capability 派生而非配置**：从 (Type, Verification) 推导并缓存，避免"配置了但实际没权限"的假象。
3. **唯一性**：`(ChannelType, ChannelId)` 复合唯一——**不假设跨类型唯一**（微信平台事实今天全局唯一，但凭证/API 完全不同，且未来微信调整唯一性域不受我们控制）。
4. **凭证密文**：AppSecret/Token/EncodingAESKey 等仍在 WeChatOperations 维护（AES-GCM 密文，明文不落库），业务侧只查询配置信息，**不解密凭证、不复制凭证**。

### 4.2 通道配置供给层（契约 + Provider + 内存缓存 + 三机制更新）

**依赖方向**（v0.2 定案）：

```
各消费者（事件验签 / 签票 / URL 组装 / 免登）
        │ 经 Registry 统一入口
        ▼
IChannelRegistry（组合选区 + 缓存层，Federation 只依赖此契约）
        │ 未命中 → 下钻
        ▼
Provider 集合（按优先级，装配决定，未装配源自然跳过）
  ├─ DB Provider（WeChatOperations，可选装配，权威）
  └─ Static Provider（Federation.WeChat 平台库内置，配置文件，默认，零 DB 零扩展依赖）
        ▼
原始存储（DB 密文 / 配置文件明文）
```

**设计规则**：

1. **Federation 只依赖契约 `IChannelSource`**（Federation.Abstractions）——不直接依赖 WeChatOperations 扩展；DB Provider 经 DI 注册进集合（与平台库并列，可选装配，`TryAddEnumerable`），Federation 对实现零感知；
2. **默认 Provider = 简化静态源**：内置在 Federation.WeChat 平台库，读 `TKWF:Federation:WeChat:Channels` 配置文件，不依赖 DB；WeChatOperations 未装配时链路仍可用（降级语义：静态配置可验签、可签票）；
3. **组合选区**：Registry 按优先级（DB 优先 → 静态回退），优先级**配置化**（替代现状硬编码 `Insert(0)`）；
4. **内存缓存挂在 Registry 层**（统一一份，所有消费者共享），不挂在各 Provider 内（避免多份副本、失效不统一）；缓存内容 = **解密后的明文配置**（验签热路径零解密，不落盘、不进日志，属进程内信任边界）；
5. **静态源不失效**（配置变更靠重启/重载，语义 = 启动快照）；失效机制只针对 DB 源。

**缓存更新三机制**（针对 DB 源，按即时性分层，缺一不可）：

```
┌─ 显式失效（管理端改配置后调用）
│    Invalidate(channelId?) ← 逐通道或全量；来源：WeChatOperations 管理端点 / 运维接口
│
├─ 事件失效（配置变更传播）
│    通道配置变更事件 ChannelConfigChanged{ channelId, version }
│    → 本地总线订阅 → 命中通道失效；来源：DB Provider 写路径（落库变更时发布域事件）
│    （跨进程部署 → 事件经总线/Redis pub-sub，本期不展开）
│
└─ TTL 兜底（事件漏发时的自愈安全网，60~300s）
     显式/事件失效优先，TTL 只在两者都未触发时兜底
```

### 4.3 通道不可达降级策略（v0.3 补充）

微信事件推送 **5 秒无响应 → 微信自动重试（约 3 次）→ 最终失败**；**验签失败频发会触发微信安全告警甚至停用服务器 URL**。因此"不响应"与"提示性响应"必须分场景，不能一刀切：

| 场景 | 默认行为 | 理由 |
|---|---|---|
| S1 验签失败（篡改/重放） | **不响应**（硬线，**不可配置**） | 安全边界；频发触发微信告警 |
| S2 通道不存在（未注册） | **不响应** + 告警日志 + 指标计数 | 防通道枚举探测；运维靠日志/指标发现（静默≠不可观测） |
| S3 通道存在但 disabled | **提示响应**（文案可配置，默认"服务暂停中，请稍后再试"） | 合法用户已过验签，提示友好且不泄露内部细节 |
| S4 凭证缺失/解密失败 | **不响应**（硬线，不可配置）+ 告警日志 + 指标 | 配置事故属内部状态，静默 + 告警最稳 |
| S5 消息类型无 handler 命中 | **提示响应**（默认文案"感谢您的关注，请稍后再试"——现有 DefaultReplyText 语义） | 纯体验兜底，无安全风险 |

**开关形态**（不搞逐场景 5 开关，一个总开关 + 文案配置）：

```jsonc
"TKWF:Federation:WeChat:EventReply": {
  "UnknownChannelReplyEnabled": false,        // S2：是否回复提示（默认 false = 静默防探测；开发/调试期可开）
  "DisabledChannelReplyTemplate": "服务暂停中，请稍后再试",  // S3 文案
  "DefaultReplyText": "感谢您的关注，请稍后再试"              // S5 兜底文案（已有）
}
```

> 原则：**安全敏感场景（S1/S2/S4）fail-closed 静默 + 可观测性（日志/指标）；用户可见正常边界（S3/S5）提示 + 文案可配**。默认值可按部署环境再调，行为模型不变。

### 4.4 运营配置面（WeChatOperations 全局配置能力，v0.4 补充）

**动机**：第 1 部分中"业务可配项"已积累一批（URL 模板、S3/S5 文案、S2 开关、弱身份清理策略、TicketMode/TTL），若继续散在 appsettings 中，运营改一处文案都要改配置重启。**WeChatOperations 提供运营配置服务**将其统一收拢，并复用 §4.2 供给模式（契约 + Provider + 缓存 + 三机制更新），不新造机制。

**配置域总表**（联邦/微信侧业务可配项全集）：

| 配置域 | 配置项 | 示例 | 出处 |
|---|---|---|---|
| 图文回复 | 落地 URL 模板（含占位符） | `https://m.loongba.cn/{mid}/auth?t={ticket}` | §八 |
| 回复文案 | S3 disabled 文案 / S5 兜底文案 | "服务暂停中，请稍后再试" | §4.3 |
| 降级行为 | S2 `UnknownChannelReplyEnabled` 开关 | false | §4.3 |
| 弱身份清理 | enabled / inactiveDays / action / recoveryWindowDays / excludeBound | 180 / soft_delete / 90 / true | §十五 O2 |
| ticket | TicketMode / TTL | Sealed / 300s | §六 |

**配置服务形态**：

```
WeChatOperations（运营扩展）新增"运营配置"能力
  ├─ 实体：OperationsConfig 系列（全局级单例配置，含 Version / UpdatedAt / UpdatedBy）
  ├─ 管理 API（运营页面，[GenerateController] 生成端点）：
  │    GET/PUT 各配置域（读写 + 版本）
  │    POST preview-render   ← 模板预览：提交模板 + 示例占位符值 → 渲染后 URL/文案
  │    GET  test-url         ← 测试地址：按当前模板 + 测试通道签票 → 可直达完整链接
  └─ 读取契约：IOperationsConfigSource（WeChatOperations 实现 DB 源）
         → 与 §4.2 同构：静态配置（Options）降级，DB 权威，
           内存缓存 + 显式/事件/TTL 三机制更新
```

**关键规则**：

1. **DB 权威、静态配置（Options）降级**：出厂默认（180 天/软删、S5 文案、默认模板骨架）来自 appsettings；DB 未配置用默认，DB 配置后以 DB 为准；
2. **静态源不失效**（重启/重载更新），DB 源走三机制——与 §4.2 同机制，不新造轮子；
3. **预览/测试**：保存前 `preview-render` 所见即所得；保存后 `test-url` 立即自测链路（对齐现有 `wechat/test/{channel}/{ticket}` 测试端点语义），不依赖真机微信；
4. **与 O2 边界**（权责分离落位）：
   - 配置在 **WeChatOperations**（运营就近，策略配置 = 运营配置面一个配置域）；
   - 执行在 **AuthCenter**（L1/L2 数据所有者，清理能力契约，不含策略）；
   - 触发在**业务系统**（手动按钮 / 业务定时任务读策略 → 调 AuthCenter 能力）；
   - 连接 = 运营配置服务 + 清理能力契约。

## 五、身份模型

### 5.1 三层身份

```
L1 外部身份 External Identity          —— "在哪里的身份证"
   key: (Provider, ChannelType, ChannelId, ExternalUserId)
   附: UnionId（可空）、Profile 档案、Assurance 等级、ProfileSource

        │ 归一（同 Provider 有 UnionId 时跨 channel 归并同人）
        ▼
L2 平台身份 Platform Account            —— "这个人"
   key: platformUid（全局唯一，首次解析时分配）
   附: 绑定因素 AuthFactor（L1 ↔ L2）、平台级档案

        │ 绑定（每个租户一张卡，业务侧）
        ▼
L3 商户会员 Membership                  —— "在某店的会员卡"（业务领域，下一轮细化）
   key: (TenantAlias, platformUid) 唯一
```

### 5.2 档案与 Assurance

| 档案字段 | 订阅号（仅事件） | 认证服务号（网页授权） | 说明 |
|---|---|---|---|
| `ExternalUserId`（openid） | ✅ | ✅ | 必有 |
| `UnionId` | ❌（需绑开放平台） | ✅ | 跨公众号归并键 |
| `NickName` / `AvatarUrl` | ❌ | ⚠️ 可能 | 新规需授权/填写组件，**字段必留、值可空** |
| Gender / City / Province / Country / Language | ❌ | ✅ | 预留 |
| SubscribeStatus / SubscribeTime | ✅ | ✅ | 事件侧可得 |
| PhoneNumber | ❌ | ✅（独立组件） | 独立字段，null = 未授权 |
| `AssuranceLevel` | `event` | `base` / `userinfo` | 档案可信等级 |
| `ProfileSource` | — | `oauth_userinfo` / `user_filled` / `merchant_set` | 防"微信用户"当真名 |

**档案写入语义（拿到一次就记录，但按优先级合并）**：

```
优先级：user_filled > merchant_set(仅L3) > oauth_userinfo > event
规则：补空/升级（低→高填 null 字段）；以新为准（同源刷新）；
     绝不覆盖：user_filled 不被 oauth 默认值（"微信用户"+灰头像）覆盖；
     永远不把 "微信用户" 当真名（PresentationSource 挡）。
```

## 六、ticket 形态（T1 / T3，配置决定）

```
                        ┌─ T1 自包含：时间戳+加密串直接进 URL（轻量，无中间人）
 ticket 架构形态        │
       只有两种 ────────┤
                        └─ T3 中间人：SealedTicket 句柄（推荐，扩展性好）
                               └─ 存储后端是【配置项】：DB（默认）| Redis | ...
```

- **T3 是默认**：`ISealedTicketService<T>` 在 TrustCenter 已有 DB CAS 实现（`TKWF_SealedTicket`：Payload AES-GCM 密文落库、只存 SHA256(ticket) 索引、used 原子 CAS 防重放、可绑定核销人、TTL 可配）；
- **T1 是轻量选项**：超轻场景（临时凭据等），上层不感知；
- **上层统一走 `ILoginEntryService`**（或等价门面），实现选择由配置（如 `TicketMode`）决定——这是明确设计，不是约定。

### 6.1 示例：`FederatedTicketPayload`（契约草案，字段白名单制）

```jsonc
{
  "provider": "wechat",               // 与 channelType 的取值矩阵见下方说明
  "channelType": "mp_service",
  "channelId": "gh_xxx",              // 不变键（正式 = 微信唯一 ID）
  "channelAlias": "prana",            // 不可变对外名（slug 语义，A14 定稿）；展示名另存 ChannelConfig.DisplayName（可变、不入票）
  "externalUserId": "oXXXX",          // openid
  "unionId": "uXXXX",                 // 可空
  "platformUid": "u-…",               // L2 平台身份（AB 阶段已分配，A11）
  "assurance": "userinfo",            // event | base | userinfo
  "iat": 0, "exp": 0, "jti": "…"      // 时效与单次标识
}
```

> **provider × channelType 取值矩阵（评审 P2/缺陷 2 补充）**：契约文档需定义合法组合防非法（如 `provider=wechat` + `channelType=alipay_mini_program`）。进「Federation.Abstractions」契约时的约束：provider ∈ {wechat, alipay, douyin, ...开放注册表}；channelType 合法值由各 provider 定义（wechat: mp_subscription/mp_service/mini_program/work_wechat...）。
> **payload 字节预算（评审 R9）**：当前 11 字段序列化约 300–500B，SealedTicket 上限 4068B，余量充足；后续扩字段须记录预算。

**明确不含**：`mid/tenant`（AB 不认识租户，业务链接里的 mid 由业务模板决定，与票无关）；`targetRoute`（URL 由业务模板构造，路由去向业务模板即知）。

**`profile` 是否入票——已定稿（O1，评审拍板）**：**不入票**。ticket 断言"是谁"（身份断言），不承载"长什么样"（展示档案）——关注点分离；event 级票本无档案，不入票对所有票统一处理；PII 控制面更小。档案获取：C 侧按需调 **AuthCenter 档案接口**（`GetProfileByUIdAsync` 既有能力，鉴权基于已认证会话；调公众平台接口取头像昵称时顺带 ProfileSync 旁路）。

## 七、联邦/微信侧时序（AB 阶段，本部分为 v0.2 重点）

```
① 微信用户触发事件（关注 / 图文消息 / 菜单点击 / 二维码）
   │  事件经 ChannelAlias 接入URL 到达 Federation 事件端点
   │  （Federation 先解析 alias → 内部 ChannelConfig——alias 只出现在平台侧接入 URL）
   ▼
② A 身份采集（联邦层）
   ├─ 解析出 (ChannelType, ChannelId, openid) [+ unionId（若可得）]
   ├─ 凭证/验签：由 WeChatOperations 通道配置支撑（密文不出库）
   ├─ 关注/取关事件 → 关注域记录（FollowState）
   └─ 产出"外部身份"（L1 级信息，含 assurance=event 或更高）
   ▼
③ B 身份归一（AuthCenter）
   ├─ 首次遇到该 L1 → 分配 platformUid（L2 预置，AutoProvision 开启）
   ├─ 已有 → 复用（unionid 优先归并，其次 (provider,channelType,channelId,openid)）
   ├─ 档案：拿到一次昵称/头像 → 记录到 AuthCenter 内部（按 §5.2 合并策略）
   └─ 得到 { platformUid, openid, unionId, channelId, channelType, channelAlias, assurance }
   ▼
④ 签票
   ├─ 组装 FederatedTicketPayload（§6.1）
   ├─ 经中间人（T3: SealedTicket / T1: 自包含）签发 → ticket
   └─ TTL：过期 / 单次消费（严格单次，可用性见 §六+§十一）
   ▼
⑤ 图文回复（业务模板）
   ├─ 取该 channel 的业务图文模板（配置）
   ├─ 白名单占位符替换：{ticket} 等（联邦层不解析/不校验业务段，见 §八）
   └─ 返回图文 + URL（带 ticket）
```

**工程约束**：微信要求事件回复 5 秒内——签票（DB 写或加密）毫秒级可满足；**回复路径不做重活**（如调 user/info 取档案），档案补取放在用户点击后的 C 环节（Enrichment）。

## 八、URL 构造职责（配置分离）

```
业务（运营）配置 URL 模板 —— 模板是业务资产，含 mid 等业务段
  例：https://m.loongba.cn/{mid}/auth?t={ticket}

联邦/微信层执行：
  事件到达 → 取该 channel 的业务模板 → 签票 → 替换占位符 → 返回图文
  ① 只替换白名单占位符：{ticket}（+ 如需 {channelAlias}，取自 ChannelConfig 非用户输入）
  ② 业务段（mid 等）原样输出，不解析、不校验、不存储
  ③ 用户点击后 → 在业务系统打开（联邦/微信层不关心构造方式与落地页实现）
```

- mid 出现在 URL 里，是因为**业务模板写了它**，不是联邦层认识它；
- 安全：占位符白名单 + 业务段字面输出，防模板注入 → 开放重定向。

## 九、C 侧兑付边界（业务领域，本节只定边界，细节下一轮细化）

```
业务系统（C）拿到 ticket（FederatedTicketPayload）
  ├─ ① 兑付：经中间人 Redeem（或本地解 T1）→ payload
  ├─ ② 解读：provider / channelType / channelId / openid / uid / unionid / assurance / exp/jti
  ├─ ③ 校验：时效 / 幂等（T3 中央单次已兜 / T1 需 jti 缓存） / 通道未登记 → 拒绝
  ├─ ④ 业务查询：
  │     ├─ 通道信息：(channelType, channelId) 查 WeChatOperations（缓存）→ 通道配置
  │     ├─ 商户归属：业务库 (channelType, channelId) 查商户行 → mid（见 §十）
  │     ├─ 关注/取关：关注域查询接口（消费结果，不实现微信协议）
  │     └─ 会员：业务库按 platformUid 查 L3
  ├─ ⑤ 免登：payload.platformUid → 建业务会话 / 换 sessionKey
  └─ ⑥ 业务自决：会员卡 / 注册 / 关注引导 ……（与联邦/微信层零依赖）
```

## 十、渠道 ↔ 商户绑定（定位在业务侧）

**绑定关系挂在商户行上，不建独立表**——生命周期与商户一致，避免别名副本同步问题：

```
Merchant（业务库，保存商户信息处）
  ├─ Alias                 ← 业务别名（= mid，业务自定）【业务领域下一轮细化】
  ├─ ...业务信息
  ├─ ExternalChannelType   ← 通道形态（mp_service / mp_subscription / mini_program）
  └─ ExternalChannelId     ← 通道 ID（不变键；正式 = 微信唯一 ID）
  （不存 ChannelAlias——展示/归因时现查 WeChatOperations，单一事实源）
```

**关联查询方向**（业务侧主动）：

```
(C, Ch) → ① WeChatOperations（缓存）→ 通道完整配置（凭证密文不解不开）
        → ② 业务库商户行 → mid（业务别名）+ 商户业务信息
```

**一通道多商户**（集团/二级组织）：业务规则消歧（按 openid 归属 / 入口域），本期不展开，结构预留。

## 十一、认证分级（L0–L4）

| 级别 | 语义 | 判定 | 典型页面 |
|---|---|---|---|
| **L0 匿名** | 只看公开内容 | 仅需 tenant | 商户介绍、活动列表、券展示 |
| **L1 已识别** | 知道是谁（有 L1 身份），未必是会员 | 有效 ticket / 身份会话 | 认证落地、关注引导 |
| **L2 已登录** | 有平台会话 | sessionKey 有效 | 个人中心骨架 |
| **L3 是会员** | 当前租户有 L3 会员 | L2 + L3 存在 | 会员卡、我的积分、兑换 |
| **L4 强认证** | 实名 / 手机号绑定 | 额外因素 | 储值、提现、大额券 |

未登录引导：L0 永远可看；L3 功能点击 → 无 L1/L2 → 关注引导；有 L1 无 L3 → 注册引导；有 L3 会话失效 → 静默重建。（页面实现归第 2 部分）

| 风险 | 设计 |

## 十五、开放问题（已择优定稿 — 评审 2026-10-29 Oracle7）

> 三项重点开放问题经评审已全部定稿：**O1 不入票 / O2 权责分离（soft+physical 本期）/ O3 仅 Sealed / O4-4 按域多表**。逐项裁决与理由见 §十六，以下保留各问题的背景与权衡备查。

### O1. `profile` 是否入票

> ✅ **定稿（评审）**：**不入票**（关注点分离：票断言"是谁"≠展示档案；event 级票无档案，统一不入）。档案读取接口归 **AuthCenter**（既有 `GetProfileByUIdAsync`，鉴权基于已认证会话；独立档案模块会碎片化身份域，不建）。

- **背景**：C 侧注册会员页需预填昵称/头像。两条途径——(a) 入票：AB 签票时塞档案，C 兑票即得（零额外调用）；(b) 不入票：C 按需调档案接口取（多一次 RTT，assurance=event 时需先授权补全）。
- **权衡**：
  - 入票代价：票体膨胀（昵称+头像 URL 全量 base64 后 ticket 长 500~900 字符）→ 图文链接变长（微信/客户端截断风险）；PII（昵称/头像）进入 ticket 载体（URL/日志/分享链）；签票热路径附加档案读取负担。
  - 不入票代价：注册预填多一次 RTT；档案接口需鉴权/审计/脱敏（受控入口）。
  - 关键事实：T3 中间人模式下 payload 本就不占 URL——入票只是"图省一次调用"，却放弃 T3 短句柄优势；且 event 级票（图文路径）本来就无档案，入票对部分票无效，不入票对所有票统一。
  - **倾向（用户思路，非结论）**：**不入票**。签票热路线不做额外读写；业务系统明确需要时主动读取（调公众平台接口取头像昵称时顺带更新 ProfileSync 旁路，不进签票路径）。
- **评审确认点**：① 入/不入/折中（昵称入、头像不入）；② 档案读取接口归属（AuthCenter 档案接口 / 独立身份档案模块）与鉴权审计策略。

### O2. L2 弱身份留存策略（能力归系统，策略归业务）

> ✅ **定稿（评审）**：权责分离方案成立；默认值确认（180 天/软删/90 天恢复/有绑定者除外）；本期先 **soft_delete + physical_delete**（physical 是 GDPR 删除权必需），**anonymize 后置**（语义不清需独立 spec）；设置入口 = WeChatOperations 运营配置面一个配置域（域语义定义在 AuthCenter.Abstractions，A17 张力约束）。

- **背景**：A11 定案 L2 事件阶段预置（AutoProvision）→ 任何发过消息/关注过公众号的人都会建平台账号，含大量"永不成为会员"的弱身份（仅 provider/channel/openid，无档案无绑定）。
- **动因**：合规（openid 属个人信息，保存期限 = 目的所需最短时间）；存储成本（随粉丝线性增长）；安全面（僵尸账号）。
- **关键事实**：AutoProvision 开启 → 用户再次交互自动重建账号 → **清理弱身份用户无感知、业务无损失**；弱身份不触碰业务数据 → 清理低风险。
- **权责分离设计（v0.4 补充）**：**系统提供能力，业务配置策略，触发归业务**——
  - **能力层**（数据所有者 = AuthCenter / 账号域）提供清理服务契约：`QueryWeakIdentitiesAsync(criteria)` / `PurgeAsync(ids, mode)` / `GetWeakStatsAsync()`，**策略参数由调用方传入，AuthCenter 不存"何时清、清哪些"**；
  - **策略层**（业务/运营侧配置）：WeChatOperations（举例）提供**全局设置**：
    ```jsonc
    { "weakIdentityRetention": {
        "enabled": true,            // 总开关
        "inactiveDays": 180,        // 无活动阈值
        "action": "soft_delete",    // soft_delete | physical_delete | anonymize
        "recoveryWindowDays": 90,   // 软删可恢复窗口（soft 时有效）
        "excludeBound": true        // 有会员绑定/档案者永不清理
    } }
    ```
  - **触发归业务**：手动（运营页面按钮）或业务自带定时任务（框架不内置调度，或插件式）；
  - **出厂默认值**（开箱即用、业务可改）：180 天无活动 / 软删除 / 90 天恢复窗口 / 有绑定者除外。
- **"无活动"定义（显式）**：无新事件 / 无票据签发 / 无档案更新 / 无会话。
- **评审确认点**：
  ① 清理能力契约归属（AuthCenter，还是账号域独立模块）；
  ② 设置入口归属（WeChatOperations 设置面 / 平台管理 / 均可装配）；
  ③ 出厂默认值是否认可（180 / 软删 / 90）；
  ④ 三个动作（软删/物理/匿名化）本期全提供，还是先软删+物理。

### O3. T1 自包含是否本期实现

> ✅ **定稿（评审）**：**仅 T3，TicketMode 配置位保留**（DI 切换成本极低，比"仅抽象接口预留"更友好；可接受的 YAGNI 妥协——一个枚举值 + DI switch）。

- **背景**：ticket 形态 T1（自包含加密串）/ T3（SealedTicket 中间人），`TicketMode` 配置决定（A10）。
- **权衡**：
  | 维度 | T3 | T1 |
  |---|---|---|
  | 单次消费 | ✅ 天然（DB CAS） | ❌ 需 jti 缓存（有缓存即退化回 T3 一半） |
  | 中央撤销 | ✅ 删记录 | ❌ 无法撤销 |
  | 密钥轮换 | ✅ 无影响 | ❌ 轮换致存量票全失效 |
  | PII 控制 | ✅ payload 不进 URL | ⚠️ payload 直达 URL |
  | 依赖 | DB（本项目必然存在） | 零依赖 |
  | 现状 | **已实现且成熟** | 未实现，需新增成本 |
- **关键事实**：T1 唯一相对优势是"零依赖"，但本项目 DB 必然存在，该优势不存在；T3 已实现，T1 反而是新增实现成本；免登/券码两个已知场景都需要单次消费与可撤销。
- **倾向**：**本期仅实现 T3**；`TicketMode` 契约与配置位保留（可配 `SelfContained`），取值仅 `Sealed` 可用；T1 形态预留、实现后补（契约层不感知，将来加 T1 不影响上层）。
- **评审确认点**：契约/配置位是否本期就位，还是连配置位也砍掉（仅抽象接口预留）。

### 16.5 设计缺陷与实现注意（会被现实打脸的假设）

1. **alias 可变性矛盾** → 已按 A14 修复（不可变）；
2. **Verification"独立可查"不成立**——微信无认证状态 API，人工配置字段（1.2）；
3. **运营配置面跨域承载** → 已按 A17 补充域边界（只存值，语义校验走各域契约）；
4. **T3 payload 密钥与 SsoClient credential 共钥（keyed ISymmetricKeyProvider 同键）**——轮换影响面耦合：移交时评估独立密钥键（如 `SymmetricKeyProviderKeys.TrustCenterSealedTicket`）；
5. **"5 秒/3 次重试"硬编码假设**——签票路径 SLA 定为 **< 3 秒**（留 2 秒余量），不以"满足 5 秒即可"为目标。
