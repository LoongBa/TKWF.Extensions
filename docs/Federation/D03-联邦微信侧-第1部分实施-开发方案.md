## 三、1.1 `FederatedTicketPayload` 契约（Federation.Abstractions）

### 3.1 契约定义（D03 §6.1 定稿形态）

新文件 `Federation.Abstractions/FederatedTicketPayload.cs`，namespace `TKWF.Ext.Federation`：

```csharp
/// <summary>
/// 联邦免登票据载荷（D03 §6.1——Federation 域专用，AB 签票 → CD 兑付的唯一耦合点）。
/// <para>与框架 Core <see cref="FederatedIdentity"/> 不互替（A7/P2）：FederatedIdentity 是框架通用
/// 「已可信外部身份」POCO（LoginAsFederatedAsync 路径）；本载荷是 Federation 域票据契约
/// （provider/channelType/channelAlias/platformUid/assurance 语义），仅经 ISealedTicketService&lt;T&gt;
/// 泛型中间人密封。</para>
/// </summary>
public sealed record FederatedTicketPayload(
    string Provider,              // 开放注册表：wechat / alipay / douyin ...
    string ChannelType,           // 通道形态：mp_subscription / mp_service / mini_program / work_wechat ...（provider 定义合法值，见 ChannelTypeRegistry）
    string ChannelId,             // 不变键（正式 = 微信唯一 ID gh_xxx）
    string? ChannelAlias,         // 不可变对外名（slug 语义）；可空 = 未配置
    string ExternalUserId,        // openid
    string? UnionId,              // 可空（跨 channel 归并键）
    string? PlatformUid,          // L2 平台身份（AB 阶段已分配；可空 = 未分配）
    string Assurance,             // event | base | userinfo（开放字符串，出票方声明）
    long Iat,                     // 签发 Unix 秒（DateTimeOffset.UtcNow.ToUnixTimeSeconds()）
    long Exp,                     // 过期 Unix 秒
    string Jti);                  // 单次标识（签发方生成，≥16B 随机）
```

**字段白名单制**（D03 §6.1 明确不含 mid/tenant/targetRoute/profile——AB 不认识租户、档案不入票、URL 由业务模板构造）。

### 3.2 provider × channelType 取值矩阵（评审 P2/缺陷 2 补充）

- `Provider`：开放注册表（wechat/alipay/douyin/...），与 `ChannelConfig.PlatformType` 同构——不枚举死；
- `ChannelType` 合法值由各 provider 定义——FA 提供 `ChannelTypeRegistry` 静态字典 + 校验 helper：

```csharp
public static class ChannelTypeRegistry
{
    // provider → 合法通道形态集（开放注册表；新 provider 扩展此字典）
    public static readonly IReadOnlyDictionary<string, IReadOnlyList<string>> LegalChannelTypes =
        new Dictionary<string, IReadOnlyList<string>>(StringComparer.Ordinal)
        {
            ["wechat"] = ["mp_subscription", "mp_service", "mini_program", "work_wechat"],
        };
    public static bool IsLegal(string provider, string channelType)
        => LegalChannelTypes.TryGetValue(provider, out var types) && types.Contains(channelType);
}
```

- 校验位置：**签票入口**（`ILoginEntryService`/`EventReplyHandlerBase` 组装 payload 前）——非法组合直接拒（不隐式透传）；兑付侧（`FederatedTicketPayload` 解码后）**不校验**（载荷来自已密封票据，中间人保证来源可信；校验语义留给 C 侧业务）。**倾向如此分割**：签票侧 fail-fast（配置错误早暴露），兑付侧零开销（热路径）。
- **payload 字节预算（评审 R9）**：11 字段 JSON 序列化 ≈ 300–500B < SealedTicket 上限 4068B（TrustCenter `MaxPayloadBytes = 4096-12-16`）；契约注释记录预算，扩字段须复查——新增 `PayloadBudget.cs` 常量 + 单元测试锁定上限（`Serialize(Payload) < 1024B` 防御线）。

### 3.3 命名空间与依赖

- 纯 BCL record，零新依赖（FA 最小依赖面 `TKWF.Domain` 不变）；
- `ChannelTypeRegistry` 纯静态字典（零 DI）。

### 3.4 条件 1 闭合——`ChannelConfig.Capabilities` 字段（Oracle6 阻断条件）

**决策：方案 A——FA `ChannelConfig` 新增 `ChannelCapabilities` 属性**：

```csharp
public sealed class ChannelConfig
{
    // ...既有 8 属性不动...
    /// <summary>
    /// 通道能力面（D03 §4.1 Capability——(ChannelForm, Verification) 派生的协议能力，
    /// 非营业能力）。<b>默认 <see cref="ChannelCapabilities.None"/> = 刻意 fail-closed</b>。
    /// 投影规则：DB Source 按实体 ChannelForm/Verification 经 capability resolver 派生填充；
    /// 静态 Source 按 <c>IChannelSource.Capabilities</c> DIM 填充（per-source 粗粒度，对齐既有语义）。
    /// </summary>
    public ChannelCapabilities Capabilities { get; init; } = ChannelCapabilities.None;
}
```

- **per-channel 语义**：`IChannelSource.Capabilities` 是 per-source（一个源一个平台），无法表达"同一 WeChatOperations DB 源下多公众号各自 (Form, Verification) 不同 → 能力不同"——`ChannelConfig.Capabilities` 属性承载 per-channel 粒度（条件 1 根因）；
- **零破坏**：`init` + 默认 `None`——既有 9 平台库 + StaticChannelRegistry + DbChannelRegistry 投影零改动编译通过；
- §八.3 投影映射表对应行更新：`Capability 派生 | ChannelConfig.Capabilities（per-channel，默认 None）| §4.3 resolver`；
- 营业能力（模板消息/支付）仍 Extra 承载（`Extra["capabilities_ext"]`）——协议能力与营业能力分层（确认点 A）。

## 四、1.2 通道模型扩展（WeChatOperations）

### 4.1 现状语义澄清（勘察结论）

现 `WeChatChannelConfigEntity.ChannelType` = **协议通道类型**（`wechat_oauth`/`wechat_event`——平台库 `ISsoChannel.ChannelType` 选区依据），**与 D03 的 ChannelType（通道形态 mp_subscription/mp_service/mini_program）语义完全不同**。直接复用会破坏协议选区，因此：

- **新增列 `ChannelForm`**（通道形态，D03 ChannelType 语义）：`mp_subscription`/`mp_service`/`mini_program`/`work_wechat`，接入时定、稳定（一级字段）；
- `ChannelType`（协议类型）列**保留不动**——协议选区语义零破坏；
- `WeChatChannelConfigEntity` 增 `Verification` 列（none/verified，**人工配置字段**——评审 R10：微信无认证状态 API）。

### 4.2 实体变更（表 `TKWF_WeChatChannelConfig`）

| 变更 | 说明 |
|---|---|
| + `ChannelForm`（max50，默认 `mp_service`） | D03 ChannelType 语义；接入时定 |
| + `Verification`（max20，默认 `none`） | 人工配置字段（R10） |
| 索引调整 | 现有 `ChannelId` 唯一 + `AppId` 唯一；**新增** `(ChannelForm, ChannelId)` 复合唯一（D03 §4.1.3），保留 ChannelId 唯一不变（既有数据零迁移）；ChannelForm 校验经 `ChannelTypeRegistry`（wechat 域） |
| `DisplayName`（已有） | 可变展示名，不入票（A14——现有列语义天然符合） |
| `Alias`（**新增列**，可空） | 通道对外别名（slug：小写字母数字连字符）；全局唯一索引；**写入后不可变**（1.6 守卫） |

### 4.3 Capability 派生（(ChannelForm, Verification) → 能力面）

- **派生不落库**（D03 §4.1.2）：`WeChatChannelCapabilityResolver`（WeChatOperations）——`(ChannelForm, Verification)` → `ChannelCapabilities`（FA `[Flags]` 现有枚举：None/OAuth/Event/Follow/FollowQuery/SilentAuthorize/Menu）：

```
mp_subscription × none      → Event | Follow
mp_subscription × verified  → Event | Follow（订阅号认证后仍无网页授权——微信平台事实）
mp_service      × none      → Event | Follow
mp_service      × verified  → Event | Follow | OAuth | SilentAuthorize | FollowQuery | Menu
mini_program    × (任意)     → OAuth | SilentAuthorize | Event | Follow（小程序授权域独立）
work_wechat     × (任意)     → OAuth | Menu（企微对接面；预留）
other           × (任意)     → None（fail-closed）
```

- 落点：**`IChannelSource` 投影处**（1.7 供给层）——`WeChatChannelConfig` → `ChannelConfig` 投影时把 `ChannelForm`/`Verification` 入 `ChannelConfig.Extra` + `Capabilities` 派生填充（不扩展 FA `ChannelConfig` 公共列——Extra 字典已承载平台特定负载，零 FA 破坏）。**评审确认点**：Capability 派生结果入 `ChannelConfig.Extra["capabilities"]`（int 序列化）还是 `IChannelSource.Capabilities` 静态声明增强？**倾向**：DB Provider 投影时按实体行动态计算 Capabilities（`IChannelSource.Capabilities` 是 DIM 默认静态声明——DB 源可覆盖 DIM 提供动态值；FA 接口语义允许）。具体见 §八.3 投影映射表。
- `ChannelCapabilities` 枚举**增位**：D03 提到 网页授权/userinfo/静默授权/模板消息/支付 五个具体能力——现有枚举 6 位（OAuth/Event/Follow/FollowQuery/SilentAuthorize/Menu）。**评审确认点**：本期是否细化为 userinfo/模板消息位？**倾向**：不加位——D03 Capability 是运营视角能力面，`OAuth` 位已覆盖网页授权、`SilentAuthorize` 覆盖静默授权；细粒度能力（模板消息/支付）属营业能力非认证能力，留 Extra 承载（`Extra["capabilities_ext"]="template_msg|pay"`）——避免枚举膨胀。

### 4.4 破坏性

- 仅加列（ChannelForm/Verification/Alias）——SyncStructure 开发环境自动建列；生产 DBA 迁移脚本（新增列 + 索引 + 存量回填 ChannelForm=`mp_service` 默认）。
- `WeChatChannelConfigEntity` DTO 投影暴露新列（管理 API 可读可写）。

### 5.1a Orchestrator 签名适配（P2 未含文件——决策必要）

勘察事实：`IFederatedLoginOrchestrator.LoginAsync(FederatedIdentity identity)` 签名吃**框架通用身份**（AuthCenter 门面），P2 迁移清单**未含** `FederatedLoginOrchestrator.cs`/`IFederatedLoginOrchestrator.cs`；依赖方向约束：AuthCenter ⟂ Federation（L2 门控单向，G17——AuthCenter 不得反向引用 FA）。**决策**：

- **Orchestrator 签名不动**（仍吃 `FederatedIdentity`——框架通用基础类型，`LoginAsFederatedAsync` 同型）；
- `ExternalTicketLoginService` 兑票得 `FederatedTicketPayload` → **门面内适配转换**为 `FederatedIdentity`（UId=payload.PlatformUid??"" / ChannelId / ExternalUserId / ChannelType=**协议类型推导**，见下）→ Orchestrator（编排语义不变）；
- 适配函数 `FederatedTicketPayload.ToFederatedIdentity(string protocolChannelType)` 放 FA（静态扩展方法——单点转换，测试锁定字段映射）。

**协议类型映射（语义碰撞处理）**：payload.ChannelType = 通道形态（mp_service）；Orchestrator 的 `channel_type` claim 现状写协议类型（wechat_event/wechat_oauth）。**决策**：

- payload **不含协议类型字段**（白名单 11 字段已定稿）；签票侧组装时（EventReplyHandlerBase/LoginEntryService）从自身通道类型（handler 已知 `wechat_event` 等）+ 形态（ChannelForm→payload.ChannelType）**双写**：payload.ChannelType=形态，同时 `Extensions["protocol_type"]="wechat_event"`（开放字典承载附加语义，不破坏白名单）；

- **⚠️ 命名碰撞警示（条件 4 闭合——实施红线）**：
  ```csharp
  // payload.ChannelType = entity.ChannelForm（通道形态 mp_service/mp_subscription...）
  //    而非 entity.ChannelType（协议类型 wechat_oauth/wechat_event——不入票）！
  ```

**取数通道（审核 P0-1 修复）**：`IChannelSource` 是普通 DI 集合元素，拿不到域用户；而 DataService 的 DI 注册是 throw-factory（只可经 `User.Use<T>()` 解析）。故新增可选契约 `IUserBoundChannelSource`（Federation.Abstractions，见 ADR-Federation-通道来源用户绑定契约）——`CompositeChannelRegistry` 构造时（守卫工厂帧内已注入 `IDomainUser`）向实现方绑定用户；DB 源以 `IDomainUser.Use<DataService>()` NoAop 直建取数。未绑定 → 空列表 + Warning（fail-closed 降级静态源），**禁止** `IServiceProvider` 直取 DataService。

### 8.4 注册与降级

- WeChatOperations 初始器 `TryAddEnumerable<IChannelSource, WeChatChannelRegistrySource>()`（可选装配——未装配时集合仅静态源，链路仍可用：**静态配置可验签、可签票**，D03 §4.2.2）；
- `CompositeChannelRegistry` 改：按 Priority 排序遍历 Provider 集合 + 缓存层 + 未装配源自然跳过（空集合 → 静态源兜底——平台库 `Federation.WeChat` 的 `WeChatChannelSource` 经 `AddWeChatFederationChannels()` 注册，消费者装配时二选一/二选二）；
- **评审确认点**：`DbWeChatChannelSource`（现有）与 `SsoChannelRegistryEntity`（Federation 主包 DB 源）去向——**倾向**：`DbWeChatChannelSource` 改造为 `WeChatChannelRegistrySource`（1.2 实体扩展后投影）；Federation 主包 `SsoChannelRegistryEntity` **停用新装配**（旧装配保留兼容、文档标注废弃——D03 A9 权威归 WeChatOperations；彻底删除留后续清理迭代）。**Oracle6 裁决：成立 ✅**。
- **条件 5 闭合——双 DB 源 alias 优先级（迁移期间并存）**：
  - `WeChatChannelRegistrySource` 声明 `Priority=100` > `SsoChannelRegistryEntity` 系源 `Priority=0`（+ 静态源 0）；
  - `CompositeChannelRegistry` 组合语义 = **按 Priority 降序首命中返回**（首个返回非 null 的源即终值）——高 Priority 源的 alias 覆盖低 Priority 源；
  - 运维指导：迁移期间不建议两源同 ChannelId 重复配置 alias（冲突时 WeChatOperations 侧优先——D03 A9 权威归一）；文档标注 `SsoChannelRegistryEntity` 废弃。

### 8.5 凭证模型边界（D03 §4.1.4）

- 凭证（AppSecret/Token/EncodingAESKey）**仍在 WeChatOperations 维护**（AES-GCM 密文落库）；业务侧/消费者只查配置信息，**不解密凭证、不复制凭证**——`ChannelConfig` 承载凭证是为事件验签/出站客户端热路径（进程内信任边界，现有语义）：Token/EncodingAESKey 由 DB 源投影期解密为明文（验签信任根，与静态源同语义），AppSecret 不进公共列（出站经 `DbWeChatCredentialResolver`）；
- 缓存存明文（进程内信任边界——D03 §4.2.4），不落盘不进日志。
