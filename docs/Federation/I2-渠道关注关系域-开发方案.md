## 一、背景与边界

### 1.1 问题

现状**没有任何扩展知道「谁关注了我们的公众号」**：

| 缺口 | 证据 |
|---|---|
| 关注/取关事件只回复、不落状态 | `WeChatEventChannel.HandleEventAsync` 返回 `null`，仅把 `msg_type`/`event`/`__decrypted_xml` 富化进字典 |
| 订阅统计是日粒度累计，无单用户粒度 | `SubscriptionStatEntity`（`StatDate` 维度），答不了「某 openid 当前是否关注」 |
| 消费者无法订阅「某人取关」 | 无任何域事件 |
| 「关注即登录」不可用 | `{ticket}` 占位符在模板 handler 中不替换（V0.5.0 已知缺口） |

### 1.2 三层职责（不可越界）

```
渠道协议层（Federation.{平台}）
    只做协议：验签 / 解密 / 解析 → 产出 ChannelEvent（语义事实）
关注关系域（Federation 主包）
    只做状态与事实：FollowEvent 日志 + FollowState 聚合根 + 域事件
业务决策层（消费方业务 / WeChatOperations 作示例）
    只消费域事件 → 决策（冻卡 / 停权益）→ 调 AuthCenter 冻结能力
```

- **AuthCenter 不感知 follow**：`FreezeAsync(reason)` 的 reason 只是字符串键
- **关注域不调 AuthCenter 的冻结**：域内只发 `FollowChangedEvent`
- **业务层不碰协议**：只消费域事件

### 1.3 与 Iteration 1 的衔接

Iteration 1 提供两件东西供本迭代消费：

| 提供方 | 能力 | 本迭代用途 |
|---|---|---|
| AuthCenter | `FreezeAsync(uid, reason)` / `ReleaseFreezeAsync(uid, reason)` | 业务层示例（§11 E7） |
| AuthCenter.Abstractions | `IExternalIdentityService.GetByExternalIdAsync(channelId, externalUserId)`（D6 合并后契约） | 编排层把 `openid → UId`，把 `UId` 放进 `FollowChangedEvent` 与 handler 信封 |

> 反例（已否决）：AuthCenter 增加 `IsFollowing` / `UnfollowedAt` 列——把渠道订阅语义塞进认证域，且无法承载多平台多公众号。

## 二、概念模型

### 2.1 术语

| 概念 | 含义 | 载体 |
|---|---|---|
| **Channel** | 一个可交互渠道实例（公众号 / 服务号 / 钉钉组织号…） | `ChannelConfig`（已有） |
| **ExternalSubject** | 渠道侧用户标识（微信 openid / 钉钉 userid / unionid） | `string`（不再引入 `AnchorType`——见 §2.2） |
| **ChannelEvent** | 平台无关的**语义事实**（关注/取关/扫码/消息/菜单点击） | 契约 `ChannelEvent`（新增） |
| **FollowEvent** | 「某主体在某渠道于某时刻关注/取关」的**不可变事实** | `FollowEventEntity`（追加写） |
| **FollowState** | 该主体当前关注状态 | `FollowStateEntity`（聚合根，唯一索引） |
| **LoginEntry** | 免登入口（带票链接 / 静默授权 URL） | 契约 `ILoginEntryService` |

### 2.2 `FollowState` 的定位裁定（聚合根，不是派生投影）

Iteration 1 的 D9 裁定「禁止派生投影列」（不得把可由既有列运算得到的值存第二份）。本迭代的 `FollowState` **不属于该禁令范围**，判据如下：

| 判据 | 派生投影列（D9 禁止） | `FollowState`（本迭代） |
|---|---|---|
| 能否在查询期从同表/同域数据算出 | 能（如 `Age = now - Birthday`） | **不能**（跨渠道异构事件流，且需要 O(1) 点查） |
| 写者 | 无（纯运算） | **单一写者**：仅 `IFollowStateService` 的事件驱动路径 |
| 可重建校验 | 无需 | **有**：`RebuildAsync` 从 `FollowEvent` 重建并逐行比对 |
| 并发控制 | 无 | **有**：`(ChannelId, ExternalUserId)` 唯一索引 + `LastEventAt` 排序守卫 |

同时**否决**在 `FollowEvent` 上用窗口函数实时聚合代替 `FollowState`：微信事件 5 秒 SLA 路径上做全表扫描不可接受，且无法表达「乱序事件不覆盖新状态」。

### 2.3 不引入 `AnchorType`（v0.1 §2 的 `ExternalSubject` 行收敛）

v0.1 提到 `字符串 + AnchorType`。本版删除该概念：`ChannelConfig.PlatformType` + `ChannelId` 已足够表达「这是哪个渠道的谁」，再加一层 `AnchorType` 枚举只会产生「openid / unionid / userid 三种值塞同一列」的歧义。`UnionId` 作为**跨渠道关联的二级索引列**存在，不是身份主键。

## 三、契约设计（Federation.Abstractions V0.2.0）

### 3.1 D1a：通道契约归属纠正（R1）

**动作**：`_Framework/TrustCenter.Abstractions/ISsoChannel.cs` **整文件移动**到 `_Framework/Federation.Abstractions/ISsoChannel.cs`，命名空间 `TKWF.Ext.TrustCenter` → `TKWF.Ext.Federation`。

**理由链**：

1. 信任内核（TrustCenter）对 `ISsoChannel` **零功能消费**——只有注释与描述文本提到它（§1.4 证据）。
2. `Federation.Abstractions` 的定位（2026-10-18 ④ 裁定）就是「通道编排契约收口」；`ISsoChannel` 是通道契约本身，却留在上游包，导致 `Federation.Abstractions → TrustCenter.Abstractions` 这条**反向语义依赖**。
3. 迁出后 `Federation.Abstractions` 可**完全解除**对 `TrustCenter.Abstractions` 的项目引用——依赖图变单向：TrustCenter（内核）⟂ Federation（连接层）。
4. 本次本来就要破坏 `HandleEventAsync` 签名（R2/R3），0.x 阶段一次做完，避免二次破坏。

**否决的替代方案**：

| 备选 | 否决理由 |
|---|---|
| 保留在 TrustCenter.Abstractions，新类型也放那里 | 内核继续承载通道协议类型（信封、回复、授权上下文），与其「纯信任内核」定位矛盾；且每次通道协议演进都要动内核包版本 |
| 拆分 `ISsoChannel`（OAuth 部分留内核、事件部分去 Federation） | 一半接口在内核一半在连接层，实现方要引两个包，比整体迁移更乱 |
| 保持 `namespace TKWF.Ext.TrustCenter` 只换程序集（零 using 改动） | 包名与命名空间错位：消费方引 `TKWF.Federation.Abstractions` 却要 `using TKWF.Ext.TrustCenter`，而该命名空间的其余类型来自另一个包——排障地狱 |

**迁移影响**（机械性，v0.5 按实查收窄）：**8 个平台库**（WeChat/QQ/DingTalk/WeCom/Oidc/Google/Microsoft/Alipay——`Federation.Template` 是脚手架不参与构建，不计入）+ WeChatOperations + Federation 主包 + 测试，把 `using TKWF.Ext.TrustCenter;` 改为 `using TKWF.Ext.Federation;`（已具备后者的只需删前者：如 `DingTalkEventChannel.cs:7-8` 两 using 并存）。**Google/Microsoft 是把 csproj 的 `TrustCenter.Abstractions` 引用替换为 `Federation.Abstractions`**（两库现不引 FA，实查确认）——仅当仍消费 TC 其余契约（`IToken2Service` 等）时保留双引并就近加注释说明。

### 3.2 传输层：`ChannelInboundContext`（R2）

```csharp
/// <summary>入站报文上下文（传输层——原始 body / query / 路径参数；由装配层构造，不承载业务语义）。</summary>
public sealed record ChannelInboundContext(IReadOnlyDictionary<string, string?> Parameters);
```

- 与今日 `SsoChannelEventContext` 字段完全一致（纯改名），**语义收窄**：只允许放协议原始字段（`__raw`、`msg_signature`、`timestamp`、`nonce`、`echostr`、`channel_id`）
- **禁止**再往里写业务语义（`uid` / `msg_type` / `event` / `__decrypted_xml` 全部迁到 `ChannelEvent`）
- 同时服务 3 个 DIM 方法：`HandleEventAsync` / `VerifyUrlAsync` / （未来）其他入站协议

### 3.3 语义层：`ChannelEvent` / `ChannelEventOutcome` / `ChannelEventDispatch`

```csharp
/// <summary>平台无关的语义事件（协议层解析产物——只描述「发生了什么」，不含回复/不含业务决策）。</summary>
public sealed record ChannelEvent
{
    public required string ChannelId { get; init; }
    public required string ChannelType { get; init; }        // wechat_event / dingtalk_event
    public required string ExternalUserId { get; init; }      // openid / userid
    public string? UnionId { get; init; }
    public required string EventType { get; init; }           // follow|unfollow|scan_follow|scan_only|message|menu_click|...
    public string? EventKey { get; init; }                    // 扫码 scene / 菜单 key
```

**关键设计取舍**：

| 取舍 | 决策 | 理由 |
|---|---|---|
| `Rejected` 是否用异常表达 | **不用异常，用状态** | 微信回调必须 200 空回复（5 秒 SLA）；异常在装配层被吞成 null，无法区分「信任根拒绝」与「代码 bug」；状态可精确断言 |
| `ChannelEventOutcome` 是否携带平台回复 | **不带** | V0.4.0 起平台不再自回 XML（`HandleEventAsync` 恒 null，回复由 handler 层产出）；带一个恒 null 的字段 = 死接口 |
| `ExternalUserId` 是否可空 | **不可空** | 关注域主键的一半；平台解析不出 openid 时应返回 `NotApplicable`/`Rejected`，而不是造半个事件 |
| `RawPayload` 放语义层还是传输层 | **语义层** | MessageGateway 的 SyncProxy 需要完整 XML 透传；放语义层后 handler 无需再接触传输字典（V0.4.0 的 `__decrypted_xml` 就是被字典化的教训） |
| `Attributes` 是否保留字典 | **保留但只读、键名强制平台前缀** | 有些平台字段（如微信 `ToUserName`）需要透出但不足以上升为一等属性；**键必须 `{platform}.{Name}` 前缀**（oracle6 C6）——平台库不得自行命名裸键，跨平台键冲突由此消除；首个 3 平台的键清单见下表，新增平台须同步补清单 + ADR 记录 |

**单一签票原语 + 单一 URL 组装点**（R4，oracle6 C2 校正 + C8 粒度补全）：

- **前提澄清（v0.4）**：`ILoginEntryService` 是**本次新增**契约（`Federation.Abstractions 0.2.0` 新文件），**不是**仓库既有设施——v0.3 未写明这一点，易被误读为「既有服务」。实现必须**建立在框架既有原语 `ISealedTicketService<FederatedIdentity>` 之上**（主框架 `TKW.Framework.Domain.Ticket`，TrustCenter `SealedTicketService<T>` DB 后端）——与 `EventReplyHandlerBase.cs:80-81` 用的是**同一个签票原语**，**不引入第二套票据实现**（否则正是 R4 要消灭的漂移）。
- **URL 基址复用单一事实源**：`ILoginEntryService` 复用 `FederationEventReplyOptions.TestTicketEndpointBaseUrl` / `RoutePrefix`（`EventReplyHandlerBase.cs:36/39`），**不新增 `BaseUrl` 配置项**（否则基址双源）。`FederationLoginEntryOptions` 只保留开关与 TTL：
  ```csharp
  public sealed class FederationLoginEntryOptions
  {
      public bool Enabled { get; set; }                                   // 默认 false（显式启用）
      public string TicketPath { get; set; } = "/login/ticket";           // SPA 落地页路由（非 AuthCenter API 端点）
      public int TicketTtlSeconds { get; set; } = 300;                    // 必须 ≤ AuthCenter 密封票据 TTL
      public Dictionary<string, string> ChannelBaseUrls { get; set; } = new(); // 按 ChannelId 覆盖基址（可选）
  }
  ```
- **事实校正（v0.2 的前提有误）**：`EventReplyHandlerBase`（`_Framework/Federation/EventReplyHandlerBase.cs:28`）与 `WechatEventReplyHandlerBase`（`_Framework/Federation.WeChat/WechatEventReplyHandlerBase.cs:46`）是**兄弟类**（各自 `: DomainServiceBase, IEventReplyHandler`），**无继承关系**；前者在**全仓生产零子类**（唯一子类为测试 `ProbeEventReplyHandler`），后者才是生产基类（`WeChatOperationsReplyHandler.cs:36` 继承它）且当前**无签票耦合**（`WechatEventReplyHandlerBase.cs:293-295` 明示「`{ticket}` 不替换——本基类无签票耦合」，并指明业务 handler 应改用主包 `EventReplyHandlerBase` 或 `User.Use<ISealedTicketService<FederatedIdentity>>()`）。

  - `ReplacePlaceholders` 增**静态重载** `ReplacePlaceholders(string text, string? uid, string? openId, string? channelId, string? ticket)`，`{ticket}` → `ticket ?? ""`；原静态方法保留（供无签票场景与既有调用）；**`{ticket}` 文本替换仍只有一处**（本重载）；

    2. **已注册但能力未开 / 配置缺失 / 签票失败 → 返回 null + Warning 日志，不阻断回复**：`LoginEntry.Enabled=false`、基址与 `ChannelBaseUrls` 均空、`IssueAsync` 抛异常（票据后端不可用）三种情形 → `{ticket}` 替换为**空串**，其余文本照常渲染；
  - 禁止 ctor 注入 `ILoginEntryService`（DI004）——只能经基类 `User` 帧内解析。
- **`EventReplyHandlerBase`（主包签票基类）改造边界（v0.4 收敛）**：**不改其行为**——`BuildTestTicketUrl`（`:107-114`）/`BuildTemplateUrl`（`:116-123`）改为委托 `ILoginEntryService` 的同一 URL 组装实现（**逐字节等价，测试锁定**），从而「`{platformId}/{channelId}/{ticket}` 路径拼装」在全仓只有一处；签票调用点仍为 `EventReplyHandlerBase.cs:80-81`，不改写为 `ILoginEntryService`（避免把「签票」与「URL 组装」两个关注点绑死）。**该改动对生产回复内容零影响**（无生产子类），方案与 ADR 均须写明，避免评审误判为行为变更。
- `{ticket}` 替换点仍唯一（`WechatEventReplyHandlerBase.ReplacePlaceholders`）——`ILoginEntryService` 只产出 URL，不做文本替换。

### 4.3 幂等键与排序规范

**`DedupeKey`**：`{channelId}|{eventType}|{externalUserId}|{occurredAtUnix}|{eventKey ?? "-"}|{messageId ?? "-"}`

- 超 256 字符 → `SHA256(key)` 十六进制（保留可判定性，不做截断——截断会产生假碰撞）
- 微信事件无 `MsgId`，`CreateTime` 秒级 + `FromUserName` + `Event` 已足够唯一；重复推送必然同键

**排序守卫**（oracle6 C4 校正——**不可用元组 `>` 运算符**）：

```csharp
// C# ValueTuple<T1,T2> 未定义 > 运算符，且该形式无法翻译为 SQL —— 必须写成两段比较：
newer = evt.OccurredAt > state.LastEventAt
     || (evt.OccurredAt == state.LastEventAt && evt.ReceivedAt > state.LastReceivedAt);
// 仅当 newer 时覆盖状态字段；事件行无论是否 newer 都落库（事实不可丢）
```

> 两处实现必须同型：① `FollowStateService.RecordAsync` 的 LINQ `Where`（条件更新 `EntityUpdateWhereAsync`）；② 更新前的内存判定（`EntityUpdateWhereAsync` 返回 0 行时用于判定「是否被排序守卫挡下」而非「行不存在」）。

## 五、编排与事件流

### 5.1 时序（`EventOrchestrator.OrchestrateAsync`）

```
1. Factory.CreateAsync(channelId, channelType)            // 通道实例化（帧内 User 供给）
2. outcome = channel.HandleEventAsync(inbound, ct)        // 验签+解密+解析 → ChannelEvent
3. if outcome.State == Rejected            → 返回 null（信任根一票否决：不记录、不回退 handler）
   if outcome.State == NotApplicable       → 直接进入 5（非事件通道，无事件可记）
4. evt = outcome.Event
   dto = await ExternalIdentity.GetByExternalIdAsync(channelId, evt.ExternalUserId)   // 只读，不建号；返回 ExternalIdentityDto?（UId/ChannelId/ExternalUserId/LinkedAt）
   uid = dto?.UId                                                                    // oracle3 P1-3：明示 dto→UId 取值路径
   dispatch = new ChannelEventDispatch(evt, uid)
5. try { reply = await 双桶迭代 handlers(dispatch) } catch { 日志; reply = null }      // 业务回复优先
6. try { await FollowState.RecordAsync(evt) }         catch { 日志; }                  // R3：记录在后
7. return reply
```

双桶迭代（保持既有语义）：`ChannelId` 绑定桶 → `ChannelType` 类型桶 → first-non-null-wins。

### 5.2 为什么「记录在后」（R3，核心修正）

v0.1 写「先记录再回复」，理由是「回复失败不影响状态」。该理由在**独立事务**下成立，但在本框架下不成立：

- `IEventOrchestrator.OrchestrateAsync` 是 AOP 帧的最外层，所有域服务写操作共享**同一个 UoW / 同一个物理事务**
- PostgreSQL 中任意语句失败即 **abort 整个事务**——`DedupeKey` 唯一约束冲突（并发重投）会让事务进入 aborted 状态
- 若记录在前：冲突 → 事务中毒 → 后续 handler 的业务写（如 WeChatOperations 的 `InteractionLog`）**全部失败**
- 若记录在后：handler 的业务写已成功执行，记录冲突只影响自身与提交阶段，回复内容已生成

同时 `try/catch` 分段保留「回复失败不影响状态」：第 5 步异常被吞，第 6 步照常执行。

> ⚠️ **R3 附条件（oracle 复审要求必须明示）**：`RecordAsync` 的 `DedupeKey` 唯一约束冲突**仍会 abort 同一物理事务**——`try/catch` 只能保住「回复内容已生成」，**保不住 handler 的业务写**。即：并发重投时，`WeChatOperations` 的 `InteractionLog` / 订阅统计写（以及与关注事件同事务的任何扩展写）**会被一起回滚**。这是本迭代**接受的已知代价**（换来的是：正常路径上「回复优先于记录」，且微信 5 秒 SLA 不因幂等查询变慢）；落地前须确认 DMP-Lite 侧「审计日志偶尔缺一条（限于并发重投窗口）」可接受，并在 `docs/WeChatOperations/微信公众号运营扩展-使用指南.md` 与 ADR 中写明该语义。**根治方向（不在本迭代）**：把 `RecordAsync` 移到独立事务/独立连接（需框架提供 `RequiresNew` 或事件后置补偿），已在 §十七 O5 登记。

**并发冲突的处置**：

1. `RecordAsync` 先按 `DedupeKey` **查存在**（常规路径零异常）
2. 插入仍冲突（真并发）→ 捕获唯一约束异常 → 立即 `return Recorded=false`（**不在同一事务内继续写任何东西**，避免二次中毒）
3. 微信侧 5 秒超时未收到响应会重投（最多 3 次），下一轮幂等命中

> **遗留风险（明示）**：同一请求内「记录冲突」会连带回滚该请求此前同事务的写（PG 语义）。本迭代接受该代价（概率 = 同事件真并发重投，且被回滚的是审计日志而非状态）；若实测偶发，再向框架组申请「保存点级子事务」原语，**不做扩展侧事务 hack**（AGENTS §8 数据访问红线）。

### 5.3 失败隔离矩阵

| 失败点 | 状态是否记录 | 是否回复 | 是否发域事件 | 处置 |
|---|---|---|---|---|
| 验签/解密失败 | 否 | 否 | 否 | `Rejected` → 200 空回复（微信显示失败但不重投协议层） |
| 解析不出 openid | 否 | 走 handler（dispatch 不产生） | 否 | `NotApplicable` |
| handler 抛异常 | **是** | 否（null） | 是（若状态变化） | catch + 日志；编排返回 null |
| 记录失败（DB 故障） | 否 | **是** | 否 | catch + 日志；微信重投补齐 |
| 域事件处理器抛异常 | 是（已提交） | 是 | 派发失败 | 事件总线隔离（框架侧），不影响请求 |
| 平台能力不足（无 `Follow`） | 否 | 是 | 否 | 按能力跳过，不报错 |

### 5.4 协议门控（不可绕过）

- `unsubscribe` 属微信 `NoReplyEvents`——平台基类返回 null 回复；**记录照常发生**（记录与回复完全解耦）
- 因此「取关时带票」在协议层不可能，免登入口只存在于 `follow` / `message` / 菜单点击路径（写入使用指南）

### 5.5 存量行为零回归断言

| 行为 | 断言 |
|---|---|
| 非事件通道（QQ/Alipay/Google/Microsoft/Oidc） | `HandleEventAsync` DIM → `NotApplicable`；`Capabilities` 默认 `None`；编排零副作用 |
| 微信探针 handler 门控（`ProbeEventReplyHandlerEnabled` 默认 false） | 不变——探针仍不产回复 |
| 微信未启用 ticket（默认 false） | 回复内容与 V0.5.0 **逐字节一致** |
| `RawXml` 透传优先（V0.4.2） | MessageGateway 的 `__decrypted_xml` → 语义层 `RawPayload`，透传链不断 |
| MessageGateway 幂等键（`evt:` 前缀） | 不变（其键构造基于 `WechatEventContext`，与本迭代契约无关） |

## 十二、风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| PG 事务中毒（唯一冲突 abort） | 同请求内其他写被回滚 | 记录后置（R3）+ 预查 + 冲突即返回；明示遗留风险；必要时申请保存点原语 |
| 契约类型跨包迁移 | 下游 403（未发布新包时） | 发布顺序严格（§14）；`--skip-duplicate` 幂等 |
| 微信事件无 `MsgId` | 幂等键依赖秒级时间 | `CreateTime` + `FromUserName` + `Event` 三元组；重复推送同键必命中 |
| `UnionId` 未开放 | 跨渠道关联不可用 | 可空；`GetByExternalUserIdAsync` 不依赖它 |
| 未认证服务号无网页授权 | 免登不可用 | `Capabilities.SilentAuthorize` 不声明 → 入口自然降级 |
| 微信 5 秒 SLA | 记录耗时挤压回复 | 记录在回复之后；DB 单次 upsert，无外部调用 |
| `SubscriptionStat` 口径变化 | 历史数据与新口径不可比 | 开发阶段无生产数据 → 直接切换，不保留双写 |
| `Source` 语义迁移 | 旧 `Source` 值映射歧义 | 文档明确「迁移期 `Source` = 扫码 scene 值」；无历史数据 |

## 十五、ADR 计划

新建 `docs/Federation/ADR/ADR-Federation-渠道事件信封与关注关系域.md`，三问必填：

- **目的与目标**：把「渠道协议」与「关注业务」彻底切开——平台层只产 `ChannelEvent` 事实，关注域只维护状态与事件，业务层只消费事件做决策。
- **问题**：现状用 `IDictionary<string,string?>` 传语义（`uid`/`msg_type`/`event`/`__decrypted_xml` 四个魔法键），消费方只能靠约定取值；关注状态无处存放（日粒度统计表答不了「现在关不关注」）；通道契约寄居信任内核包，导致连接层反向依赖内核。
- **使用场景**：微信关注/取关落状态并发事件供业务冻结决策；WeChatOperations 订阅统计改为派生；未来钉钉/企微按同契约接入；**不适用**：非事件通道（QQ/Alipay/OIDC 系）与「把关注当认证因素」（明确否决）。
