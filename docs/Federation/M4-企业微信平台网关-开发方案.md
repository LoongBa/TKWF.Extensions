# M4 企业微信平台网关库 开发方案（TKWF.Federation.WeCom）

> **立项来源**: 平台网关立项依据（近中远）M4（P1 中期）｜ **类型**: L1 平台库（国内 B 端——与微信生态互操作）
> **版本**: v0.1.0 ｜ **日期**: 2026-10-06 ｜ **状态**: 📋 提议（待 Oracle 评审）
> **关联**: 国内总规划（企业微信行 + §三模板 + 信任根分档）｜ 检索事实（企业微信官方文档——双授权流）｜ N1 模板｜ N2 锚点策略｜ WeChat 先例（`_Framework/Federation.WeChat/`——企业微信与微信同家族，模式最接近）
> **关键约束**: 纯库（无 Initializer 无 `[TKWFExtension]` 零持久化零 Store）；**完整形态**（企业微信有通讯录/事件回调——组件 3/4 齐备）；**双授权流**（内置客户端 Webview 跳转 + 桌面端扫码）；**无独立 token 端点**（code 直接换身份）；通讯录回调信任根 = AES + sha1（对齐 WeChat 先例——同家族）

---

## 一、背景与目标

### 现状

企业微信（WeCom，腾讯）是国内 To B **企业员工身份**标配——与微信生态互操作（员工用企业身份登录外部系统，企业微信账号体系与微信同源但独立）。联邦互联已落地微信公众平台（`wechat_oauth`/`wechat_event`）——**企业微信与微信同家族**（验签算法/message 加解密/回调形态几乎相同），是平台网关模板最接近的一次复制；同时补足微信公众平台未覆盖的**企业员工身份维度**（userid/部门/通讯录回调）。

### 目标

1. **`TKWF.Federation.WeCom` 纯库**——OAuth 通道（`wecom_oauth`）+ 事件/通讯录回调通道（`wecom_event`）；
2. **双授权流**：内置客户端 Webview 跳转（`open.weixin.qq.com/connect/oauth2/authorize`）+ 桌面端扫码（`login.work.weixin.qq.com/wwlogin/sso/login`——`@wecom/jssdk` `ww.createWWLoginPanel` 内嵌组件）；
3. **code→userid**（无独立 token 端点——`getuserinfo` 直接换身份）+ `snsapi_privateinfo` → `user_ticket`（敏感信息增强，96442 网页授权登录）；
4. 通讯录/事件回调信任根（AES + sha1——对齐 WeChat 先例 `WeChatEventCrypto`）；
5. 按 N1 模板 + N2 锚点策略（企业微信 open_userid 是体系内明示全局唯一 ID——锚点辅助）。

### 不包含

| # | 内容 | 去向 |
|---|------|------|
| 1 | `@wecom/jssdk` **内嵌扫码组件前端**（`ww.createWWLoginPanel`） | 装配层/前端职责——库提供扫码 authorize URL（`login_type=CorpApp\|ServiceApp`），前端内嵌脚本归消费方页面 |
| 2 | **通讯录管理 API**（成员增删改/部门树——`user/get` 等组织管理能力） | 非认证面（LN 组织管理）——Federation 只消费"员工身份认证 + 敏感信息增强"，组织管理 API 归 L7 非认证能力面（YAGNI 待业务驱动） |
| 3 | **企业微信-微信 unionid 打通**（双通道 + 主体一致性） | 国内总规划复核：成本高非默认能力——锚点须 TKWF 侧自建映射（N2），不依赖跨生态对齐 |
| 4 | `snsapi_privateinfo` **敏感信息持久化**（手机号/邮箱落库） | 隐私最小化——user_ticket 一次性换取即用即弃（1800s），敏感字段不落库 |

## 二、协议事实（官方文档核实——国内总规划 §五矩阵）

| 项 | 事实 |
|----|------|
| 授权形态 | ① **内置客户端 Webview**：仅跳转（`open.weixin.qq.com/connect/oauth2/authorize`——企业微信客户端内网页授权）；② **桌面端扫码**：`login.work.weixin.qq.com/wwlogin/sso/login`（跳转 / `@wecom/jssdk` `ww.createWWLoginPanel` 内嵌组件）——**两者换身份端点相同** |
| Authorize 参数 | `appid`=企业 **CorpID**（三方=SuiteID）+ `redirect_uri` + `response_type=code` + `scope` + `state` + `agentid`（`snsapi_privateinfo` 必填）+ **`#wechat_redirect` 必须尾缀**（Web 登录用 `login_type=CorpApp\|ServiceApp`） |
| Token/身份端点 | **无独立 token 端点**——`code` 直接换：`GET qyapi.weixin.qq.com/cgi-bin/auth/getuserinfo?access_token&code`（code 5min 一次性；域名须完全匹配可信域名否则 50001） |
| 用户标识 | 企业成员 → **`userid`**（互联/上下游为 `CorpId/userid` 复合）；非企业成员 → **`openid`**（对当前企业唯一）+ 条件性 `external_userid`；三方应用 `open_userid`（**全局唯一**——同一服务商跨应用相同） |
| 敏感信息 | `snsapi_privateinfo` → **`user_ticket`**（1800s 取敏感信息——手机号/邮箱等；**自建 96442 + 三方 98179 网页授权均返回，扫码 98177 不返回（Oracle 评审 P1-4 修正）**——须成员在可见范围）；**scope 选取归装配层（authorize URL 构造时决定 snsapi_base/privateinfo）+ `Options.DefaultScope` 兜底；启动期校验 scope=privateinfo 且 AgentId 缺 → fail-fast（P1-5）** |
| 成员信息 | `GET cgi-bin/user/get?access_token&userid`（name/department/mobile/email/avatar 等——**2022-06-20 起敏感字段须 OAuth2 手动授权**，三方不可取 name 等） |
| 验签/安全 | OAuth 回调**无签名**（仅 state 防 CSRF）；**事件/通讯录回调 AES-256-CBC + `sha1(sort(token,timestamp,nonce,msg_encrypt))`**（EncodingAESKey 43 字符，ReceiveId=corpid/suiteid；URL 验证 1s 响应，业务 5s 响应；官方：无法保证 100% 回调成功——不强依赖回调） |
| scope | `snsapi_base`（静默仅 userid）/ `snsapi_privateinfo`（手动敏感信息，须成员在可见范围）；**无 `snsapi_login`** |
| 联盟锚点 | ⚠️ 部分对齐——`open_userid` 体系内明示全局唯一 ID（三方应用）；与微信 unionid 打通需双通道+主体一致性（非默认）——锚点须 TKWF 侧自建映射（N2） |

**设计要点（从事实导出）**：
- **完整形态**：企业微信有通讯录/事件回调 → 组件 1/2/3/4/5/6/7/8（对齐微信双通道）；
- **双授权流统一**：Webview 跳转与桌面扫码**换身份端点相同**（`getuserinfo`）——通道只需区分**授权进入方式**（装配层构造 authorize URL），`getuserinfo` 收 code 逻辑共用；
- **无独立 token 端点**：code 直接换 userid——无 access_token 出站步骤（区别于微信 `sns/oauth2/access_token`）；
- **企业级 access_token 仍需要**：`getuserinfo` 依赖**企业 access_token**（`cgi-bin/gettoken`——corpsecret 换取应用级 token）→ L1 缓存 + 并发锁 + 提前刷新（对齐 WeChatApiClient access_token 缓存模式）；
- **external_uid 语义（Oracle 评审 P0-1 定案——双策略 + 三方优先 open_userid）**：企业微信 `getuserinfo` 对**企业成员只返回 `userid`、不返回 openid**（官方 `path/96442` 自建 + `path/98179` 三方双端点确证——成员响应体无 openid 字段），N3 QQ"恒有 openid"先例不可机械平移。**裁定 external_uid 选取策略（按应用类型 + 成员状态）**：

```
external_uid 选取策略（Oracle 评审 P0-1 定案）：
├─ 三方应用（path/98179 getuserinfo3rd）企业成员：
│    external_uid = open_userid   ← 全局唯一（同服务商跨应用相同），最佳稳定键——直接作映射主键
│    （corpid + userid 经 DTO 透出作组织维度辅助）
├─ 自建应用（path/96442 getuserinfo）企业成员：
│    external_uid = {CorpId}:{userid}   ← 互联企业须 CorpId 复合消歧
│    （userid 复用风险经 N2 §3.2 治理：不自动并合 + 认证用户绑定 + 冲突拒绝 + 人工解绑流程——离职解绑归装配层/编排层）
├─ 非企业成员（任意应用类型）：
│    external_uid = openid   ← 对当前企业/服务商唯一
│    （external_userid 经 DTO 透出作锚点辅助）
└─ open_userid（三方应用，全局唯一）→ 优先作联盟锚点辅助写入（N2 §3.1 anchor 列平台无关值）
```

> **裁定理由（对齐 N3 QQ 先例 + P0-1 修正）**：QQ `external_uid = openid` 因其**恒有 openid**；企业微信 API 形态不同——成员/非成员返回**不同标识类型**，无统一字段。userid 虽是组织维度键但**是自建应用成员主场景唯一可用标识**——离职/复用错绑风险经 N2 §3.2"不自动并合 + 认证用户绑定 + 冲突拒绝 + 人工解绑流程"治理（缓解手段不是"弃用 userid 改用不存在的 openid"）；三方应用场景 open_userid 全局唯一（无复用风险）最优，**完全规避 userid 复用风险**。

## 三、组件设计（按 N1 模板完整形态 + 对齐微信双通道形态——同家族）

```
_Framework/Federation.WeCom/
├── TKWF.Federation.WeCom.csproj             # ProjectReference ..\Federation\TKWF.Ext.Federation.csproj + TKWF.Domain（条件）+ Microsoft.Extensions.Http；不引 AspNetCore
├── WeComOptions.cs                           # [Options("TKWF:Federation:WeCom")]——Channels 列表（WeComChannelConfig）+ AgentId（授权 scope 用）
├── WeComChannelConfig.cs                     # ChannelId + CorpId + CorpSecret + AgentId + Token + EncodingAESKey（凭证自持——Oracle P2-4；CorpSecret 应用级/通讯录级——**缓存键区分，P1-2**）+ EnableSensitiveInfo（P1-5）
├── WeComApiClient.cs                         # 出站：gettoken（企业 access_token——corpsecret 换取应用级 token，L1 缓存 + 并发锁 + 提前 5min 刷新；**缓存键 = corpid + ":" + corpsecret 用途标识——应用级 vs 通讯录级 token 互不覆盖，Oracle 评审 P1-2**）+ getuserinfo（code→身份 一次性，按应用类型+成员状态解析 open_userid/{CorpId}:{userid}/openid）+ user_ticket 换敏感信息（snsapi_privateinfo，即用即弃）+ 成员信息裁剪（user/get）；**通讯录回调验签只需 Token+EncodingAESKey，不需 access_token（P1-2 消歧）**
├── WeComOauthChannel.cs                      # ISsoChannel（ChannelType="wecom_oauth"）——回调 code→身份（AuthenticateAsync 内 getuserinfo 换——authorize 构造归装配层）；AuthLevel=2
├── WeComEventChannel.cs                      # ISsoChannel（ChannelType="wecom_event"）——通讯录/事件回调验签 + 解密 + 身份→external_uid；**信任根一票否决**（msg_signature 验签 + AES 解密 + **receiveid 提取比对**）
├── WeComEventCrypto.cs                       # 验签逻辑类（AES-256-CBC + sha1(sort(token,timestamp,nonce,msg_encrypt)) + FixedTimeEquals 恒定时间比对——对齐 WeChatEventCrypto 同家族独立实现 + **增量：DecryptMsg 返回 (msgXml, receiveId) 元组/DecryptAndVerify 一体化，提取 plain[20+msgLen..] 与 corpid/suiteid 比对，Oracle 评审 P1-1**）
├── WeComUserInfo.cs                          # 响应裁剪 record（OpenId/Userid/ExternalUserid/OpenUserid——敏感字段如手机号/邮箱经 user_ticket 拉取的用独立 WeComSensitiveInfo record 或标注 [SensitiveData] 防日志泄露，P2-3；DeviceId 不透出——隐私最小化）
├── WeComAuthorizeUrlBuilder.cs               # authorize URL 构造辅助（静态纯字符串：BuildWebviewUrl/BuildScanUrl——P2-4 降装配层双流 URL 出错风险）
├── WeComFederationServiceCollectionExtensions.cs  # AddWeComFederationChannels()——AddOptions().Configure + AddHttpClient<WeComApiClient> + TryAddEnumerableConstructible<ISsoChannel, WeComOauthChannel/WeComEventChannel>

```

### 3.1 WeComOauthChannel 流程（双授权流统一）

```
装配层构造 authorize URL（双授权流 URL 模板——Oracle 评审 P1-3，两流构造差异归装配层、库只收 code）：
① Webview：open.weixin.qq.com/connect/oauth2/authorize?appid={CorpID}&redirect_uri={enc}&response_type=code&scope={scope}&agentid={AgentId}&state={state}#wechat_redirect
   （#wechat_redirect 尾缀仅 Webview 流必填）
② 桌面扫码：login.work.weixin.qq.com/wwlogin/sso/login?login_type=CorpApp|ServiceApp&appid={CorpID}&agentid={AgentId}&redirect_uri={enc}&state={state}
   （无 #wechat_redirect——用 login_type 参数区分 CorpApp/ServiceApp；即 @wecom/jssdk 内嵌组件对应形态）
→ 企业微信授权（Webview 跳转 / 扫码）→ 回调 ?code=&state=（域名须完全匹配可信域名否则 50001）
→ 验 state（CSRF——归装配层）→ WeComApiClient：gettoken（企业 access_token 缓存）→ getuserinfo?access_token&code → 身份识别（按应用类型 + 成员状态）
→ (可选 snsapi_privateinfo，响应含 user_ticket 时条件性拉取——P1-5/P1-4：自建 96442 + 三方 98179 均返回，扫码 98177 不返回→降级仅身份）
→ SsoChannelAuthResult(Success, ExternalUserId=open_userid（三方成员）/ {CorpId}:{userid}（自建成员）/ openid（非成员）——Oracle 评审 P0-1 双策略, AuthLevel=2)
→ (channel_id=wecom_oauth, external_uid) → uid（Federation 编排层，N2 锚点策略）
```

### 3.2 WeComEventChannel 流程（通讯录/事件回调）

```
企业微信通讯录变更/事件推送 → 接收端点（装配层映射）
→ WeComEventCrypto.Verify（msg_signature = sha1(sort(token, timestamp, nonce, msg_encrypt)) + AES-256-CBC 解密——EncodingAESKey 43 字符 Base64Decode 派生 32 字节 AESKey；**ReceiveId 校验**（corpid/suiteid——三方应用为 suiteid））
→ 验签失败即拒（**信任根一票否决**——漏验 = 可伪造任意员工身份 = 体系崩溃）
→ 解密后事件体（ChangeType/UserID/OpenUserID 等）→ 进程内调 Federation 门面（映射/解绑——帧内 AOP，零自签）
→ 落库即返（**回调不阻塞**——官方"无法保证 100% 回调成功"→不强依赖回调达成业务）
```

### 3.3 external_uid 语义（SSO 归一——Oracle 评审 P0-1 双策略定案 + N2 定案）

- **external_uid 双策略（Oracle 评审 P0-1 定案）**——按应用类型 + 成员状态选取：
  - **三方应用企业成员 → `open_userid`**（体系内明示全局唯一——同服务商跨应用相同，最佳稳定键，直接作映射主键，**完全规避 userid 复用风险**）；
  - **自建应用企业成员 → `{CorpId}:{userid}`**（互联企业须 CorpId 复合消歧；userid 复用风险经 N2 §3.2"不自动并合 + 认证用户绑定 + 冲突拒绝 + 人工解绑流程"治理，离职解绑归装配层/编排层）；
  - **非企业成员 → `openid`**（对当前企业/服务商唯一；`external_userid` 经 DTO 透出作锚点辅助）；
- **userid（企业成员）**：组织维度辅助字段（DTO 透出/绑定流程用，非联邦映射主键）；
- **open_userid（三方应用）**：全局唯一——**优先作 external_uid（§二 P0-1 定案）**，同时作联盟锚点辅助写入（N2 §3.1：anchor 列存 TKWF 自生成平台无关锚点值 + 辅助写入）；
- **`user_ticket` 敏感信息**：一次换取即用即弃（1800s），**不落库**（隐私最小化）；**数据流闭环（Oracle 评审 P1-4）**：`ApiClient.GetSensitiveInfoAsync(user_ticket)` → `WeComSensitiveInfo` DTO（敏感字段标注防日志泄露）→ 编排层帧内 `User.Use<ISsoAccountQueryService>()` 消费做绑定 → 帧结束随 GC 回收即弃——不进审计日志 ArgumentsJson/不持久化；**扫码场景（98177）不返回 user_ticket——敏感信息增强不可用，降级仅返回身份**。

### 3.4 信任根（事件/通讯录回调——对齐微信同家族）

- **对齐微信**：`sha1(sort(token,timestamp,nonce,msg_encrypt))` + AES-256-CBC（EncodingAESKey 43 字符）——同家族算法，`WeComEventCrypto` 复刻 `WeChatEventCrypto` 逻辑（独立实现避免跨库依赖——P2-1：三平台同构（WeChat/WeCom/DingTalk）登记"验签基元提炼待办"——待第 4 个同算法平台落地后评估，YAGNI 暂不实施）；
- **receiveid 校验实现细节（Oracle 评审 P1-1）**：WeChat 先例 `DecryptMsg` 只取 msg **丢弃 receiveid**（明文布局 `random(16) + msg_len(4) + msg + receiveid`）——WeCom 须**增量**提取 `plain[20+msgLen..]` 作 receiveid 并与本 channel 的 corpid（企业自建）/suiteid（三方）`FixedTimeEquals` 恒定时间比对，不符抛 `CryptographicException`（信任根一票否决）——防跨企业回调混串；方法形态：`DecryptMsg` 返回 `(msgXml, receiveId)` 元组 或 `DecryptAndVerify(encodingAESKey, msgEncrypt, expectedReceiveId)` 一体化；
- **URL 验证握手（Oracle 评审 P1-6）**：企业微信回调 URL 验证 = GET 带 `echostr`（AES 加密随机串）——验签 + 解密 echostr → 回显明文（**1s 硬约束**）；**URL 验证归装配层**（端点握手，不在 `EventChannel.AuthenticateAsync` 内——后者服务事件回调业务），库提供 `VerifyAndDecryptEcho(token, aesKey, timestamp, nonce, echostr, msg_signature)` 原语（复用 VerifySignature + DecryptMsg）；
- **回调可靠性**：官方"无法保证 100% 回调成功"——业务**不强依赖回调**（认证主路径走 OAuth 出站；回调只做增量/解绑通知）；URL 验证 1s / 业务 5s 响应——按官方超时实现；**回调响应策略统一（P2-2）**：验签+解密+落库归阻塞路径、业务异步、按平台最严超时（M4 实施时回填 N1 模板固化）。

## 六、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| userid 组织维度键被误用为联邦身份键（离职/复用错绑） | 灾难 | **双策略 + 人工解绑（Oracle 评审 P0-1）**——三方成员用 `open_userid`（全局唯一零复用风险）/自建成员 `{CorpId}:{userid}` 复合 + N2 §3.2 人工解绑流程治理；userid 仅组织维度辅助——语义断言测试（F5） |
| 双授权流实现分裂（Webview vs 扫码两套逻辑） | 中 | 换身份端点统一（getuserinfo）——仅 authorize 构造在装配层分流；库层单一路径 |
| `snsapi_privateinfo` 敏感信息落库（隐私违规） | 高 | user_ticket 一次性换取即用即弃（1800s）——**数据流闭环（Oracle 评审 P1-4）：ApiClient 换取 → WeComSensitiveInfo DTO（敏感标注）→ 编排层帧内消费 → 帧结束即弃**——F5 不持久化边界 + 代码审查 |
| ReceiveId 未校验（跨企业回调混串） | 高 | WeComEventCrypto ReceiveId 校验（corpid/suiteid）——F3 负路径 |
| 回调不可靠（官方不保证 100%）被强依赖 | 中 | 业务不强依赖回调（认证主路径 OAuth 出站；回调仅增量通知）——文档注记 |
| 与微信 unionid 打通被默认依赖 | 中 | 锚点自建映射（N2 平台无关）+ open_userid 辅助——不依赖跨生态对齐 |
