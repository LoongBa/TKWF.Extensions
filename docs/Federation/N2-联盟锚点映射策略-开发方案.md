# N2 联盟锚点跨平台映射策略 开发方案

> **立项来源**: 平台网关立项依据（近中远）N2（P0 近期——**任何 L1 平台实施前置**）｜ **类型**: L0 设计
> **版本**: v0.1.0 ｜ **日期**: 2026-10-05 ｜ **状态**: 📋 提议（待 Oracle 评审）
> **关联**: 国内总规划 §5.1（待设计项，Oracle 评审 P1-1 登记）｜ ADR-AuthCenter-归层与命名（§五.3/§五.7 契约）｜ `ISsoChannelMapService`/`ISsoAccountLinkService`/`FederationAnchorOpenId` 既有契约｜ 立项依据 N2
> **关键约束**: 本方案是**设计定案**（产出设计决策 + 契约影响面），不实现代码；为 N3/N4 等平台立项提供锚点设计前置

---

## 一、背景与问题

### 问题

各平台 openid/unionid/sub **均封闭于各自开放平台体系**（国内规划 §五关键结论 + 国外规划复核实证）：

- QQ unionid = 开发者账号维度（≤60 应用），支付宝 unionid = 应用分组维度——**均与微信 unionid 不可对齐**；
- Google `public` sub / Microsoft・LinkedIn `pairwise` sub / Slack `(sub, team_id)` / Apple `sub`（不透明）——**OIDC 内 sub 也仅 issuer 内唯一**；
- 企业微信-微信 unionid 同体系但**双通道 + 主体一致性**前置（非默认能力）。

**结论**：跨平台统一身份**必须由 TKWF 侧自建映射**——但 `FederationAnchorOpenId`（联盟锚点）的**语义、绑定并合规则、国内外混合归一、数据主权**未定案（国内规划 §5.1 待设计项，Oracle P1-1）。

### 目标

1. **裁定 FederationAnchorOpenId 语义**（锚点存什么）；
2. **裁定多平台绑定并合规则**（同一用户多平台如何关联同一 uid）；
3. **裁定国内外混合归一**（`(issuer, sub)` 与 `(channel_id, external_uid)` 统一）；
4. **裁定映射表数据主权与并发冲突**（多平台网关库写同一映射表）；
5. 输出契约影响面（AuthCenter.Abstractions / Federation 需否调整）——**设计定案，不实现**。

## 三、设计选项与决策

### 3.1 FederationAnchorOpenId 语义（锚点存什么）

| 选项 | 描述 | 评估 |
|------|------|------|
| **A. 锚点 = 某平台 unionid（主锚点）** | 选微信 unionid 作为唯一锚点，其他平台映射指向它 | ❌ 平台封闭（QQ/支付宝不可对齐）；企业微信双通道前置非默认——**单平台主锚点不可扩展** |
| **B. 锚点 = TKWF 内部全局 uid（推荐）** | `FederationAnchorOpenId` 存 **TKWF 自生成的平台无关锚点值**（独立于 uid 的稳定锚点），所有平台 `(channel_id, external_uid)` 经 `PlatformAccountMap` 指向同一 uid；微信 unionid 场景降级为"其中一个 channel 映射 + 锚点加速快照" | ✅ 平台无关、可扩展（国内外混合归一自然）；锚点有独立加速直认意义（`GetByFederationAnchorAsync` 不退化） |
| **C. 双锚点（主 + 次）** | 主锚点（内部 uid）+ 次锚点（微信 unionid 加速） | ⚠️ 复杂度高，收益有限 |

**决策（Oracle 评审 P1-4 定案——二选一落定）**：**选项 B，且 anchor 列存 TKWF 自生成的平台无关稳定锚点值（非 uid 本身、非 null）**——理由：
1. anchor 列存 **自生成锚点值**（如 `anc_` 前缀 + CSPRNG）——`GetByFederationAnchorAsync(anchor)` 保持独立反查语义（不退化 `≡ GetByUId`）；
2. **不废弃 anchor 列**（微信既有落地 `FederationAnchorOpenId` 已写数据可平滑迁移——新锚点值生成后重写列，旧值按 channel 映射保留）；
3. **不改 `SetFederationAnchorAsync` 契约签名**——调用语义从"写微信 unionid"演化为"生成并写平台无关锚点值"（Federation 编排层在首个渠道绑定时生成）；
4. 与 `PlatformAccountMap` 并行：anchor 列 = 加速直认快照（冗余，非唯一依赖），映射表 = 归一主数据。

### 3.2 多平台绑定并合规则

| 场景 | 规则 |
|------|------|
| 首次登录（无本地账号） | 建本地 uid + 写该平台 `(channel_id, external_uid)` 映射 |
| 再次同平台登录 | 映射直认 uid（不变） |
| 第二平台登录（已有本地账号） | **不自动并合**——需用户验证（登录态下绑定 / 手机号验证 / 扫码确认）；禁止静默自动合并（安全：防账号劫持——攻击者若控制某平台 external_uid 即可窃取账号） |
| 绑定并合接口 | 复用/扩展 `ISsoChannelMapService.LinkAsync`（用户已认证上下文下调）——**仅认证用户可绑新渠道** |
| 冲突（同一 external_uid 已映射到不同 uid） | 拒绝 + Warning（映射表联合唯一约束兜底） |

### 3.3 国内外混合归一

- **统一模型**：无论国内 `(channel_id, external_uid)` 还是国外 `(issuer, sub)`，**归一为 `(channel_id, external_uid)` 映射表行**——`channel_id` 承载渠道标识（`wechat_oauth`/`google_oidc`/`apple_oidc` 等），国外 `external_uid = sub`（存不透明字符串，P12）；
- **pairwise ClientId 维度（Oracle 评审 P1-5 定案）**：国外 pairwise 平台（Microsoft/LinkedIn）同用户不同 App sub 不同——**裁定 channel_id 复合编码**：`channel_id = "{platform}_oidc:{client_id}"`（如 `microsoft_oidc:{client_id}`）——**不改 `PlatformAccountMapEntity` 表结构、不加 ClientId 列、不动既有 `UX_PlatformAccountMap_Channel` 联合唯一索引**（复合编码天然保证 pairwise 隔离；public 平台 client_id 为通配 `*`）；对既有索引零影响，查询模式不变（channel_id 精确匹配）。实施时若有特殊场景需独立列再评估（本方案已裁定默认方向）。
- **锚点归一**：所有平台映射均指向 TKWF 内部 uid（3.1 B）——国内外天然统一，无需特判。

### 3.4 映射表数据主权与并发冲突

- **数据主权**：`PlatformAccountMapEntity` + `FederationAnchorOpenId` 列**归 AuthCenter 主包**（既有裁定）——平台网关库**不建映射表**（零持久化零 Store，P2），仅经 `ISsoChannelMapService`/`ISsoAccountLinkService` 契约读写；
- **并发冲突**：`ChannelId/ExternalUserId` 联合唯一索引兜底（DB 约束）；写失败（重复）→ 读回 + 判定（同 uid 幂等 / 不同 uid 拒 + Warning）；
- **匿名面**：映射写接口**仅认证用户上下文可调**（`ISsoChannelMapService.LinkAsync` 门面守卫）——平台网关库通道只返回 external_uid，不直接写映射（归一归 Federation 编排层）。

## 四、契约影响面（设计定案——评估是否需调整）

| 资产 | 现状 | 本方案影响 |
|------|------|-----------|
| `ISsoAccountLinkService.SetFederationAnchorAsync` | 写 `FederationAnchorOpenId`（微信 unionid） | **语义演化**：改写 TKWF 内部 uid 或新增内部 uid 映射——**向后兼容评估**（微信既有落地数据迁移） |
| `ISsoChannelMapService.LinkAsync` | 写 `(channel_id, external_uid)` → uid | **保持**——已是归一模型；国外 sub 经同接口（channel_id 含 client 维度待定） |
| `PlatformAccountMapEntity` | `ChannelId/ExternalUserId` 联合唯一 | **可能加 `ClientId` 列**（pairwise 平台）——实施时定 |
| 无新契约 | — | **不新增 Store/契约**（红线：映射归 AuthCenter 主包，平台网关库零持久化） |

## 六、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| FederationAnchorOpenId 语义演化破坏微信既有落地 | 高 | 向后兼容评估（迁移/双写/列语义扩展）——实施前专项评估，本方案登记 |
| 自动并合被滥用（账号劫持） | 灾难 | 不自动并合 + 认证用户绑定 + 冲突拒绝（3.2 铁律） |
| pairwise 平台 sub 跨 App 混淆 | 中 | channel_id 含 client 维度或映射表加 ClientId 列（3.3） |
| 平台网关库越权写映射 | 中 | 红线：映射归 AuthCenter 主包；通道只返回 external_uid（3.4） |
