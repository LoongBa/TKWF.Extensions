# N4 支付宝平台网关库 开发方案（TKWF.Federation.Alipay）

> **立项来源**: 平台网关立项依据（近中远）N4（P0 近期）｜ **类型**: L1 平台库（国内 C 端/交易）
> **版本**: v0.1.0 ｜ **日期**: 2026-10-05 ｜ **状态**: 📋 提议（待 Oracle 评审）
> **关联**: 国内总规划（支付宝行 + §三模板 + 信任根分档）｜ 检索事实 bg_af8d3de9（支付宝开放平台官方文档）｜ N1 模板｜ N2 锚点策略
> **关键约束**: 纯库（无 Initializer 无 `[TKWFExtension]` 零持久化零 Store）；**RSA2 双向签名**（商户私钥签请求/支付宝公钥验签响应）；信任根完备（强双向签名——P5 适用出站方向）；不引 AspNetCore

---

## 一、背景与目标

### 现状

支付宝开放平台是国内 C 端交易/政务/电商强场景身份源（DMP 多商户关联度高）——联邦互联未接入。

### 目标

1. **`TKWF.Federation.Alipay` 纯库**——OAuth 通道（`alipay_oauth`）：跳转 + 扫码 + H5 端内 JSAPI 三形态 → code → user_id(open_id)；
2. **RSA2 双向签名**——商户私钥签请求 + 支付宝公钥验签响应（信任根完备）；
3. **手机号 = 可选增强**（企业资质 + 字段申请审核——非稳定能力）；
4. 按 N1 模板复制骨架 + N2 锚点策略（支付宝 unionid = 应用分组维度，锚点自建映射）。

## 二、协议事实（官方文档核实 bg_af8d3de9）

| 项 | 事实 |
|----|------|
| 授权形态 | **跳转**（PC 拼接授权链接）+ **扫码**（`alipay.user.info.auth` 生成扫码页 URL）+ **H5 端内 JSAPI**（`ap.getAuthCode` 半屏授权浮层；端外需唤起客户端） |
| Authorize 端点 | `https://openauth.alipay.com/oauth2/publicAppAuthorize.htm`（GET）——`app_id` + `scope`（必填）+ `redirect_uri`（URLEncode，须与配置回调一致）+ `state`（可选，base64 ≤100 位，CSRF）；沙箱 `openauth-sandbox.dl.alipaydev.com` |
| Token 端点 | `alipay.system.oauth.token`（经 `https://openapi.alipay.com/gateway.do` 统一网关）——`grant_type=authorization_code/refresh_token` + `code` + **RSA2 私钥签名（无 client_secret）**；auth_code 3min~24h 动态；access_token 示例 300s + refresh_token |
| 用户标识 | `user_id`(open_id)（**应用维度唯一**，新商户建议 open_id 替代 user_id；须启用 openid 配置，灰度 USER_ID→OPENID_AND_USERID→OPEN_ID）+ `unionid`（**应用分组维度**，须绑定分组） |
| 用户信息 API | `alipay.user.info.share`（经 gateway.do，需 scope `auth_user`）——user_id(open_id)/avatar/nick_name/province/city/gender；**默认无手机号**（须企业认证 + 挂"获取会员信息"功能包 + 申请 mobile 字段，1-3 工作日审核，行业类目限制，个人账户不行） |
| 验签/安全 | **强 RSA2 双向签名**：商户上传商户公钥到支付宝后台；商户私钥签请求；支付宝公钥验签响应与异步通知（`AlipaySignature.rsaCheck`/`rsaCheckV1`/`rsaCheckV2`）；回跳参数本身无签名（仅 auth_code/app_id/scope） |
| scope | `auth_base`（静默仅 user_id，自动跳转）/ `auth_user`（主动授权取基本信息，需用户同意）/ `auth_ecard`/`auth_invoice_info` 等 |

**设计要点（从事实导出）**：
- **RSA2 信任根完备**：出站请求签名 + 响应/通知验签——信任根分档"强双向签名"（P5 适用）；
- **open_id 配置启用**：接入前置须启用 openid 配置（控制台 openid 配置管理，灰度阶段）——本方案要求启用 `OPEN_ID`（或 `OPENID_AND_USERID` 过渡）；
- **unionid = 应用分组**：跨应用对齐须绑定应用分组（可选增强）；
- **手机号可选**：非稳定能力（资质+审核）——设计上标记可选增强，默认不依赖。

## 三、组件设计（按 N1 模板 + 出站-only 形态）

```
_Framework/Federation.Alipay/
├── TKWF.Federation.Alipay.csproj      # ProjectReference ..\Federation\TKWF.Ext.Federation.csproj + TKWF.Domain(条件) + Microsoft.Extensions.Http；不引 AspNetCore
├── AlipayOptions.cs                    # [Options("TKWF:Federation:Alipay")]——Channels 列表（ChannelId/AppId/商户私钥路径/支付宝公钥路径/EnableMobile）
│                                        └─ 内含 AlipayChannelConfig 类（⚠️ 按 WeChat 先例同文件——见平台网关模板 §2.5 注）
├── AlipayApiClient.cs                  # 出站：gateway.do 签名调用（RSA2 私钥签请求 + 支付宝公钥验签响应）；code→user_id（oauth.token）；user.info.share；扫码页 URL（alipay.user.info.auth）
├── AlipayOauthChannel.cs               # ISsoChannel（ChannelType="alipay_oauth"）：**回调 code→user_id**（AuthenticateAsync 内签名换取；authorize 构造归装配层——Oracle 评审 P1-1，对齐 WeChat 先例）；AuthLevel=2；**ctor 收 ChannelConfig?（v0.3.0 多通道工厂预取——不再注入 IOptions/AlipayChannelConfig 单实例选区）**
├── AlipayChannelSource.cs              # 组件 8.5：多通道静态来源（IChannelSource——v0.3.0 多通道联邦必带）：AlipayOptions.Channels 投影 ChannelConfig（公共列 AppId + Extra{PrivateKeyPath, AlipayPublicKeyPath, EnableMobile}）
├── AlipayUserInfo.cs                   # 响应裁剪 record（UserId/NickName/Avatar/...——手机号可选）
├── AlipayFederationServiceCollectionExtensions.cs  # AddAlipayFederationChannels()——AddOptions().Configure + AddHttpClient<AlipayApiClient> + TryAddEnumerableConstructible<ISsoChannel, AlipayOauthChannel> + **TryAddEnumerable(IChannelSource, AlipayChannelSource)（v0.3.0 多通道行）**
└── (无 Initializer 无 [TKWFExtension])
```

> **三种授权形态的边界（Oracle 评审 P1-1 定案——无需组件 2 分支）**：跳转/扫码/H5 JSAPI 三种形态在 `AuthenticateAsync` 端点处**全部收敛到 code→user_id 同一处理路径**——前端授权获取 code 的差异**全部归装配层**：① 跳转 = 装配层拼接 `publicAppAuthorize.htm?app_id=&scope=&redirect_uri=&state=`（302）；② 扫码 = 装配层经 `AlipayApiClient` 调 `alipay.user.info.auth` 取扫码页 URL；③ H5 JSAPI = 前端 `ap.getAuthCode`（纯前端 SDK）。channel 只做回调 code→user_id（与 WeChat 完全对齐）。

### 3.1 AlipayOauthChannel 流程

```
/sso/login?target_app_id=X → 装配层构造支付宝 authorize URL（app_id + scope=auth_base|auth_user + redirect_uri + state）
→ 302 支付宝授权页（跳转/扫码）→ 回调 /sso/oauth/{channelId}/callback?auth_code=&state=（v0.3.0 多通道：带 channelId 段精确选区；无前缀降级默认通道）
→ 验 state（CSRF）→ AlipayApiClient: alipay.system.oauth.token（RSA2 签名）auth_code → user_id(open_id)
→ SsoChannelAuthResult(Success, ExternalUserId=user_id, AuthLevel=2)
→ (channel_id=alipay, user_id) → uid（Federation 编排层，N2 锚点策略）
→ **双锚点写入（Oracle 评审 P1-4）**：user_id(open_id，应用维度) 写 `PlatformAccountMapEntity.ExternalUserId`（应用维度映射）；unionid（应用分组维度，绑定分组后可用）经 `ISsoAccountLinkService.SetFederationAnchorAsync` 写 `FederationAnchorOpenId`（联盟锚点——对齐 N2 §3.1 选项 B：锚点列存 TKWF 自生成平台无关值，unionid 为写入辅助）——复刻微信双锚点先例
```

> **多通道选区（v0.3.0 模板对齐）**：`AlipayOauthChannel` ctor 收 `ChannelConfig? channel = null`（ISsoChannelFactory 预取 POCO 直传——非域服务规避 DI004）；凭证 = 公共列 AppId + Extra 扩展字典 `{PrivateKeyPath, AlipayPublicKeyPath, EnableMobile}`（RSA 私钥路径进 Extra 而非 AppSecret 列——对称/非对称分离，方案 F5 零表结构变更）；ChannelId 精确选区支持多渠道支付宝应用（每商户一个 app_id）。

### 3.2 信任根（强双向签名——Oracle 评审 P2-4 表述修订）

- **信任根分档 = 强双向签名**（对齐国内规划 §五信任根分档——出站方向完备）：商户私钥（PKCS8）对请求参数签名（`sign_type=RSA2`，参数按 key 排序 & 拼接，`biz_content` 嵌套 JSON 作为顶层参数参与签名——P2-1）；支付宝公钥验签响应/通知（`rsaCheck`）——信任根完备；
- **redirect_uri 校验（Oracle 评审 P1-2）**：redirect_uri 须与支付宝控制台配置一致（防开放重定向）——启动期预检或装配层校验；对齐 Federation `IsOriginAllowedAsync` 先例（QQ N3 亦补此项）；
- **CSRF**：state 参数（可选，base64 ≤100 位）——**本方案强制要求 state**（官方建议"无 state 或与 session 不一致时拒绝服务"）；
- 回跳参数本身无签名（auth_code/app_id/scope）——安全重心在签名换取链 + state。

### 3.3 token 生命周期与续期（Oracle 评审 P1-3）

- `alipay.system.oauth.token` 返回 access_token + refresh_token + expires_in；
- **续期策略**：access_token 过期前经 refresh_token 换新（`grant_type=refresh_token`，同样 RSA2 签名）——`AlipayApiClient` 封装刷新方法；联邦认证面一次换取即用（不缓存用户级 token，对齐 QQ N3 P1-5 原则）；refresh_token 长续期归 L7 非认证面（YAGNI）；
- ⚠️ **时效核实（Oracle 评审 P1-5）**：方案初稿"access_token 300s / auth_code 3min~24h 动态"——**以支付宝官方文档实际值为准**（300s 偏短疑似混淆微信 7200s/OAuth 标准 3600s；auth_code 一次性短时有效，范围描述待官方确认）；实施时按官方文档定 expires_in 处理。

### 3.4 手机号可选增强（非稳定能力）

- 默认 `alipay.user.info.share` 返回基础信息（无手机号）；
- 需手机号：企业认证 + 挂"获取会员信息"功能包 + 申请 mobile 字段（1-3 工作日审核 + 行业类目限制）——`AlipayOptions.Channels[].EnableMobile` 开关，开启时依赖消费方已通过审核（文档标注"需资质条件的可选增强"）。

## 六、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| RSA2 签名实现复杂（参数排序/签名串/公钥证书模式） | 高 | 主推普通公钥模式（商户公钥 + 支付宝公钥），复用框架 Utility Cryptography 先例 `AlipaySignUtil`（已实证存在——`_TKWF/_Framework/Utility/Cryptography/Signatures/AlipaySignUtil.cs`：`BuildSignature` 商户私钥签请求 + `VerifyCallbackSignature` 支付宝公钥验签）；**证书模式（app_cert_sn/alipay_root_cert_sn）AlipaySignUtil 未提供——须自实现或扩展工具类，不可声称"复用先例覆盖证书模式"（Oracle 评审 P2-5）** |
| open_id 灰度（USER_ID→OPEN_ID 迁移） | 中 | 接入前置启用 openid 配置；统一用 open_id 字段（兼容 USER_ID 过渡） |
| 手机号非稳定能力 | 中 | 默认不依赖；EnableMobile 开关 + 资质审核指引（文档标注可选增强） |
| 商户私钥泄露 | 灾难 | 私钥文件 chmod 600 不进代码库；生产 fail-fast 缺钥拒启动；支持 KMS/装配注入 |
| state 可选被滥用 | 中 | 本方案强制要求 state（官方建议语义）——CSRF 负路径测试 |
