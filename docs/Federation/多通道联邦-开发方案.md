# 多通道联邦（Multi-Channel Federation）开发方案

> **立项来源**: 联邦互联（Federation）功能特性——"多身份向外连接"能力演进（用户 2026-10-07 裁定）
> **类型**: 核心能力迭代（federation 多层）｜ **版本**: v0.1.0 ｜ **日期**: 2026-10-07 ｜ **状态**: 📋 提议（待 Oracle 评审）
> **关联**: 平台网关中期 M1-M4 / N1-N4 全系平台库｜ N2 联盟锚点映射策略｜ AGENTS §8 配置分层｜ ORM 边界 ADR15 ｜ Oracle 评审（本条）
> **关键约束**: 多通道联邦 = **联邦互联的多通道功能特性**（非独立扩展、非全栈多租户平台）；管理门户**不在本扩展模块范围**；设计前瞻兼容支付宝等未来平台（勿返工）

---

## 一、背景与目标

### 现状

联邦互联目前支持**单一身份向外连接**：一个消费方实例 = 一种平台凭证（Channels[0]）。但真实诉求是**多身份**：

| 场景 | 需求 |
|------|------|
| 单一身份代表己方平台 | 一个公众号 / 一个应用（现状已支持） |
| **每商户一个微信公众号** | 多商户平台：每个商户用自己的公众号登录，openid 映射回各自商户本地用户 |
| **每用户个人公众号 / 支付宝等未来平台** | 设计前瞻——兼容多凭证形态（RSA 私钥/扫码/小程序） |

**核心断点（探索实证）**：**14 处硬编码 `Channels.FirstOrDefault()`**——配置层能配 N 个通道实例，运行时只物化第 1 个，其余静默失效：

| 平台库 | 硬编码位置 |
|--------|-----------|
| Federation.WeChat | `WeChatOauthChannel`/`WeChatEventChannel`（2） |
| Federation.DingTalk | `DingTalkOauthChannel`/`DingTalkEventChannel`（2） |
| Federation.WeCom | `WeComOauthChannel`/`WeComEventChannel`（2） |
| Federation.QQ | `QqOauthChannel`（1） |
| Federation.Template | `{Platform}OauthChannel`/`{Platform}EventChannel`（2）⚠️ **模板已固化此缺陷，新平台复制即继承** |

且注册层无 keyed services（`TryAddEnumerableConstructible<ISsoChannel, XChannel>()` 按**类型**注册一次），`ISsoLogin` 编排门面只在 4 个 README 中作形态示意（**代码零实现**），`/sso/oauth/{channelId}/callback` 路由不存在。

### 目标

1. **多通道实例化**：单实例联邦持有 N 个 IdP 通道（每商户/每应用一个 ChannelId），运行时按 ChannelId 精确选区；
2. **两层存储**：静态配置（现状 Options.Channels）= 种子/回退，**数据库（ChannelRegistry 实体）= 动态权威**（商户自助接入零重启）；两迭代可实现，设计一次到位；
3. **门面/路由定形**：`ISsoLogin(channelId)` 门面 + `/sso/oauth/{channelId}/callback` 路由（无前缀降级默认通道）——一次定形避免返工；
4. **前瞻兼容**：凭证模型 = 公共列（AppId/AppSecret）+ 扩展 JSON 列——支付宝（RSA 私钥）/OIDC（ClientSecret+TokenIssuers）等未来平台**不改表**；
5. **模板修正**：Federation.Template 消除 `FirstOrDefault()` 缺陷，未来平台（支付宝 N4）复制即正确。

## 二、术语与命名

| 术语 | 定义 |
|------|------|
| **多通道联邦（Multi-Channel Federation）** | 主名——联邦互联的多通道功能特性。单实例联邦互联持有多个 IdP 通道实例。 |
| **联邦多租户（Multi-Tenant Federation）** | 副名/业务视角——每商户/每应用 = 一个租户身份层；与全栈多租户平台的边界：仅身份层（通道凭证 + openid 映射 + accesscode 维度），**不含**管理门户/配额/租户切换。 |
| 通道实例（Channel Instance） | ChannelId 标识的最小隔离单元——凭证 + openid 映射（`UX_PlatformAccountMap_Channel`）+ accesscode（`ChannelId` 列）。 |
| 通道别名（ChannelAlias） | 通道实例的**对外名**（URL 路径段/展示/客户端入参，2026-10-08 用户裁定双键）——与内部 ChannelId 一一对应；可读直观 + 保护内部键；缺省 = ChannelId（存量零迁移）。 |
| 默认通道（Default Channel） | 无 channelId 前缀时降级选区的通道（静态配置 Channels[0] 或 registry 标记默认）。 |
| ChannelRegistry | 通道注册表——ChannelId → 通道配置（凭证）的两层读取门面（静态 + DB）。 |

## 三、组件设计

### 3.1 凭证模型（公共列 + 扩展 JSON——前瞻核心）

```
// 公共列（各平台 ChannelConfig 的公共核——WeChat/QQ/DingTalk/WeCom 实证均有）
ChannelId          // 通道实例键（ISsoChannel.ChannelId 选区依据）
PlatformType       // 平台类型字符串（wechat_oauth / qq_oauth / alipay_oauth...开放注册表，不枚举）
AppId              // 平台应用凭证键（公共惯例——DingTalk AppKey/WeCom CorpId 映射到本列）
AppSecret          // 平台应用密钥（对称密钥类；OIDC 平台=ClientSecret）

// 扩展 JSON 列（平台特定负载——对齐 SsoChannelAuthContext 可扩展键值模式哲学）
ExtraJson          // AES-GCM 整段加密的 JSON：WeChat {Token, EncodingAESKey} / DingTalk {CorpId, AppKey}
                   // WeCom {CorpId, CorpSecret, AgentId, ...} / 支付宝（未来）{AppPrivateKey(RSA), ...}
                   // OIDC（未来）{ClientSecret, DiscoveryUri, TokenIssuers, ...}
```

- **公共列权衡（用户裁定 2026-10-07）**：AppId 公共列可支撑"registry 机构列表展示 AppId、按 AppId 精确查"等运维面；平台私密负载（私钥/入站密钥）进扩展 JSON——两者结合兼顾运维可读 + 前瞻扩展。
- **映射规则约束（Oracle M7 修订）**：AppId 列**仅承载平台 OAuth 握手的应用标识**；法人级标识（CorpId/OrgId/AgentId 类）一律进 ExtraJson，不挤占 AppId——防止未来平台"应用 ID + 法人 ID 双标识"（如企业微信既有 CorpId 又有 AgentId）单值映射丢失语义。
- **新增平台零表结构变更**：支付宝接入 = 新 PlatformType 字符串 + 库内定义 ExtraJson 结构解析 → 零 DDL。
- **多环境前瞻（Oracle M11 修订）**：沙箱/生产环境凭证同 AppId 但端点不同——ExtraJson 内承载 `{ "Environment": "sandbox" | "production" }`（支付宝/微信实证按环境切端点）→ 零 DDL 前瞻路径，不设公共 Environment 列。

### 3.2 两层存储（静态 + DB）

```
IChannelRegistry（Federation 域门面——接口 + 组合/双实现）
├── Task<ChannelConfig?> GetAsync(string channelId, CancellationToken ct)        // 按 ChannelId 精确定位
├── Task<IReadOnlyList<ChannelConfig>> GetAllAsync(CancellationToken ct)          // 枚举（构建通道集合/校验）
├── Task<ChannelConfig?> GetDefaultAsync(CancellationToken ct)                    // 默认通道（见语义边界）
└── Task<bool> IsEnabledAsync(string channelId, ct)                               // 启用状态（CHANNEL_DISABLED 校验）

实现①：StaticChannelRegistry（现状立即落地）
    - 来源 = 各平台库 Options.Channels（现状配置，零迁移）
    - ChannelType → 平台类映射收编各库；GetAll = 聚合全部平台库 Channels
实现②：DbChannelRegistry（动态权威，第二迭代）——**只读 DB，纯净无回退依赖**
    - 来源 = SsoChannelRegistryEntity（SG1 实体 + DataService，见 3.3）
实现③：CompositeChannelRegistry（运行时门面——Oracle M3 引入）
    - 组合语义：DB 命中优先 → StaticChannelRegistry 回退 → null
    - DbChannelRegistry 不依赖 Static（跨实现解耦）；组合归 Composite 单点
    - P1 即注册 Composite 形态（内部仅 Static），P2 换 Db 注入零返工（Oracle S2 预留）
```

- **默认通道语义边界（Oracle M11 修订）**：`GetDefaultAsync` 的"默认" = **单实例向后兼容降级**（无前缀 `/sso/oauth/callback` 时选区），**不承诺多公众号场景下有业务合理默认**（多公众号下谁当默认由装配层显式决策——`channelId` 必填或按装配策略指定）；方案文档 + 使用指南均按此措辞，防多通道下"默认"歧义。
- **静态明文密钥处置（Oracle M12 修订）**：静态 Options 内 AppSecret/ExtraJson 字段**允许承载明文**（开发态便利，现状即如此）；但使用指南**强制生产用 DB 层**（DB 全程密文列）——明文风险面收敛为文档 + 约定，且 DB 层才是动态接入的生产路径。
- **接口先行**：`IChannelRegistry` 接口在本次迭代定义 + 静态实现落地；DB 实现第二迭代补（两层共用同一选区接口，**不返工**）。
- 归属：Federation 域（`TKWF.Ext.Federation`）——不挤 AuthCenter `IPlatformCredentialService`（那是内部 Provider 凭证，非联邦通道凭证，Oracle P2-4 凭证自持边界）。

### 3.3 SsoChannelRegistryEntity（DB 层，第二迭代）

```
[Table("TKWF_SsoChannelRegistry")] + [DomainGenerateCode(UserType=nameof(FederationUserInfo))]
├── ChannelId(64 唯一) / PlatformType(32) / AppId(128) / AppSecretEncrypted(512)——公共列
├── ExtraJsonEncrypted(4000)——平台特定负载 AES-GCM 整段加密（keyed ISymmetricKeyProvider "Federation" 复用）
├── IsDefault(bool) / IsEnabled(bool) / CreateTime / UpdateTime
└── 唯一索引 UX_SsoChannelRegistry_ChannelId
```

- **容量核验（Oracle M6 修订）**：`ExtraJsonEncrypted(4000)`——RSA-2048 PEM 私钥约 1.7KB、OIDC DiscoveryUri + 多 TokenIssuer + Scopes 组合约 1.5KB+、加密后 base64 膨胀 ~33%——**2000 字节密文列会在 OIDC + RSA 平台溢出**，上调至 4000 起步（P1 文档定案即锁死容量，避免 P2 实体迁移）。`AppSecretEncrypted(512)` 承载对称密钥/AES-GCM 密文足量。
- 加密语义：对齐 `SsoClientService` 既有模式（`[FromKeyedServices(Federation)] ISymmetricKeyProvider` + `AeadEncryptionUtil` 单段格式）——`AppSecretEncrypted`/`ExtraJsonEncrypted` 均密文列，服务层加解密。
- 数据访问红线：无 Store 伪层——`SsoChannelRegistryEntityDataService`（SG1 生成）+ `SsoChannelRegistryService` 门面组合（`User.Use<DataService>()` 懒加载，DomainServiceBase）。
- 管理面措辞（Oracle M4 修订）：**管理端点不建**（无 `[GenerateController]`——管理门户不在本扩展模块范围，用户裁定）；但 **Registry 服务层方法保留**（`RegisterAsync`/`UpdateAsync`/`UnregisterAsync`——供静态→DB seed 与消费方自建管理端点经 `User.Use<>()` 消费）。两陈述不互斥：库不交付管理 UI/API，只交付服务层写入能力。
- **xCodeGen 接线（Oracle M9 修订）**：P2 落地必须包含 ①`.xCodeGen/extensions/Federation.xCodeGen.json` 新增 `SsoChannelRegistryEntity` 条目（或确认现有 Federation 条目覆盖新增实体——审计后定）②`ChannelId` 唯一索引 UX 在实体 FreeSql `[Column]` 声明 ③`.g.cs` 生成物入库（AGENTS §8 自检清单 7 项——`run-xcodegen.ps1 -Ext Federation` 重跑 + 时间戳新鲜）

### 3.4 选区机制（替代 14 处 FirstOrDefault）

**⚠️ 前置 gate（Oracle M1/M2/M8——动代码前必须定案）**：

**① 构造策略（M1 拍板）**：通道 ctor 仅注入 `(IDomainUser user, IChannelRegistry registry, string channelId)` + 平台库非域依赖（logger/options 等）——**凭证解析不落 ctor**（避 Async-in-ctor 反模式），统一在 `AuthenticateAsync` 首次调用经 `registry.GetAsync(channelId)` 懒加载（纯异步无同步反模式）；**废弃"registry 同步缓冲"备选**（静态层虽纯内存，但引入同步/异步双 API 是坏味道）。静态层实现为纯内存（无异步 IO），`GetAsync` 实现返回 `Task.FromResult` 即可——接口统一异步签名，不另设同步变体。

**② ISsoChannel 集合注册处置（M2 定案）**：`TryAddEnumerableConstructible<ISsoChannel, XChannel>()` **保留**——但语义角色从"消费方帧内枚举"收敛为 **`ISsoChannelFactory` 的内部索引源**（工厂经集合按 `ChannelType` 精确定位 + 按需构造）。理由：集合守卫工厂（ADR92）仍承载 IDomainUser 的 AOP 帧内供给，**不废弃不双注册**；消费方**禁止**再直接 `[FromServices] IEnumerable<ISsoChannel>` 枚举（帧内枚举语义不变但不再作为选区入口——新人/文档明确门面专责）。存量消费方若已帧内枚举集合，行为兼容（集合仍可枚举），但多通道语义下集合内每类型多实例，枚举需自行按 ChannelId 过滤——使用指南标注此迁移路径。

**③ 通道工厂注册形态（M8 拍板）**：`ISsoChannelFactory` 注册为 **Singleton + `AddConstructibleService`**（守卫工厂形态）：ctor 注入 `IEnumerable<ISsoChannel>`（集合版守卫工厂，帧内供给）+ `IChannelRegistry`；`CreateAsync(channelId)` 在 **AOP 帧内**（门面 `ISsoLogin` 调用链）经 registry 取凭证 → `ActivatorUtilities.CreateInstance` 构造目标通道（channelId 为显式参数）。**帧外构造（启动期预热/后台任务）无 IDomainUser → 抛守卫 = 正确 fail**（测试覆盖帧内/帧外双路径）。

```
改造后通道构造：
    {Platform}OauthChannel(IDomainUser user, IChannelRegistry registry, string channelId, ...)
        : base(user) { _registry = registry; _channelId = channelId; }

    AuthenticateAsync(context, ct):
        var cfg = await _registry.GetAsync(_channelId, ct);   // 首次懒加载 + 缓存于字段（后续复用）
        var secret = ParseCredential(cfg);                    // 平台库解析自身凭证（公共列 + ExtraJson）
        ... code → token → openid 流程不变
```

- **区块当前断点（14 处 `FirstOrDefault()`）**收敛到 `IChannelRegistry` 一处——各平台库只负责"解析自身凭证"（公共列映射 + ExtraJson 解码），不感知选区。

### 3.5 路由定形（一次定案）

```
/sso/oauth/callback                        → 默认通道（无前缀：registry.GetDefaultAsync）
/sso/oauth/{channelId}/callback            → 指定通道（内部键——精确选区，即使只配一个也走此路径）
/sso/oauth/{channelAlias}/callback         → 指定通道（对外别名——装配层经 registry 解析为 ChannelId 后选区，§3.7）
/sso/event/{channelId}/callback            → Event 入站回调（WeChat/WeCom/DingTalk 消息/事件验签 URL，Oracle M5 补充）
```

- **语义（用户确认）**：无前缀 = 降级默认商户（单实例免前缀，存量零破坏）；带前缀 = 精确选区（多实例语义）。
- **双键选区（2026-10-08 用户裁定）**：**内部 ChannelId（持久化键）+ 对外 ChannelAlias（直观别名，保护内部键）两者都支持**——路由段可为 `channelId` 或 `channelAlias`，装配层统一经 registry 解析（先 alias 精确匹配 → 再 channelId 匹配 → 未中 `CHANNEL_NOT_FOUND`）。外部 URL 暴露 alias 不泄露内部键；alias 缺省 = channelId（存量零迁移）。详见 §3.7。
- **Event 通道路由（Oracle M5 定形）**：现状 EventChannel 也是 `FirstOrDefault()` 断点（WeChat/WeCom/DingTalk 6 处），本方案 **P1 同步定形 Event 回调 URL**——`/sso/event/{channelId}/callback`（channelId 入路径段，装配层按段精确选区验签 + 解密）。**不得只改 OAuth 通道不管 Event 通道**（两通道同断点，P1-2 一并收敛）。
- **错误/异常完整 + HTTP 映射建议表（Oracle M5 补充）**：

| FailReason | 语义 | 建议 HTTP |
|-----------|------|-----------|
| `CHANNEL_NOT_FOUND` | channelId/channelAlias 不存在（registry 无此通道） | 404（回调场景重定向错误页） |
| `CHANNEL_DISABLED` | channel 存在但 IsEnabled=false | 403 |
| `CHANNEL_REGISTRY_UNAVAILABLE` | registry 故障/初始化未完成（与 NOT_FOUND 区分，Oracle S3） | 503 |
| 平台码（`QQ_CODE_REQUIRED` 等） | 缺参/平台业务错误 | 400 |

  全部 `FailReason` 机器可读 + 装配层按上表映射，不静默。Table 为**建议**（装配层可按场景调整状态码，但 FailReason 语义必须一致）。
- 路由归属：装配层（`ISsoLogin` 门面为库侧能力，`/sso/*` 端点映射归 Federation/消费方装配——现状一致，不引 AspNetCore 入库）。

- `_Framework/Federation.Template/{Platform}OauthChannel.cs`（及 EventChannel）——`FirstOrDefault()` → `IChannelRegistry` 选区；

### 3.7 ChannelAlias 对外别名（2026-10-08 用户裁定——内部键与对外别名双轨）

> **需求来源（用户）**：ChannelId 是内部 id（数据库持久化），对外有两个顾虑——① 不要直接暴露主键/内部键当 ChannelId；② 别名更直观（且保护内部键）。**裁定：两者都支持**——内部 `ChannelId`（持久化选区键，现状不变）+ 对外 `ChannelAlias`（直观展示名/URL 段，可选，缺省 = ChannelId）。

- **别名语义**：`ChannelAlias` = 通道实例的**对外名**（URL 路径段/展示/客户端入参），与内部 `ChannelId` 一一对应（同实例双名）。alias 可读（`merchant-a`/`edu-course`），不含内部持久化痕迹；`ChannelId` 保持现状（持久化键——静态配置/DB 行/accesscode/`UX_PlatformAccountMap_Channel` 全部不变）。
- **数据模型**：`ChannelConfig` 增 `Alias`（string?，可空，缺省 null = 用 ChannelId 对外）；`SsoChannelRegistryEntity` 增 `ChannelAlias`（string?，**非唯一索引/不加 UX**——alias 允许与既有 ChannelId 同名兼容迁移；解析优先级：alias 精确匹配 → ChannelId 匹配）；静态层 `ChannelSource` 投影增 `Alias`（平台库 Options.ChannelConfig 增 Alias 字段，可选）。
- **registry 解析**：`IChannelRegistry` 增 `Task<ChannelConfig?> GetByAliasOrIdAsync(string key, ct)`（或装配层 helper：先 `GetByAliasAsync` 未中再 `GetAsync`——**实现二选一，接口层面以"统一解析入口"定形**，避免装配层手写双查）。内部消费（通道/accesscode/映射）**一律用 ChannelId**——alias 只在对外入口（路由段/客户端入参）解析一次后归一内部键。
- **路由**：`/sso/oauth/{channelAlias}/callback` 与 `/sso/oauth/{channelId}/callback` **并存**——装配层先按段尝试 alias 解析（GetByAliasOrId），未中 404（`CHANNEL_NOT_FOUND`）。**微信平台侧配置**：公众号后台「网页授权域名」域名级共享；「服务器配置 URL」每公众号独立完整 URL（含各自 alias/channelId 段）——域名共享、路径区分。
- **安全**：alias 非敏感（凭证在服务端）；alias 保护内部键（不暴露持久化编号）；alias 冲突由注册门面校验（同 alias 二次注册 fail-closed，对齐 RegisterAsync Conflict 语义）。
- **默认通道**：`GetDefaultAsync` 语义不变（alias 不参与默认选区——默认按内部 IsDefault 标记）。

### 3.8 客户端换取边界（2026-10-08 讨论记录——**非裁定**，现状已满足）

> **边界确认（用户讨论）**：客户端 SDK 拉起微信（PC/iOS/Android/鸿蒙）——**SDK 集成层不经过联邦互联**（appid + 回调 scheme 等参数**保存在客户端**，微信 SDK 标准集成）；**身份换取必须经联邦互联服务端**（code 一次性票据上抛服务端 → `ISsoLogin.LoginAsync` 换取 → 签发 token2）——凭证（AppSecret/私钥）在服务端，客户端永不自持密钥。
>
> **讨论结论（2026-10-08，用户澄清）**：客户端发起的情况**若不需要任何额外参数，现状门面即已满足**（`ISsoLogin.LoginAsync(channelId/alias, context(code))` 已覆盖"code → 服务端换取"全流程）——**不裁定新增对外端口/增强选配**。仅当未来出现"客户端需在换取前验证额外身份获取参数"（如设备指纹/环境校验）时，再评估装配层 `POST /sso/oauth/exchange` 端点约定——届时归装配层 minimal API（Federation 不引 AspNetCore，AGENTS 分层原则），门面不变。

- **客户端 SDK 参数**：appid/scheme/universal link **存客户端**（微信 SDK 要求，非联邦互联职责）；联邦互联只消费"code → 服务端换取"。**授权发起（authorize URL 构造）归装配层/客户端**（现状一致，通道不感知 state）。
- **换取入参**（现状门面）：`channelId`（或未来 alias）+ `code`（必填）+ `redirect_uri`（平台语义——支付宝不经、QQ 必传一致性）+ `SsoChannelAuthContext` 参数包承载。
- **安全**：code 一次性上抛（客户端不留存）；换取频控/验签归装配层（对齐 `/sso/login` 现状）。
