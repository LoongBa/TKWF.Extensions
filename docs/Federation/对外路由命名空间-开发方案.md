## 一、目的与目标

联邦互联对外路由命名空间**语义化重构**，使路由结构表达"联邦互联"的结构语义：

1. **根前缀** `/sso`（体验词，SSO=单点登录）→ `/feberation`（结构词，对齐扩展中文名「联邦互联」+ 项目惯例拼写 Feberation）——路由读出来即知是"对外联邦互联"。
2. **二级平台段** = 联邦简称（平台族）——路径天然区分微信/钉钉/企微/QQ/支付宝/OIDC 系，"多平台路由一目了然"不依赖 channelId 命名猜平台。
3. **通道段** = 通道实例精确定位；**通道段可省语义**为设计决策点（Oracle 评审焦点——多通道模式默认降级是否保留）。
4. **捆绑修复** `HandleEvent` event 通道不可达缺陷（实证真实 bug，与路由重构天然协同）。

目标状态：`/feberation/{platformId}/...`（平台集成面）+ `/feberation/jwks|authorize/*|trust/*|identity/*`（信任/委托面）双面共存；路由即文档（读路径知平台）；event 端点可用。

## 二、问题

1. **`/sso` 语义模糊**：SSO 是体验词（用户感知的"单点登录"），Federation 是结构词（系统间联邦互联）——与扩展中文名「联邦互联」不对齐；`/sso` 无法表达"这是对外连接层"的架构语义。
2. **路由无平台维度**：`/sso/event/{channelId}`、`/sso/oauth/{channelId}/callback` 从路径**看不出平台**——"哪个平台的事件"须依赖 channelId 命名惯例（`wechat-mp-yibalian` 式前缀带平台名）或查配置，多平台并存时路由可读性差。
3. **`HandleEvent` event 通道不可达（实证缺陷）**：`HandleEvent` 硬编码 `CreateAsync(channelId, null)`（FederationWebExtension.cs L154），工厂 null 分支谓词 `IsOAuthChannel` **只白名单 `*_oauth`/`*_oidc`**（SsoChannelFactory.cs L96-98 `EndsWith` 显式排除 `*_event`）——`wechat_event`/`dingtalk_event`/`wecom_event` 通道不可达：双注册场景命中错误通道（误导性 400），单注册场景 404。
4. **文档-代码漂移 3 处**（存量，随本次修正）：平台库指南 GET/POST 不一致（`/sso/login` 列 GET 实为 POST）；`/sso/event/{channelId}/callback` 带 `/callback` 后缀而代码无；README §3 配置 JSON 漏 4 个新端点开关。

## 三、设计决策

### 决策 1：根前缀默认值 `/sso` → `/feberation`（可配保留）

- `FederationEndpointOptions.RoutePrefix` 默认值改 `/feberation`（`TKWF:Federation:Web:RoutePrefix` 可配不变，消费方可改回 `/sso`）。
- 全部端点模板由 prefix 单点拼接（现状 8 条路由共用 `prefix` 变量），改动集中在 `FederationWebExtension.ConfigureEndpoints`。
- 拼写对齐项目惯例（Feberation——AGENTS/README/用户语境统一使用），与中文名「联邦互联」同构。

### 决策 2：二级平台段 = PlatformType 开放注册表 + Ordinal 校验

- 平台段 `{platformId}` 与 `ChannelConfig.PlatformType` **同字符串空间**（现状即开放注册表 string——`wechat/qq/dingtalk/wecom/alipay/oidc/google/microsoft`，注释明示"开放注册表不枚举"，DB 列 MaxLength 64 无约束）。
- **端点解析校验**：registry 取得 `cfg` 后校验 `cfg.PlatformType == platformId`（Ordinal）——不一致 → `CHANNEL_NOT_FOUND`（404）——**防跨平台错配**（路由段写 dingtalk 而通道实为 wechat）。
- OIDC 系无歧义：`oidc`/`google`/`microsoft` 三库 PlatformType 各自独立（`oidc_oidc`/`google_oidc`/`microsoft_oidc`）——平台段可无歧义映射到具体库。

### 决策 3：event 缺陷捆绑修复（channelType 精确推导）

- event 端点（`{prefix}/{platformId}/event[/{channelId}]`）：handler 取 `cfg.PlatformType`（权威，非路由段）推导 `channelType = $"{cfg.PlatformType}_event"` 传工厂——**精确匹配分支命中 `*_event` 模板**（修复缺陷）。
- login/oauth 端点：channelType 保持 `null`（OAuth/OIDC 自动推导语义正确——登录/授权回调意图就是 OAuth 通道）。
- 通道模板 null（如 QQ 出站-only 无 event 通道）→ `CHANNEL_NOT_FOUND`（404，合理语义）。
- 同时消除 null 分支 `FirstOrDefault` 的 DI 注册序不确定性（event 场景不再走 null 分支）。

### 决策 4：信任/委托面根级（跨平台，不挂平台段）

- `jwks`（token2 公钥分发）/ `authorize/start`（委托发起）/ `trust/issue`（已认证签发）/ `identity/claim`（兑现）——**跨平台语义，不属任何平台**，保持根级。
- 与平台集成面同前缀并存：`/feberation` 为命名空间根，二级段语义分流（平台族 vs 端点名）。

### 决策 5：通道段可省语义——多通道模式默认降级（**Oracle 评审焦点**）

现状：`GetDefaultAsync()`（IsDefault → 首项）+ `LoginDefaultAsync` 降级语义；使用指南已记录边界——**"默认通道语义仅为向后兼容，不承诺多公众号下业务合理默认（显式决策 channelId）"**（多通道联邦方案 §3.2）。

候选立场：

| 候选 | 语义 | 优点 | 风险 |
|------|------|------|------|
| **A 全保留降级** | 所有端点通道段可省 → `GetDefaultAsync` | 单通道/测试友好；与现有 `LoginDefaultAsync` 语义对齐；零心智负担 | 多通道下省略 = **非确定性静默选区**（IsDefault→首项）——违反设计原则"缺省=守卫硬失败不静默失效"；event 端点被微信后台填死 URL，省略通道=部署配置错误却静默落到默认公众号 |
| **B 按通道数守卫** | 单通道（注册表=1）省略 → 降级（无歧义）；多通道（>1）省略 → 硬失败 `CHANNEL_REQUIRED`（400） | 符合"缺省=守卫硬失败"；多通道静默错配归零；单通道零成本 | 需 registry 通道计数能力；行为随通道数变化（部署形态影响 API 语义） |
| **C 按端点区分** | login 保留降级（程序发起，channelId 是自然可选参数）；event/oauth 回调守卫硬失败（IdP 后台填死 URL，省略 = 配置错误应 fail-fast） | 语义按端点自然分化；login 向后兼容 | 规则不对称（学习成本）；oauth 回调的子应用委托场景 `GET .../oauth/callback`（无通道段默认降级）被收紧 |

**Oracle 裁定（2026-10-11，评审条件 1）**：**选 B**——按**活跃通道数**（`IsEnabled=true`）守卫，错误码 **400 `CHANNEL_REQUIRED`**。理由：A 会将"自认不承诺但不守卫"的静默选区反模式固化（`GetDefaultAsync` 多通道下 = IsDefault→首项非确定性静默选区）；B 符合"缺省=守卫硬失败不静默失效"，单通道场景（活跃=1）降级无歧义零成本。

**B 守卫落点（Oracle 条件 1——4 处消费者，不在 `SsoChannelFactory.CreateDefaultAsync`）**：工厂层返回 `ISsoChannel?`，null 已承载"未找到"语义，无法区分"必须指定"——守卫在消费者层：

| 消费者 | 位置 | B 守卫行为 |
|--------|------|-----------|
| `SsoLogin.LoginDefaultAsync` | SsoLogin.cs | 活跃数 >1 → `SsoChannelAuthResult(false, null, "CHANNEL_REQUIRED", 0)` |
| `ExternalIdpAuthenticator.ResolveChannelAsync` | ExternalIdpAuthenticator.cs | 活跃数 >1 → `ExternalIdpAuthResult(false, null, "CHANNEL_REQUIRED", 0)` |
| `SsoSubAppBridge.StartAsync` | SsoSubAppBridge.cs | `ChannelId` null 且活跃数 >1 → `AuthorizeStartResult(false, null, null, "CHANNEL_REQUIRED")` |
| `HandleOAuthCallback`（无通道段形态） | FederationWebExtension.cs | 活跃数 >1 → 400 CHANNEL_REQUIRED；==1 → 解析默认通道 channelId 传 `CompleteOAuthAsync` |

**活跃通道数判定**（Oracle 补充）：`IChannelRegistry.GetAllAsync()` + `.Count(c => c.IsEnabled)`——静态层纯内存、DB 层查询仅在通道段省略时触发（非每请求），通道数通常个位数，性能可接受；**`GetActiveCountAsync` 专方法非本轮必须**（后续优化项）。**多通道 + 有 IsDefault 标记也一律 CHANNEL_REQUIRED**——IsDefault 只在单通道场景（无选择）才生效。

**C 不选理由**（Oracle）：`ExternalIdpAuthenticator` 不走 HTTP 端点（端点区分不适用）；`authorize/start` 的 `ChannelId` 是 body 参数（二分法不成立）；B 是统一规则，C 引入学习成本且覆盖不全。

## 五、端点行为变化（对照）

| 现状（0.6.0） | 新形态 | 变更点 |
|---|---|---|
| `POST /sso/login[/{channelId}]` | `POST /feberation/{platformId}/login[/{channelId}]` | 前缀 + 平台段插入 + 平台段校验 |
| `GET /sso/oauth/{channelId}/callback` | `GET /feberation/{platformId}/oauth/{channelId}/callback` | 前缀 + 平台段插入 + 平台段校验；**新增无通道段形态** `.../oauth/callback`（默认降级——文档已有代码缺失的漂移顺带补实） |
| `POST /sso/event/{channelId}` | `POST /feberation/{platformId}/event[/{channelId}]` | 前缀 + 平台段插入 + **event 通道精确推导（缺陷修复）** + 新增无通道段形态 |

| `POST /sso/authorize/start` / `trust/issue` / `identity/claim` | `POST /feberation/authorize/start` 等 | 仅前缀 |
