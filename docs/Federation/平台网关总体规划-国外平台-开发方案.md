# 联邦互联平台网关总体规划（国外平台）——开发方案

> **范围**: `TKWF.Federation.{平台}` 平台网关库的**国外平台方向规划**（姊妹文档：国内平台见 [《平台网关总体规划（国内平台）》](./平台网关总体规划-开发方案.md)）；遵循既有设计原则；**不考虑兼容过渡**——OIDC 收敛（ADR §五.8 对外协议面 v0.2.0 方向）与本规划（身份源适配维度）正交：国外平台以**标准 OIDC 为主流**，天然收敛
> **版本**: v0.1.0 ｜ **日期**: 2026-10-05 ｜ **状态**: 📋 提议（待 Oracle 评审）
> **关联**: ADR-AuthCenter-归层与命名（§五.8 协议面扩展余地）｜ 联邦互联使用指南 ｜ WeChat 先例（`_Framework/Federation.WeChat/`——平台网关模板）｜ 国内平台总规划（同模板不同协议阵营）
> **关键约束**: 平台网关 = **纯库**（无 Initializer 无 `[TKWFExtension]` 无持久化零 Store——tkwf-extension 铁律）；ISsoChannel 窄适配；凭证自持；不引 AspNetCore；库 → Federation 扩展单向依赖

## 一、背景与目标

### 现状

国内平台网关已规划（微信✅/QQ/支付宝/钉钉/企业微信/B站/小红书——首批 5 平台协议矩阵已填充）。**国外平台与国内平台协议形态差异大**（用户裁定拆两份文档）：

| 维度 | 国内（微信/QQ/支付宝…） | 国外（Google/Microsoft/Apple…） |
|------|------------------------|---------------------------------|
| **协议** | 私有 OAuth + 特殊验签 | **标准 OIDC（主流）** + 私有 OAuth2（少数） |
| **验签** | 私有签名机制 + 入站事件回调验签 | **JWKS + RS256**（OIDC 标准） |
| **用户标识** | `openid`/`unionid`（平台封闭） | `sub`（OIDC，issuer 内唯一，public/pairwise） |
| **用户信息** | 私有 API | 标准 `/userinfo` |
| **授权形态** | 跳转 + **扫码** | **纯跳转，无扫码** |

### 目标

1. **国外平台清单与优先级**（OIDC 阵营 / 私有 OAuth2 阵营 + 排除项）；
2. **通用 OIDC 客户端基座**——Google/Microsoft/LinkedIn/Slack 等标准 OIDC 平台**共享一个 OIDC 通道基座**（Discovery + JWKS + /userinfo 标准流），每平台仅配置差异（端点/scope/sub 语义）——这是与国内"一对一私有适配"的最大差异，也**正向呼应 ADR §五.8 的 OIDC 收敛方向**（对外 OIDC 端点薄层 v0.2.0 与上游 OIDC 消费共享协议资产）；
3. **私有 OAuth2 平台**（GitHub/Facebook/Amazon）——走 WeChat 式专属适配器（非 OIDC 基座）；
4. **协议差异矩阵**（跨平台 sub 语义/验签/scope）+ 实施顺序与验收。

## 二、设计原则

**继承**：国内文档 §二 P1-P10 全部适用（平台网关 = 纯库 / 零 Store / ISsoChannel 窄适配 / 凭证自持 / 信任根一票否决 / 不引 AspNetCore / 单向依赖 / 注册责任归库侧 / 协议差异收敛于 channel / 数据流归一）。

**新增/强化**（国外场景特有）：

| # | 原则 | 说明 |
|---|------|------|
| P11 | **标准 OIDC 优先** | 平台支持标准 OIDC（Discovery + JWKS + /userinfo）→ 走**通用 OIDC 通道基座**（`OidcChannelBase`，配置驱动），不写平台专属逻辑；仅私有 OAuth2 平台写专属适配器 |
| P12 | **sub 二元组持久化** | OIDC `sub` 为 **issuer 内唯一**（OIDC Core 1.0 明确定义"locally unique within the Issuer"）——Google `public`（跨 App 相同）/ Microsoft・LinkedIn `pairwise`（跨 App 不同，PPID）/ Slack `public`（team-scoped）/ Apple `UUID+teamIdentifier`（同一 Developer Team 跨 App 相同）。**Federation 侧一律存 `(issuer, sub)` 二元组 + 经 TKWF 自建锚点映射为本地 uid**——不依赖任何跨平台对齐 |
| P13 | **OIDC 无入站回调 = 出站信任为主** | 国外平台无事件推送入站（对比国内微信/钉钉/企业微信）——信任根依赖出站换取（code→token 需 client_secret/私钥）+ 验 id_token 签名（JWKS）；无入站事件通道形态 |
| P14 | **Apple 专用语义** | Apple 是 OIDC **变体**（非完整 OIDC）：无 discovery URL、scope 用 `name`/`email` 非 `openid`、`response_mode=form_post` 才能拿 user、**无独立 userinfo（user 仅首次授权一次性返回）**——须独立适配器 + 本地持久化 user 载荷 |

## 三、平台清单与优先级

### 判据

国内判据基础上叠加国外特有：
- **标准 OIDC 合规**（Discovery/JWKS/userinfo 齐全）→ 复用通用基座，接入成本低，**优先**；
- **OIDC 变体**（Apple）→ 专属适配器，但价值高（移动端必需）；
- **私有 OAuth2**（GitHub/X/Facebook/Amazon）→ 专属适配器，视场景价值；
- **无 id_token 无 JWKS** → 信任根弱（不透明 Bearer），场景驱动。

### 清单

| 优先级 | 平台 | 协议 | sub 语义 | 验签 | 场景价值 | 接入形态 |
|--------|------|------|---------|------|---------|---------|
| 🔴 **第一批** | **Google** | **标准 OIDC** | `public` | JWKS RS256 | 全球覆盖率最高；OIDC 参考实现基线 | **通用 OIDC 基座** |
| 🔴 **第一批** | **Microsoft Entra ID** | **标准 OIDC** | `pairwise`（跨 App 不同） | JWKS RS256 | 企业工作/学校账场景必需；双租户（common/consumers/organizations） | **通用 OIDC 基座**（tenant 配置化） |
| 🔴 **第一批** | **Apple** | OIDC **变体** | `UUID+teamIdentifier` | JWKS RS256 | 移动端登录必需；private email relay 隐私合规亮点 | **专属适配器**（AppleOidcChannel） |
| 🟡 **第二批** | **GitHub** | **私有 OAuth2** | 无 sub（REST `id`） | ❌ 无 JWKS（不透明 Bearer + `GET /user` 校验） | 开发者场景 | **专属适配器** |
| 🟡 **第二批** | **LinkedIn** | **标准 OIDC**（2023 起） | `pairwise` | JWKS RS256 | B 端职业身份；OIDC 权限需申请 | **通用 OIDC 基座** |
| 🟢 **第三批** | **Slack** | **标准 OIDC** | `public`（team-scoped） | JWKS RS256 | B 端团队协作 | **通用 OIDC 基座** |
| 🟢 **第三批** | **Facebook** | **私有 OAuth2** | App 内唯一 Graph `id` | ❌ 无 JWKS（Debug Token 校验） | 移动/游戏登录 | **专属适配器** |
| 🟢 **第三批** | **Amazon** | **私有 OAuth2** | Amazon Customer ID（跨 App 相同） | ❌ 无 JWKS | 电商场景；token 端点区域化较复杂 | **专属适配器** |
| ⚪ 不建议 | **X/Twitter** | 私有 OAuth2 + **PKCE 强制** | 无 sub（`data.id`） | ❌ 无 JWKS | API 大幅收紧；App 类型限制严；价值有限 | 排除（除非明确诉求） |
| ⚪ 不建议 | Notion | 无 OAuth/OIDC 登录端点 | — | — | 不适用 | 排除 |

**第一批 = Google / Microsoft / Apple**（OIDC 三大件，覆盖消费 + 企业 + 移动）；第二批按场景启动。

> **自托管/云 OIDC IdP（Oracle 评审 P2-3 补充）**：本清单聚焦**第三方大平台**（消费/企业级 IdP）。**Keycloak / Okta / Auth0 / Authentik 等自托管或云 OIDC IdP**（国外企业自建身份域常见选择）**不需专属适配器**——经**通用 OIDC 基座（§五）配置驱动接入**（Discovery URL + scope + 凭证），零专属代码。消费方有此类需求时直接装配基座即可，不计入平台清单。

## 四、协议差异矩阵（国外平台）

> 差异收敛于 channel 实现（P9）；标准 OIDC 平台差异收敛于**配置 + sub 语义处理**（共享基座），私有 OAuth2 收敛于专属适配器。

| 平台 | 协议 | authorize 端点 | token 端点 | userinfo | JWKS | sub 语义 | 用户信息 | scope | 唯一注意点 |
|------|------|---------------|-----------|----------|------|---------|---------|-------|-----------|
| **Google** | 标准 OIDC | `accounts.google.com/o/oauth2/v2/auth` | `oauth2.googleapis.com/token` | `openidconnect.googleapis.com/v1/userinfo`（标准） | `www.googleapis.com/oauth2/v3/certs` | `public`（跨 App 相同） | 标准 userinfo | `openid`/`email`/`profile` | 无特殊 |
| **Microsoft** | 标准 OIDC | `login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize` | 同域 `/token` | `graph.microsoft.com/oidc/userinfo` | `{tenant}/discovery/v2.0/keys` | **`pairwise`**（同一用户跨 App 的 sub 不同——PPID） | 标准 userinfo | `openid`+`profile`+`email` | `{tenant}` 决定认证受众（common/consumers/organizations/租户 ID）；PKCE 强推荐 |
| **Apple** | OIDC **变体** | `appleid.apple.com/auth/authorize` | `appleid.apple.com/auth/token` | **无独立 userinfo**（user 仅首次 `form_post` 返回；后续 email 在 id_token） | `appleid.apple.com/auth/keys`（多钥按 kid 匹配） | `UUID+teamIdentifier`（同 Team 跨 App 相同） | 首次授权一次性 `user` 载荷（name+email）——须本地持久化 | `name`/`email`（**非 openid**） | `response_type=code id_token`（禁单独 id_token）；`response_mode=form_post`；private email relay（`*@privaterelay.appleid.com`）；**无 discovery URL**（硬编码端点） |
| **GitHub** | 私有 OAuth2 | `github.com/login/oauth/authorize` | `github.com/login/oauth/access_token` | `api.github.com/user`（私有 REST） | ❌ 无 | 无 sub（REST `id` 整数） | 私有 REST | `read:user`/`user:email` 等 | 不透明 Bearer；OIDC 仅用于 Actions 工作负载（非用户身份）；Device Flow 支持 |
| **LinkedIn** | 标准 OIDC | `linkedin.com/oauth/v2/authorization` | `linkedin.com/oauth/v2/accessToken` | `api.linkedin.com/v2/userinfo` | `linkedin.com/oauth/openid/jwks` | **`pairwise`** | 标准 userinfo（email 可缺失） | `openid`/`profile`/`email` | OIDC 权限须向 LinkedIn 申请开通；无公开 `.well-known`（官方给出 discovery 内容） |
| **Slack** | 标准 OIDC | `slack.com/openid/connect/authorize` | `slack.com/api/openid.connect.token` | `slack.com/api/openid.connect.userInfo` | `slack.com/openid/connect/keys` | `public`（但 team-scoped——同人不同 workspace 不同 sub） | 标准 userInfo（驼峰方法名） | `openid`/`email`/`profile` | 2023 起取代 legacy oauth/v2 |
| **Facebook** | 私有 OAuth2 | `facebook.com/v25.0/dialog/oauth`（**版本号在 URL**） | `graph.facebook.com/v25.0/oauth/access_token` | `graph.facebook.com/me` | ❌ 无 | App 内唯一 Graph `id` | 私有 Graph | `public_profile`+`email` | 不透明 Bearer；Debug Token 校验；版本化端点 |
| **Amazon** | 私有 OAuth2 | `amazon.com/ap/oa` | `api.{region}.amazon.com/auth/o2/token`（区域化） | `api.amazon.com/user/profile` | ❌ 无 | Amazon Customer ID（跨 App 相同） | 私有 profile API | `profile`/`profile:user_id`/`postal_code` | 浏览器场景 PKCE 强制；token 端点区域化 |

**关键结论**：
- **OIDC 三大件（Google/Microsoft/Apple）+ 补充（LinkedIn/Slack）= 5 个标准 OIDC 平台共享 `OidcChannelBase`**——配置差异（endpoint/scope/tenant）+ sub 语义策略（pairwise 存 `(iss, sub, client_id)` 注意跨 App），代码复用率 >80%；
- **Apple 是最大"非标"**——独立适配器，但价值高（移动端必需）；
- **私有 OAuth2（GitHub/Facebook/Amazon/X）**——WeChat 式专属适配器；X 不建议（API 收紧 + 无 JWKS + 无 OIDC）；
- **国外全部无扫码、无入站事件回调**——信任根 = 出站凭证 + id_token JWKS 验签（简化通道形态，无事件通道）。

## 五、通用 OIDC 通道基座（P11 落地形态）

```
TKWF.Federation.Oidc（独立公共基座库——Oracle 评审 P1-7：5 平台共享 >80% 代码，倾向独立库避免重复/循环依赖）
  ├── OidcChannelBase : ISsoChannel —— 配置驱动（OidcPlatformConfig：authorize/token/userinfo/jwks/discovery + scope + sub 语义）
  │     ├── OidcAuthFlow（Discovery 可选 / 端点配置化 / code→token（client_secret 或私钥 JWT 断言） / id_token JWKS 验签 RS256 / userinfo 拉取）
  │     └── Token2 归一：(issuer, sub) → uid（Federation 锚点映射）
  ├── GoogleOidcChannel（ChannelType="google_oidc"，配置差）
  ├── MicrosoftOidcChannel（ChannelType="microsoft_oidc"，tenant 配置）
  ├── LinkedInOidcChannel / SlackOidcChannel（配置差）
  └── AppleOidcChannel（独立——OIDC 变体，非继承基座）
```

- **与 ADR §五.8 OIDC 收敛方向的关系（Oracle 评审 P1-2 收敛表述）**：ADR 的 OIDC 收敛 = **对外协议面**（Federation 对下游提供标准 OIDC 端点薄层，v0.2.0）；本规划 = **身份源适配面**（Federation 上游消费 Google 等 OIDC IdP）。**上下游共享的是底层 OIDC 原语**（Discovery 解析 / JWKS 管理 / id_token 验签 / claims 映射），**不共享协议角色逻辑**（上游 = RP 验签方，下游 = OP 签发方——语义相反）。本规划仅承诺：**上游 OIDC 消费的公共原语提炼为基座**；**下游 OIDC 提供（v0.2.0）的协议资产复用关系待 v0.2.0 立项时评估，本规划不预设上下行共享**。
- **OidcChannelBase 与 `TKWF.Utility.OAuthClient` 引擎职责边界（Oracle 评审 P1-3）**：引擎（BCL，归主框架）尚未实施——OidcChannelBase **最小职责 = channel 适配 + 配置驱动**，不含 JWT 实现/加密原语（那些归引擎/BCL）；OIDC 原语（Discovery/JWKS/id_token 验签）**若引擎可用则委托引擎**，否则基座内联并标注"待引擎落地后迁移"——避免与未来引擎重叠返工。本规划批准 **`TKWF.Federation.Oidc` 独立基座库**（P1-7）承载 channel 适配层，引擎模式待主框架落地。
- **PKCE**：Google/Microsoft/LinkedIn/Slack 均支持（Microsoft 强推荐）——OIDC 基座内置 `code_challenge_method=S256`（对齐 OAuth 2.1）。

## 六、实施顺序与验收

### 实施顺序

1. **`TKWF.Federation.Oidc` 基座（或并入首平台）** → **Google**（OIDC 参考实现基线）→ **Microsoft**（tenant 配置化验证）→ **Apple**（变体适配器）——第一批闭环；
2. 第二批 **GitHub**（私有 OAuth2 专属适配器首例）→ **LinkedIn**（OIDC 基座广度验证）；
3. 第三批按需（Slack/Facebook/Amazon）。

### 验收标准（对齐国内 F1-F8 模式）

| 需求ID | 验收条件 | 验收方式 |
|--------|---------|---------|
| F1 | 库零 Initializer 零 `[TKWFExtension]` 零持久化零 Store（纯库判定） | 架构检查 |
| F2 | OIDC 基座：Discovery（可用时）+ code→token（PKCE S256）+ id_token JWKS 验签（RS256 + kid 白名单 + iss 校验）正确；篡改/伪造 id_token 拒（信任根负路径） | 自动化测试（正负） |
| F3 | sub 语义处理：pairwise（Microsoft/LinkedIn）跨 App 不同 sub → 存 `(iss, sub, client_id)` 不误并；public（Google/Slack）跨 App 相同可并 | 自动化测试 + 语义断言 |
| F4 | Apple 专用：form_post user 一次性持久化；id_token email 回落；private email relay 透传 | 自动化测试 |
| F5 | 私有 OAuth2（GitHub）：非 OIDC 路径（REST `GET /user` 取 id + 不透明 Bearer）独立适配 | 自动化测试 |
| F6 | `AddXxxFederationChannels()` 注册进 `IEnumerable<ISsoChannel>` 集合，未装配通道自然跳过；**多 IdP 同时装配（如 Google + Microsoft + Apple）后集合正确枚举所有已注册通道（Oracle 评审 P2-7）** | 自动化测试 + 探针门面 |
| F7 | 红线合规：零 Store / 零构造注入 / 零裸 ORM；凭证自持 | 代码审查 + skill 自检清单 |
| F8 | 全量回归不破坏（当前基线全绿，避免固定数字过期——Oracle 评审 P2-5） | slnx 测试 |

## 八、复核结论（2026-10-05 librarian 专项复核 bg_9336a46d）

> 前版 6 项待核实全部复核：**5 项已确认/修正，Apple sub 格式仍无法官方确认（重大——不解析）**。复核来源均为官方文档。

| # | 项 | 复核结论 | 设计影响 |
|---|----|---------|---------|
| 1 | **Apple discovery** | ✅ **修正——Apple 提供 discovery**（`appleid.apple.com/.well-known/openid-configuration`）；但 2025-06 起有两个并存端点（`account.apple.com/.well-known/...` 声明 issuer=`account.apple.com`），而 id_token `iss` 恒为 `appleid.apple.com`——discovery 与 token issuer 可能不一致 | OIDC 基座 Discovery **配置驱动 + issuer 容错**——校验 token 的 `iss`（非 discovery 的 issuer）；issuer 不匹配不静默失败 |
| 2 | **Apple sub 格式** | ⚠️ **无法官方确认**——Apple 官方仅声明 sub 是 "unique, stable string" 且 "team-scoped"（同 team 跨 App 相同、跨 team 不同），**从未文档化 `{UUID}+{teamIdentifier}` 格式与 `+` 拼接符**（社区观察非契约） | 🔴 **不得解析 sub 结构**（不按 `+` 切分/提取 teamIdentifier）——sub 当**不透明字符串**整体持久化；Apple 可随时变更格式而不违约 |
| 3 | Apple JWKS kid 匹配 | ⚠️ 官方不显式说明（RFC 7515 §4.1.4 隐含） | 遍历全部密钥按 JWT header `kid` 精确匹配（禁取第一把）——但 Apple 官方未背书；业界实践已定（Apple Forum DTS 未反驳） |
| 4 | LinkedIn discovery | ⚠️ **修正——LinkedIn 有 discovery**，但位于 **`/oauth/.well-known/openid-configuration`**（非标准根路径） | 硬编码 `{issuer}/.well-known/` 会漏 LinkedIn——基座支持配置驱动 discovery URL 覆盖 |
| 5 | Slack sub 跨 workspace | ⚠️ 官方未直接声明，但可从 user_id 语义推出：**sub=user_id，workspace-scoped**（普通 workspace 同人跨 workspace sub 不同；Enterprise org 内有全局 ID U/W 开头） | 按 **`(sub, team_id)` 复合键**存储——单存 sub 会跨 workspace 错绑 |
| 6 | X/Twitter discovery | ✅ **确认无 OIDC**——官方 API 仅 OAuth 1.0a/2.0 端点，无 `.well-known` | X 归 OAuth-only（LinkByEmail 邮箱链接策略），不纳入 OIDC 基座——已建议排除 |
| 7 | GitHub Actions OIDC | ✅ 确认——Actions OIDC = 工作负载身份联邦（`sub` 是仓库/工作流 ID，非用户身份） | 不适用联邦互联身份面——文档已澄清 |

**复核启示（修订 P11-P14 的落地约束）**：
- OIDC Discovery **必须配置驱动**（LinkedIn `/oauth/.well-known/`、Apple 双端点冲突、X 无 discovery——硬编码路径必错）；
- `sub` **不透明字符串原则**（P12 强化）——不解析结构（Apple）、复合键（Slack `(sub, team_id)`）、issuer 校验（Apple 双端点）；
- **敏感字段非默认**（企业微信手机号/支付宝手机号均需资质+申请+审核——非稳定能力，见国内文档复核）。
