# 联邦互联平台网关总体规划（国内平台）——开发方案

> **范围**: `TKWF.Federation.{平台}` 平台网关库的**下一步方向规划——国内平台**（国外平台见姊妹文档 [《平台网关总体规划（国外平台）》](./平台网关总体规划-国外平台-开发方案.md)）；遵循既有设计原则；**不考虑兼容过渡**（不背 SSO 历史包袱、不为未来 AuthCenter 合并预设迁移、OIDC 收敛作为对外协议面方向独立演进——本规划只解决"更多 IdP 身份源"单一问题）
> **版本**: v0.1.0 ｜ **日期**: 2026-10-05 ｜ **状态**: 📋 提议（待 Oracle 评审）
> **关联**: ADR-AuthCenter-归层与命名（§五.8 协议面扩展余地）｜ 联邦互联使用指南 `docs/Federation/联邦互联-使用指南.md` ｜ WeChat 先例 `docs/Federation.WeChat/微信公众平台连接器-使用指南.md` + `_Framework/Federation.WeChat/`（模式模板）
> **关键约束**: 平台网关 = **纯库**（无 Initializer 无 `[TKWFExtension]` 无持久化零 Store——tkwf-extension 铁律）；ISsoChannel 窄适配；凭证自持；信任根一票否决；不引 AspNetCore；库 → Federation 扩展单向依赖

---

## 一、背景与目标

### 现状

联邦互联（Federation）四层归层模型已落地，**平台网关库模式已验证**——`TKWF.Federation.WeChat`（微信公众平台连接器 V0.1.0）是首个先例：

- 纯库形态（无 Initializer / 无 `[TKWFExtension]` / 零持久化零 Store）✅
- `ISsoChannel` 窄适配：`WeChatOauthChannel`（wechat_oauth）+ `WeChatEventChannel`（wechat_event）——键值上下文承载协议差异 ✅
- 凭证自持（`WeChatOptions`，Oracle P2-4）✅
- 信任根一票否决（`WeChatEventCrypto` msg_signature + AES 验签）✅
- `AddWeChatFederationChannels()` 注册扩展方法（TryAddEnumerableConstructible<ISsoChannel>，ADR92）✅
- 测试 18 用例全绿（OAuth 正负 + 信任根正负 + 生产路径探针门面）✅

### 问题

- **身份源单一**：目前仅微信（`wechat_oauth`/`wechat_event` 双通道）——国内主流 IdP（QQ/支付宝/钉钉/企业微信）尚未接入；
- **模式未模板化**：WeChat 先例的组件清单/双通道/出站客户端/信任根/注册扩展形态**未提取为可复制的网关模板**——每接一个平台从零设计（重复劳动 + 一致性风险）；
- **优先级未裁定**：国内平台众多（C 端消费 + B 端企业），需按业务价值/协议差异/接入成本裁定顺序。

### 目标

1. **裁定国内平台清单与优先级**（第一批/第二批/排除项 + 判据）；
2. **提取"平台网关通用模式"**（从 WeChat 先例模板化——组件/流程/注册/配置/信任根形态），新平台按模板复制实现；
3. **每平台协议差异矩阵**（授权形态/用户标识/验签/scope——差异收敛于 channel 实现，核心逻辑零改动）；
4. **实施顺序与验收标准**（按优先级分批，每批对齐 F1-F8 验收模式）。

> **不考虑兼容过渡（用户裁定 2026-10-05）**：本规划不背 SSO 命名/旧形态包袱、不为 AuthCenter 包名合并预设过渡、不评估 token2 与 OIDC 平行——**OIDC 收敛（对外协议面 v0.2.0）是独立演进轨道**，与本规划（身份源适配维度）正交，互不阻塞（协议面两维度的设计初衷，ADR §五.8）。

## 二、设计原则（遵循既有裁定，全部已在 WeChat 先例实证）

| # | 原则 | 出处 | 说明 |
|---|------|------|------|
| P1 | **平台网关 = 库非扩展** | AGENTS §8 纯库判据 | `TKWF.Federation.{平台}`（单包多命名空间），无 Initializer 无 `[TKWFExtension]`——有持久化或有服务需装配才为扩展，平台网关纯协议 → 库 |
| P2 | **零持久化零 Store** | tkwf-extension skill §5 铁律 | 出站 API 能力内聚于客户端类（内存态缓存），**不创建 `I{Xxx}Store`/`{Xxx}Store` 伪层**（WeChat 实证：`WeChatApiClient` 纯内存态 access_token 缓存） |
| P3 | **ISsoChannel 窄适配** | Oracle P1-1 | 通道实现 Federation 定义的 `ISsoChannel`（ChannelType/ChannelId/AuthenticateAsync），键值上下文 `SsoChannelAuthContext(IReadOnlyDictionary<string,string?>)` 承载协议差异——新增平台不扩展契约，仅实现 |
| P4 | **凭证自持** | Oracle P2-4 | 平台凭证（AppSecret/私钥等）归网关库自持（Options 节），**复不复用** Authentication `IPlatformCredentialService`——生产 AES-GCM 密文或装配注入，永不明文进配置库 |
| P5 | **信任根一票否决** | 设计文档 §8.1 + WeChat 实证 | 入站回调/事件验签**漏验 = 可伪造任意 external_uid = 体系崩溃**——验签失败即拒，无降级无旁路；恒定时间比对。**适用范围澄清（Oracle 评审 P1-5）**：P5 针对**入站回调/事件验签**——平台无入站回调（如 QQ 仅出站 OAuth、国外 OIDC 无事件通道）时 P5 不适用（**非违规**），信任根降级为"出站 code 一次性 + state CSRF + client_secret/私钥换取 + id_token JWKS 验签"（见 §五信任根分档） |
| P6 | **不引 AspNetCore** | Oracle 评审点 5 | 库纯逻辑 + HttpClient（`Microsoft.Extensions.Http`）；入站端点归 Federation 扩展/消费方装配层；验签逻辑收 `byte[]`/`Stream` |
| P7 | **单向依赖** | Oracle P1-1 | 库 → `TKWF.Ext.Federation` 扩展 → `Authentication.Abstractions` + 主框架——单向无循环 |
| P8 | **注册责任归库侧** | Oracle 评审点 7/T6 | 库提供 `AddXxxFederationChannels()` 扩展方法（`TryAddEnumerableConstructible<ISsoChannel, X>`，ADR92 集合版守卫工厂）；channel 业务参数经 Options 注入不占 ctor IDomainUser 槽 |
| P9 | **协议差异收敛于 channel** | ADR §五.8 预留原则 | 核心 Federation 逻辑（accesscode/token2/应用注册）**不感知协议类型**——新增协议 = 新增 channel 实现，零核心改动 |
| P10 | **数据流归一** | WeChat 实证 | `(channel_id, external_uid) → uid` → token2——所有平台（OAuth 跳转/扫码/事件推送）统一归一，联盟锚点配合（`FederationAnchorOpenId` 写锚点 / `ISsoChannelMapService.LinkAsync` 映射） |

## 三、平台网关通用模式（WeChat 先例模板化）

> **模板即模式**：新平台按此 8 组件模板复制实现，协议差异仅落在组件 2（OAuth 通道）与组件 3/6（事件/验签）的协议细节，其余（客户端/配置/注册/依赖/测试）结构固定。

| # | 组件 | 形态（WeChat 实证） | 平台差异点 |
|---|------|---------------------|-----------|
| 1 | **出站客户端** `XxxApiClient` | typed client（ctor: HttpClient + IOptions + ILogger）；access_token L1 缓存 + SemaphoreSlim 并发锁 + 提前 5min 刷新；code→uid 一次性不缓存；用户信息响应裁剪 | 令牌端点 / 用户信息端点 URL 与响应结构 |
| 2 | **OAuth 通道** `XxxOauthChannel` | `ISsoChannel`（`ChannelType="{platform}_oauth"`）——authorize 构造（在装配层）+ 回调 code→external_uid（`AuthenticateAsync` 内 code 换标识）；AuthLevel=2 | 授权形态（跳转 vs 扫码）/ 用户标识字段（openid/unionid/user_id） |
| 3 | **事件/回调通道** `XxxEventChannel`（可选——平台支持入站推送时） | `ISsoChannel`（`ChannelType="{platform}_event"`）——入站验签 + 解密 + FromUserName→external_uid | 验签算法（msg_signature/AES/RSA）+ 事件体结构 |
| 4 | **验签逻辑类** `XxxEventCrypto`（可选） | 纯逻辑（收 `byte[]`/`Stream`）+ 恒定时间比对；**信任根一票否决** | 签名/解密算法（SHA1/AES-256-CBC/RSA-SHA256...） |
| 5 | **配置** `XxxOptions` + `XxxChannelConfig` | `[Options("TKWF:Federation:{平台}")]`——`Channels` 列表（ChannelId + 凭证 + 验签密钥）；凭证自持 | 平台特有凭证字段（AppId/AppSecret/私钥/Token/AESKey） |
| 6 | **用户信息 DTO** `XxxUserInfo` | 响应裁剪 record（对齐 Authentication 既有语义） | 用户信息字段（昵称/头像/手机/工号...） |
| 7 | **注册扩展** `XxxFederationServiceCollectionExtensions` | `AddXxxFederationChannels(this IServiceCollection, Action<XxxOptions>? = null)`——AddOptions().Configure + AddHttpClient<XxxApiClient> + TryAddEnumerableConstructible<ISsoChannel, XxxOauthChannel(/XxxEventChannel)> | 无（固定形态） |
| 8 | **测试** `Extension.Federation.{平台}.Tests` | `XxxTestHost : TestHostBase`（public BindScope 包装）+ OAuth 正负 + 信任根正负 + 探针门面生产路径枚举 | 平台协议样本（验签样本/响应样本） |

> **出站-only 精简形态（Oracle 评审 P1-6）**：组件 3（事件/回调通道）与组件 4（验签逻辑类）对**无入站回调平台**缺省——QQ（无事件推送）/ 支付宝出站面 / B站 / 小红书（设备授权无回调）/ **全部国外 OIDC 平台**均属此形态。出站-only 形态 = **组件 1/2/5/6/7/8**（出站客户端 + OAuth 通道 + 配置 + 用户信息 DTO + 注册扩展 + 测试）。信任根对应降级（见 §五信任根分档 + P1-5 澄清）——不因缺事件通道而缺失安全能力，安全重心转移至出站换取 + 验签。

**依赖接线（固定）**：
```xml
<!-- TKWF.Federation.{平台}.csproj -->
<ProjectReference Include="..\Federation\TKWF.Ext.Federation.csproj" />   <!-- 实现 ISsoChannel（Oracle P1-1） -->
<PackageReference Include="TKWF.Domain" Condition="'$(UseLocalFw)' != 'true'" />
<PackageReference Include="Microsoft.Extensions.Http" />                  <!-- typed client -->
<!-- ⚠️ 不引 AspNetCore（P6）——库纯逻辑，入站端点归装配层 -->
```

**slnx 接线（固定）**：`TKWF.Federation.{平台}` + `Extension.Federation.{平台}.Tests` 入 `TKWF.Extensions.slnx`；README 一览表加行（Tag 前缀 `Federation.{平台}/v`）。

## 四、平台清单与优先级（国内优先）

### 判据

| 判据 | 权重 | 说明 |
|------|------|------|
| **Web 授权流可行性** | 必选 | 平台必须提供**网页端 OAuth2/OIDC 授权**（跳转或扫码）——移动端 SDK 一键登录（华为/小米等）非 Web 联邦层，**排除** |
| **业务场景价值** | 高 | C 端：用户渗透率 / 交易场景关联（DMP 多商户）；B 端：企业员工登录（教育线/企业客户） |
| **微信生态互补** | 中 | 是否补充微微信未覆盖的用户群（QQ 用户 / 支付宝交易用户 / 钉钉企业员工） |
| **接入成本** | 中 | 协议成熟度 / 文档完备度 / 是否标准 OAuth2（vs 自研加解密） |
| **信任根可行性** | 必选 | 入站回调可验签（防伪造 external_uid）——无法验签的平台不接入 |

### 清单

| 优先级 | 平台 | 类型 | Web 授权形态 | 场景价值 | 信任根 |
|--------|------|------|-------------|---------|--------|
| 🔴 **第一批** | **QQ**（QQ 互联） | C 端 | OAuth2.0（PC/手机站点跳转；无扫码） | 国内老牌第三方登录，覆盖微信外的 QQ 用户群 | ⚠️ 无回调验签（仅 state） |
| 🔴 **第一批** | **支付宝**（开放平台） | C 端 | OAuth2.0（跳转 + 扫码 + H5 端内 JSAPI） | 电商/交易/政务强场景；DMP 多商户关联 | ✅ RSA2 双向签名 |
| 🔴 **第一批** | **钉钉**（开放平台） | B 端 | 扫码登录第三方网站 + H5 跳转（iframe DTFrameLogin 内嵌 + 跳转；新 OAuth2 协议） | 国内 To B 企业员工登录标配；教育线企业场景 | ✅ 事件回调 AES+sha1（官方建议 Stream Mode） |
| 🔴 **第一批** | **企业微信**（WeCom） | B 端 | 客户端内 Webview 跳转 + 桌面端扫码（@wecom/jssdk） | 企业员工身份，与微信生态互操作 | ✅ 事件/通讯录回调 AES+sha1 |
| 🟡 **第二批** | **B站**（哔哩哔哩） | C 端 | 标准授权码重定向（Web PC + H5） | 年轻用户群；内容生态 | ⚠️ 业务接口需 header 签名（x-bili-accesskeyid + Authorization）；mid 明文 UID 隐私需评估 |
| 🟡 **第二批** | **小红书**（开放平台） | C 端 | **设备授权扫码（RFC 8628）**——Web 无重定向，扫码+轮询 | 种草/电商人群（女性/新消费强） | ⚠️ 无 unionid（仅 open_id）；设备授权模型 |
| 🟡 **第二批** | **抖音**（开放平台） | C 端 | OAuth2.0（网页/扫码） | 内容/电商新场景 | 待核实 |
| 🟡 **第二批** | **飞书**（Lark） | B 端 | 扫码/OAuth + 通讯录 | B 端新锐（客户用飞书则接） | 待核实 |
| ⚪ 不建议 | 微博 | C 端 | OAuth2.0 | 社交场景衰退，价值低 | — |
| ⛔ 排除（非认证） | **知乎** | C 端 | **无账号登录**（仅内容/圈子 API，HMAC/静态密钥鉴权） | **非身份认证**——开放能力 = 内容 API（创作者/聚合），无第三方网站账号登录；未公开申请渠道 | — |
| ⛔ 排除（非认证） | **美团** | C 端/B 端 | **业务数据授权**（外卖/到店/团购场景子域；C 端走微信小程序中转） | **非身份联合登录**——OAuth = 业务授权（门店/订单/核销），非"用户用美团账号登录你的网站"；无通用 open_id | — |
| ⛔ 排除 | 华为/小米/OPPO/vivo 等设备厂商 | C 端 | 移动 SDK 一键登录 | **非 Web 联邦层**（无网页授权流） | — |

**第一批 = QQ / 支付宝 / 钉钉 / 企业微信**（C 端两极 + B 端两极，覆盖微信外的国内主流身份源）；第二批（B站/小红书/抖音/飞书）按需启动，模式已模板化，启动即复制。

> **非认证平台排除说明（用户洞察 2026-10-05）**：生活服务/电商类平台的 OAuth 侧重点在**营销/电商/核销等业务数据授权**（如美团外卖/团购、商家门店授权），未必是"身份认证"——与联邦互联"用户身份联合登录"目标不匹配（即便存在 OAuth 端点，语义 = 业务数据授权而非身份联合）。知乎类似（开放能力 = 内容 API 非账号登录）。详细调研见独立文档 [`docs/Federation/非认证能力平台调研.md`](./非认证能力平台调研.md)——避免未来重复调研。

## 五、协议差异矩阵（国内平台）

> 差异全部收敛于 channel 实现（P9），核心 Federation 逻辑零感知。矩阵基于各平台官方文档检索（2026-10-05，librarian bg_af8d3de9 等）；待核实项标注。

| 平台 | 授权形态 | authorize 端点形态 | token 端点 | 用户标识 | 用户信息 API | 验签机制 | scope 体系 | 联盟锚点对齐 |
|------|---------|-------------------|-----------|---------|-------------|---------|-----------|-------------|
| **微信**（已落地） | 跳转 + 扫码（公众号/开放平台） | `open.weixin.qq.com/connect/oauth2/authorize` | `sns/oauth2/access_token` | `openid`（应用维度）+ `unionid`（开放主体维度，申请开放） | `sns/userinfo` | 事件推送 `msg_signature` SHA1 + AES-256-CBC（信任根） | `snsapi_base`（静默，仅 openid）/ `snsapi_userinfo` | ✅ unionid 联盟锚点（`FederationAnchorOpenId` 已落地） |

### 5.1 联盟锚点跨平台映射策略（待设计——Oracle 评审 P1-1）

> **Oracle 评审（bg_03e79942）指出**：§五关键结论声明"锚点须 TKWF 侧自建映射"但**映射策略细节缺失**——这是实施前须设计的子项，本规划显式登记为**待设计项**（不阻塞规划获批，阻塞实施）。

**设计问题（实施前必须回答）**：
1. **FederationAnchorOpenId 语义**：锚点存什么？——某平台 unionid 作为"主锚点"（如微信 unionid）？还是 TKWF 自生成的全局 uid？（建议：锚点 = TKWF 内部 uid，各平台 `(channel_id, external_uid)` 映射表指向它——FederationAnchorOpenId 列仅承载"主平台锚点"加速直认，非唯一依赖）
2. **多平台绑定并合规则**：同一用户首次经微信登录（写锚点），再经 QQ 登录如何关联到同一 uid？——手动绑定？手机号/邮箱关联（QQ/部分平台无手机号——不可依赖）？扫码确认？外部身份源映射独立于认证流程？
3. **国内外混合归一**：同一用户经 Google（sub）与微信（openid）登录如何归一？——`ISsoChannelMapService` 映射表天然支持（`(issuer, sub)` 与 `(channel_id, external_uid)` 归一为本地 uid），但"首次归一触发的账号合并"流程（安全策略：禁止自动合并、需用户验证）须设计。
4. **映射表数据主权**：`PlatformAccountMapEntity` 扩展归 Authentication 主包（既有裁定）——多个平台网关库写入同一映射表的并发/冲突处理（同一外部 uid 映射到不同本地 uid 时的策略）。

**边界**：本规划只登记待设计项 + 建议方向，详细设计归各平台网关库立项时的配套设计文档。

**复核结论（2026-10-05 librarian 专项复核，补充）**：
- **QQ unionid** ✅ 官网自助申请（connect.qq.com 应用接口 → Unionid 申请；应用审核须"通过"；≤60 应用硬上限；邮箱渠道 2019-09-02 停止）——unionid 非默认，需预申请；
- **QQ 手机号/邮箱** ✅ 官方确认无获取接口（`get_user_info` 仅昵称/头像/性别/省市等，且官方明示性别/省市非真实数据）——QQ 联邦只能匿名账号关联（openId/unionId），无手机号绑定能力；
- **企业微信 user_ticket** ✅ 确认仅 96442（网页授权登录，`snsapi_privateinfo` + 成员在可见范围）返回；**98177（Web 登录扫码）不返回**——走 Web 登录拿不到敏感字段，必须走网页授权登录才有手机号/邮箱链路；
- **企业微信 unionid 与微信** ⚠️ 同一体系（unionid = 微信开放平台账号主体），但**双通道前置**（须微信侧小程序/服务号取 unionid + WeCom 授权取 external_userid）+ **主体一致性硬约束**（unionid 主体须 == WeCom 授权企业/服务商主体）——跨生态对齐成本高，非默认能力；
- **钉钉 SyncHTTP 超时** ⚠️ 两值均真实：**1200ms = URL 校验握手** / **2500ms = 日常事件响应**（官方两文档各写一值，未合并）——按最严 1200ms 实现；须"落库即返 success + 异步业务"（钉钉原文要求）；
- **钉钉旧协议（qrconnect/snsapi_login）** ⚠️ 文档 2021-12-21 迁历史、存量可用"暂不下线"，**未明示新应用可否申请**——不建议新接入，走新 OAuth2 协议；
- **支付宝手机号** ✅ 确认 `alipay.user.info.share` 默认不返回，**非独立接口**——须企业认证 + 挂"获取会员信息"功能包 + 申请 mobile 字段（1-3 工作日审核，行业类目限制，个人账户不行）——非稳定能力，设计上标记"需资质条件的可选增强"。

**信任根分档**（入站安全能力，影响通道形态）：
- **无回调验签**（QQ）——仅 state 防 CSRF，出站换取比对不足；身份可信度依赖"我方向平台发起的授权 + code 一次性"，入站方向（如未来事件推送）无验签能力
- **强双向签名**（支付宝）——RSA2 请求/响应/通知全签名，信任根完备
- **对称 + 特殊验签**（微信/企业微信）——appkey 对称 + 入站 msg_signature/AES
