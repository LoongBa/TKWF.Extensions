## 一、背景与动机

微信图文链路最小配置冒烟已闭环（v0.14.0 内置卡片 link 走测试端点 → v0.15.0 测试端点 HTML 化 → DMP 实机冒烟打通）。冒烟可用之后，测试反馈完整性问题浮出：

1. **Q1 类型不可区分**：内置"链路测试"测试卡片标题固定——发图片、点菜单、扫码触发的回复内容完全一样，无法从回复内容判断是哪个事件/消息类型触发（CLICK vs text vs SCAN），只能翻服务器日志对照。
2. **Q2 uid 恒空**：测试端点展示页 uid 恒空——即使 openid 已绑定平台账号（`EventOrchestrator` 能查到 uid），签票载荷 `UId` 写死空串，已绑定用户在测试反馈中与未绑定无差别，无法验证绑定链路是否生效。
3. **P2 转义无回归锁**：v0.15.0 commit message 宣称"`WebUtility.HtmlEncode` 防注入"，但**无回归锁测试**——XSS 防护面处于无锁状态，后续改动可能悄悄破坏。

本迭代三项改动互相独立，均为"小、聚焦、零风险"的测试设施增强。

## 三、设计

### 3.1 占位符扩展（Q1）——`WechatTemplateEventReplyHandler.BuildArticles`

`BuildArticles` 内新增局部函数 `Render(string? text)`，替换既有逐篇 `ReplacePlaceholders(...)` 调用（articles 数组路径与单图文兼容回退路径**两处统一**）：

```
Render(text) =
  ReplacePlaceholders(text ?? "", ctx.UId, ctx.OpenId, ctx.ChannelId, ticketUrl)   // 既有 5 参：{uid}/{openid}/{channel_id}/{channel_type}/{ticket}
    .Replace("{msg_type}", ctx.MsgType ?? "")
    .Replace("{event}", ctx.Event ?? "")
    .Replace("{type}",
        MsgType 分流：string.Equals(ctx.MsgType, "event", OrdinalIgnoreCase)
            ? ctx.Event ?? ctx.MsgType ?? ""     // 事件消息 → Event（CLICK/VIEW/subscribe/SCAN…）
            : ctx.MsgType ?? "")                  // 普通消息 → MsgType（text/image/voice…）
```

- **独立占位符** `{msg_type}`/`{event}`：业务模板可精确引用原始值。
- **合并占位符** `{type}`：按 **MsgType 分流**——`msg_type=event`（事件消息）→ 显示 Event（CLICK/VIEW/subscribe/SCAN）；普通消息（text/image/voice/...）→ 显示 MsgType。
- 内置"链路测试"卡片：`Title: "链路测试" → "链路测试·{type}"`、`Description: "点击验证完整回复链路" → "点击验证完整回复链路（{type}）"`——发图片见 `·text`、点菜单见 `·CLICK`。
- 业务模板**透明受益**：Render 应用于全部图文条目，业务模板同样可引用三个新占位符（v0.16.0 起）。

### 3.2 契约变更（Q2）——`BuildTestTicketUrlAsync` 尾部追加 `uId`（修正后签名）

## 四、关键设计决策记录

### A 段：为什么 `{msg_type}`/`{event}` 独立 + `{type}` 合并？

内置卡片只需要一个统一显示位表达触发源，业务模板则需要精确引用原始值——三个占位符并存：独立占位符保精确性，合并占位符保简洁。`{type}` 语义（事件→Event、普通→MsgType）与"用户直觉"对齐：普通消息没有 Event，显示 MsgType；事件消息的 MsgType 恒为 event，无信息量，显示 Event。

### B 段：`{type}` 从 `??` 合并修正为 MsgType 分流（关键设计修正）

**最初设想**：`ctx.Event ?? ctx.MsgType`（null 合并——Event 非空则用 Event）。**实测失败**：

```
WechatEventContext.FromChannelEvent（语义层重建，WechatEventContext.cs L220-232）：
    ["msg_type"] = msgType ?? "event"                        → 无 msg_type 归一为 "event"
    ["event"]    = rawEvent ?? evt.EventType                 → rawEvent（平台原始 wechat.Event）缺失
                                                                → 降级 evt.EventType（归一契约值）
WeChatEventChannel.cs L474：归一兜底 (eventValue ?? "unknown", …)
测试宿主 CreateEventDispatch（WeChatTestHost.cs L88）：EventType = eventValue ?? "unknown"
```

→ 语义层重建场景 `ctx.Event` **恒非空**（平台原始值 / 归一契约值 / `"unknown"` 兜底）——**文本消息 Event 也非空**（归一 `message` 或兜底 `"unknown"`）→ `??` 永不回退到 MsgType → 文本消息标题显示"链路测试·unknown"而非"链路测试·text"。

**修正**：MsgType 分流判断——`string.Equals(ctx.MsgType, "event", OrdinalIgnoreCase) ? ctx.Event ?? ctx.MsgType : ctx.MsgType`。附带确认：`FromChannelEvent` 对无 msg_type 的载荷归一为 `"event"`（L231 `msgType ?? "event"`）→ **事件消息恒命中分流条件**，分流判据可靠。核心结论：**不能以 Event 非空判定事件形态**（B 段教训已固化于实现注释）。

### C 段：`uId` 参数追加至 `ct` 之后（P4 教训落地 + Oracle 评审裁定）

v0.15.0 审核报告 P4 教训："接口扩展参数追加尾部"。本次 `uId` 参数位置经历一次评审修正：

- **4b19eac 原提交**：`(…, requestBaseUrl, uId, ct)`——`uId` 插在 `requestBaseUrl` 与 `ct` 之间（初稿直觉上"紧邻业务参数"）；
- **Oracle 评审裁定**：接口新参数须追加**最末尾**（所有既有参数之后，含 `ct`）——`(…, requestBaseUrl, ct, uId)`。理由：可选参数表是对外契约的可变形态，插中间会破坏既有调用点按位传参的稳定性直觉；追加尾部则既有调用（含按位省略尾部省略）零改动、二进制兼容面最大（C 段与《微信图文模板解析链》的 `requestBaseUrl` 追加位置保持同一纪律）。
- **调用点联动修正**：签名变化后 `ResolveTestTicketUrlAsync` 不能再按位传 `(…, ctx.UId, ct)`（uId 现在在 ct 后）——改为尾部全命名 `ct: ct, uId: ctx.UId`（CS8323：命名参数后不可跟位置参数；此处 `platformId: "wechat"` 命名在前，尾随参数须按位对齐或显式命名，全命名最稳妥）。

## 八、风险与边界

| 边界 | 说明 |
|------|------|
| 未绑定 null → 空串语义 | `uId=null` → 签空串 = 旧行为逐字节等价；展示页 uid 空仍与"未绑定"同现，但冒烟场景不依赖绑定（零配置冒烟照常），已绑定场景才有差异——语义无混淆风险 |
| Event `"unknown"` 兜底值认知 | 语义层重建的 `ctx.Event` **恒非空**（平台原始值 / 归一契约值 / `"unknown"` 兜底）——**不得以 Event 非空判定事件形态**（B 段教训）；`{type}` 已按 MsgType 分流正确处理；业务模板若直接引用 `{event}` 需知悉兜底值语义（事件消息下 `{event}` 显示实际 Event，普通消息下显示归一值/`unknown`） |
| 占位符对业务模板透明受益 | `{msg_type}`/`{event}`/`{type}` 应用于 articles 与单图文两路径——业务模板可引用；若业务模板恰好含字面 `{type}` 文本会被替换（与 `{uid}`/`{ticket}` 同类既有占位符语法约定，冲突风险低且可预期） |
| 转义覆盖面 | 转义仅覆盖测试端点 HTML 展示页字段（`WebUtility.HtmlEncode`，v0.15.0）；404/400 错误路径保持 JSON 契约（机器可读）不变；主要外部输入面（external_user_id/openid）已由 P2 回归锁锁定 |
| 测试宿主契约漂移 | `ILoginEntryService` 契约扩展需同步两测试宿主 Fake 签名——本轮已同步（修正后签名）；后续契约扩展继续遵循"参数追加最末尾"（P4 教训 + Oracle 裁定）降低同步成本 |
