## 一、目标与背景

MFA V0.2.2（当前已发布 tag）在**挑战-验证链**与**绑定生命周期**上存在三处安全缺陷（P0），本轮 v0.3.0 全部闭环。为什么必须修：

| # | 缺陷 | 攻击链 / 后果 | 违反 |
|---|------|--------------|------|
| MF-01 | **TOTP 同窗重放**：验证器门不记账，同一步内同一验证码经新票据可反复通过 | 攻击者窃得主凭证 + 一次 TOTP 码 → `RequestChallengeAsync` 拿新票据 → 同一步码再过一次 → **第二因素形同虚设**；频控只限暴力、不拦重放 | **RFC 6238 §5.2 MUST**（验证器不得接受已成功验证 OTP 的二次使用） |
| MF-02 | **pending 滞留阻断重绑**：绑定中途放弃（IsConfirmed=false 行）无清理路径 | 重绑撞 UX 唯一约束（`TKWFIX_MfaSecret_User_Method`）→ 未处理 DB 异常 500；唯一恢复路径 `DisableAsync` 用户不可预期 | 绑定生命周期语义（§3.2） |
| MF-03 | **SMS 挑战手机可覆盖**：挑战期 `context.Phone` 覆盖绑定 Phone | 手机所有权仅绑定验证一次；主认证泄露攻击者传**自己手机** → 验证码发到攻击者手机 → **第二因素失效**；与 README「换号走 Disable+Enroll」矛盾，指南未披露覆盖能力 | SMS 绑定语义（§3.3） |

目标状态（3 句内）：①TOTP 验证**同一时间步码只接受一次**（last-used-step 落库记账，RFC 6238 §5.2 合规，跨实例权威）；②绑定 pending 行**可预期替换**——重绑自动清滞留、UX 约束不再 500、既有 pending 停止阻塞；③SMS 挑战**恒发绑定手机**——`context.Phone` 覆盖能力移除，与 README「换号走 Disable+Enroll」一致，指南显著警示。

## 二、数据模型变更（MF-01 增列）

### 2.1 `MfaSecretEntity` 增 `LastUsedTotpStep` 列

| 项 | 定案 |
|----|------|
| 列名 | `LastUsedTotpStep` |
| 类型 | `long?`（可空——SMS 方法恒 null；TOTP 绑定激活后首次验证前为 null） |
| 位置 | `[FreeSql.DataAnnotations.Column(Position = 11, IsNullable = true)]`（紧跟 UpdateTime，追加不改既有列序） |
| 索引 | **不建**——无按列查询谓词（读写均按主键/用户），随 `TKWFIX_MfaSecret_User` 走；`CanUpdate=true`（默认，CAS 更新需可写） |
| DTO | `[DtoFieldIgnore]`——内部簿记（时间步计数器），不透出消费方（对齐 `EnrollTokenHash` 敏感簿记先例；防表面噪声/误用） |
| 文档 | 中文注释锚定语义：**最近一次验证成功所匹配的 RFC 6238 时间步**（`unixSeconds / TotpTimeStepSeconds`；时窗容差匹配时记录**匹配步**而非当前步）+ 拒绝条件 `matchedStep <= LastUsedTotpStep` |

### 2.2 兼容性（存量行零迁移）

- 存量 TOTP 绑定行 `LastUsedTotpStep = NULL`：断言 `NULL == 从未使用` → 升级后**首次验证无条件放行**（`LastUsedTotpStep is null` 分支），无行为回退。
- 建表路径：框架 `SyncTables` 统一托管（ADR49）——`IsNullable=true` 纯追加列，**消费方无手工 DDL 前置**；测试宿主 `MfaTestSupport.SyncStructure` 随实体声明自动同步。
- 挑战表（`TKWF_MfaChallenge`）/恢复码表（`TKWF_MfaRecoveryCode`）**零变更**。

### 2.3 SG1/xCodeGen 生成物重生成（AGENTS §8 纪律——实体型扩展固有）

## 三、P0 逐条闭环

### 3.1 MF-01 — TOTP 同窗重放（RFC 6238 §5.2）

#### 3.1.1 现状分析（代码位置已核实）

- `TotpMfaMethod.VerifyChallengeAsync`（TotpMfaMethod.cs **L150-176**）：L156 取 active secret → L161-163 票据归属校验（活动 = 未消费 + 未过期 + 属当前用户/方法）→ L166-169 解密 secret 后 `TotpGenerator.Validate`（L168 以 `DateTimeOffset.UtcNow` 当前步 ±`TotpClockSkewWindows` 时窗验证）→ L172 `Challenges.MarkConsumedIfActiveAsync` 原子单次消费（并发恰一成功）。
- `TotpGenerator.Validate`（TotpGenerator.cs **L108-123**）：`currentStep ± skew` 循环比对，返回 bool——**无"匹配步"输出**。
- 缺陷根因：挑战票据（ADR-MFA-挑战票据与验证模型）的一性 + 单次消费只防**同票据重放**；TOTP 无状态验证——票据行在 `TotpMfaMethod.RequestChallengeAsync`（L129-147）**每次挑战新建**（L137-145），攻击者重发挑战即可拿到新票据，同一步码在时窗内**再次验证通过**。`MfaService.VerifyChallengeAsync`（MfaService.cs L162-185）频控（L170-176，5 次/5min 滑动窗口）只限暴力尝试，不区分"同一码重放"。

#### 3.1.2 选项对比

| 选项 | 做法 | 优点 | 缺点 | 判定 |
|------|------|------|------|------|
| **A. last-used-step 落库记账（选定）** | `MfaSecretEntity` 增 `LastUsedTotpStep`（§2）；验证成功按**匹配步** CAS 条件更新（`WHERE Id=@id AND (LastUsedTotpStep IS NULL OR LastUsedTotpStep < @step)`）；`matchedStep <= LastUsedTotpStep` → 统一失败 | RFC 6238 §5.2 业界标准解法（FreeOTP/两因素库同型）；DB 权威**跨实例生效**（对齐挑战单次消费 `MarkConsumedIfActive` 先例）；NULL 存量兼容零迁移；时钟漂移容忍保留 | 每次验证多一条条件更新（更新已存在于激活路径，成本可忽略） | ✅ |
| B. 内存 used-steps 记账 | `ConcurrentDictionary<userId, step>` 记已用步 + 窗口清理 | 零表变更 | **单实例语义**（重启丢失、多实例绕过——与 C8 频控同边界但频控有 DB 化候选正名，记账无）；TOTP 第二因素价值高于发码频控，内存态不可接受 | ❌ |
| C. 收紧时窗 `skew=0` | 仅接受当前步 | 实现最简 | **不解决同步内重放**（同一步仍可复用新票据）；破坏时钟漂移容忍（设备慢 30s+ 即误锁死）；RFC 6238 §5.2 明确要求"验证器须记录 used OTP"——收紧窗口不是合规解法 | ❌ |

#### 3.1.3 选定方案与理由

**选定方案 A**：验证成功按**匹配步**记账 + CAS 条件更新（`<` 递增守卫），拒绝 `matchedStep <= LastUsedTotpStep`。理由：①合规——直接落实 RFC 6238 §5.2 MUST（同 OTP 二次使用被拒），且语义精确（拒绝的是一次"已成功使用的码"，不拒绝新步）；②跨实例权威——DB 列与挑战单次消费同存储语义，多实例部署下重放防护不降级（区别于 C8 频控的内存边界）；③时钟漂移容忍完整保留——`±skew` 窗口照旧，仅新增"用过即废"；④兼容零迁移——NULL=从未使用，存量行首验放行。

#### 3.1.4 实施细节（方法级）

1. `TotpGenerator` 增 `TryValidateWithStep(string code, string base32Secret, long unixSeconds, int timeStepSeconds, int digits, int skewWindows, out long matchedStep)`——内部复用 `ComputeForCounter` 循环（含恒定时间比较），命中即 `matchedStep = step` 返回 true；既有 `Validate` 改委托新方法（签名不变——TotpGeneratorTests 零影响，AGENTS 兼容纪律）。
2. `MfaSecretEntityDataService` 增委托方法：
   ```csharp
   /// <summary>CAS 更新 last-used-step（WHERE id + (null 或递增) 守卫——并发恰一成功；败者 0 行）。</summary>
   public Task<int> TryAdvanceLastUsedTotpStepAsync(long id, long matchedStep, CancellationToken ct = default)
       => EntityUpdateWhereAsync(f => f.Id == id && (f.LastUsedTotpStep == null || f.LastUsedTotpStep < matchedStep),
                                 f => new { LastUsedTotpStep = matchedStep }, ct);
   ```
   （`EntityUpdateWhereAsync` 为 `.g.cs` 已生成内部原子原语——ADR89 单语句 WHERE 谓词更新，零新增基座；**setColumns 用匿名类型 `new { LastUsedTotpStep = matchedStep }`（评审 P2-1 闭环）**——对齐同程序集 `MfaChallengeEntityDataService.cs` L49-52 `MarkConsumedIfActiveAsync` 的 ADR89 先例写法，不构造整实体。）
3. `TotpMfaMethod.VerifyChallengeAsync` 重排验证序（L165 后插入记账，消费保持 L172 原样）：
   ```
   ① L152-154 句柄解析 → ② L156-158 active secret → ③ L161-163 票据归属
   → ④ 解密 → ⑤ TryValidateWithStep（命中得 matchedStep；失败统一 false）
   → ⑥ 先 TryAdvanceLastUsedTotpStepAsync(active.Id, matchedStep)——affected != 1 → 统一 false（同/更低步已被并发用）
   → ⑦ 再 MarkConsumedIfActiveAsync（既有单次消费）→ ⑧ 成功
   ```
   - **竞态语义**：两并发（不同挑战、同步码）→ ⑥ CAS 恰一成功（败者 0 行返 false）；保守拒真（罕见：同窗两设备并发验同码仅一成功）记录为已知边界——安全侧（拒真 < 放重放）。
   - **失败路径**：⑥/⑦ 失败均走既有统一 false（不区分原因防枚举——MfaService 日志层承载 FailReason）。
4. **确认绑定（ConfirmEnroll）不动**：`ConfirmEnrollAsync`（L93-126）的一次码校验是激活流（单次消费挑战码），不写 last-used-step——激活与验证语义分离，避免首验被激活码污染。

#### 3.1.5 边界（兼容性/破坏性）

- **API 表面零破坏**：无公共签名变更（`Validate` 委托保持）；仅有行为收紧——同一步码二验返回 false（安全修复方向，记录为 RC 变更）。
- **一致性**：⑦ 消费失败（挑战被并发抢）时 ⑥ 已记账——该步码后续被拒（保守拒真，见 3.1.4 竞态语义）。
- **SMS 方法**：列恒 null、零路径消费——零影响。

### 3.2 MF-02 — pending 滞留阻断重绑（UX 唯一约束 500）

#### 3.2.1 现状分析（代码位置已核实）

- `MfaService.EnrollAsync`（MfaService.cs **L92-104**）：L97 仅查 **active**（IsConfirmed=true）判定已启用；命中才返回统一形态（防枚举），未命中直接 L100 委派方法。**pending（IsConfirmed=false）行不在守卫内**。
- `TotpMfaMethod.EnrollAsync`（TotpMfaMethod.cs **L60-90**）L82 / `SmsMfaMethod.EnrollAsync`（SmsMfaMethod.cs **L61-91**）L84：直接 `CreateAsync` 落新行——与滞留 pending 行撞 `TKWFIX_MfaSecret_User_Method` 联合唯一（MfaSecretEntity.cs L22）→ **未捕获 DB 异常自然传播 → 消费方 500**。
- 滞留成因：绑定中途放弃（未 Confirm）/ 发送失败（SmsMfaMethod.EnrollAsync L87 注释自认 pending 滞留）；`EnrollExpireAt` 过期只使 Confirm 失败（C3），**行不清理**；`GetPendingSecretAsync`（DataService L31-32）只被 Confirm 路径消费。
- **唯一恢复路径**：`DisableAsync`（MfaService.cs L124-141）L129-132 `GetByUserAsync` 全量删除（含 pending）——但语义是"解绑"（级联删挑战 + 恢复码，用户不可预期"我还没绑上为什么先解绑"）；README/指南**未披露**该恢复路径。

#### 3.2.2 选项对比

| 选项 | 做法 | 优点 | 缺点 | 判定 |
|------|------|------|------|------|
| **A. Enroll 编排先物理删 pending（替换语义，选定）** | `MfaService.EnrollAsync` 在委派前：`GetPendingSecretAsync(userId, method)` 非空 → `DeleteAsync(id)`（对 TOTP/SMS 统一出口，非方法内） | 攻击面最小（无新实体无新契约）；替换语义直观（新绑定覆盖上次未完成绑定，与 UX 唯一"一条绑定"一致）；pending 遗留自动收敛（重绑即清，无需后台清理任务） | 在途 pending（未到期）被删——语义=重新开始（发码/生成新 secret），接受（与消费方预期"重试绑定"一致）；并发 Enroll 双删同 row 会有一方 0 行——DeleteAsync 幂等（此处我方职责，先删后建原子性见 3.2.4） | ✅ |
| B. Confirm 失败/过期清理 + 定时清理任务 | ConfirmEnroll 失败（Token 过期）时删 pending + BackgroundJobs 周期扫 `EnrollExpireAt` 过期行 | 保留 pending 至自然终局 | **双重失效窗口**（至 Confirm 触发或任务周期运行——期间重绑仍 500）；引入后台任务依赖（BackgroundJobs 扩展间依赖 + 装配复杂度，v0.1.0 零依赖定调被破坏）；过期未 Confirm 的行仍需 Disable 恢复 | ❌ |
| C. 唯一约束降级为非唯一（歧义多行） | 放宽 UX，查询侧取最新 | 不再撞约束 | **破坏数据不变量**（"每用户每方法一条绑定"是双方法一实体模型根基，IsMfaEnabled/GetEnabledMethods 均依赖其确定性）；退化兜底，非修复 | ❌ |

#### 3.2.3 选定方案与理由

**选定方案 A**：`MfaService.EnrollAsync` 统一编排出口——委派前发现同 (userId, method) 存在 **pending** 行则**物理删除**（替换语义），再走既有发起路径。理由：①根除 500——重绑不再撞 UX 约束（无论 pending 是否过期）；②无新实体/无新契约/无后台任务——攻击面最小、保持 v0.1.0 零扩展间依赖定调；③用户可预期——"再次发起绑定 = 重新开始"（ABP/业界多因素绑定同语义），消费方无需被告知 Disable 恢复路径；④pending 遗留自动收敛——不再长驻 DB。

#### 3.2.4 实施细节（方法级）

1. `MfaService.EnrollAsync`（L92-104）在 L97 active 守卫后、L100 委派前插入：
   ```csharp
   // 替换语义（MF-02 闭环）：滞留 pending（未确认绑定）直接物理删除——重绑不再撞 UX 唯一约束
   var pending = await Secrets.GetPendingSecretAsync(userId, m.Method, ct);
   if (pending is not null)
       await Secrets.DeleteAsync(pending.Id, ct);
   ```
2. **DataService 侧无新增**：`GetPendingSecretAsync`（DataService L31-32）/`DeleteAsync`（**基类 `DomainDataServiceBase` L102** 的原子删除——`.g.cs` 生成基座直接暴露，非手写；评审 P2-7 闭环）均既有。
3. **并发边界**：先删后建非单语句原子（两并发 Enroll → 双删双建仍可一者撞约束）——与现实错位（同一用户双端并发绑定属异常编排，非攻击面：pending 行属该用户自身）；**失败仍统一自然传播**（不再新吞异常）。是否加"创建时容错重删一次"的二次兜底 → **本轮不做**（YAGNI，若评审要求可加 `EntityCreateAsync` 捕获唯一约束异常重删重试，记录为开放项）。
4. **Disable 语义不变**（L124-141 仍全量级联）；README/指南同步"重绑自动清 pending"（§五）。**SMS 场景重绑披露（评审 P1-1③ 闭环）**：pending 替换语义在 **TOTP 方法**下直接生效；**SMS 方法**下重绑路径先经 `SendCodeAsync`（L182-184）TTL 守卫——**发码成功后 5min TTL 内的再 Enroll 仍被"短信验证码已发送"拦截**（刻意防发码滥用，属预期语义非缺陷）；**TTL 过后（挑战过期）或发送未成功时替换语义照常生效**（pending 清 + 重新发码）——此语义写入 README/指南（§五）。

#### 3.2.5 边界（兼容性/破坏性）

- 行为变更方向：pending 滞留期间重绑从"500"→"自动替换"——正向修复，消费方零适配。
- 唯一约束保持（不降级）；激活行不受影响（active 守卫在前，已启用仍返回统一形态防枚举）。

### 3.3 MF-03 — SMS 挑战手机可覆盖（绑定语义绕过）

#### 3.3.1 现状分析（代码位置已核实）

- `SmsMfaMethod.RequestChallengeAsync`（SmsMfaMethod.cs **L132-146**）：L134 取 active → L138-142：
  ```csharp
  // 发送手机 = context.Phone 覆盖 ?? 绑定 Phone（MfaChallengeContext.Phone 支持重发场景指定）
  var phone = context?.Phone;
  var targetPhone = string.IsNullOrWhiteSpace(phone) ? active.Phone : phone.Trim();
  ```
  **挑战期可向任意手机发码**——`active.Phone`（绑定手机）仅作 fallback。
- 入口暴露：`MfaService.RequestChallengeAsync`（MfaService.cs L146-159）L155 原样透传 context；`IMfaService.RequestChallengeAsync` 契约（IMfaService.cs L39）+ `MfaChallengeContext.Phone`（IMfaService.cs L66）均有 Phone 槽。
- **攻击链**：手机所有权只在绑定验证一次（确认码发绑定手机）。攻击者窃得主凭证后 `RequestChallengeAsync(userId, "sms", new MfaChallengeContext(Phone: 攻击者手机))` → 验证码发到攻击者手机 → 第二因素失效。
- **文档矛盾**：README「绑定激活后 `Phone` 不可变（`CanUpdate=false`）——换号走 Disable+Enroll」（MfaSecretEntity.cs L51 + README 数据模型节）；指南 §3.3 挑战示例**未传 context**（`RequestChallengeAsync(userId, "sms")`）但也**未披露**覆盖能力——沉默的豁免口。
- **调用面核实（全仓 grep 实证）**：生产代码零处传 `MfaChallengeContext`（仅 `MfaService` 透传框架内，MfaService.cs L155）；测试 `_Tests/Extension.MFA.Tests/SmsMfaMethodTests.cs`（L60/76/97/109/149/184/189/214 全走 `ct:` 命名参数，无 context）；指南示例零覆盖使用。**破坏面 = 唯一内部豁免路径，无现网消费方依赖**。

#### 3.3.2 选项对比

| 选项 | 做法 | 优点 | 缺点 | 判定 |
|------|------|------|------|------|
| **A. 挑战期恒用绑定 Phone，忽略 context.Phone（选定）** | L138-142 改 `var targetPhone = active.Phone;`（context 参数保留——契约签名不炸，仅行为忽略）；若未来需"换号"走契约化 `ChangePhoneAsync` 或 Disable+Enroll（README 既有语义） | 绑定语义彻底闭合（所有权=绑定时验证一次，挑战只信绑定号）；破坏面最小——**行为收紧**（传了也恒发绑定号），已核对全仓零生产调用方传 Phone；对齐 README「换号走 Disable+Enroll」 | `context.Phone` 从此静默失效——已在使用该豁免的消费方（理论）行为变化；指南须显著警示（§五） | ✅ |
| B. 强制校验 `Phone == active.Phone`，不等则拒绝 | 保留覆盖能力但要求一致 | 保留"显式指定重发目标"表面能力 | **多一条攻击面/容错路径**（校验一致性无安全增益——绑定号是唯一权威，校验只是确认"没传错"）；错误码分支拓宽枚举面；无实际需求背书（全仓零调用方） | ❌ |
| C. 新契约 `ChangePhoneAsync` 换号 | 显式换号 API（旧号验证 + 新号绑定） | 功能演进褒义 | **范围膨胀**——换号是产品功能（v0.1.0 已裁"换号走 Disable+Enroll"），安全修复不应顺手开新面；需新实体/流程/测试 | ❌ |

#### 3.3.3 选定方案与理由

**选定方案 A**：挑战期**恒用绑定 Phone**（`active.Phone`），`context.Phone` 行为忽略（签名保留防二进制破坏）。理由：①绑定语义闭合——手机所有权一经绑定验证即锁定，挑战只信绑定号，攻击者的覆盖通道被物理移除；②零依赖消费方——全仓核实无生产调用方依赖该覆盖（见 §3.3.1 调用面核实），行为收紧即安全修复；③与既有文档契约一致——README「换号走 Disable+Enroll」从"被绕过"到"被落实"；④契约签名不炸——`MfaChallengeContext.Phone` 槽位保留（标记 Obsolete 理由见 3.3.5），非破坏性 API 变更。

#### 3.3.4 实施细节（方法级）

1. `SmsMfaMethod.RequestChallengeAsync`（L138-142）改：
   ```csharp
   // 挑战手机恒用绑定 Phone（MF-03 闭环——context.Phone 故意忽略：手机所有权仅绑定验证一次，
   // 挑战期可覆盖 = SMS 绑定语义绕过；换号走 Disable+Enroll（README 语义））
   var targetPhone = active.Phone;
   if (string.IsNullOrWhiteSpace(targetPhone))
       return null; // 无可用手机（激活绑定应有 Phone，防御）
   ```
   `context` 参数保留（签名不变——`IMfaMethod.RequestChallengeAsync` 契约零改动）。
2. `MfaChallengeContext.Phone` 属性补 `[property: Obsolete("挑战目标手机恒为绑定手机——context.Phone 被忽略；换号走 Disable+Enroll")]`（编译器级警示——静态导出调用面违约，消费方改传即见警告；**目标必须为 `[property:]`（评审 P2-2 闭环）**——`MfaChallengeContext` 是位置记录，裸 `[Obsolete]` 默认只标**构造参数**、编译器隐式生成的 `Phone` 属性不受警示，消费方 `ctx.Phone = ...` 仍静默编译；`[property: Obsolete]` 才命中属性槽位，赋值/读取即见 CS0618；**代码不删**——删属性 = 契约破坏性变更，本方案拒绝）。
3. `MfaService.RequestChallengeAsync`（L146-159）不变（透传 context——方法层忽略，编排层零改动）。
4. **同步修订 XML 文档注释（评审 P1-3 闭环）**：`IMfaService.cs` **L65** `MfaChallengeContext` 类注释原文"挑战上下文——SMS 可覆盖发送手机号"与修复后的忽略语义**自相矛盾**——改为"**挑战上下文（历史槽位——`Phone` 已废弃，恒用绑定手机号，勿再传入）**"，与步骤 2 的 Obsolete 语义一致，消除"文档契约仍宣称覆盖能力"的残留入口。

#### 3.3.5 边界（兼容性/破坏性）

- **破坏性声明**：行为变更（RC）——挑战期传入非绑定 `context.Phone` 从"发到指定手机"→"忽略并仍发绑定手机"；经查全仓无生产调用方传 Phone（仅理论豁免路径），列 RC + 指南显著警示；`[Obsolete]` 警示后续版本可升级为删除（另行迭代，本方案不动）。
- **TOTP 方法**：无 Phone 语义，零影响。
- **绑定流不受影响**：`SmsMfaMethod.EnrollAsync`（L61-91）仍接受 `MfaEnrollContext.Phone` 绑定新号（绑定语义不变）。
