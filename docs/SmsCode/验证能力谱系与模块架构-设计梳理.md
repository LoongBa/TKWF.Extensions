# 验证能力谱系与模块架构 —— 设计梳理（SmsCode/Captcha 立项前置）

> **版本**：v0.1（2026-11-15）
> **状态**：架构裁定已评审（oracle-pro6 + oracle3 双 Oracle 合流），待 M0 开发方案评审
> **关联**：DMP-Lite 需求转达（v0.10.8 手机号验证码登录与 CHAPTCHA 扩展模块）、`docs/变更记录.md`
> **触发**：DMP 短信验证码登录 + CHAPTCHA 立项时，框架侧要求"从全局+前瞻角度寻求综合最优解"，不局限于当前需求

---

## 1. 背景与目标（3 句）

DMP-Lite 转达了"手机号验证码登录 + CHAPTCHA 人机验证"扩展模块需求（P1，UserH5 前端已对接等待契约）。在为该需求冻结契约前，框架侧重新审视：**验证能力是几乎所有业务系统的日常重复工作**，不应只为本需求做一个一次性模块，而应从全局+前瞻角度梳理"验证"的完整谱系、模块边界与未来演进路径。本文档是架构梳理的正式化产出——它不替代 M0 开发方案，而是方案的**谱系基座**：回答"做一个什么形状的模块才不会被下一次需求推翻"。

## 2. 验证能力谱系全景

### 2.1 三大正交族

验证的本质 = 对一个命题的信任度裁决。按"验证的问题"分三大族（**正交，非互斥**）：

| 族 | 验证命题 | 子族 / 子模式 | 本仓库现状 |
|---|---|---|---|
| **A. 身份因子族（OTP）** | "是不是你"（持有者证明） | A1 投递码：短信 / 邮件 / 语音 / 推送；A2 生成码：TOTP（时间同步）/ HOTP（计数）/ 恢复码（预生成清单）；A3 无码票据：魔术链接 / 扫码确认 | ✅ 已覆盖：A1 短信（AuthCenter 首因素 + MFA 二因素两处）、A1 邮件（仅作密码重置通道，无独立码引擎）、A2 TOTP（MFA）、A2 恢复码（MFA）；缺：语音 / 推送 / 魔术链接 |
| **B. 人机族（CAPTCHA）** | "是不是人"（非自动化） | B1 本地生成：图形文字 / 数学题 / 语义题；B2 交互挑战：滑块 / 点选；B3 无感行为：reCAPTCHA v3 评分 / 极验无感 / 设备指纹；B4 工作量证明：Friendly Captcha | ❌ **完全空白**（本立项从零引入） |
| **C. 授权票据族** | "此操作被授权过" | 一次性票据 / OAuth 授权码 / 兑换码（本仓库 TrustCenter / AuthSurface / OAuthTicket 已覆盖） | ✅ 已覆盖——**本次不重复造** |

> **关键结论 1**：C 族已成熟，不在本次范围；A 族已有丰富先例**但无统一底座**；B 族是本次的主要增量——**CAPTCHA 与 OTP 正交**（OWASP 因子桶：验证"是否人类"与验证"是否持有人"是不同因子桶，"CAPTCHA+短信"不构成 MFA，但先后组合是防刷短信预算的标准定式）。

### 2.2 两种子模式分界（决定 SPI 面的形态）

| 面向 | 分界 | 说明 |
|---|---|---|
| **OTP 族** | **校验归属**：本地自存全栈（生成+存储+校验，SHA256+CAS）vs 发送即服务（阿里云/腾讯云——校验归你）vs 校验也服务化（Twilio Verify——校验归供应商） | 中国渠道基本是"发送即服务"，校验必须在自家服务端完成（红线）；Twilio Verify 形态是**同门面换实现**，非配置开关 |
| **CAPTCHA 族** | **生成/校验归属**：本地自托管（零依赖，最弱——易被 solver）vs 第三方托管（reCAPTCHA / Turnstile / 极验 / 腾讯云——**服务端二次校验为唯一权威**） | **中国市场约束**：reCAPTCHA / Cloudflare Turnstile 大陆不可用 → 第三方 v1 目标 = 极验 / 腾讯天御 / 阿里云验证码 |

### 2.3 场景矩阵

| 场景 | 验证目标 | 常用方式组合 |
|---|---|---|
| 注册 | 真人 + 地址真实 | CAPTCHA 门控 → 邮箱/短信验证地址 |
| 登录（首因子） | 本人 | CAPTCHA 门控（防刷预算）→ 短信码 / 邮件码 / 魔术链接 |
| 登录（2FA） | 更高置信 | TOTP / 推送 / 短信（NIST 偏好：TOTP/推送 > SMS） |
| 找回/重置 | 本人 | CAPTCHA 门控 → 短信码 / 邮件码 / 扫码票据 |
| 绑定/解绑手机邮箱 | 地址真实 | 短信码 / 邮箱码 |
| 敏感操作（支付/改密） | step-up | 短信码 / TOTP / 推送确认 |
| 防刷匿名接口（投票/抽奖/表单/爬虫） | 真人 | CAPTCHA（独立于一切业务场景） |
| 高对抗（抢购/批量） | 高级程序对抗 | Arkose / 极验 + 设备指纹 / 行为评分 |

### 2.4 涉及"多次验证先后组合"的需求形态（本次及可预见）

| 形态 | 说明 | 编排归属 |
|---|---|---|
| **前置门控**（CAPTCHA→OTP 发送） | 防刷短信预算——**本次 DMP 需求** | 扩展门面内（安全默认是领域决策，禁消费方自装门序） |
| 认证链（密码→2FA） | MFA 已解决（登录编排归消费方） | 消费方 / 既有门面 |
| 找回链（CAPTCHA→短信→改密） | 复用前置门控 + 既有 PasswordResetService 场景 | 消费方编排，扩展提供原子能力 |
| 因素切换（短信→语音 fallback / 登录短信 vs 绑定邮箱） | Twilio 同 verification 跨通道复用；本仓 v1 **不建**（defer，见 §4.3） | v1.1+ |

## 3. 外部借鉴调研结论

> 三路调研（本仓盘点 / ABP 与 .NET 生态 / CAPTCHA 与 OTP 市场）已并行完成，要点记入本节；完整报告留存会话记录与调研 agent 输出。

### 3.1 本仓库既有 14 种验证形态（盘点实证）

| 形态 | 扩展 | 核心机制 |
|---|---|---|
| 短信验证码（首因素、场景化） | AuthCenter | SHA256+单次消费+TTL5min+Scene+频控 |
| 短信登录编排 / 密码重置三通道 / OAuthTicket | AuthCenter | 同上 + 频道抽象 + PKCE 5min |
| TOTP / 短信二因素 / 挑战票据 / 恢复码 | MFA | RFC6238 + per-user×method 独立实现 |
| 密封票据 / 授权码 | TrustCenter | 120s + CAS + AES-GCM payload |
| 兑换码 | AuthSurface | SHA256+CAS+频控 |
| 密码重置（平行实现） | Account | userName-keyed（已知双实现） |
| 框架基座 | TKW.Framework.Utility/Domain | IRateLimitCheck / ISealedTicketService / ISymmetricKeyProvider |

> **关键结论 2**：短信码是**唯一**被"首因素+二因素"复用的渠道；但存在 **`ISmsSender`（AuthCenter）与 `IMfaSmsSender`（MFA）两套投递抽象并存**、频控语义分叉（phone×scene vs per-user×method）的实证——即"语义不同→独立实现"在仓库内部已是既有裁定（MFA Oracle Q1）。新立项落地后将成为**第三个短信引擎**（rule of three 触发评估信号）。

### 3.2 ABP 及生态借鉴

| 来源 | 可借鉴点 |
|---|---|
| ABP Framework | CAPTCHA 捆在 Account 内（reCAPTCHA 包装 + 每场景开关 UseCaptchaOnLogin/Registration/ForgotPassword——**场景参数化**）；2FA 三 Provider + `ISmsSender` 通道抽象；社区 `EasyAbp.Abp.VerificationCode`（`IVerificationCodeManager.GenerateAsync(codeCacheKey, lifespan, config)`）——**通用短码原语**（多模块需求涌现后产物，非前瞻设计） |
| ASP.NET Core Identity | 内置 TokenProvider 集合（DataProtector/Email/Phone/Authenticator，按名注册 `AddTokenProvider(name, type)`）——**Provider 集合注册形态** |
| Django | allauth 场景即设置（`ACCOUNT_EMAIL_VERIFICATION_BY_CODE_ENABLED`、`*_MAX_ATTEMPTS`、`*_TIMEOUT`）——场景参数化非场景模块化；**captcha 为独立可插拔 app**（django-simple-captcha / django-recaptcha） |
| Spring | CAPTCHA 前置 Filter（认证前）+ 校验后单次删除；community spring-security-otp（Provider+Filter+Tokenstore+SendStrategy） |
| Twilio Verify / Cognito / Firebase | 校验服务端化 / 挑战状态机 / 自适应认证——服务形态，本仓自建引擎不追此形态（扫码类 A3 除外） |

> **关键结论 3**：生态定式 = **薄原语（社区级）+ 正交能力模块（OTP/CAPTCHA 分家）+ 上层编排归领域门面**；CAPTCHA 因对抗性持续演化 + 第三方生态主导 + 独立失败域，**永远不内置为框架/模块的附属开关**。

## 4. 架构裁定（双 Oracle 合流，即本设计的骨架）

> 裁定依据：谱系全景（§2）+ 本仓盘点（§3.1）+ 生态证据（§3.2）+ 市场证据（§3.3 会话记录）。裁定的提出与理由已由 oracle-pro6 / oracle3 双 Oracle 评审合流，标记为 **b+ 共识**。

### 4.1 模块形态（Q1）：b+ —— DMP 先行，但引擎写为"未来统一核心的胚胎"

- **否决 (a) 现在建统一核心（TKWF.Ext.Verification）**：14 形态的价值在**语义**不在 150 行原语（统一只收原语=捕获 ~10% 价值 + 新增协调成本；强收语义撞 MFA Oracle Q1 先例）；单消费者抽象必错冻结（oracle2 冻结"5 次/15min"已与 AuthCenter"次/小时"分叉——第二数据点即证）；ABP 终态本身非大一统。
- **否决 (c) 现在建 Verification.Abstractions 契约包**：契约需 ≥2 实现方或跨扩展消费者才付租；今日唯一真实跨扩展边 = SmsCode→Captcha，用 `Captcha.Abstractions` 承接即可；错冻结 > 不冻结。
- **b+ 含义**：本模块引擎从第一天写成**通用形态**——场景注册表驱动（scene→策略：码长/TTL/频控/是否 CAPTCHA 门禁），零 DMP 特有逻辑进引擎；落地后即第三个短信引擎（rule of three 达标），同时它是未来 `TKWF.Ext.Verification` 的**候选内核本体**，届时收敛=机械上移而非重写。

### 4.2 CAPTCHA 模块（Q4）：拆为独立 `TKWF.Ext.Captcha`（+ Captcha.Abstractions），即日拆分

- **推翻"捆绑进 SmsCode 模块"的子裁定**（C1 主裁定不变：独立立项，不并入 AuthCenter）。
- 理由：① **第二消费者设计期即出现**——AuthCenter 注册/找回匿名面是已知无防护缺口（ABP/Django/OWASP 三证据）；捆绑将迫使 AuthCenter 将来引用商家会员域模块（方向错误，且 TKWF0022 届时还得再拆）；② OWASP 因子桶：CAPTCHA 消费者集合=一切匿名表单，≠短码消费者；③ 对抗性持续演化需独立失败域与版本节奏；④ WeChatChannels 拆分先例同型。
- 形态：`TKWF.Ext.Captcha`（主包：`ICaptchaProvider` SPI + 自建图形 Provider v1 + 验证门面 + Options）+ `TKWF.Ext.Captcha.Abstractions`（契约包，零实体零 SG1）；SmsCode 经 `Captcha.Abstractions` **可空依赖**消费（`[TKWFExtensionDependency]`，沿 AuthCenter⇄Emailing.Abstractions 先例）；消费方双白名单。CHAPTCHA challenge 端点契约随迁本模块。**CAPTCHA 场景无关**（只发/验挑战，"哪些场景要门禁"归消费方场景注册表）。

### 4.3 引擎写法与收敛出口（Q2/Q3/Q5）

- **内部共享原语**：`VerificationCodeEngine`（internal，非 public API）——码生成 + SHA256 散列 + TTL + 单次消费 + attempt-cap + scene 作用域；**不提取框架**（3 消费者未全到）、**不引用 AuthCenter**（避免耦合）。
- **三面 SPI**（锁形状不锁媒介）：
  - ① 挑战面 `ICaptchaProvider`（Generate→不透明挑战载荷+token；Verify→`{passed, score?}`——**score 作可选字段现在就入结果形状**，评分型 Provider 门面按场景阈值裁决，只换实现不改契约）；
  - ② 投递面 `ISmsSender`（send-only，名字与 AuthCenter 对齐但**类型独立**——物理发送方可同时实现两者；生产未装配→503 fail）；
  - ③ 生命周期面（v1 本地自存；外部验证服务型=同门面另实现，非配置 if-else）。
- **塑形决策（防返工清单）**：
  1. 注册形态：`DomainServiceBase`+`AddConstructibleService`；多 Provider 用 `TryAddEnumerableConstructible`（ADR92）；
  2. **频控键前缀独立**（`smscode:`，严禁复用 AuthCenter `sms-ip:` 桶——不同域不同配额）；
  3. 场景白名单=契约常量（v1 闭集：login 及 DMP 所需），扩场景=加注册表条目不加引擎；
  4. 频控沿 AuthCenter 已验证形状：subject×scene COUNT 窗 + IP 点检查桶（框架 `IRateLimitCheck`）；oracle2 冻结默认值（60s/日 10/5 次·15min）不动；
  5. 实体沿 SmsRecord 形状（SHA256 + IsVerified 单次消费 + IP + Scene，只增语义）；⚠️ 红线：模板/内容/JSON 列显式 `[MaxLength(-1)]`，标识列定长；
  6. **租户维度归消费方**（`ISmsCodeScopeResolver`——消费方注入 scope 前缀如 `merchant:{UId}`，模块保持租户无关）。
- **收敛出口 ADR 必含**：谱系表指针、否决 (a)/(c) 理由、触发器（见 §4.3.1 精确化后版本）、名字预留（`ISmsCodeService`/`ISmsSender`/场景注册表形状），收敛零改名。

### 4.3.1 MFA/AuthCenter 收敛裁定（X'——延迟迁移、契约留门，2026-11-15 oracle-pro5）

> 用户讨论点：「短信验证核心是验证手机号，场景（登录/2FA/找回）只是应用之一」→ 是否应让 AuthCenter/MFA 直接调用 SmsCode（X）而非第三处独立实现（Y）。oracle-pro5 裁定 **X'**：否决 X 与 Y-forever。

**决定性判据 = 主语语义（非迁移成本）**：
- 「验证手机号是原子」对 **A 族第一因素分支**成立（login/register/bind/reset：subject=phone=投递目标）；**对 MFA 第二因素不成立**——MFA 挑战时刻验证的是「已登记因素的持有」（README 铁律：挑战手机恒绑定 Phone、context.Phone 忽略、所有权仅绑定验证一次、换号走 Disable+Enroll）：subject=user×method、按 challengeId 句柄验证、per-user 频控键、投递目标=绑定手机、生命周期挂 Enroll/Disable 级联。MFA 与 DMP 共享的只是**机制**（CSPRNG/SHA256/TTL/CAS/恒时比较），不是同一**原子能力**。X-now 要求 SmsCode v1（契约已按唯一消费方 DMP 冻结）立即长出 subject 泛化 + 句柄验证 + 每用户频控——P1 关键路径上为 MFA 猜测接口。
- **Y-forever 被实证否决**：两份既有拷贝**已漂移**——AuthCenter `SmsVerificationService` L158 `string.Equals(Ordinal)`+大写 hex vs MFA `FixedTimeEquals`+小写 hex（核码实证，2026-11-15）。同一机制一个发布周期内分叉出安全相关差异；MFA 后续演进候选（DB 跨实例频控 / TTL 重发 TOCTOU 唯一约束消除 / 挑战清理）全是机制级改动——每多一份拷贝，每次机制修复多一处回植。

**触发条件（可测试）**：
- **主触发（需求侧）**：MFA 某迭代范围触及 `SmsMfaMethod.SendCodeAsync`/`VerifyChallengeAsync` 的**机制路径**（码生成/哈希/TTL/单次消费 CAS/频控机制，非其上 MfaService 编排；已知候选：DB 跨实例频控 / TOCTOU 唯一约束 / 挑战清理）且 SmsCode 已发布 v1.0+ → 该迭代内改为委托 SmsCode，禁止就地补丁第二引擎（边际迁移成本≈0：机制修复本来就要写）。
- **加速触发（安全侧）**：任一机制级安全修复需回植 ≥2 个引擎（SmsCode / AuthCenter SmsVerificationService / MFA SmsMfaMethod）→ 该安全发布内全量收敛。
- **不采纳**「今天共享抽象、MFA 内部实现之」变体（只买签名统一、零去重收益，无跨包调用点预冻结接口违背仓先例）；MFA 形态契约验证由代码评审断言承担。MFA README 旧收敛出口「评估 Authentication.Abstractions 拆包」**supersede**——出口已具体化为 SmsCode 引擎（未来 TKWF.Ext.Verification 体）。AuthCenter 同构问题同款处理（同触发器、非本次迭代）。

### 4.4 门控编排（Q6）：扩展级门禁，消费方零接线

- `SendCodeAsync(scene, phone, captchaToken)` 门面签名**内联门禁**：scene.RequiresCaptcha=true → 先经 Captcha 门面验 token，**通过才生成+发送**（Casdoor 保预算先例 + Spring pre-auth 位序）；缺失/无效→错误码 fail-closed；**场景要求门禁但 Captcha 未装配→fail-closed 守卫异常**（禁静默跳过）。
- 禁止消费方自装门序——安全默认是领域决策（配置分层原则），交消费方组装必然有人装错（先 send 后验=泄露预算）。
- **多场景=单引擎+场景注册表**（Django scene-as-config）；每场景一引擎=复制频控/TTL/消费语义，正是本裁决要消灭的重复。
- **不建 `IVerificationGate` 可组合链 / 不建"验证流"抽象 / 不建因素切换会话**（v1 只有一组门，抽象是过度设计；v1.1 当 2+ 门场景出现时再提炼，对齐 `IFederatedLoginOrchestrator` 抽取时机先例）。

## 5. 模块装配地图（v1 冻结形态）

```
消费方（DMP）
├── [TKWFEnabledExtension] SmsCodeExtensionInitializer<>
├── [TKWFEnabledExtension] CaptchaExtensionInitializer<>
├── 实现 ISmsSender（腾讯云/阿里云 send-only，或 dev 回显）
├── 实现 ISmsCodeScopeResolver（merchant:{MerchantUId}）
└── 登录编排门面（消费方自建：MemberInfo 命中 → VerifyCode → 建会话 → IdentitySession，对齐 MemberLoginService 先例）

TKWF.Ext.SmsCode（主包）
├── ISmsCodeService : IDomainService        ← 门面（SendCodeAsync 含 captchaToken 门参 / VerifyCodeAsync）
├── ISmsSender / ISmsCodeScopeResolver      ← 消费方实现（TryAdd）
├── SmsCodeService : DomainServiceBase      ← AddConstructibleService 注册
├── VerificationCodeEngine（internal）      ← 共享原语（生成+SHA256+TTL+单次消费+attempt-cap+scene）
├── SmsRecordEntity + DataService（SG1）    ← 落库（CodeHash/Scene/IsVerified/ExpireAt/IP）
├── SmsScenes 常量                          ← v1 闭集（login 等，消费方可扩展）
└── SmsCodeOptions（TKWF:SmsCode 节）       ← TTL/频控默认/门禁开关

TKWF.Ext.Captcha（主包）
├── IChaptchaService : IDomainService       ← 门面（IssueAsync/VerifyAsync）
├── IChaptchaProvider : IDomainService      ← SPI（TryAddEnumerableConstructible 多注册）

└── CaptchaOptions（TKWF:Captcha 节）       ← EnabledProviderType/TTL/attempts

├── IChaptchaProvider / IChaptchaService    ← SPI + 门面契约
└── DTO（ChaptchaChallenge / ChaptchaVerifyResult{passed, score?}）
```

## 6. 冻结边界（NOW vs LATER）

### NOW（v1，DMP P1 交付）

- `TKWF.Ext.SmsCode`：通用引擎（场景注册表驱动）+ 门面（内联 CAPTCHA 门禁）+ `ISmsSender`/`ISmsCodeScopeResolver` + 频控键 + 实体 + snake_case 错误码（oracle2 九项契约冻结项，challenge 端点除外随迁）
- `TKWF.Ext.Captcha`（+ `.Abstractions`）：SPI + 自建图形 Provider + 门面 + challenge 端点 + Options
- 4 份 ADR：① 模块边界与 CAPTCHA 拆分（本裁定）；② 引擎原语与收敛出口（§4.3）；③ 场景注册与租户维度归属（§4.3.6）；④ Captcha SPI 与子模式（分数/音频/滑块 defer 记录）

### NOW｜SmsCode v1 ADR 今日冻结项（保 X 后续廉价，不承诺 X——oracle-pro5 裁定）

1. **引擎键控**：存储与引擎 API 以不透明 `Subject`+`Scene` 键控（v1 恒 subject=phone），投递目标独立参数（v1 恒=phone）；**列名 Subject 不叫 Phone**；频控键 `{scene}:{subject}`（+`smscode:` 前缀）；活跃行唯一性按 (Subject,Scene)。——「手机所有权是原子」兑现为引擎形态的**唯一必要泛化**；若焊死 Phone，b+ 的「未来 Verification 体」承诺即空洞。
2. **错误契约分层**：引擎返回类型化结果；snake_case 错误码映射只住 DMP 门面/端点层——MFA 未来委托**不继承 DMP 错误契约**。
3. **依赖方向**：恒消费方→SmsCode；本迭代**不建** Abstractions 包（无跨扩展消费者不拆包，WeChatChannels/Federation.Abstractions 同律），但门面 public 面禁含 DMP 专有类型——未来抽包=移文件零重设计。
4. **发送渠道**：v1 自持 sender 契约（Phone+Content 形）；MFA 迁移时一行适配器衔接 `IMfaSmsSender`。
5. **评审断言（MFA 人格验收）**：SmsCode v1 代码评审须核引擎可表达：subject=user×method、行 Id 即验证句柄、per-user 频控键、投递≠subject——以评审代真实消费者完成契约验证。
6. §4.3.1 触发器表 + 本裁定记录入收敛出口 ADR。

### LATER（显式推迟，触发器见 §4.3.1）

- `TKWF.Ext.Verification` 统一核心及任何 `Verification.Abstractions`（触发器三选一）
- 腾讯/极验/阿里 CAPTCHA 适配器（DMP 选型后，纯增量经 SPI）
- 外部验证服务型 OTP 引擎（Twilio Verify 形态，同门面换实现）
- 音频 CAPTCHA（无障碍，载荷变体不阻断）、滑块/行为验证、设备指纹、魔术链接、独立邮箱码引擎、Passkey（谱系已记录）
- AuthCenter/MFA 迁移（永不强迫，走各自迭代，收敛=换内部引擎实现 + 对外门面签名不变，非破坏）
