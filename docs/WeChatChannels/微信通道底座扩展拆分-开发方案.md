## 一、背景与动机

### 1.1 架构前提（DMP 定案：分库多租户）

DMP-Lite 为**分库多租户**架构（1 平台库 + n 租户库）。微信运营能力两个消费侧：

- **平台侧（Platform）**：平台库管理**接入平台的公众号通道**（多通道设置/凭证/事件链路）——仅用 `IChannelConfigService` 1 门面 + 手写端点 `/api/admin/wechat-channels`
- **租户侧（Merchant）**：租户库，商户对**指定通道**内容运营（素材/菜单/回复规则/统计/日志）

### 1.2 现状问题

`WeChatOperations`（V0.8.1 待发布，11 实体、10 门面）单模块混装两类能力：平台侧仅有通道管理 + 事件链路诉求，却被迫装配运营扩展全链（Federation.WeChat 出站/转发网关/8 运营门面/11 表全建）——**依赖面浪费 + 权限纠缠（`WeChatOperations.Query/.Manage` 两键共用）+ 版本线耦合**。

### 1.3 方案演进

| 候选 | 描述 | 结论 |
|------|------|------|
| A. 单模块 + Mode 配置 | `WeChatOperationsOptions.Mode` 装配时裁剪 | ❌ 平台被迫打包运营全链；权限共键无法隔离；违背"装配即模式"哲学（用户裁定不勉强） |
| B. 拆两扩展 | 通道底座下沉独立扩展，运营扩展依赖复用 | ✅ **定案**（本方案） |

---

## 二、目标

1. **通道底座独立**：新扩展 `TKWF.Ext.WeChatChannels`（平台多通道管理）——平台侧只装通道底座，零运营依赖
2. **运营扩展保留**：`WeChatOperations` 运营 8 门面 + 转发网关，通道能力**复用** WeChatChannels（不重复实现）
3. **装配即模式**：平台装配 WeChatChannels = 平台模式；租户装配 WeChatOperations = 运营模式——**无 Mode 配置项**（P3 能力即注册行为）
4. **权限隔离**：`WeChatChannels.Query/Manage`（新键）与 `WeChatOperations.*`（不变）独立授权
5. **（本迭代不做）** GUI 装配面拆分、运营实体租户兼容——见 §四 D9 单列与 D8 衔接

## 四、设计原则评估吸收（2026-11-05，Sisyphus 评审）

> 上轮对 DMP v0.10.5 方案执行 tkwf-design-principles 逐条对表（元原则 → P1-P10 → 错误模式）。结论：**拆分方向附条件通过；D9 否决单列**。修订如下：

### 4.1 否决项 D9：运营实体租户兼容（IEntityTenant）——**单列迭代，不在本方案实施**

**原因（实证）**：DMP 转达声称"分库模式零影响（无租户上下文不注入谓词）"——仅覆盖读路径表象。主框架实证（`DomainDataServiceBase.cs`）：

- **写路径守卫无条件激活**（与租户过滤注册无关）：创建 `HandleAuditOnCreate` L498-521 / 单条更新 `VerifyTenantOnUpdateAsync` L360-386 / 批量更新 `VerifyTenantOnBatchUpdateAsync` L395-426 / 删除 `VerifyTenantOnDeleteAsync` L449-464——`entity is IEntityTenant` 即触发，**无租户上下文一律抛 `DomainException`**（ADR34 P1-3"写必窄"，SystemActor 亦须 `ExecuteInTenantAsync`）
- 读路径 `TenantGlobalQueryFilter` 为 opt-in（不注册不过滤 ✅）——但写守卫无 opt-in

**落地后果（若按转达文本实施）**：事件入站链路（`/feberation/event/{channelId}`，不在租户路径下）handler 写 `InteractionLog` 抛异常 → **事件回复链路崩溃**；后台作业（转发日志回写）抛异常；AdminUI 非 `/m/{mid}/` 路径写操作 500。

**单列迭代前置条件**（实施时另立方案，本方案不触碰）：① 事件帧租户识别（channelId → TenantId 映射，消费方 `IContextExtractor`）；② 后台作业显式 `ExecuteInTenantAsync`；③ 消费方路由全覆盖审查；④ **AdminUI 写操作租户上下文存在性审查**（非 `/m/{mid}/` 路径写操作须有租户来源，O6 闭环）。D10 平台表声明（通道表不实现 IEntityTenant）**保留**——通道表平台级语义与租户无关，可于本方案立即生效（但当前通道表本就不实现，零动作）。

### 4.4 namespace 决策记录（O5 定案）

- **选择**：`TKWF.Ext.WeChatChannels`（契约包 + 主包跨程序集同 namespace）
- **理由**：P2 扩展身份单一事实源——WeChatChannels 是**完整实现扩展**（实体/DataService/Web/Initializer），非 Federation.Abstractions 式纯契约包；沿用旧 namespace 使两个扩展身份共源，诊断/审计/文档归属模糊。消费方一次性 using 迁移成本（Platform 手写端点 + Merchant AdminUI 页面）低于长期身份混淆成本
- **影响**：消费方 `using TKWF.Ext.WeChatOperations` → `using TKWF.Ext.WeChatChannels`（仅通道面类型；运营面类型仍 `TKWF.Ext.WeChatOperations`）；SG3 重生成；REST 路由不变（相对 RestRoute + 新模块前缀）

### 4.5 评审确认无问题项（保持 DMP 定案）

- **D5 路由定案**：`[ApiExpose(RestRoute="/channels")]` 已是相对路径——下沉后 `[assembly: ExtensionModule("WeChatChannels","wechat-channels")]` 自动得 `/api/wechat-channels/channels`，RestRoute 常量零改动。**选新段**（不留旧 `/wechat-ops/channels` 兼容尾巴——P5 显式决策 + 禁止为兼容留尾巴）。消费方 SG3 重生成面接受
- **D6 权限键**：`WeChatChannels.Query/Manage` 新键（`[RequirePermission]` 字符串随门面下沉同步改）；运营 `WeChatOperations.*` 不变
- **D7 版本线**：WeChatChannels.Abstractions V0.1.0 + WeChatChannels V0.1.0（新包首发）→ WeChatOperations V0.9.0（破坏性大版本：V0.8.1 先发布再拆，避免交叠）→ 消费方适配
- **门面命名保持** `IChannelConfigService`（不因下沉改名）——消费方仅换 using 命名空间/项目引用，不换方法名（O5 定案 namespace 迁 `TKWF.Ext.WeChatChannels`，见 §4.4）
