## 一、背景与现状

### 1.1 需求来源

公众号运营扩展：**配置信息管理 + 菜单管理（两阶段）+ 消息运营（全类型回复配置）**。完整需求：

- **菜单管理**：读取当前生效菜单（`get_current_selfmenu_info`）/ 全量覆盖发布（`menu/create`）/ 本地基准 JSON + 历史备份版本
- **消息运营（全消息类型回复配置）**：
  - **菜单（CLICK）Key→回复内容映射表**（**独立于菜单结构，改映射不重新发布菜单**）
  - **关键字自动回复**（text 消息，完全/包含匹配 + 默认兜底；开启开发模式后微信后台关键词自动回复失效，必须自建）
  - **关注欢迎消息配置**（subscribe 事件回复内容——文字/图文）
  - **各种消息的回复配置**（image/voice/video/shortvideo/location/link 消息 + SCAN 扫码 + VIEW/VIEW_MINIPROGRAM 菜单事件——均可配置回复）
  - **素材库**（文本 + 图文，被欢迎语/关键词/Click 复用）
- **统计（订阅、取消订阅）**：关注/取关事件计数与趋势（按 channel 按日）
- **日志与查询**：用户交互消息日志 / 菜单发布操作日志
- **基础运维**：AccessToken 状态查看（只读）/ 黑白名单（可选）/ 配置启停开关
- **GUI**：阶段一无 GUI（技术代录入 JSON/配置）；阶段二 GUI 可视化编辑器——**本仓库先不做，出拆分方案交 DMP-Lite 项目实现，磨合后拆回**

### 1.2 现状链路（Federation.WeChat V0.4.0）

```
微信 POST → /feberation/{platformId}/event[/{channelId}]
  → ResolveChannelAsync → VerifyUrlAsync（GET echostr 握手）
  → AuthenticateAsync（msg_signature + AES 解密，信任根一票否决）
  → OrchestrateAsync（uid 只读查询富化）
      → WeChatEventChannel.HandleEventAsync（V0.4.0 编排放权：验签+解密+富化 __decrypted_xml → 返回 null）
      → EventOrchestrator 双桶迭代（W3 绑定桶优先 → ChannelType 桶回退）
          → IEventReplyHandler（IChannelSpecificEventReplyHandler 精确绑定）
              → WechatEventReplyHandlerBase 二级分发（OnSubscribe/OnText/OnClick/OnImage/OnVoice...）
                  → BuildTextReply / BuildNewsReply（多图文信封）
  → Results.Text(reply.Content, reply.ContentType)（200 空回复兜底）
```

### 1.4 缺口清单（本方案解决的问题）

| # | 缺口 | 现象 | 根因 |
|---|---|---|---|
| G1 | **菜单/素材出站 API 缺失** | 无菜单读取/创建/删除出站能力 | `WeChatApiClient` 仅 OAuth/用户信息三方法 |
| G2 | **多公众号运营配置无 DB 事实源** | 运营扩展需按 ChannelId 管理多公众号 | `WeChatOptions` 仅静态配置节 |
| G3 | **凭证解析不可插拔** | DB 凭证（加密）无法到达出站调用 | `ResolveCredential` private 只读 Options |
| G4 | **template handler 仅单图文** | 需求"图文 pattern + 支持多图文"不满足 | `WechatTemplateEventReplyHandler` 构造单篇 |
| G5 | **回复规则无数据底座** | 欢迎语/关键词/Click 映射/全消息类型回复无实体模型 | 无运营扩展 |
| G6 | **订阅/取关无统计** | 需求"统计（订阅、取消订阅）"无数据 | 无运营扩展 |
| G7 | **交互/发布日志无落库** | 运营排查/追溯无数据 | 无运营扩展 |
| G8 | **AccessToken 状态无只读视图** | 运维需看有效期/异常 | 缓存内存态，无查询面 |
| G9 | **handler 桶位/优先级未定义** | DB 规则优先 + template 兜底语义无法保证（同桶迭代顺序未定义） | Oracle P0——双 handler 注册关系未明确 |

### 3.2 平台库增强（Federation.WeChat V0.4.1）

#### 3.2.1 菜单出站 API（不引 Senparc，自实现）

**裁定**：不引入 Senparc.Weixin.MP——平台库保持"轻量纯库"定位（`TKWF.Federation.{平台}` 全部自实现：QQ/支付宝均无第三方协议库）；但**借鉴 Senparc 的 JSON 结构**（`Entities.Menu`：`ButtonGroup`/`SubButton`/`SingleClickButton`/`SingleViewButton` 等字段命名与微信官方一致）设计自有 poco，保证协议对齐。

**新增**（`WeChatApiClient` 增方法，token 自管不动——显式传 token 调出站）：

| 方法 | 微信端点 | 职责 |
|---|---|---|
| `Task<string> CreateMenuAsync(string accessToken, string menuJson, CancellationToken ct)` | `cgi-bin/menu/create`（POST 全量覆盖） | 提交菜单 JSON，成功返回（`errcode==0`），失败抛异常含微信错误码 |
| `Task<WeChatSelfMenuInfoResult?> GetCurrentSelfMenuInfoAsync(string accessToken, CancellationToken ct)` | `cgi-bin/get_current_selfmenu_info` | 拉当前生效菜单，返回结构化 poco |
| `Task DeleteMenuAsync(string accessToken, CancellationToken ct)` | `cgi-bin/menu/delete` | 删除当前菜单 |

**自有 poco**（`WeChatMenuPoco.cs`——**提交/返回结构命名区分**，Oracle P2）：

```csharp
// 提交结构（menu/create——raw JSON string 透传，自由形态编辑器输出）
// 创建菜单：CreateMenuAsync(token, json)——json 为完整按钮结构（button 数组），仅验证合法 JSON + button 非空
// 返回结构（get_current_selfmenu_info——结构化 poco，供展示/回填编辑器）
public sealed record WeChatSelfMenuInfoResult(int IsMenuOpen, WeChatSelfMenuInfo? SelfMenuInfo);
public sealed record WeChatSelfMenuInfo(WeChatMenuButton[] Button);
public sealed record WeChatMenuButton(
    string Type, string? Name, string? Key, string? Url,
    string? MediaId, string? ArticleId, string? AppId, string? PagePath,
    WeChatMenuButton[]? SubButton);                            // sub_button 递归子菜单
```

> **菜单 JSON 处理策略**：菜单结构自由形态（click/view/miniprogram/media_id/article_id/view_limited 等类型参数各异）——**提交 = raw JSON 透传**（编辑器自由形态），**返回 = 结构化 poco**（展示/回填编辑器）。两类结构命名区分（提交 string / 返回 poco），消除混淆。

#### 3.2.2 `IWeChatCredentialResolver`（凭证解析可插拔）

**裁定**：凭证来源演进链 Options → DB 加密 → 未来 KMS/Secret Manager——可插拔契约是必然抽象方向。契约落**平台库**（凭证来源是平台库演进方向，扩展只负责注册实现）。

```csharp
// 平台库新增契约
public interface IWeChatCredentialResolver
{
    Task<WeChatChannelConfig?> ResolveAsync(string appId, CancellationToken ct = default);
}
// 缺省实现（平台库内——DI 注册，非 ctor 内 new）：读 WeChatOptions.Channels 按 AppId 匹配（现状语义迁移）
public sealed class OptionsWeChatCredentialResolver(IOptions<WeChatOptions> options) : IWeChatCredentialResolver
{ ... }
```

- **DI 注册缺省实现**（Oracle P1）：`AddWeChatFederationChannels()` 内 `TryAddSingleton<IWeChatCredentialResolver, OptionsWeChatCredentialResolver>()`——ctor 收**非空** `IWeChatCredentialResolver`（容器编译期保证注入），**不做 ctor 内 fallback**（避免绕过 DI 生命周期管理）
- `ResolveCredential` private 改为经 resolver 调用（异步）
- 扩展注册 DB 实现：`TryAddEnumerableConstructible<IWeChatCredentialResolver, DbWeChatCredentialResolver>`（DB 命中 → 解密返回；未命中 → **委托缺省 Options 实现**——DB 权威 + 降级）

#### 3.2.3 `WechatTemplateEventReplyHandler` 多图文升级（V0.4.1）

**裁定**：多图文是通用能力——平台库 V0.4.1 小版本增强（V0.4.0 刚发布版本线干净）。

### 3.3 业务扩展（WeChatOperations V0.1.0）

#### 3.3.1 实体模型（SG1）

| 实体 | 表名 | 关键字段 | 性质 |
|---|---|---|---|
| `WeChatChannelConfigEntity` | `TKWF_WeChatChannelConfig` | ChannelId(唯一)/AppId(唯一索引)/**AppSecret 密文**/**Token 密文**/**EncodingAESKey 密文**/DisplayName/Remark/IsEnabled/ChannelType | 基础配置（DB 权威） |
| `MaterialEntity` | `TKWF_WeChatMaterial` | Name/Content(文本)/Title/Description/Url/PicUrl(图文)/Kind(Text=1/News=2)/IsEnabled | 素材库（**全局共享，规则引用**） |
| `ReplyRuleEntity` | `TKWF_WeChatReplyRule` | ChannelId/SceneType(Subscribe=1/Keyword=2/Click=3/Image=4/Voice=5/Video=6/ShortVideo=7/Location=8/Link=9/Scan=10/Default=11)/**TriggerKey**(关键词 or 菜单 key or 空——场景型规则为空)/MatchMode(Exact=1/Contains=2，仅 Keyword)/MaterialId(引用)/ReplyText(直接文本——优先于素材)/IsEnabled/SortOrder | **通用回复规则表**（全消息类型） |
| `SubscriptionStatEntity` | `TKWF_WeChatSubscriptionStat` | ChannelId/StatDate/SubscribeCount/UnsubscribeCount/NetCount(净增) | 订阅统计（按 channel 按日） |
| `MenuSnapshotEntity` | `TKWF_WeChatMenuSnapshot` | ChannelId/MenuJson(本地基准，text 大文本)/UpdatedAt | 菜单基准（本地权威） |
| `MenuVersionEntity` | `TKWF_WeChatMenuVersion` | ChannelId/VersionNo/BeforeJson(备份)/AfterJson/Operator/PublishedAt/Result(Success/Fail)/ErrorCode/ErrorMsg | 菜单发布历史（版本回滚，**含操作人——合并发布审计**） |
| `InteractionLogEntity` | `TKWF_WeChatInteractionLog` | ChannelId/OpenId/MsgTime/MsgType/Content/TriggerType(Subscribe/Keyword/Click/Image/.../Default/None)/ReplyContent/**ReplyMaterialId(可空)** | 交互日志 |
| `MenuPublishLogEntity` | `TKWF_WeChatMenuPublishLog` | ChannelId/Operator/OperateAt/Action(Read/Create/Delete/Test)/Remark | **操作审计（不含 JSON 内容——JSON 归 MenuVersion）** |

> **Oracle P1 实体职责修正**：
> - **ReplyRuleEntity 泛化**（原 KeywordRule/ClickReplyMap/WelcomeConfig 三实体合并为一张通用规则表）——覆盖需求"各种消息的回复配置"：SceneType 区分场景（Subscribe 欢迎语 / Keyword 关键词 / Click 菜单映射 / Image/Voice/Video/ShortVideo/Location/Link 消息回复 / Scan 扫码 / Default 兜底），TriggerKey 承载关键词/菜单 key（场景型规则为空），MatchMode 仅 Keyword 场景适用。**Click 映射独立于菜单结构语义保留**（SceneType=Click 的规则修改不触发 menu/create）。
> - **MenuVersion vs MenuPublishLog 职责分离**（Oracle P1）：MenuVersion = 菜单**内容版本**（before/after JSON + 发布人/结果——回滚数据源）；MenuPublishLog = **操作审计**（who/when/action=Read/Create/Delete/Test，不含 JSON——JSON 归 MenuVersion）。发布动作两者同时记录（MenuVersion 记内容 + MenuPublishLog 记审计）；非发布操作（读取/删除/测试）只记 MenuPublishLog。
> - **MenuSnapshot vs MenuVersion 一致性**（Oracle P2）：发布成功后同步更新 MenuSnapshot（本地基准 = MenuVersion 最新 AfterJson 快照）+ MenuVersion（版本追加）——同一事务保证一致。
> - **InteractionLog 加 ReplyMaterialId**（Oracle P2）：可空——追溯回复了哪个素材。

> **凭证加密**（Oracle P1 安全五补充）：AppSecret/Token/EncodingAESKey 三字段 AES-GCM 单段密文（base64(nonce‖cipher‖tag)，对齐 AuthSurface V0.2.0 规范）——keyed `ISymmetricKeyProvider`（`SymmetricKeyProviderKeys.WeChatOperations` 自建常量，Initializer `AddKeyedSingleton<FileSymmetricKeyProvider>` 生产 fail-fast/开发随机，对齐 AuthCenter E4）：
> 1. **密钥轮换**：密钥文件替换 + 重启（FileSymmetricKeyProvider 构造即加载）；未来 KMS 接管路径（resolver 实现替换）
> 2. **多实例部署**：多实例共享密钥文件（共享存储）或各实例部署同一密钥文件；文档说明
> 3. **DTO 投影**：`IChannelConfigService.GetAsync/ListAsync` 返回 DTO **不含** AppSecret/Token/EncodingAESKey（或 mask）——密文不回显
> 4. **出站日志脱敏**：access_token 经 query string 传参——HttpClient 日志/URL 日志脱敏（access_token 值不落日志）
> 5. **异常消息**：解密失败/凭证不存在异常消息不含明文（如"凭证解析失败"而非"AppSecret=xxx 解密失败"）
>
> **明文永不入库/不进日志**。

> **素材全局共享**：Material 无 ChannelId——规则按 MaterialId 引用（一个素材多规则复用）。

#### 3.3.2 门面服务（DomainServiceBase + AddConstructibleService）

| 门面 | 关键方法 | 说明 |

#### 3.3.3 事件回复：`WeChatOperationsReplyHandler`（内部组合 template 兜底）

```
渲染三层：规则层（DB 按 ChannelId 过滤）→ 素材层（DB 内容库）→ 渲染层（handler 内部组合）
```

**Oracle P0 选项 A 吸收**：`WeChatOperationsReplyHandler` **内部组合 template 兜底逻辑**——DB 规则未命中时直接读 `Channel.Extra["news_reply"]` template 返回，**不依赖编排器迭代顺序**，消费方无需额外注册 `WechatTemplateEventReplyHandler`（它仅供未启用运营扩展的场景使用）。

- 继承 `WechatEventReplyHandlerBase`（平台基类，V0.4.0 既有）——零协议改动
- **分发映射**（全消息类型）：

| 基类虚方法 | 规则场景（SceneType） | 逻辑 |
|---|---|---|
| `OnSubscribeAsync` | Subscribe | 读 ReplyRule(ChannelId + Subscribe) → 素材/文本回复；**无规则 → template 兜底**（`Channel.Extra["news_reply"]`）→ 再兜底 → null；**同时记 SubscriptionStat（订阅 +1）** |
| `OnUnsubscribeAsync` | — | **记 SubscriptionStat（取关 +1）**——回复被协议门控吞掉（副作用可做） |
| `OnTextAsync` | Keyword / Default | 读 ReplyRule(ChannelId + Keyword) → 完全匹配优先 → 包含匹配（MatchMode）→ **未命中 → Default 兜底规则** → **无规则 → template 兜底** → null |
| `OnClickAsync` | Click | 读 ReplyRule(ChannelId + Click + TriggerKey=EventKey) → 素材/文本回复；未映射 → null（不回复） |
| `OnImageAsync`/`OnVoiceAsync`/`OnVideoAsync`/`OnShortVideoAsync`/`OnLocationAsync`/`OnLinkAsync` | 对应消息类型 | 读 ReplyRule(ChannelId + SceneType) → 回复；无规则 → template 兜底 → null |
| `OnScanAsync` | Scan | 读 ReplyRule(ChannelId + Scan)（可含 TriggerKey=场景值）→ 回复；无规则 → null |
| `OnViewAsync`/`OnViewMiniProgramAsync` | — | 微信直接跳转，无回复（null）——**不做回复规则** |
| `OnDefaultAsync` | — | null（不回复不拦截——协议门控事件已由基类吞掉） |

- **channel 过滤**：所有规则读按 ChannelId 过滤（多公众号数据隔离）
- **触发类型记录**：每次回复记录 InteractionLog（TriggerType=命中场景）——运维排查
- **通道级差异**（代码级，不走动态加载）：消费方编译期注册 `IChannelSpecificEventReplyHandler`（W3 绑定桶）覆盖特定 channel 的差异化业务逻辑；DB 只存规则数据，不存 handler 类型名
- **template 兜底实现**：handler 内复用平台基类 `ReadNewsTemplate`（`Channel.Extra["news_reply"]`）+ `BuildNewsReply`——内部组合，无编排器依赖

#### 3.3.4 两源并存（DB 权威 + Options 降级）

**裁定**：启用带 DB 的运营扩展后，**DB 数据为权威**；Options 退为引导/降级（未启用扩展 / DB 无记录时兜底）。

```
接入点 ①：IWeChatCredentialResolver（平台库契约）
  DbWeChatCredentialResolver：DB 命中（ChannelId 查 WeChatChannelConfigEntity）
    → 解密凭证返回；未命中 → 委托 OptionsWeChatCredentialResolver（缺省实现——现状语义）

接入点 ②：IChannelSource（通道配置投影）
  DbWeChatChannelSource：读 DB（WeChatChannelConfigEntity → ChannelConfig 投影）
  → 注册为 IChannelSource 集合元素（CompositeChannelRegistry 遍历聚合）
  ——CompositeChannelRegistry 既有语义：DB 优先 → 静态回退（对齐 Federation SsoChannelRegistryEntity 先例）
```

**Oracle P1 聚合机制明确**：`CompositeChannelRegistry` 聚合机制 = **按注册顺序遍历全部 `IChannelSource`，取第一个命中**（DB 源注册在前 → 优先；Options 源注册在后 → 回退）。`WeChatOperations` Initializer 的注册顺序保证：`DbWeChatChannelSource` 在 `WeChatChannelSource`（平台库 Options 源）**之前**注册（`AddWeChatFederationChannels()` 已注册 Options 源——扩展 Initializer 在其后 `TryAddEnumerable` 追加 DB 源，**追加语义 = 遍历顺序在 Options 源之后**）。

> ⚠️ **顺序依赖核查点（实施验证）**：`TryAddEnumerable` 追加的 DB 源若遍历序在 Options 源之后，则"DB 优先"不成立——需验证 `CompositeChannelRegistry` 是否支持显式优先级（或调整注册时机保证 DB 源在前）。若既有实现无法保证，扩展 Initializer 用 `Insert(0, ...)` 式注册或 CompositeChannelRegistry 增 `Priority` 机制（实施时核查——见 §九 验收 7）。

#### 3.3.6 VEntity 读模型（阶段二 GUI 建，阶段一可选先建日志视图）

> **端点理解纠正（用户 2026-10-18）**：②领域扩展的业务方法经 `[GenerateController(FromDataService=true)]` **自动生成 REST 端点**（SG1 原生——对齐 AuditLogging/Identity/Notifications 先例）；③表现层扩展（DMP-Lite）是**页面/前端资产**而非后端端点。既有 `WeChatOperationsWebExtension`（13 手写端点）V0.1.0 已发布保持不动，网关模块**不新增手写 WebExtension**——路由规则/下游/日志/状态管理经门面 `[RequirePermission]` 标注 + `[GenerateController]` 暴露。

**需求本质**：本系统作为微信消息回调唯一入口，支持配置消息路由规则对接存量运营系统。借鉴成熟平台（NeuChar/微管家/第三方 SaaS 公众号平台）设计——回调入口只做**验签、解密、消息解析、路由规则判断、幂等校验**，分两条分支：

1. **主响应分支**（决定本次回复）：
   - 分支 A：本地处理（默认）——本系统生成被动回复，**异步抄送消息副本给下游（可选）**；主线程立刻返回 XML，下游投递异步执行不占 5 秒窗口
   - 分支 B：同步代理转发（少量场景，开关控制）——命中规则转发原始请求，下游返回 XML 作响应；**超时熔断**，下游超时切本系统兜底回复
2. **副分支：异步抄送（推荐）**——无论主分支 A/B，命中规则将消息副本异步投递下游（存储/业务记录/工单/CRM 同步），**下游无权回复微信用户**

**行业最佳实践**：绝大多数对接旧运营系统场景用**异步抄送**（不占 5 秒窗口、稳定性最高）；同步透传只做特殊路由（如客服关键词直接切旧客服系统接管）。

**三种转发策略**（运营配置选择）：
1. **本地处理 + 异步抄送**（推荐默认）——主线程本地业务 + 被动回复返回微信；异步队列投递副本下游（记录/工单/CRM）
2. **同步透传**（接管本次回复）——转发原始请求，下游返回 XML 作回复；超时降级本系统兜底
3. **前置处理后同步透传**（谨慎使用）——验签/日志/过滤/改写后转发下游；超时风险高，仅少量特定场景

**关键约束**（硬性）：
- 微信回调同步请求 **5 秒时限**，单次请求只能返回**一份回复**给微信
- 同步转发超时风险 → **熔断降级**
- **幂等是硬性需求**：微信自动重试回调，不做幂等会造成下游重复收到同一消息——基于 `MsgId` / `FromUserName+CreateTime` 去重
- 转发的原始报文需与微信回调格式一致（XML，**兼容加密模式**），对接下游存量运营系统

**运营可配置项**：模块全局开关 / 消息匹配规则（消息类型、事件类型、文本关键词包含/完全匹配）/ 下游目标地址与超时 / 熔断降级策略 / 幂等开关 / 转发全链路日志（原始消息、匹配规则、转发模式、下游请求结果、异常记录）

**优先级排序**：先交付本期核心运营能力（配置/素材/规则/菜单/统计/日志）→ 消息网关独立迭代（不阻塞、不耦合——网关规则命中时调用本期门面能力，反之本期 handler 不受网关影响）。

### 十·二、同步透传与熔断降级机制（设计定稿——分支 B：SyncProxy）

**① 同步透传流程（⚠️ P0-1 选 A 已裁定——SyncProxy 暂缓实施，设计如下）**：命中 SyncProxy 规则后，网关在 `WeChatOperationsReplyHandler` 主响应分支接管本次回复——将微信回调原始报文（`__decrypted_xml` 明文 XML）POST 转发至 `DownstreamEndpointEntity.Url` → 下游返回 XML → 原样作为本次被动回复返回微信（text/news 信封由下游自组）。微信回调同步请求 **5 秒时限**、单次请求只能返回**一份回复**——转发成功即提交下游 XML；任何失败路径只允许降级本地兜底，绝无双回复（若转发已提交成功则不再降级）。
> **P0-1 裁定（选 A）**：下游 XML **原样透传**与平台基类 `BuildReplyResult`（恒走 `BuildNewsReply`/`BuildTextReply` 重组）存在双重信封矛盾——根因是 `WechatReplyPayload`（`Federation.WeChat` 平台库）无 RawXml 逃逸口。**正解：平台库 `Federation.WeChat` V0.4.2 增 `WechatReplyPayload.RawXml` 可选字段 + `BuildReplyResult` 优先检查非空则直接返回（改动面 1 字段 + 3 行检查，存量零破坏）**——非主框架转达（该类型在本扩展仓库平台库）。**实施节奏：AsyncCopy/LocalOnly/幂等/熔断先行，SyncProxy 待平台库 RawXml 就绪后补**（验收 #5/#6）。

**② 超时熔断**：超时预算须给兜底留余量——微信 5 秒内须完成"转发判定 + 本地兜底渲染"（规则查库+模板封包 ≤1s），故 `Endpoint.TimeoutSeconds` **默认 2 秒、上限强制 ≤3 秒**（配置超限拒收 fail-fast，防运维误配吞掉兜底窗口）；实现经 linked `CancellationTokenSource.CancelAfter(TimeoutSeconds)` 传入 `SendAsync`（typed client 的 `HttpClient.Timeout` 为全局属性，不能按端点设）。超时/不可达 → 记 `MessageForwardLogEntity(Status=Timeout/Fail)` → 降级本地兜底。熔断状态：**自建轻量三态（关→开→半开→关）**，每 DownstreamEndpoint 一个内存计数对象——连续失败 ≥N（默认 3）开闸 → 开窗期（默认 60s）直接走本地兜底不转发 → 窗口期满放行单次**半开探测**（成功清零回关、失败重置开窗）。**裁定**：主框架 HealthCheck（无熔断原语）/RateLimiting（Web 层限流非服务可用性）均不适用，自建内存三态——同步透传场景量小、探测成本可忽略；简化两态需定时强制恢复，会在窗口后盲目超时一次浪费微信窗口，三态语义清晰；纯内存进程重启即清零（对齐 `WeChatApiClient` 纯内存缓存先例，不落库）。

**③ 降级链**：下游超时/不可达/返回非 XML/返回错误 → 依次尝试：①本地回复规则（复用既有 handler 本地分支——ReplyRule 按原消息类型全链：规则→素材→文本）→ ②template 兜底（`Channel.Extra["news_reply"]`）→ ③`Options.DefaultReplyText`——即对齐既有渲染三层，降级 = 回退本地分支，网关只负责"先转发、失败回退"，不复制渲染逻辑。

**④ 原始报文转发裁定**：**透传 `__decrypted_xml` 明文 XML 原样转发，不重新组装**。理由：①它就是微信原始报文的解密保真形态（ToUserName/FromUserName/CreateTime/MsgType 全字段原样），重新组装必丢字段/顺序漂移，下游存量系统期望微信原格式；②加密（EncodingAESKey）是微信↔本系统的传输层信任边界，解密后明文才是"业务原报文"——下游不持微信密钥、不再验签，透传明文语义正确；下游若需再加密属另场景（上游另有 appid），记录为边界排除。

**⑤ HttpClient 形态**：出站转发经 **typed client**（`AddHttpClient<DownstreamForwardClient>`——DI 生命周期托管防 socket 悬挂，对齐 `WeChatApiClient` 先例；转发无 token 概念，**不复制**其 access_token 缓存/并发锁逻辑）；转发日志经 SG1 `MessageForwardLogEntity`（ChannelId/OpenId/MsgId/EndpointId/**Status=Success/Timeout/Fail/InvalidXml**/转发耗时/降级分支），best-effort 写入不阻塞回复（对齐 `InteractionLogEntity` 先例）。

**⑥ 安全**：下游响应**不做验签**——本系统是微信回调唯一入口（验签解密已完成），下游是本系统主动转发的接收方、不持微信 Token/EncodingAESKey，"业务回复"非微信协议报文，此为信任边界声明；伪造危害面仅回复内容且经 URL 白名单单向出站，可接受。下游 URL/凭证归 `DownstreamEndpointEntity`（URL 即白名单语义——仅可转发至已配置端点）+ AuthToken **AES-GCM 密文落库**（keyed `ISymmetricKeyProvider`，解密仅出站瞬时，对齐 `WeChatChannelConfigEntity` 凭证先例）；出站日志脱敏——AuthToken/密文不落日志、异常消息无明文。

### 十·三、异步抄送机制（设计定稿——BackgroundJob 队列 + 门面入队）

> **选型定案（2026-10-18 修订——用户裁定"本扩展无需跨扩展事件"）**：异步抄送**不使用 `[DistributedEvent]` Outbox 事件**——投递消费方 = **本扩展自己**（投递 handler 做 HTTP POST 到 DownstreamEndpoint——配置归属本扩展），**无任何其他扩展订阅"微信消息被抄送"**，下游是存量 HTTP 系统非 TKWF 扩展——**没有跨扩展语义**。正解：**框架 `IBackgroundJobManager.EnqueueAsync<WeChatMessageForwardJob>`**（`TKWF_JobRecord` 持久化队列——重启续投 + 重试 MaxRetryCount=3 + `GetJobStatusAsync` 状态追踪 + SystemActor 自动绑定，**零跨扩展事件接线**）。内存 `Channel<T>` 因崩溃丢失不可用于抄送副本。消费 `IBackgroundJobManager` 为用户裁定"极个别特例"（框架契约非 IDomainService 不可改接口）——门面内非域基础设施注入。
> **跨扩展事件判定（2026-10-18 用户裁定）**：本扩展抄送**无跨扩展事件需求**——`[DistributedEvent]` Outbox 事件保留为**后续迭代**（若未来其他扩展需订阅微信消息/下游需事件驱动再启用——Approval D3 先例场景），本期**不建事件类型不接事件派发**。

**① 需求本质**：异步抄送 = 主线程完成本地业务并生成被动回复 XML 后立即返回微信（不占 5 秒回包窗口），消息**副本**经异步通道投递下游（存储/业务记录/工单/CRM 同步）。关键边界：**下游无权回复微信用户**——抄送通道是单向数据流，不含任何主动回包能力，下游仅消费消息快照。

**② 机制对比与定案**（2026-10-18 修订）：

| 维度 | DB Outbox（事件） | 内存队列（Channel\<T\>） | **BackgroundJob 队列（定案）** |
|------|-------------------|--------------------------|------------------------------|
| 事务一致 | ✅ 同事务落库 | ❌ 入队与业务无原子性 | ❌ 独立 scope 写 JobRecord（业务回滚可能幻象抄送——**幂等表已防下游重复**，幻象仅多一次下游调用由下游幂等吸收；可接受） |
| 消息不丢（进程重启） | ✅ | ❌ 内存随进程丢失 | ✅ 持久化（TKWF_JobRecord 重启续投） |
| 多实例部署 | ✅ 分布式锁 | ❌ 各实例独立队列重复投递 | ✅ 分布式锁 |
| 实现成本 | 需 AddOutbox + 事件派发 | 框架无通用队列设施 | **零新表 + `AddBackgroundJobs<TUserInfo>()` + `[BackgroundJob]` 一个作业类** |
| 可重放/可审计 | ✅ | ❌ | ✅（JobRecord + `GetJobStatusAsync`） |
| 测试友好性 | DB 态可断言 | 需等后台消费 | JobRecord 落库断言 + 手动 ExecuteAsync 直测 |
| **跨扩展语义** | ❌ 本扩展无跨扩展事件需求 | — | ✅ 纯内部投递无事件接线 |

> **定案理由**：投递消费方 = 本扩展自己（无跨扩展订阅）→ 跨扩展事件（`[DistributedEvent]`+`[DomainEventHandler]`）是**过度设计**；BackgroundJob 持久化队列直接满足（重启续投/重试/状态追踪/SystemActor 自动绑定），零事件派发接线成本最低。事务一致性缺口（独立 scope 入队）由**幂等表（微信侧去重）+ 下游幂等（IdempotencyKey 透传）**双层兜底——幻象抄送仅多一次下游调用，不造成重复业务副作用。

**③ 投递语义**：**at-least-once**——`BackgroundJobWorker` 重试（指数退避 `2^RetryCount` 分钟，`MaxRetryCount=3` 默认），下游**必须幂等**。系统幂等表只保证微信侧去重，**不保证下游去重**：给下游透传 `IdempotencyKey`（msgId+fromUserName+createTime 复合键）供其自行幂等。投递失败重试：`RetryCount` + 指数退避（上限 5 次，超限转死信标记——**P2-3 范围裁定：阶段一不实施死信落地，超限静默丢弃仅记日志告警**；`MaxRetryCount` 超限后 `JobRecord.Status=Failed` + `LastError` 记录为技术债，死信表后续迭代）。投递器生命周期：**进程内 `BackgroundJobWorker` 常驻**（SystemActor 自动绑定 + 分布式锁单飞，零扩展侧后台线程——对齐 Approval D4"扩展不内建调度器/后台线程"）。

**④ 接口形态**（对外契约稳定，机制层可换）：

```csharp
/// 异步抄送门面：入队语义固定，实现层随机制替换（Outbox/内存/EventBus 均可落为同一契约）
public interface IMessageForwardDispatcher
{
    /// <param name="channelId">公众号 channel 实例 id</param>
    /// <param name="endpointId">命中的下游端点配置 id</param>
    /// <param name="rawXml">消息副本原始 XML（快照，防下游再查微信）</param>
    /// <param name="msgId">微信 MsgId</param>
    /// <param name="fromUserName">发送者 openid</param>
    Task EnqueueAsync(string channelId, string endpointId, string rawXml,
                      string msgId, string fromUserName, CancellationToken ct = default);
}
```

契约定位：**门面形态（用户裁定 2026-10-18——框架设计原则：不允许普通 DI 注册，除非极个别特例）**——接口标 `IDomainService` + 实现继承 `DomainServiceBase` + **`AddConstructibleService` 注册**（守卫工厂：帧内 CurrentAopUser 供给 ctor IDomainUser，帧外解析抛守卫——fail-fast 非静默降级）；ctor `(IDomainUser, ILogger)`（非域基础设施可注入）；入队数据访问（转发日志回写）经基类 `User.Use<MessageForwardLogEntityDataService>()` 懒加载（DI004 合规，禁 sp.GetRequiredService C1 绕行——普通 DI 特例仅限主框架/Abstractions 契约实现等接口不可改场景，本扩展自有门面一律守卫工厂）。入队方法只保证"已受理"（同步落库/入队即返回，不阻塞微信回包），投递状态经 `MessageForwardLogEntity` 回写——**不设计 Store 伪层，数据访问全走 SG1 DataService**。
> **P1-1 事件形态（skill 对齐）**：`WeChatMessageForwardEvent : DomainEvent`（record，`[DistributedEvent]` 标记——Outbox 持久化路由）+ 消费 handler 实现 `IDistributedEventHandler<WeChatMessageForwardEvent>` + `[DomainEventHandler]` 特性 + **注册形态待实施确认**（Outbox 派发在非 User.Use 帧内——须对齐主框架 SystemActor 机制（BackgroundJobWorker 自动 BeginSystemScopeAsync 先例），可能是接线型特例 + SystemActor 或集合版守卫工厂；实施时按框架事件派发上下文定）。

**⑤ 与幂等表/转发日志关联**：异步抄送**走 `MessageForwardLogEntity`**，Status 为 `Queued（已入队）→ Success（投递成功回写）/ Fail（重试超限，附 RetryCount+LastError）`。时序链路：**微信回调 → 幂等检查（命中即重放旧回复，不入队）→ 本地业务+被动回复 → 门面入队（`IMessageForwardDispatcher.EnqueueAsync` → `IBackgroundJobManager.EnqueueAsync<WeChatMessageForwardJob>`，落转发日志 Status=Queued）→ `BackgroundJobWorker` 后台投递下游（Job 内 HTTP POST + 幂等键透传）→ 成功回写 Status=Success**。幂等表在前、异步投递在后——幂等命中分支永不产生异步投递，天然避免重复抄送。

> **⚠️ 消费方接线前置**（实施验收项）：消费项目须已注册 `AddBackgroundJobs<TUserInfo>()`（作业队列基础设施——`TKWF_JobRecord` 表 + `BackgroundJobWorker` 常驻；缺接线则 `EnqueueAsync` 解析 `IBackgroundJobManager` 失败，`InitializeAsync` fail-fast 探测提示）。**无 Outbox/事件派发接线**（本方案不用事件）。

### 十·四、消息幂等机制（设计定稿——微信回调重试去重）

**① 幂等键设计**：微信两种推送形态键来源不同——消息（text/image/voice/video/shortvideo/location/link）带 `MsgId`；**事件（subscribe/unsubscribe/click/scan/location 等）无 MsgId**，仅 `FromUserName + CreateTime`：

| 形态 | 幂等键规范化 |
|------|-------------|
| 消息（MsgId 非空） | `msg:{channelId}:{MsgId}` |
| 事件（MsgId 空） | `evt:{channelId}:{FromUserName}:{CreateTime}` |

- **判定规则**：`MsgId` 非空用 MsgId，空（事件推送）回退 `FromUserName+CreateTime`；`msg:`/`evt:` 前缀类型隔离，避免不同形态键同构碰撞。**ChannelId 入键**——隔离多公众号，杜绝跨通道 `FromUserName+CreateTime` 巧合相等被误判重复。
- **同键重复回调语义**：**静默跳过**——不重复投递下游、不改变主链，仅追加 SkippedDuplicate 日志供对账；同步代理模式本可复用首次转发结果，阶段一简化为返回兜底回复（不占 5 秒窗口等待）。

**② 幂等表设计**：`WeChatMessageIdempotencyEntity`（表 `TKWF_WeChatMessageIdempotency`）：Id 自增主键 / `IdempotencyKey`（规范化键，**唯一索引**）/ ChannelId / MsgId（可空，事件为 null）/ FromUserName / CreateTime（微信原始时间原样留存）/ FirstSeenAt（首见 UTC）/ **LastStatus**（1=Pending 处理中 / 2=Forwarded 已转发 / 3=Skipped 重复跳过）/ ForwardLogId（可空，关联转发日志）。SG1 声明式对齐 `SubscriptionStatEntity` 样式（`partial` + `[Table]` + `[DomainGenerateCode]` + `[FreeSql.DataAnnotations.Index("TKWFIX_WeChatMessageIdempotency_Key", nameof(IdempotencyKey), IsUnique = true)]`）；数据访问走生成 DataService（零手写 ORM）。

**③ 并发安全**（微信可能并发重试，同键双请求几乎同时到）：对齐 `SubscriptionStatService.RecordAsync` 既有"查 → 建 → 唯一索引兜底 TOCTOU → **败者重查**"模式：按 IdempotencyKey 查 → 命中即重复（不论 Pending/Forwarded）走跳过分支；未命中创建（Pending 先占键），撞唯一约束（并发双建）→ 败者重查见胜者记录 → 同样按"键已占用"跳过——**判决语义由"键存在"决定，不依赖状态精确值**，竞态下胜者未及置 Forwarded 亦不重复转发。

**Pending 裁定：跳过，不等待**——等待会耗尽 5 秒回调窗口且异步抄送模式下无共享响应可合并；跳过即保证下游至多收到一次。**P1-2 状态迁移裁定（2026-10-18）**：幂等建键（Pending）**与 Outbox 事件登记同事务，事务提交即迁 Forwarded**（语义=已入队待投递，非已投递成功）——OutboxSender 持久化续投保证最终交付，进程崩溃遗留 Forwarded 记录由 Outbox 续投补偿，**无陈旧 Pending 数据丢失窗口**（P1-5 联动消解）；投递精细化状态归 `MessageForwardLogEntity.Status`（Queued/Success/Fail）承载。**P1-5 兜底**：`PendingTimeoutMinutes=5`（可配）——极端场景（Outbox 登记失败且建键事务已提交）Pending 超时后允许新请求复用键重建 Pending+转发；`IdempotencyRetentionDays=7` 仅清理 Forwarded/Skipped 终态记录。幂等建键（Pending→Forwarded 同事务）与首条转发日志同事务，保证"占用即记录"。

**④ 清理策略**：微信重试均在推送后分钟级至数小时内完成。保留期默认 **7 天**（覆盖全部重试窗口 + 对账余量），`WeChatMessageGatewayOptions.IdempotencyRetentionDays` 可配。**阶段一同步惰性清理**：幂等写入时顺带 `DeleteWhere(FirstSeenAt < UtcNow - 保留期)`（写入频率低、成本可忽略）；表量增大后改 `IRecurringBackgroundJobManager` 定时清理（后续迭代）。

**⑤ 幂等表与转发日志的关联**：`MessageForwardLogEntity`（表 `TKWF_WeChatMessageForwardLog`）：ChannelId/MsgId/FromUserName/MessageType/MatchRuleId（命中的路由规则，可空）/ForwardMode/DownstreamEndpointId（可空）/StatusCode/ResponseBody（截断）/DurationMs/Status（Success/Fail/Timeout/SkippedDuplicate/NoRule/Queued）/ErrorMsg（脱敏——不含下游凭证）/ForwardedAt/RetryCount。

关系裁定：**1:N（每次回调一条日志）**——幂等表每键一行是"是否已处理"的判决事实；转发日志是处理轨迹，每次回调各记一行：首见记 Forwarded/Fail/Timeout/NoRule/Queued，重复回调记 SkippedDuplicate（重试风暴对账可见）。幂等表 `ForwardLogId` 指向**该键最后一次**日志行（可空），供从幂等键快速追溯下游投递结果；对账按 IdempotencyKey 或 ChannelId+MsgId 关联。

### 十·五、挂载点与响应流改造（设计定稿）

**① 挂载点定位（裁定：方案 A 入口统一前置，组件化）**：既有链实证：微信 POST → `WeChatEventChannel` 验签解密富化 `__decrypted_xml`（返回 null 编排放权）→ `EventOrchestrator` 双桶迭代 → 平台基类 `HandleAsync` 模板方法（Parse → ResolveChannel → private `DispatchAsync` 二级分发 → 协议门控 → `BuildReplyResult` 信封闭包）→ 各 `OnXxx` 分支 → 渲染三层 → `WechatReplyPayload` 返回微信。**约束：基类 `HandleAsync` 非 virtual、`DispatchAsync` private，handler 无法 override 公共入口**——故裁定**方案 A（入口统一前置）**，实现形态 = **独立网关组件 + 各分支首行统一单行调用**：

- 新增内部门面 `IMessageGatewayService : IDomainService`（继承 `DomainServiceBase`，`AddConstructibleService` 注册），封装幂等检查 → 路由规则匹配 → 决策产出（LocalOnly/AsyncCopy/SyncProxy/SkipDuplicate）→ 转发日志留痕；数据访问全走 SG1 DataService（`User.Use<TDataService>()` 懒加载，与既有 `RuleDs` 同型）——零 Store 伪层、零构造注入（DI004）。
- handler 每个可回复分支首行统一调用 `var gate = await _gateway.RouteAsync(ctx, ct)`（`if (gate.Handled) return gate.Result;`）——**物理分散、逻辑统一**：插入的是同一行组件调用而非各自网关逻辑，消除方案 B"分散易漏"缺陷；后续新增分支仅补一行。适用面（**P2-2 精确化**）= 10 个可回复/可转发 override 分支（Subscribe/Text/Click/Scan/Image/Voice/Video/ShortVideo/Location/Link）+ **OnLocationEventAsync（LOCATION 事件——上报地理位置，可转发应补入）** + OnTextAsync 内 Default 兜底分支；Unsubscribe（协议门控吞回复）、View/ViewMiniProgram（微信直跳）不插。裁定理由：网关逻辑体量与 handler 既有 300+ 行组合核心相当，内联双重膨胀且不可单测；组件独立可生产路径测试，handler 保持"组合核心"单一职责。

**② 响应流改造**：
- **幂等检查位置**：最前——验签解密后、任何业务查询/渲染/统计之前（各分支首行网关调用内第一步），重复回调直接短路（不重复转发/不重复计数）。
- **LocalOnly**：走既有渲染三层，零改动（等价既有规则命中语义）。
- **AsyncCopy**：本地渲染为主响应 + 消息副本异步入队（副分支，转发日志记 Pending/Queued）→ 返回本地 `WechatReplyPayload`，主线程零等待。
- **SyncProxy**：下游业务载荷**接管内容源**（替代本地三层结果；信封闭包走平台库 `WechatReplyPayload.RawXml` 逃逸口——P0-1 选 A，SyncProxy 暂缓）；超时/失败 → 降级链：本地渲染 → `TemplateFallback` → `Options.DefaultReplyText` → 最后 null。

**③ 5 秒时限保障**：SyncProxy 下游硬超时（默认 2s 可配、上限 ≤3s）+ 降级渲染预算 ~1s + 余量，总耗时恒 < 5s，超时即降级不等待；AsyncCopy 异步投递不阻塞响应（Outbox 登记同步、投递后台——机制见 §十·三）；网关自身异常 fail-safe 降级 LocalOnly 不阻断回复；任何分支超预算一律降级兜底。

**④ 与统计/日志的交互**：订阅统计：subscribe/unsubscribe 为真实事件语义与转发无关——正常回调仍计数，**幂等跳过（重复回调）不计数**（最前短路，`RecordStat` 不执行，防微信重试重复计数）。交互日志：LocalOnly/AsyncCopy 本地有回复走既有 `RecordInteractionAsync` 仍记录；SyncProxy 以下游转发日志（`MessageForwardLogEntity`）为主记录，不重复写本地交互日志（防双表语义混淆）；**幂等跳过留痕**：`MessageForwardLogEntity` Status=`SkippedDuplicate`（审计需要，不静默吞事件）。

**⑤ 改造影响面**：新增默认开关 **`WeChatMessageGatewayOptions.GatewayEnabled`**（默认 false——**P1-4：开关归属独立网关 Options，非 `WeChatOperationsOptions`**，对齐 §十·六 配置分层）+ 规则集为空 → 网关直通（入口先判开关，未启用零额外查询），既有 13 override 分支内部逻辑零改动（仅加一行），**67 用例全绿保持、既有用例零修改**；新增测试覆盖：三策略命中/幂等跳过/降级链/超时降级/开关关直通。

### 十·六、暴露面与配置分层（设计定稿——修订：端点自动生成 + 三部分边界）

**① 暴露面形态裁定（用户 2026-10-18 修订）**：网关管理端点**不新增手写 WebExtension**——②领域扩展的业务方法经 `[GenerateController(FromDataService=true)]` **自动生成 REST 端点**（SG1 原生——对齐 AuditLogging/Identity/Notifications 先例）；既有 `WeChatOperationsWebExtension`（13 手写端点）V0.1.0 已发布**保持不动**（向后兼容）。门面接口方法级 `[RequirePermission]` 标注（对齐 `ChannelConfigService`/`LogQueryService` 先例）+ 方法级 `[ApiExpose]`（SG1b 生成控制器），权限沿用 `WeChatOperations.Manage`（写）/`WeChatOperations.Query`（读）。网关模块拟暴露方法（自动生成端点形态，路由前缀归表现层 DMP-Lite）：

> **表现层边界**：上述方法生成的 REST 端点 + **页面/前端资产**归 **③ 表现层扩展（DMP-Lite 项目组剥离）**——本仓库不做页面、不建 `.Web` 包；DMP-Lite 经 `[GenerateController]` 生成的端点消费（对齐开发方案 §八 GUI 拆分方向 + tkwf-use-extension §4.7 页面装配形态）。

**② 配置分层**（AGENTS §8）：领域决策入**独立 `WeChatMessageGatewayOptions`**（`[Options("TKWF:WeChatOperations:Gateway")]`——职责分离裁定：转发网关为独立子域、独立 fail-closed 默认与生命周期，不复用 `WeChatOperationsOptions`（DefaultReplyText/SecretEncryptionKeyPath/IsProduction/InteractionLogRetentionDays 属既有运营能力）；配置节仍挂 `TKWF:WeChatOperations` 根下保内聚，对齐 Federation `:ChannelRegistry`/`:Web` 拆节先例）：
- **领域键**（`TKWF:WeChatOperations:Gateway`）：`GatewayEnabled=false`（**fail-closed 默认关**——未开全局开关/未配规则时既有 handler 行为零回归；**P1-4：开关归属本 Options，非 `WeChatOperationsOptions`**）；`IdempotencyRetentionDays=7`（0=不清理，对齐 InteractionLogRetentionDays 约定；**P1-5：仅清理 Forwarded/Skipped 终态**）；`PendingTimeoutMinutes=5`（**P1-5：Pending 独立短超时**——超时后允许新请求复用键重建 Pending+转发，防陈旧 Pending 数据丢失窗口）；`AsyncForwardRetryCount=3`/`BackoffSeconds=2`（指数退避）；`DefaultSyncTimeoutSeconds=2`（微信 5 秒窗口留 1 秒本地兜底余量；上限 ≤3 校验）
- **表现层暴露面**（`WeChatOperationsEndpointOptions` 增 4 开关，`TKWF:WeChatOperations:Web`）：`RouteRulesEndpointEnabled`/`DownstreamEndpointsEndpointEnabled`/`ForwardLogsEndpointEnabled`/`GatewayStatusEndpointEnabled` **默认 true**（仅 HTTP 映射开关——关闭端点不影响网关运行；fail-closed 由领域 `GatewayEnabled` 承载，表现层不存在关闭领域行为的对应开关）
- **硬性不设开关**：幂等去重（MsgId/FromUserName+CreateTime）为 §十 硬性需求强制开启，`IdempotencyRetentionDays`/`PendingTimeoutMinutes` 仅控保留/超时

**③ 安全**：下游 `AuthToken` 经 keyed `ISymmetricKeyProvider` **复用既有 `WeChatOperationsKeyProviderKeys.WeChatOperations` 键**（同扩展同信任边界——避免第二把密钥的轮换/备份运维面）；`DownstreamEndpointDto` **投影不含 AuthTokenCipher**（对齐 `WeChatChannelConfigDto`——`HasCredentials` 布尔指示）；转发日志 `ErrorMsg` **脱敏**（记录时剥离 Authorization/query token 等下游凭证、下游响应体截断 500 字符）；`GetGatewayStatusAsync` 只读 DTO 不含敏感（仅 Enabled/计数/最近状态，不含规则/端点明细）。
