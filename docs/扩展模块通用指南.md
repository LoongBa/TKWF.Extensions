# TKWF 扩展模块通用指南

> 本指南回答**消费方视角**的公共问题：如何引用、启用、接线任意 `TKWF.Ext.*` 扩展。
> 这是 37 份扩展使用指南中「启用/接线」公共内容的**单一事实源**——各扩展指南只保留特有内容，公共部分引用本文档。
> 扩展开发者视角（怎么写一个扩展）见主框架私有 `D17-TKWF扩展机制与业务模块全景-设计方案.md` §4.4；机制原理与审核清单见本仓 [`扩展模块机制-设计原理与审核经验.md`](./扩展模块机制-设计原理与审核经验.md)。
>
> 适用：所有启用了 TKWF 扩展的消费方领域项目（Domain 侧）+ Web 项目（装配侧）。

---

## 一、核心概念

| 概念 | 说明 |
|------|------|
| **扩展** | `TKWF.Ext.*` 独立包（权限/身份/通知/MFA 等 40+ 主包、60+ 包含 Abstractions/平台库），独立版本（MinVer），与主框架版本无关 |
| **发现 ≠ 启用**（V4.9.85/ADR47） | 扩展 DLL 被引用后，SG1 编译期**发现**其 `[TKWFExtension]` 初始化器（生成能力清单）；但**发现不自动启用**——须消费方**两处声明**：① `[TKWFEnabledExtension]` 编译期白名单（聚合控制器/页面能力清单）；② `ConfigureExtensions` 内 `registry.Enable("Name")` 运行期启用（`IsEnabled` 默认 false，三钩子只对已启用扩展执行） |
| **启用双通道（实测口径）** | 只写特性不写 `Enable` → 扩展被聚合进权威注册但**三钩子不执行**（服务未注册/过滤器不生效）；只写 `Enable` 不写特性 → 三钩子执行但控制器/页面不聚合（无 API/页面）。**两处都要**；生产先例：DMP-Lite `DmpDomainInitializer` |
| **三钩子**（Domain 侧） | `ConfigureServices`（DI 注册）/ `ConfigureFilters`（AOP 过滤器）/ `InitializeAsync`（异步种子），由 DomainHost 启动流程自动调用 |
| **Web 装配钩子**（v4.10.45/ADR87） | Web 类扩展（认证/限流/健康检查/SignalR）装配宿主面（中间件/端点）走独立 `IWebExtension` 机制，与 Domain 三钩子**正交** |
| **依赖倒置**（ADR48 D7） | 扩展间依赖走 `.Abstractions` 契约包，不引用实现项目（L2 门控 `TKWF0022` Error） |

## 二、接入流程（消费方三步）

### 第 1 步：引用扩展包

**NuGet 包模式**（生产消费方推荐）：

```xml
<PackageReference Include="TKWF.Ext.Identity" Version="0.5.3" />
<!-- 扩展经 PackageReference 传递引用主框架包（TKWF.Domain 等，CPM 集中版本）；
     依赖扩展（如 Identity → Permissions.Abstractions）自动解析 -->
```

**源码模式**（扩展仓库内联调/开发）：

```xml
<ProjectReference Include="..\_TKWF.Extensions\_Framework\Identity\TKWF.Ext.Identity.csproj" />
```

**按分发形态引用（v4.10.122 裁定）**：扩展分**契约型**与**自包含型**，不要一律"主包 + Abstractions 成对"：

| 形态 | 判据 | 引用方式 |
|------|------|----------|
| **契约型** | 其他扩展需引用其接口/wire DTO（存在跨扩展契约消费方） | 主包 + `*.Abstractions` **成对** |
| **自包含型** | 零跨扩展契约消费（仅终端应用消费，DTO 在主包 `Contracts/`，README 首屏声明） | **单包**；无 Abstractions 包属预期 |

禁止第三形态（空 Abstractions + DTO 留主包）。逐扩展判型看该扩展 README 首屏声明；开发新扩展的判据与升格（自包含 → 契约型须先抽契约包）见主框架 `G17A §7.8`。

### 第 2 步：白名单声明 + 运行期启用（两处都要）

扩展不"发现即启用"——消费方须**同时在两处声明**（编译期聚合与运行期执行是两条独立通道）：

```csharp
using TKWF.Ext.Identity;   // 引入扩展命名空间（含初始化器类型）

[TKWFEnabledExtension(typeof(IdentityExtensionInitializer<>))]   // ① 编译期白名单
public class MyDomainInitializer : DomainHostInitializerBase<MyUserInfo>
{
    protected override void ConfigureExtensions(ITkExtensionRegistry registry, IServiceCollection services)
    {
        registry.Enable("Identity");                              // ② 运行期启用（三钩子执行）
    }
}
```

- `[TKWFEnabledExtension]` 支持 `AllowMultiple`——多个扩展同一初始化器上并列声明。
- **① 白名单**：SG1b 据此把扩展能力清单（控制器接口 / 页面清单）聚合进领域权威注册；白名单外直接引用 = `TKWF0032` Error。
- **② `registry.Enable`**：`TkExtensionDescriptor.IsEnabled` 默认 **false**，三钩子只对 `IsEnabled == true` 的扩展执行。**只写 ① 不写 ② = 服务未注册、过滤器不生效、种子不执行**（表现为运行时 `XxxService 未注册`）。
- 说明：框架未把 ① 自动映射为 ②（截至 v4.10.150 实现），因此"双声明"是现行唯一正确形态；本仓历史文档"`[TKWFEnabledExtension]` 是唯一启用通道"为过度简化，自 2026-11-28 起统一修正。
- **未声明**：扩展被发现但**不启用**——DI 注册缺失、Filters 不生效（表现为运行时 `XxxService 未注册`，详见 §五）。
- ⚠️ **纯扩展宿主边界**：若领域项目自身**没有任何领域类型**（无实体/服务/控制器），SG1a 走空壳早退路径，扩展描述符为空——此时 `registry.Enable` 会抛"扩展未在清单中"。领域项目通常有自身实体，不受影响；纯扩展装配场景需先与框架组确认（见机制文档 §7）。

### 第 3 步：Web 装配（仅 Web 类扩展，v4.10.45+）

Web 类扩展（如 AuthCenter/RateLimiting/HealthCheck/Notifications.SignalR）的中间件/端点装配走 `IWebExtension`——在 WebHost 装配链上一次性声明：

```csharp
builder.ConfigWebAppDomain<MyUserInfo, MyDomainInitializer, DomainWebOptions>(...)
    .UseWebSession()                                // 会话恢复（主框架，按需）
    .UseWebExtensions(e => e.Add<HealthCheckWebExtension>(x =>
    {
        x.AddDatabaseHealthCheck<MyEntity>("db");   // 泛型参数为实体（IDomainEntity），非健康检查类
    }))
    .BeforeRouting(...)
    .AfterRouting(...)
    .Build(...);
```

- **Domain 与 Web 正交**：业务服务 DI 由 Domain 钩子（`XxxExtensionInitializer`）注册；宿主面（中间件/端点映射）由 Web 钩子（`XxxWebExtension`）承担。二者独立声明、独立生效（`TKWF_SG1b_WEBEXT_001` 编译期门控守护边界）。
- 各扩展的 Web 钩子类型与锚点（BeforeAuthentication/BeforeRouting 等）不同——**查对应扩展指南**。

> ⚠️ **HttpAuth 自动免认证（v4.10.76，ADR108）**：主框架 `HttpAuthenticationMiddleware` 锚点后移 **AfterRouting** 读端点 `IAllowAnonymous` 元数据——**扩展端点声明 `AllowAnonymous` 即自动免 HttpAuth 认证，消费方零配置**。漏声明匿名端点会被 401（按端点粒度精确判定，整前缀排除不再必要）；旧版手动 `cfg.HttpAuth.ExcludedPathPrefixes.Add(...)` 冗余（保留无害）。详见 [`docs/HttpAuth匿名端点排除机制-开发方案.md`](HttpAuth匿名端点排除机制-开发方案.md)。

## 三、启动时序（三钩子何时执行）

```
OnServiceProviderBuilt
  ↓
OnValidateRuntimeGatesAsync     ← ADR35 统一门控验证（含扩展 SG1 生成的 GateRules）
  ↓
SyncTables / SyncViewsAsync     ← 扩展实体建表/视图
  ↓
ExtensionInitializer.InitializeAsync()   ← 种子数据 + 启动期预检（fail-fast）
```

| 钩子 | 执行时机 | 用途 |
|------|---------|------|
| `ConfigureServices` | `InitializeDiContainer`（DI 构建前） | TryAddScoped 注册业务服务 |
| `ConfigureFilters` | `ConfigGlobalFilters`（FilterBuilder 构建） | 注册 AOP 过滤器（权限/安全日志等） |
| `InitializeAsync` | `OnEnsureSystemReadyAsync` 之后 | 种子数据、密钥预检（fail-fast） |

> 三钩子锚定 **DomainHost** 且零 ASP.NET Core 依赖——Web 装配（宿主注册/中间件/端点）由 `IWebExtension` 独立承载，**不进三钩子**（v4.10.45 正交注记，ADR87）。

## 四、扩展初始化器内安全解析模式（启动期 DI 铁律）

> 背景：Authentication v0.3.1（2026-10-02）修复启动期 `Unable to resolve service`——`InitializeAsync` 中裸 `sp.GetService<ITokenService>()` 解析构造注入 DataService 的服务，在启动期无域作用域会撞守卫（数据访问红线 + 域作用域语义）。

**错误模式**（启动期裸解析）：

```csharp
// ❌ InitializeAsync / ConfigureServices 里裸 GetService 解析含 DataService 依赖的服务
var tokenService = sp.GetService<ITokenService>();   // 解析需 CurrentAopUser 域作用域 → 抛守卫异常
```

**正确模式**（系统作用域 + Use<T>）：

```csharp
public override async Task InitializeAsync(IServiceProvider sp)
{
    var host = sp.GetRequiredService<DomainHost<TUserInfo>>();
    await using var sysScope = await host.BeginSystemScopeAsync();     // V0.5.4 起不传参——框架内部 CreateScope 建子 scope
    var tokenService = sysScope.System.Use<ITokenService>();           // Use<T> 内设 SystemUser 域上下文
    if (tokenService is TokenService concrete)
        concrete.EnsureKeysLoaded();                                   // fail-fast 预检
}
```

要点：
- ⚠️ **`BeginSystemScopeAsync()` 必须不传参**（V0.5.4 修复，2026-10-05 框架组转达）：传参（如 `BeginSystemScopeAsync(sp)`）按 M1 所有权契约（`DomainHost.cs`）**原样绑定传入 provider、不建子 scope**；而 `InitializeAsync(IServiceProvider sp)` 收到的是**根容器**（`ServiceProviderBuiltCallbackAsync` 保持根容器）→ `System.Use<Scoped 守卫工厂>()` 从根解析 → **Development（ValidateScopes=true）启动必崩**（`Cannot resolve scoped service ... from root provider`，EduPlatform 实证）。不传参 → 框架内部 `_ServiceProvider.CreateScope()` 建子 scope 并自拥生命周期。**同 defect 曾复制至 Federation/Tagging/Permissions/Identity 四处 Initializer，已一并修复**（方案 A' 复制链根因）。**v4.10.128 起升级为硬门禁**：传宿主 root 直接抛 `DomainGuardException`（"[系统作用域守卫] BeginSystemScopeAsync 不接受宿主根容器..."），不再静默产生 captive 依赖；合法形态仅两种——`BeginSystemScopeAsync()` 不传参（框架自建子 scope）或**传 `scope.ServiceProvider`**（调用方已有子作用域时）。
- `scope.System.Use<T>()` 要求 `T : IDomainService`（空标记接口准入）——`Use<T>` 内设 `CurrentAopUser=SystemUser`，DataService 在合法域作用域下构造（**自治铁律零妥协**）。
- 预检逻辑抽静态单一真相源（如 `TokenService.LoadKeysCore`），运行期 Lazy 与启动预检共用，避免双实现漂移。
- **消费方零感知**：该改动属扩展内部；消费方只需白名单声明（第二步）。

### 四之二、keyed 基础设施消费（v4.10.61/ADR96，密钥类设施标准形态）

> 背景：E4 密钥管理抽象（2026-10-06）——扩展侧 5 份静态密钥持有者复制链收敛为框架 `ISymmetricKeyProvider`/`FileSymmetricKeyProvider`（`TKW.Framework.Domain.KeyManagement`）+ `DevKeyCache<TKey>`（`TKW.Framework.Utility.Caching`）。**多扩展同容器各自注册同一接口类型的 provider → 普通 `AddSingleton` 会 last-wins 冲突**（后注册覆盖先注册，错误密钥风险）——keyed services 是唯一干净解。

**注册形态**（扩展 Initializer `ConfigureServices`）：

```csharp
// 三扩展（AuthCenter/Federation/MFA）各自注册自己的 provider，key 隔离
services.AddKeyedSingleton<ISymmetricKeyProvider, FileSymmetricKeyProvider>(
    SymmetricKeyProviderKeys.AuthCenter,   // ⚠️ 必须用常量类（Core/KeyManagement），防 typo 静默解析错 key
    (sp, _) => new FileSymmetricKeyProvider(
        o.SecretEncryptionKeyPath, o.IsProduction,
        sp.GetService<ILogger<FileSymmetricKeyProvider>>()));
// 族系 A（dev 签名密钥缓存，仅 AuthCenter/Federation）——DI 单例非静态
services.AddSingleton(new DevKeyCache<TokenService.RsaKeySet>());
```

**消费形态**（服务 ctor `[FromKeyedServices]` 注入）：

```csharp
internal sealed class PlatformCredentialService : DomainServiceBase, IPlatformCredentialService
{
    public PlatformCredentialService(
        IDomainUser user,
        [FromKeyedServices(SymmetricKeyProviderKeys.AuthCenter)] ISymmetricKeyProvider keys,
        IOptions<AuthCenterOptions> options,
        ILogger<PlatformCredentialService> logger)
        : base(user)
    { _keys = keys; ... }
}
```

要点：
- **守卫工厂 ctor 中 keyed 基础设施（`ISymmetricKeyProvider`）与域服务注入（`IDomainUser`）可并存**——前者走 DI 键解析（`ActivatorUtilities.CreateInstance` 对 `[FromKeyedServices]` 生效，框架侧 `GuardFactoryKeyedEndToEndTests` 实证），后者走守卫工厂显式参数，互不干扰。
- **`DevKeyCache<TKey>`**：`where TKey : class, IDisposable`——扩展侧 `RsaKeySet`/`EcKeySet` 须实现 `IDisposable`（Dispose SigningKey + VerifyKeys 全量）；dev 分支 `_devKeys.GetOrCreate(() => CreateDevKeySet(...))`，生产 PEM 分支恒不走缓存。
- **静态密钥类时代终结**：`PlatformCredentialKeyStore`/`DevRsaKeyCache`/`FederationSecretKeyStore`/`DevEcKeyCache`/`MfaSecretKeyStore` 全部删除——生产 fail-fast / 开发两分支语义由 `FileSymmetricKeyProvider` 统一承载；`ResetForTests` 为框架 internal 钩子（IVT 测试访问），公开接口不含测试关注。
- 详见 skill `tkwf-extension` §4.10（v1.9）心得 #17/#18/#19。

### 四之三、UI 装配分工模式（2026-11-06 裁定——常态规则）

> 背景：扩展模块的页面装配（GUI）——扩展贡献的不仅是服务端点，还有页面装配形态。为避免各消费方页面装配漂移（路由/权限/导航菜单形态各自为政），2026-11-06 用户裁定分工（**不限于联邦/微信，常态规则**）：
>
> | 层 | 归属 | 内容 |
> |----|------|------|
> | **装配模式设计** | 框架组 / 扩展模块组 | 页面贡献契约（`IPageContributor` + `PageDescriptor` + spec 词汇，v4.10.73 ADR106）、装配形态（白名单 + `PageAssemblyWebExtension`）、路由/权限/配置节约定、页面清单与关切定义 |
> | **装配实现** | 消费方（如 DMP-Lite 的 Merchant.AdminUI / Platform.Web） | 页面 UI 实现（技术栈/布局/UX 自由） |
> | **回归** | 扩展模块组 | 消费方实证后按回收验收标准拆回 `.UI` 扩展（StaticWebAssets/RCL）+ 沉淀 skill |

**原则**：模式单源（每扩展一份装配模式定义，防消费方各自发明装配形态——P2 唯一权威事实源 + P5 显式决策）；实现自由（表现层关切消费方自治）；事后回归成本低于事前定契约。页面贡献终态 = `IPageContributor` 声明式（接口即意图声明 + spec 纯契约名 + 跨扩展引用白名单门控）；`IPageContributor` 未落地的过渡期用 **R2 路径**（消费方自研前端直连 REST 端点）兜底，机制落地后零破坏演进。**⚠️ R2 增长上限（Oracle2 C5 同步）**：`IPageContributor` 落地后**新页面必须声明式贡献**，R2 不得用于新页面（防漂移为 de-facto 标准）。

> **过渡注记（2026-11-28 闭环）**：三个 UI 技能已落地于框架 AE-Kit canonical 位置（`../_TKWF/docs/AE-Kit/skills/`，经 `.agents/skills/tkwf` Junction 即时生效）：`tkwf-extension-ui`（扩展侧设计）/ `tkwf-use-extension-ui`（消费侧接线）/ `tkwf-ui-split-back`（回收评审）；契约单一事实源 = `tkwf-extension-ui/references/page-contract.md`。本节仅保留消费方面向与本分工裁定本身。

**框架侧缺口清单**（v4.10.73 明示待实现，微信域 GUI 拆分的驱动信号）：① `IPageContributor` 接口本体（两仓均未落地）② TS codegen ③ `@tkwf/reference-components`。

**首个实例**：微信域管理 UI 双面拆分（2026-11-27 取代原混装方案）——运营面 [`docs/WeChatOperations/管理UI-运营面-开发方案.md`](WeChatOperations/管理UI-运营面-开发方案.md) + 通道治理面 [`docs/WeChatChannels/管理UI-通道治理面-开发方案.md`](WeChatChannels/管理UI-通道治理面-开发方案.md)，边界判据见 [`ADR-WeChatOperations-管理UI单双通道扩展边界.md`](WeChatOperations/ADR/ADR-WeChatOperations-管理UI单双通道扩展边界.md)。原混装方案 [`微信公众号运营GUI-拆分方案.md`](WeChatOperations/微信公众号运营GUI-拆分方案.md) 已 superseded（保留历史）。

### 四之四、测试宿主必须安装 SG1 生成的项目元数据（v4.10.122 经验）

生成 DTO 的写入路径（`DataService.CreateAsync(dto)` / `CreateBatchAsync`）经 `IDomainDto<T>.ApplyToEntity` → `CreateMapper` → `ValidationCache<TDto>.Meta`，而 `Meta` 在**静态构造时**读 `ProjectMetaContextBase.Instance.GetPropertyMap(...)`：

- 测试宿主手工建 DI（绕开 `DomainHost`）时 `Instance` 为 null → `Meta` 为空字典 → 映射**静默不发生**（不抛错，只是字段不落库，极易误判为"框架不映射"）；
- 依赖"生成 DTO 写入"的测试必须在**首个用例之前**安装扩展生成物的 `ProjectMetaContext`（`Instance` setter 为 protected，经子类公开——对齐各测试项目 `FakeMetaContext` 先例）：

```csharp
// 测试类静态构造：首个用例前执行
static GeneratedDtoCreateContractTests()
    => MetaCtx.Install(TKWF.Ext.Xxx.Generated.ProjectMetaContext.GetOrCreateInstance());

private sealed class MetaCtx : ProjectMetaContextBase
{
    public static void Install(IProjectMetaContext ctx) => Instance = ctx;
    public override ProjectConfiguration Configuration => null!;
    public override MetadataChangeLog ChangeLog => null!;
    public override string MetadataSchemaVersion => "test";
}
```

- **反例**：给测试宿主塞手写 `IProjectMetaContext` 空桩——`Meta` 依然为空，`ApplyToEntity` 全路径静默失效（= 生成物健康清单 #6「禁手写空桩」的实测依据）；
- **参照实现**：`_Tests/Extension.AuditLogging.Tests/GeneratedDtoCreateContractTests.cs`（B3 契约测试：生成 DTO → `CreateAsync`/`CreateBatchAsync` 落库 + Id 由库分配；v4.10.122 起去 Skip 转绿）。

## 五、常见接线错误速查

| 症状 | 原因 | 处置 |
|------|------|------|
| `XxxService 未注册——…路径跳过` | 扩展白名单未声明（发现≠启用，DI 注册缺失） | `[TKWFEnabledExtension(typeof(XxxExtensionInitializer<>))]` 声明 |
| **白名单已声明，但服务仍未注册 / 过滤器不生效 / 种子不执行** | 只写了编译期白名单，漏了运行期启用（`IsEnabled` 默认 false） | `ConfigureExtensions` 内补 `registry.Enable("Xxx")`（见 §二 第 2 步） |
| `扩展 'Xxx' 未在清单中`（`registry.Enable` 抛） | 宿主项目自身零领域类型 → SG1a 空壳早退，扩展描述符为空 | 确认领域项目含自有实体/服务；纯扩展宿主场景先与框架组确认（机制文档 §7） |
| 启动抛 `解析需处于域作用域` 守卫 | 扩展/消费方在启动期裸 `GetService` 解析 DataService 依赖 | 见 §四 系统作用域模式 |
| **Development 启动抛 `Cannot resolve scoped service ... from root provider`**（v4.10.128 起更明确：`DomainGuardException`「系统作用域守卫」） | `InitializeAsync` 内 `BeginSystemScopeAsync(sp)` 传宿主 root（V0.5.4 前形态——Authentication/Federation/Tagging/Permissions/Identity 五处曾同犯；v4.10.128 起直接抛、不再静默 captive） | 改 `BeginSystemScopeAsync()` **不传参**（框架内部 `CreateScope()` 建子 scope）或传 `scope.ServiceProvider`；见 §四 要点 |
| 启动抛 `Issuer 未配置` / `SigningKeyPath 未配置` | 生产 fail-fast 门（缺配置） | 配置 `TKWF:{扩展名}` 对应节 |
| 旧静态方法不存在（`AddXxx`/`MapTkfwXxx` 编译失败） | v4.10.45 Web 钩子收敛——静态方法破坏性删除 | 改 `UseWebExtensions(e => e.Add<XxxWebExtension>(...))` |
| Web 中间件不生效（但 DI 注册正常） | 只声明了 Domain 白名单，未装配 Web 钩子 | WebHost 链 `UseWebExtensions` 补声明 |
| `TKWF0022` Error（L2 门控） | 扩展引用了其他扩展的实现项目而非 Abstractions | 改引 `.Abstractions` 契约包 |
| 密钥 provider 解析到错误 key（加解密用错密钥） | keyed 注册 key 字符串 typo / 普通 AddSingleton 多扩展 last-wins | 用 `SymmetricKeyProviderKeys` 常量类 + `AddKeyedSingleton` + `[FromKeyedServices]`；见 §四之二 |
