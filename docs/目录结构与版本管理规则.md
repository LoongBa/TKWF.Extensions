# 目录结构与版本管理规则

> 本文档记录 `TKWF.Extensions` 仓库的目录结构约定、版本级联规则和文档生命周期管理。
> 所有人类成员和 AI Agent 均需遵守。

---

## 一、仓库定位与边界

```
_TKWF/               主框架（TKW.Framework）：领域框架、扩展机制基座、SG、Infrastructure
_TKWF.Extensions/    本仓库：TKWF 业务扩展包（TKWF.Ext.*）+ 扩展测试 + 扩展文档
```

- 本仓库**不包含**主框架核心代码；扩展包经 `$(TKWFSourceRoot)` ProjectReference 跨仓库引用主框架源码
- 扩展包与主框架 slnx 解耦：`TKW.Framework.slnx` 不含扩展项目，扩展在 `TKWF.Extensions.slnx`
- 扩展机制基座文档（D17/ADR37-39）属主框架文档，不在本仓库

## 二、目录结构

```

│       ├── README.md      # 扩展独立 README（技术规范/使用手册）

├── _Tests/                # 扩展测试
│   └── Extension.{扩展名}.Tests/
├── docs/                  # 扩展文档（统一在此，方便查看）
│   ├── AGENTS.md          # Agents 路由指南（默认上下文）
│   ├── 目录结构与版本管理规则.md   # 本文档
│   ├── 测试约定-SQLite物理事务与Noop限制.md   # 测试基建约定（SQLite 事务边界 + Noop 限制 + PG 容器评估）
│   ├── {扩展名}/           # 各扩展独立指南区（使用指南，公开）
│   ├── 模板/               # 开发方案/审核报告/ADR 模板
│   └── 草稿/               # 讨论中未定稿
├── Directory.Build.props  # TKWFSourceRoot + MinVer + 打包公共属性 + _PushToRefs
├── Directory.Packages.props   # CPM 集中包版本
├── .gitignore
├── README.md              # 根 README（仓库总览）
└── TKWF.Extensions.slnx   # 扩展解决方案
```

### 文档归属约定

| 文档 | 位置 | 说明 |
|------|------|------|
| 扩展指南（使用手册） | `docs/{扩展名}/xxx-使用指南.md` | **统一在 /docs 下**，方便查看；一个扩展一份 |
| 扩展开发方案/审核报告 | 主框架私有 `_TKWF/docs/03_扩展模块/{扩展名}/{扩展名}-开发方案.md` / `-审核报告.md` | **各扩展各自独立迭代，不公开** |
| 扩展 ADR | 主框架私有 `_TKWF/docs/03_扩展模块/{扩展名}/ADR/ADR-{title}.md` | **各扩展各自独立 ADR 目录，不公开** |
| 扩展 README | `_Framework/{扩展名}/README.md` | 扩展包源码侧的技术规范（随 NuGet 包发布） |
| 根 README | `README.md` | 仓库总览 + 扩展索引 |

## 三、版本管理（MinVer，独立版本）

采用 MinVer 风格：`V{major}.{minor}.{patch}`（git tag 前缀 `v`）。

### 3.1 版本策略：扩展独立版本（V4.9.80 起，ADR-扩展版本策略）

- **每个扩展独立版本**，从 **v0.1.0 起**；与主框架 `_TKWF` 版本**完全独立**（各打各的 tag）
- tag 触发 MinVer → 版本号自动推导（`v0.1.0` → 0.1.0）
- 后续扩展成熟后独立发布 NuGet 包（`TKWF.Ext.{扩展名}`），消费方切 PackageReference
- 主框架 API 破坏性变更致扩展不兼容时：扩展升 `minor`/`major`（SemVer 语义）

### 3.2 文档命名规则

```
docs/{扩展名}/开发方案与审核报告：{扩展名}-开发方案.md / {扩展名}-审核报告.md
docs/{扩展名}/ADR：ADR-{title}.md（三问必填：目的与目标/问题/使用场景）
```

### 3.3 Commit / Tag 纪律

| 规则 | 说明 |
|------|------|
| **避免频繁 commit/push** | 积累一定工作量后统一提交（一次迭代 1-4 个） |
| **tag 前置条件** | 必须有开发方案 + 审核报告均已就绪 |
| **tag 需同意** | 必须征得同意后才能打 tag，不得擅自发布版本 |
| **提交语义完整** | 同一主题的探索性/失败尝试改动合并为单条有意义的提交 |

## 四、每次迭代的标准流程

1. 编写 `docs/{扩展名}/{扩展名}-开发方案.md` → Oracle/人工评审
2. 按方案实施（代码 + 测试）
3. 架构决策 → `docs/{扩展名}/ADR/ADR-{title}.md`
4. 审核代码 → 编写 `docs/{扩展名}/{扩展名}-审核报告.md`
5. 更新主框架私有 `_TKWF/docs/03_扩展模块/总览和跟踪.md`（状态勾选）
6. 推送（不自动打 tag）→ 征求同意后打 tag（扩展独立版本 vX.Y.Z）

## 六、草稿 → 归档流程

```
草稿/  →  讨论定稿  →  拆分到正式目录  →  原稿移入 草稿/归档/
```

- 草稿阶段：存放于 `docs/草稿/`，无版本约束
- 定稿后：内容拆分到对应目录
- ADR：**不修改**，仅状态变更（活跃 → 已废弃 → 被替代），永久保留

---

## 七、扩展性原则

1. **扩展独立**：每个扩展 = 独立项目 + 独立测试 + 独立文档（`docs/{扩展名}/`）+ 独立版本（v0.1.0 起），不互相耦合（除显式依赖）
2. **主框架解耦**：扩展不进入主框架 slnx；主框架升级不影响扩展构建（除 API 破坏）
3. **编译期依赖**：扩展间依赖走 ProjectReference（编译期确定），不走运行时能力发现
4. **完整追溯**：所有文档有明确版本标记，历史永不删除
5. **指南统一 /docs**：各扩展指南统一存放 `docs/{扩展名}/`，方便查看；README 侧保留技术规范

## 八、表名/视图/索引前缀与撞名处理规则（2026-10-07 定案）

> 关联：框架 v4.10.66「表名别名机制一等公民化」ADR100（TABLE 门控族）+ `转达-扩展表名别名与前缀机制全链路核查`。扩展侧表名全部走 `[Table("...")]` 手写别名，实体类名不变。

### 8.1 前缀约定（框架门控）

| 对象 | 前缀 | 示例 | 门控 |
|---|---|---|---|
| 表 | `TKWF_` | `TKWF_AuditLog` | `TABLE003` |
| 视图（VEntity） | `TKWFV_` | `TKWFV_UserRoleView` | `TABLE003` |
| 索引 | `TKWFIX_` | `TKWFIX_AuditLog_ExecutionTime` | `TABLE005` |

- 消费方业务表**不受约束**（TABLE003 仅约束框架+扩展表）
- ViewSql 基表名须同步前缀（`TABLE002` 校验基表 ∈ 实体 [Table] 集合）

### 8.2 默认命名（日常）

```
表：   TKWF_{TableName}        例：TKWF_IdentityUserRole
视图： TKWFV_{ViewName}        例：TKWFV_UserRoleView
索引： TKWFIX_{IndexName}      例：TKWFIX_MfaSecret_User_Method
```

**不加扩展名**——短名优先，扩展名维度只在撞名时引入（§8.4）。

### 8.3 扩展简称自声明

每个扩展在 `_Framework/{扩展名}/README.md` **定位段**声明自己的简称（2-5 字符，可读、互斥）：

```markdown
| 表名前缀简称 | `AuthC`（撞名时用于 `TKWF_{简称}_` 区分；本扩展自声明） |
```

- 简称**每个扩展自声明**，不建中央登记表（撞名极少数，撞名对自声明即可）
- 声明即生效：未来任何扩展撞名时，查对方 README 定位段的简称，按 §8.4 让位

### 8.4 撞名处理（极少数）

- **判定**：全部实体表名规范化（统一加 `TKWF_`）后**跨扩展同名** = 撞名（同实体分部文件重复声明不算）
- **处置（追尾一方全责）**：**先完成前缀规范化者保留默认名 `TKWF_{TableName}`（不返工）**；后完成规范化（追尾）的扩展加简称，其表名改为 `TKWF_{该扩展简称}_{TableName}`
- 视图/索引同理：`TKWFV_{简称}_{...}` / `TKWFIX_{简称}_{...}`
- **不发明新名**：撞名对必须引用对方已声明简称，不得临时创造

### 8.5 当前撞名对处置（仅 1 对）

| 扩展 | 规范化先后 | 实体 | 现状 | 处置 |
|---|---|---|---|---|
| **AuthCenter** | 先（V0.9.0 已 `TKWF_` 前缀） | `PasswordResetCodeEntity` | `TKWF_PasswordResetCode` | **保留，不改** |
| **Account** | 追尾（批次 A 才加前缀） | `PasswordResetCodeEntity` | `PasswordResetCode`（裸名） | → **`TKWF_Acct_PasswordResetCode`**（简称 `Acct`） |

> 背景：两扩展服务不同账号模型（Account=userName-keyed 写 IdentityUser；AuthCenter=UId-keyed 写 AuthAccount），平行不互认（ADR-AuthCenter-身份域数据模型与密码能力边界 B.10）——是**同需求 × 双模型**的合法分化，非边界重叠。撞名由命名规则消解（追尾方全责），不引入装配互斥（分库/双端消费方均为合法组合）。

### 8.6 新增实体检查

新扩展/新实体：先查全仓规范化表名去重；撞名即按 §8.4 加简称——**不发明新名**，引用对方已声明简称。
